# Le goulot d'étranglement de la vérification

<VerifyNote lastVerified="2026-08-04" source="https://blog.codacy.com/ai-breaking-code-review-how-engineering-teams-survive-pr-bottleneck">
Les chiffres sur cette page viennent des données industrielles 2025–2026 (DORA, Faros AI, Jellyfish, Stack Overflow, Codacy, Moderne) et bougent rapidement. Revérifiez les pourcentages spécifiques si vous les citez dans un talk — la *forme* du constat est stable, les chiffres exacts décroissent chaque trimestre.
</VerifyNote>

<Callout type="objectives" items={["Voir le pattern : l'IA a déplacé le goulot d'écrire du code à lui faire confiance — et les données industrielles qui le prouvent", "Comprendre les trois forces (volume, perte de contexte, biais de plausibilité) qui rendent les PRs générées par IA uniquement coûteuses à relire", "Apprendre le routage à trois couches qui sépare les vérifications de base, le triage IA et le jugement humain focalisé", "Configurer un relecteur conscient du dépôt avec AGENTS.md / CLAUDE.md + une pile de règles par service", "Connaître la boucle composée — comment les ajouts mensuels de règles transforment le goût de l'équipe en politique vérifiable par machine sur 12 semaines"]} />

Voici un pattern qui attrape presque chaque équipe la première année où elle déploie des agents IA de codage :

> Cursor / Copilot / Claude Code sont entrés. Le débit sur les branches de feature a bondi. Puis la file d'attente de revue a empiré, le temps de cycle s'est aplati, et personne n'arrivait à trouver où le gain était parti.

C'est le **goulot d'étranglement de la vérification**. Écrire du code n'a jamais été le coût entier de livrer du code — le relire, lui faire confiance, et décider s'il est sûr à merger l'a toujours été. L'IA a fait chuter le prix de la première partie d'un ordre de grandeur et a laissé le reste du système au même prix.

## Le pattern en une phrase

> **L'IA réduit le coût de produire du code avant de réduire le coût de faire confiance au code.** La contrainte bouge. Si vous ne bougez pas votre workflow avec elle, le débit en haut du tuyau s'entasse juste à l'étape de revue.

Ou, dans le cadrage de l'écriture de Codacy sur le phénomène : *« plus de code atteint la file d'attente des pull requests, plus de changements ont besoin de vérification, et les gens de confiance pour relire le travail à risque ont toujours le même nombre d'heures dans la semaine. »*

## Les données industrielles (2025–2026)

La forme apparaît à travers plusieurs jeux de données indépendants :

| Signal | Constat | Source |
|---|---|---|
| Débit sur branches de feature | **+59% YoY** pour les équipes adoptant l'IA | Codacy (2026) |
| Débit sur main (équipe médiane) | **−7% YoY**, taux de succès à **70,8%** | Codacy (2026) |
| Pickup time pour PRs assistées IA | **2,47× plus long** avant qu'un relecteur commence | Codacy (2026) |
| Pickup time pour PRs entièrement agentiques | **5,3× plus long** | Codacy (2026) |
| PRs mergées avec **zéro revue** | **+31%** parmi les équipes lourdes en IA | Codacy (2026) |
| Taille des PRs assistées IA | **~18% plus grandes** que les PRs traditionnelles | Jellyfish, cité par MetaCTO (2026) |
| Confiance dans la justesse du code IA (sondage dev) | **29%** — bas historique | Stack Overflow Developer Survey 2025 |

Notez ce que ces chiffres *ne* disent *pas*. Ils ne disent pas que l'IA écrit du mauvais code. Ils disent que le pipeline en aval de l'IA n'était pas conçu pour le volume, la taille et la perte de contexte que les changements générés par IA apportent.

## Pourquoi les PRs générées par IA sont uniquement coûteuses à relire

Trois forces s'empilent :

**1. Volume.** Un prompt peut générer ce qui prenait auparavant une journée. Si votre équipe produit 3× les PRs, votre capacité de revue ne se met pas magiquement à l'échelle. La file grandit d'abord ; le moral grandit ensuite.

**2. Perte de contexte.** Un auteur humain se souvient des approches ratées, de la contrainte qui a écarté le fix « évident », du fichier qu'il a failli changer. Un auteur IA n'en laisse rien dans le diff. Le relecteur doit reconstruire l'intention à partir de zéro — pour *chaque* PR — parce que le voyage d'implémentation n'est pas dans le message de commit.

**3. Biais de plausibilité.** La sortie IA *a l'air* juste. Elle suit les conventions, formate proprement, importe les bibliothèques attendues. Le mode de défaillance n'est pas des erreurs de syntaxe qui sautent aux yeux — ce sont des désalignements subtils entre intention et comportement qui n'apparaissent que quand vous lisez attentivement. Cette lecture est lente, et c'est exactement la lecture que les humains sautent quand la file est profonde.

Mettez-les ensemble : plus de PRs, chacune portant moins de contexte hérité, chacune exigeant *plus* de lecture attentive qu'un diff écrit-par-humain de même taille. C'est le goulot d'étranglement.

## Le routage à trois couches qui règle le problème

L'atténuation qui apparaît répétitivement chez Codacy, MetaCTO, Moderne et le handbook FreeCodeCamp est la même forme : **stratifiez la revue pour que les humains ne voient que ce pour quoi ils sont irremplaçables.**

<Steps items={[
  {title: "Couche 1 — Base automatisée (pas d'humains, pas de jugement LLM)", body: "Format, lint, type-check, scan sécurité, politique de dépendances, scan de secrets, gate de couverture. Tourne avant qu'un relecteur soit même assigné. Bloque les échecs ennuyeux, mécaniques, qui mangent 40% de l'attention d'un humain quand la revue commence à froid. Si un changement échoue ici, il n'atteint personne."},
  {title: "Couche 2 — Triage assisté IA (bot de revue conscient du dépôt)", body: "Un relecteur IA avec un vrai contexte projet — votre architecture, vos conventions de nommage, vos anti-patterns — produit un résumé structuré : « Bloquant / Devrait fixer / Sympa à avoir / Vérifié ». Son travail n'est pas d'approuver. Son travail est de comprimer le démarrage à froid de l'humain : pointer les fichiers à risque, signaler les tests manquants, citer la règle que le diff viole."},
  {title: "Couche 3 — Revue humaine focalisée (jugement irréductible)", body: "Les humains obtiennent : intention, ajustement architectural, vérification de logique métier, conséquences inter-équipes. Les deux premières couches devraient représenter **la plupart du diff que vous auriez auparavant scruté à l'œil**. La troisième couche cesse d'être une file et devient une décision.

## Le relecteur conscient du dépôt, concrètement

Un relecteur IA générique rate la seule chose qui compte : *votre* architecture. Le pattern qui se cristallise à travers les équipes est de déplacer la connaissance institutionnelle dans des fichiers lisibles par machine que le relecteur peut consommer.

```
project-root/
├── AGENTS.md              # point d'entrée — léger, haute-valeur
├── CLAUDE.md              # symlink → AGENTS.md
├── .claude/
│   ├── settings.json      # garde-fous en lecture seule
│   ├── pr-rules/
│   │   ├── common.md      # règles qui s'appliquent partout
│   │   ├── frontend.md    # règles par workspace
│   │   └── backend.md
│   └── commands/
│       └── review-pr.md   # la commande slash de revue
├── frontend/AGENTS.md     # architecture, patterns, anti-patterns
└── backend/AGENTS.md      # règles métier, contrats, conventions de test
```

Deux choix de design dans cette disposition portent la charge :

- **`AGENTS.md` par service, pas un fichier géant.** Les longues listes d'instructions causent une conformité dégradée sur toutes les entrées — le modèle commence à survoler après la ligne 200. Gardez chaque fichier à un paragraphe par sujet, lien pour le détail.
- **Les règles sont impératives, pas aspirationnelles.** « Les contrôleurs ne doivent pas appeler les dépôts » est testable. « Essayez de garder les contrôleurs fins » est un lancer de pièce.

Voici la forme d'une commande de revue qui tourne localement avant qu'une PR s'ouvre :

<PromptCard title="Commande locale /review-pr (Claude Code / relecteur conscient du dépôt)">
{`You are reviewing a pull request against the main branch.

STEPS:
1. Fetch main, compute the merge base with the current branch, and read the full diff.
2. Read the PR title/body for stated intent. If intent is unclear, ask before reviewing.
3. Load rules in order: .claude/pr-rules/common.md, then any workspace-specific rule
   files whose path prefix matches the changed files (e.g. frontend/**, backend/**).
4. Read the nearest AGENTS.md for each changed file's service and note conventions.

OUTPUT — use exactly these sections and nothing else:

## Summary
One paragraph. What changed, and why (as stated in the PR).

## Blocking
Real defects, security issues, or rule violations that must be fixed before merge.
Format: \`path:line — <problem>. <suggested fix>.\`

## Should fix
Quality issues that would normally get pushback in review but aren't blockers.

## Nice to have
Minor improvements. The author may reasonably ignore these.

## Verified
Things you actively checked and confirmed correct. This section exists so the
human reviewer does not re-check them.

## Rule candidate (optional)
If you saw a recurring pattern this review, suggest ONE new rule for a human to
evaluate for pr-rules/. Do not modify any rule file yourself.

CONSTRAINTS:
- No praise, no manufactured concerns. If nothing is wrong in a section, write "None."
- Cite as \`file:line\`. No prose descriptions of location.
- You never modify rule files. You never approve or merge.`}
</PromptCard>

## Garde-fous : par défaut lecture seule

Un agent relecteur avec accès en écriture à `main`, aux secrets ou aux fichiers de workflow est un incident supply-chain qui attend d'arriver. La convention qui converge est un `.claude/settings.json` (ou l'équivalent dans l'outil que vous utilisez) qui bloque dur :

- **Secrets :** `.env*`, `.npmrc`, `.pgpass`, `*.pem`, `**/credentials.json`
- **Ops git en écriture :** `push`, `commit`, `rebase`, `reset --hard` — autoriser `fetch`, `diff`, `log`
- **Mutation PR :** créer, merger, ou approuver des PRs ; commenter autorisé seulement si vous voulez la sortie du relecteur postée automatiquement
- **Mutation workflow / secret :** `gh workflow run`, `gh secret`, `gh variable`

Si le relecteur ne peut que *lire*, le pire cas d'un agent compromis ou halluciné est un mauvais commentaire de revue. C'est un mode de défaillance beaucoup moins cher qu'un mauvais merge.

## Routage par risque (tout ne mérite pas la même revue)

L'autre erreur des équipes est de traiter chaque PR générée par IA de façon identique. Routez par risque :

| Tier de risque | Exemples | Revue |
|---|---|---|
| **Bas** | Changements de doc seulement, bumps de patch de dépendances passés vert par CI, mises à jour de snapshot générées | Couche 1 + triage IA ; auto-merge si les deux passent |
| **Moyen** | Code de feature dans des modules isolés, refactors dans un service | Couche 1 + triage IA + un relecteur humain focalisé |
| **Haut** | Auth, facturation, migrations, code qui traverse les frontières de service, tout ce qui touche aux données de production | Couche 1 + triage IA + relecteur senior **nommé** + doc d'intention pré-codage |

Le point n'est pas de réduire la revue — c'est de dépenser les heures humaines là où elles changent les résultats.

## Décomposition de PR : gardez les changements vérifiables

Une PR générée par IA de 10 000 lignes n'est pas relisable en un sens significatif. Elle est tamponnée ou elle stagne. Le mouvement de workflow est de forcer la décomposition :

- **Plafonner la taille de PR** avec une politique explicite de split-si-plus-grand (beaucoup d'équipes choisissent 400–900 lignes, avec les migrations générées exemptées).
- **PRs empilées** pour les features qui ont légitimement besoin de plus de portée — chaque couche est vérifiable, l'ensemble atterrit ensemble.
- **L'IA planifie, les outils déterministes exécutent.** Pour les changements à l'échelle du dépôt, traitez l'IA comme le planificateur (quels fichiers, quelle recette) et un outil déterministe comme l'exécuteur (appliquer la recette identiquement partout). Le programme basé sur OpenRewrite de Morgan Stanley à grande échelle a utilisé exactement cette séparation.

## La boucle composée

Chaque commentaire de revue récurrent est un candidat de règle. La règle va dans `pr-rules/`, le relecteur IA la reprend à la prochaine PR, et ce commentaire n'a plus jamais à être écrit par un humain. Le handbook FreeCodeCamp cadre la chronologie ainsi :

- **Semaine 1 :** le relecteur attrape 5–10% des nits récurrents de votre équipe.
- **Semaine 4 :** 20–30%, à mesure que la base de règles grandit à partir de retours PR réels.
- **Mois 3+ :** la base de règles a mûri en *goût d'équipe écrit noir sur blanc*.

La composition est le vrai fossé. Toute équipe peut installer CodeRabbit ou Greptile en un après-midi. L'équipe qui a passé 100 PRs à alimenter les commentaires de revue dans `pr-rules/` a un relecteur IA qui connaît leur dépôt. L'équipe qui ne l'a pas fait en a un générique.

La discipline de maintenance est petite mais non-négociable :

- **Chaque attrapage :** écrire une ligne dans le bon fichier `pr-rules/`.
- **Mensuel :** tailler les règles obsolètes (features retirées, patterns retraités).
- **Trimestriel :** relire chaque `AGENTS.md` par service et élaguer la dérive.

## Ce qui nécessite toujours un humain (et le fera toujours)

Le routage à trois couches est agressif, mais il y a un plancher. Les humains restent irremplaçables pour :

- **Jugement produit.** Ce changement devrait-il exister ? Un relecteur IA mesure contre des règles ; il ne peut pas mesurer contre la stratégie.
- **Conséquences inter-équipes.** Le changement a l'air correct en isolation mais casse un contrat avec le service d'une autre équipe.
- **Responsabilité.** Quelqu'un doit posséder un post-mortem quand ça part cassé. L'IA ne peut pas être appelée.
- **Revue de point aveugle IA.** Deux IAs entraînées sur les mêmes données partagent les mêmes points aveugles. Si à la fois l'auteur *et* le relecteur sont IA, une classe entière de bugs devient systématiquement invisible. Un humain les voit précisément parce que son ensemble d'entraînement est différent.

L'état final sain n'est pas « l'IA relit tout ». C'est *« l'IA dégage le bruit pour que les humains relisent les choses qui ont besoin d'un humain. »*

## Le cadrage honnête

La plupart du gain de productivité IA en codage est réel. Le débit sur branches de feature à +59% n'est pas un mirage. Mais le débit en haut d'un tuyau n'est pas le débit en bas, et chaque mesure de code *livré* — merges sur main, temps de cycle, taux d'échappement de défauts — raconte la même histoire : la contrainte a bougé, et les équipes qui n'ont pas bougé le workflow avec ont vu le gain disparaître dans la file de revue.

Les équipes qui gagnent avec les agents IA de codage en 2026 ne sont pas celles qui génèrent le plus de code. Ce sont celles avec le chemin le plus court, le moins cher, le plus confiant, de *généré* à *mergé.*
