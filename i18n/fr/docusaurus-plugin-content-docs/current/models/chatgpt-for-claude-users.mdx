Vous pensez déjà en Claude. Voilà qu'un collègue partage un Custom GPT, ou qu'un client vit dans ChatGPT, et vous devez être productif là-bas **aujourd'hui** — sans réapprendre à utiliser un assistant IA de zéro. Bonne nouvelle : presque tout ce que vous savez se transpose. Cette page fait correspondre votre modèle mental de Claude à ChatGPT, signale la poignée de choses qui fonctionnent réellement différemment, et vous indique quand chacune tend à briller.

## La carte des concepts en 60 secondes

Si vous ne lisez qu'une seule section, lisez celle-ci. Voici comment les choses que vous connaissez dans Claude s'alignent avec ChatGPT :

| Dans Claude, vous l'appelez… | Dans ChatGPT, c'est… | Même idée ? |
| --- | --- | --- |
| Claude Projects (espace de travail + fichiers + instructions de projet) | **Projects** | Oui — un concept quasiment identique |
| Style personnalisé / un prompt système enregistré que vous réutilisez | **Custom GPTs** — remplacés par les **Plugins** (skills + apps) | Proche, avec une nuance (voir ci-dessous) |
| Vos préférences au niveau du compte / « comment je veux que tu répondes » | **Instructions personnalisées** | Oui |
| La mémoire de Claude des conversations passées | **Mémoire** | Oui — même idée, évolue souvent |
| Artifacts (panneau latéral pour documents/code) | **Canvas** | Oui — même idée |
| Sélecteur de modèle (Opus / Sonnet / Haiku) | Le **sélecteur de modèle** (niveaux vitesse vs raisonnement) | Oui — même idée, noms différents |
| Utilisation d'outils / function calling (API) | **Function calling** | Oui — même forme, détails JSON différents |

À retenir : il n'y a presque *aucun nouveau concept* à apprendre. Il s'agit surtout de **renommer et de relocaliser** des choses que vous comprenez déjà.

## Projects vs Custom GPTs — la distinction qui mérite d'être bien comprise {#projects-vs-custom-gpts}

C'est le point unique où les utilisateurs de Claude se trompent le plus souvent, parce que ChatGPT propose **deux** choses qui ressemblent toutes deux à « un Claude personnalisé », et elles servent à des usages différents.

- **Projects** sont *organisationnels* — un espace de travail qui regroupe de nombreuses conversations, des fichiers téléversés et des instructions partagées autour d'un même effort continu. La continuité à travers plusieurs conversations est le but. Recourez à un Project quand vous ouvririez un Claude Project : un long fil de recherche, un texte en cours d'écriture qui évolue, un flux de travail avec des documents de référence. <VerifyNote lastVerified="2026-10-07" source="https://learn.chatgpt.com/docs/projects">Les propres termes d'OpenAI : « Utilisez un project pour garder ensemble les conversations, fichiers, instructions et sources liés » (en anglais : "Use a project to keep related chats, files, instructions, and sources together") — pour un travail qui « se poursuivra dans le temps, produira plus d'un résultat, ou dépendra des mêmes fichiers et sources » ("will continue over time, produce more than one output, or depend on the same files and sources"). La disponibilité selon les formules gratuites et payantes évolue avec le temps — consultez la page actuelle.</VerifyNote>

- **Custom GPTs** sont des *assistants packagés* — une configuration enregistrée (un prompt système, des fichiers de connaissances optionnels, des outils activés, parfois des actions d'API) que vous invoquez comme une conversation neuve et unique dotée d'une persona fixe. Ils sont conçus pour être réutilisés et partagés : une personne construit l'expertise et beaucoup l'exécutent. **Ils sont en cours de mise à la retraite.**

- **Plugins** sont le remplacement : selon les mots d'OpenAI, « un package réutilisable pour un workflow, qui peut inclure des skills, des apps, ou les deux » (en anglais : "a reusable package for a workflow that can include skills, apps, or both") — les *skills* portent les instructions sur la façon de faire le travail, les *apps* connectent ChatGPT à d'autres services. Même instinct qu'un Custom GPT, surface plus large. <VerifyNote lastVerified="2026-10-07" source="https://learn.chatgpt.com/codex/migrate-custom-gpts">OpenAI : « Nous faisons migrer les custom GPTs vers les plugins. Utilisez les jalons ci-dessous pour planifier votre migration avant la mise à la retraite des custom GPTs. » (en anglais : "We're transitioning custom GPTs to plugins. Use the milestones below to plan your migration before custom GPTs are retired.") Les jalons publiés sont Admin notice → Migration → Custom GPT retirement, moment à partir duquel « les custom GPTs cessent de tourner et quittent le répertoire GPT » ("custom GPTs stop running and leave the GPT directory"). Le GPT d'origine « reste utilisable jusqu'à la mise à la retraite » ("remains usable until retirement"), et un GPT peut encore être migré après la mise à la retraite même s'il ne tourne plus. Les dates précises dépendent de l'espace de travail (le guide est écrit pour les administrateurs ChatGPT Enterprise et les créateurs de GPT) et peuvent changer — lisez les jalons sur la page liée plutôt que de faire confiance à une date indiquée ici.</VerifyNote>

Le raccourci mental :

- **Besoin de continuité à travers de nombreuses conversations avec un contexte partagé ?** → Project.
- **Besoin d'un spécialiste réutilisable et partageable qui se comporte de la même façon à chaque fois ?** → un Plugin (et migrez le Custom GPT que vous avez déjà).

Deux pièges pour les utilisateurs de Claude :

- Une conversation avec un Custom GPT ou un Plugin tend à démarrer **à neuf** à chaque fois, avec seulement ses instructions préétablies plus cette conversation — ne vous attendez pas à ce qu'il se souvienne de votre dernière session comme le fait un fil de Project continu.
- La migration n'est **pas** sans perte. Les actions personnalisées doivent être reconstruites séparément — contre un connecteur pris en charge ou votre propre serveur MCP — donc un GPT qui s'appuie dessus demande un vrai travail, pas une conversion en un clic. Si c'est vous qui reconstruisez, [Codex Agent Plugins](/docs/models/codex-agent-plugins-catalogs) couvre la couche de packaging.

## Instructions personnalisées et mémoire — même idée, couches légèrement différentes

Dans Claude, vous définissez des préférences globales et le laissez mémoriser le contexte. ChatGPT fait pareil, simplement avec des couches plus explicites où vous pouvez définir des instructions :

<Steps items={[
  {title: "Instructions personnalisées au niveau du compte", body: "Vos préférences permanentes — ton, niveau de détail, sur quoi se concentrer. Appliquées à toutes les conversations, comme vos préférences de compte Claude."},
  {title: "Instructions de projet", body: "Contexte limité au sujet d'un Project — l'équivalent des instructions de Claude Project."},
  {title: "Instructions de Plugin (ou de Custom GPT)", body: "Le « prompt système » intégré à un assistant packagé — la skill d'un Plugin, ou le champ d'instructions d'un Custom GPT que vous n'avez pas encore migré. C'est là qu'un concepteur contrôle pleinement le comportement."},
  {title: "Ponctuel, en cours de conversation", body: "Dites-le simplement dans la conversation quand vous avez besoin d'un ajustement d'un seul message — exactement comme dans Claude."},
]} />

**La mémoire** est un système à part entière qui évolue : ChatGPT peut transporter le contexte d'une conversation à l'autre. Traitez *ce* dont il se souvient, *dans quelle mesure* et *où c'est disponible* (par ex. à l'intérieur d'un assistant packagé ou non) comme **volatil** — cela change fréquemment, alors vérifiez le comportement actuel plutôt que de le supposer. <VerifyNote lastVerified="2026-10-07" source="https://learn.chatgpt.com/codex/personalize">OpenAI : « Utilisez les instructions personnalisées pour les préférences que vous voulez voir ChatGPT suivre d'une conversation à l'autre, comme votre style de réponse préféré. » (en anglais : "Use custom instructions for preferences you want ChatGPT to follow across chats, such as your preferred response style.") La superposition est bien réelle — dans Codex, la couche personnelle vit dans votre `AGENTS.md` global, et « les projets et les dépôts peuvent aussi fournir leurs propres instructions » ("projects and repositories can also provide their own instructions"). Les détails et la disponibilité changent — consultez la page actuelle.</VerifyNote>

## Canvas, c'est les Artifacts de ChatGPT

Si vous adorez les Artifacts de Claude — un panneau latéral où un document ou un bloc de code devient un objet vivant et modifiable — vous vous sentirez chez vous avec **canvas**. Il ouvre une surface d'édition dédiée à l'écriture et au codage pour que vous et le modèle puissiez réviser sur place au lieu de régénérer tout le message. Même instinct, nom différent.

Un point à surveiller (et un bon exemple de pourquoi nous ne figeons pas les détails) : **la surface d'édition que vous obtenez dépend de là où vous êtes**, pas seulement de ce que vous avez demandé. La documentation actuelle d'OpenAI décrit le comportement d'aperçu et d'édition comme variant selon la surface — l'application de bureau prévisualise les documents générés à côté de la conversation, la CLI n'a aucun aperçu visuel, et l'extension IDE examine les fichiers dans l'éditeur. Le modèle sélectionné peut compter aussi. Si le panneau latéral n'apparaît pas, suspectez votre surface ou votre modèle avant de suspecter un bug. <VerifyNote lastVerified="2026-10-07" source="https://learn.chatgpt.com/codex/artifacts-viewer">La documentation d'OpenAI sur l'aperçu de fichiers cadre la disponibilité par surface : l'application de bureau « prévisualise les documents, présentations, feuilles de calcul et fichiers PDF générés à côté de la conversation » (en anglais : "previews generated documents, presentations, spreadsheets, and PDF files alongside the chat"), la CLI « n'inclut pas d'aperçu visuel des fichiers » ("doesn't include a visual file preview"), et l'extension IDE examine les fichiers texte et code dans l'éditeur. La page n'affirme pas qu'il existe un verrouillage par modèle : traitez donc la réserve sur le modèle comme une précaution, pas comme une règle documentée. Canvas lui-même est documenté séparément sur le centre d'aide d'OpenAI (lien dans Sources).</VerifyNote>

## Le sélecteur de modèle — choisissez par tâche, pas par nom

Tout comme vous choisissez Opus vs Sonnet vs Haiku, ChatGPT vous demande de choisir un modèle — généralement le long d'un spectre **vitesse ↔ raisonnement** (options rapides/instantanées pour les tours rapides, options à plus fort raisonnement pour les problèmes difficiles, les niveaux supérieurs étant réservés aux formules payantes). Les *noms et le nombre de niveaux changent souvent* ; la compétence durable est la même que celle que vous utilisez déjà avec Claude : **associer le modèle à la difficulté de la tâche et à votre tolérance en latence/coût.**

C'est exactement le cadre décrit dans [Choisir un modèle](/docs/models/choosing-a-model) et [Quel Claude dois-je utiliser ?](/docs/start-here/which-claude) — il est indépendant du fournisseur. Ne mémorisez pas un nom de modèle ; apprenez à lire « rapide vs profond » et choisissez en conséquence.

Pour rendre l'idée concrète plutôt que pour être mémorisé : au **7 octobre 2026**, le sélecteur propose **Astra** (le plus capable), **GPT-6.1 Sol** (« des performances proches d'Astra pour le travail complexe à un coût inférieur à Astra », en cours de déploiement sur Plus, Pro, Business, Enterprise et Edu) et **GPT-6 Luna** (le modèle efficient pour le travail ciblé à fort volume) — tandis que **GPT-5.5 est mis à la retraite de ChatGPT, ChatGPT Work et Codex le 14 octobre 2026**, tout en restant disponible sur l'API. Si vous lisez ceci bien après cette date, tous les noms de ce paragraphe ont probablement bougé. C'est précisément le point. <VerifyNote lastVerified="2026-10-07" source="https://learn.chatgpt.com/docs/models">La gamme de modèles, la disponibilité par formule et la date de mise à la retraite de GPT-5.5 sont lues sur la page des modèles actuelle d'OpenAI. Mises à la retraite antérieures qui y sont listées : GPT-5.3-Codex-Spark le 14 septembre 2026, GPT-5.4 et GPT-5.4-mini le 31 août 2026. Cette liste devient obsolète rapidement, par nature — relisez la source plutôt que de lui faire confiance ici.</VerifyNote>

## Function calling — même forme, détails JSON différents

Si vous avez fait de l'[utilisation d'outils](/docs/api/tool-use) avec Claude, le **function calling** d'OpenAI vous semblera immédiatement familier, parce que la *boucle est la même* :

<Steps items={[
  {title: "Déclarer les outils", body: "Vous décrivez chaque outil avec un nom, une description et un schéma JSON de ses paramètres (lesquels sont requis, leurs types). Même idée qu'une définition d'outil Claude."},
  {title: "Le modèle demande un appel", body: "Étant donné le prompt et les outils disponibles, le modèle renvoie un appel d'outil structuré — le nom de l'outil plus les arguments — au lieu de (ou en plus de) du texte."},
  {title: "Vous l'exécutez", body: "Votre application exécute la fonction réelle avec ces arguments. Le modèle n'exécute jamais rien lui-même."},
  {title: "Renvoyer le résultat", body: "Vous réinjectez la sortie de l'outil vers le modèle."},
  {title: "Le modèle répond", body: "Il utilise le résultat pour produire la réponse finale — et peut demander d'autres appels avant de terminer."},
]} />

Ce qui est identique : la boucle décrire → le modèle demande → vous exécutez → renvoyer le résultat → répondre, les appels multiples/parallèles, et le principe selon lequel *le modèle propose, votre code dispose*. <VerifyNote lastVerified="2026-10-07" source="https://developers.openai.com/api/docs/guides/function-calling">Confirmé mot pour mot contre le guide d'OpenAI, qui définit « une fonction » ("a function") comme « un type d'outil spécifique, défini par un schéma JSON » ("a specific kind of tool, defined by a JSON schema") avec `type`, `name`, `description`, `parameters` et `strict`, et qui liste les mêmes cinq étapes : requête au modèle avec les outils qu'il pourrait appeler → réception d'un appel d'outil → exécution du code côté application → seconde requête avec la sortie de l'outil → réception d'une réponse finale (ou d'autres appels d'outils). Les noms de champs exacts et les options changent — consultez le guide d'API actuel.</VerifyNote>

Ce qui **diffère** et vous fera trébucher si vous faites du copier-coller : les noms exacts des champs JSON, la façon dont les appels d'outils et les résultats sont représentés dans la liste des messages, les options « strict »/sortie structurée, et la forme spécifique du point de terminaison de l'API. En règle générale entre fournisseurs, **le prompting et l'architecture se transposent ; les détails du format de transmission non** — revérifiez toujours le schéma propre à chaque fournisseur.

## Ce qui se transpose (surprise : presque tout)

Vos habitudes Claude durement acquises ne sont pas perdues. Celles-ci se transposent essentiellement sans changement :

- **Structure du prompt** — rôle clair, tâche explicite, exemples, format de sortie demandé → [Bases du prompting](/docs/prompting/basics)
- **Donner le contexte délibérément** — collez le bon matériel, cadrez-le, ne déversez pas tout
- **Demander un format de sortie précis** — tableaux, JSON, étapes ; fonctionne pareil
- **Itérer sur place** — affinez via des relances (et maintenant via canvas)
- **La boucle d'utilisation d'outils** — décrivez les outils, laissez le modèle les appeler, renvoyez les résultats → [Utilisation d'outils](/docs/api/tool-use)
- **Choisir un modèle selon la difficulté de la tâche** — rapide vs profond, même arbitrage

## Ce qu'il faut réellement ajuster

Une liste courte et honnête des choses qui sont effectivement différentes :

- **Deux objets de « personnalisation », pas un.** Décidez d'emblée : espace de travail continu (Project) ou assistant packagé réutilisable (un Plugin — ou un Custom GPT en route pour en devenir un) ? Choisir le mauvais est l'erreur de débutant la plus courante.
- **Les Custom GPTs sont une cible de migration, pas une destination.** OpenAI les déplace vers les Plugins et les met à la retraite. Si vous en héritez un, planifiez sa migration ; n'en démarrez pas un nouveau.
- **Association fonctionnalité ↔ surface.** Dans ChatGPT, la disponibilité d'un panneau d'aperçu/d'édition (ou d'un outil donné) peut dépendre de là où vous l'exécutez — et parfois du modèle sélectionné. Quand quelque chose manque, vérifiez cela avant tout le reste.
- **Format de transmission des outils.** Le *concept* de function calling est identique ; les détails JSON non — ne réutilisez jamais le JSON d'outil exact de Claude tel quel.
- **Détails volatils.** Les noms de modèles, niveaux, limites et prix évoluent vite. Prenez l'habitude de confirmer à la source, exactement comme vous devriez le faire pour Claude aussi.

## Quand chacun tend à briller

Les deux sont d'excellents assistants généralistes et l'écart sur une tâche donnée est souvent faible et mouvant — traitez donc ceci comme des *tendances*, pas des lois, et laissez votre propre [évaluation sur vos propres données](/docs/models/choosing-a-model) décider :

- **Recourez à ChatGPT quand** vous avez besoin de son écosystème spécifique — un Custom GPT qu'une équipe maintient déjà, un Project qu'un collaborateur a configuré, ou un outil/une intégration intégré dont vous dépendez là-bas. Si votre client ou vos collègues vivent dans ChatGPT, les rejoindre là vaut mieux que la friction.
- **Recourez à Claude quand** vous êtes déjà dans le flux de travail Claude autour duquel ce site est construit — Projects, Artifacts, et les patterns de prompting/agent documentés partout dans AILmanac — et voulez les approfondir.

La réponse honnête la plupart du temps : **celui dans lequel vous (ou votre équipe) êtes déjà installés.** La compétence est portable ; le coût de configuration est le véritable coût de changement.
