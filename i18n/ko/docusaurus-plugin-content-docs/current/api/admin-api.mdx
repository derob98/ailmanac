공식 출처. Claude Enterprise 사용자 관리 엔드포인트는 2026년 7월 13일 기준 베타입니다(헤더 `ce-user-management-2026-07-13`); 이 페이지의 나머지 내용은 모두 일반 사용 가능(GA)입니다. 엔드포인트 형태는 베타 기간 중 정착되므로, 배포 전에는 항상 [Admin API 레퍼런스](https://platform.claude.com/docs/en/api/admin)를 교차 확인하세요.

Console에서 사람이 클릭할 수 있는 기능이라면 대체로 Admin API로 스크립트화할 수 있습니다 — 그리고 실제 팀을 Claude에서 운영한다면 결국 그렇게 해야 합니다. 이 가이드는 첫 연동의 대부분을 깨뜨리는 세 가지 함정을 피하며 그것을 해내는 방법입니다.

## Admin API란 무엇인가(그리고 무엇이 아닌가)

**Base:** 모든 엔드포인트는 `https://api.anthropic.com/v1/organizations/` 아래에 있습니다. 별도의 호스트도, 별도의 SDK도 없습니다 — `curl`, `requests`, 또는 이미 사용 중인 HTTP 클라이언트로 평범한 HTTPS 호출을 하면 됩니다.

**할 수 있는 것:** 조직 멤버, 역할, 초대, 워크스페이스와 그 멤버, 기존 API 키, 서비스 계정, 페더레이션 발급자/규칙을 조회·관리할 수 있고, Claude Enterprise의 경우 RBAC 그룹과 (읽기 전용) 커스텀 역할도 다룰 수 있습니다.

**할 수 NOT 없는 것:**

- **새 API 키 생성.** 보안상의 이유로, 새 키는 Console에서만 생성됩니다. API는 이미 존재하는 키를 조회, 이름 변경, 비활성화만 할 수 있습니다.
- **관리자 멤버 수정.** `admin`, `owner`, `primary_owner` 역할을 가진 멤버는 API로 역할을 변경하거나 제거할 수 없습니다 — 그것은 Console에서 처리합니다.
- **당신의 IdP 우회.** SSO/SCIM이 어떤 영역을 담당하고 있다면 API는 당신의 IdP와 싸우는 대신 400을 반환합니다. [SSO + Admin API](#sso--admin-api)를 보세요.

## 두 가지 자격 증명

모든 요청은 이 중 하나가 필요합니다 — 호출별이 아니라 환경별로 선택하세요.

<Callout type="tip" items={["사람이 사용하기에는 전용 OAuth 프로필이 더 안전한 기본값입니다(짧은 수명의 토큰, 감사 로그에 실제 사용자 기록).", "장수명 Admin API 키는 CI에 더 간단하지만, 프로덕션 시크릿처럼 취급하고 정기적으로 로테이션하세요.", "서비스 계정, 페더레이션 발급자, 페더레이션 규칙 엔드포인트는 org:admin OAuth 토큰만 받습니다 — 해당 경로에서는 Admin API 키가 거부됩니다."]} />

| 자격 증명 | 전송 방식 | 생성 가능 주체 | 비고 |
|---|---|---|---|
| **Admin API key** (`sk-ant-admin…`) | `x-api-key: $ANTHROPIC_ADMIN_KEY` | `admin` 역할을 가진 멤버 | 장수명. 대부분의 엔드포인트를 커버합니다. |
| **OAuth bearer token** (`org:admin` 스코프) | `authorization: Bearer $ANTHROPIC_OAUTH_TOKEN` | `admin`, `owner`, `primary_owner` 역할을 가진 멤버 | 단수명; `ant` CLI로 갱신합니다. 서비스 계정 / 페더레이션 엔드포인트에는 REQUIRED. |

두 방식 모두 모든 요청에 `anthropic-version: 2023-06-01`을 함께 보내야 합니다(Claude Enterprise 그룹 및 커스텀 역할 요청이 유일한 예외 — 아래 [베타 헤더 규칙](#the-beta-header-rule) 참조).

<PromptCard title="첫 호출: 나는 누구인가?">{`# With an Admin API key
curl -sS "https://api.anthropic.com/v1/organizations/me" \\
  -H "anthropic-version: 2023-06-01" \\
  -H "x-api-key: $ANTHROPIC_ADMIN_KEY"

# With an OAuth bearer token (org:admin scope)
curl -sS "https://api.anthropic.com/v1/organizations/me" \\
  -H "anthropic-version: 2023-06-01" \\
  -H "authorization: Bearer $ANTHROPIC_OAUTH_TOKEN"`}</PromptCard>

응답은 당신 조직의 `id`, `type`, `name`입니다. 401로 실패하면 자격 증명이 잘못된 것이고, 403으로 실패하면 역할이 너무 낮은 것입니다.

## Console vs Claude Enterprise: 호출 가능한 것

두 조직 유형은 하나의 URL 공간을 공유하지만 서로 다른 하위 집합을 노출합니다. 이것이 Admin API에서 가장 헷갈리는 부분입니다.

| 엔드포인트 | Claude Console (Platform) | Claude Enterprise (claude.ai) |
|---|---|---|
| 멤버 & 초대 | ✅ GA | ✅ **베타** (추가 헤더 없음) |
| 워크스페이스 + 워크스페이스 멤버 | ✅ GA | ❌ 사용 불가 |
| API 키 (조회 / 이름 변경 / 비활성화) | ✅ GA | ❌ 사용 불가 |
| 사용량 & 비용 리포트, 속도 제한 | ✅ GA | ❌ 사용 불가 |
| 서비스 계정, 페더레이션 발급자, 페더레이션 규칙 | ✅ GA (OAuth 전용) | ❌ 사용 불가 |
| RBAC 그룹 + 그룹 멤버 | ❌ 사용 불가 | ✅ **베타** (헤더 필요) |
| 커스텀 역할 (읽기 전용 카탈로그) | ❌ 사용 불가 | ✅ **베타** (헤더 필요) |
| [Spend Limits API](https://platform.claude.com/docs/en/manage-claude/spend-limits-api) | ❌ 사용 불가 | ✅ GA |

**AWS 상의 Claude Platform**은 세 번째 경우입니다: 워크스페이스 엔드포인트(`/v1/organizations/workspaces`)만 동작합니다. 나머지는 모두 404를 반환합니다.

## 역할 모델

역할 이름은 조직 유형마다 다르게 붙어 있습니다. 감으로 서로 매핑하지 마세요.

### Claude Console 역할

| 역할 | 가능한 작업 |
|---|---|
| `user` | Workbench 사용 |
| `claude_code_user` | Workbench + [Claude Code](/docs/claude-code/what-is-claude-code) |
| `developer` | Workbench + API 키 관리 |
| `billing` | Workbench + 결제 관리 |
| `admin` | 위 모든 것 + 사용자 관리 |

`admin` 위에는 `owner`와 `primary_owner`가 있습니다 — Console에는 이 역할들이 존재하지만 API 목적상 슈퍼 관리자로 취급됩니다.

### Claude Enterprise 역할

다섯 개의 값이 있지만, API가 *부여*할 수 있는 것은 그중 두 개(`user`와 `managed`)뿐입니다. 나머지는 `claude.ai` 조직 설정에서 지정되며 API로 수정하거나 제거할 수 없습니다.

| 역할 | 의미 |
|---|---|
| `user` | 표준 멤버 — 권한은 플랜 기본값에서 나옵니다. |
| `managed` | 권한은 **그들의 그룹에 붙어 있는 커스텀 역할에서** 나옵니다(이것이 RBAC 경로입니다). |
| `owner` | 조직 소유자. |
| `membership_admin` | 멤버를 관리할 수 있지만 결제/설정은 불가. |
| `primary_owner` | 정확히 한 명 존재. 제거 불가. |

Enterprise에서 세밀한 권한을 원한다면, 레시피는 다음과 같습니다: 그 사람을 `managed` 역할에 두고, 원하는 역할을 가진 그룹에 추가하세요.

## 베타 헤더 규칙

Enterprise에서 가장 흔한 단일 연동 버그입니다.

<Callout type="warning" items={["멤버와 초대: 추가 베타 헤더 NO — anthropic-version: 2023-06-01만 사용하세요.", "그룹과 커스텀 역할: anthropic-beta: ce-user-management-2026-07-13을 SEND하세요. 없으면 404를 반환합니다.", "그룹과 커스텀 역할 요청에는 anthropic-version이 NOT 필요합니다 — 공식 예제도 생략합니다. 베타가 졸업할 때의 예기치 못한 드리프트를 피하려면 공식 패턴을 따르세요."]} />

모든 것을 하나의 HTTP 클라이언트로 처리한다면 URL 기준으로 게이팅하세요:

```python
BETA_ROUTES = ("/v1/organizations/rbac_groups", "/v1/organizations/rbac_roles")

def headers(path: str, key: str) -> dict:
    h = {"x-api-key": key}
    if path.startswith(BETA_ROUTES):
        h["anthropic-beta"] = "ce-user-management-2026-07-13"
    else:
        h["anthropic-version"] = "2023-06-01"
    return h
```

## Enterprise Admin 키의 스코프

Claude Enterprise Admin API 키는 **스코프가 지정됩니다** — primary owner가 키 생성 시 그 키가 할 수 있는 일을 고릅니다. 동작하는 가장 작은 집합을 고르세요.

| 스코프 | 부여 사항 |
|---|---|
| `read:members` | 멤버, 초대, 그리고 **모든 커스텀 역할 엔드포인트**에 대한 GET (별도의 역할 스코프는 없습니다) |
| `write:members` | 멤버와 초대에 대한 POST/DELETE |
| `read:rbac_groups` | 그룹 + 그룹 멤버에 대한 GET |
| `write:rbac_groups` | 그룹 + 그룹 멤버에 대한 POST/DELETE. **초대 생성 시 `rbac_group_ids`를 전달하려면 이 스코프도 필요**한데, 권한을 부여할 수 있기 때문입니다. |
| `read:org_audit` | 읽기 전용 "감사 통합" 스코프 — 이 API의 모든 GET과 [Compliance API](https://platform.claude.com/docs/en/manage-claude/compliance-api) 읽기까지 커버합니다. 보안 팀의 모니터링 봇에 완벽합니다. |

## 페이지네이션 — 두 가지 다른 방식

작은 불편함이지만 "왜 목록이 비어 있지"의 큰 원인:

- **멤버와 초대**는 **ID 기반 페이지네이션**을 사용합니다: `limit`(기본 20, 최대 1000)을 넘기고 `before_id` 또는 `after_id` 중 최대 하나를 함께 보냅니다. `first_id` / `last_id`로 페이지를 넘기고 `has_more`가 `false`이면 멈춥니다.
- **그룹, 그룹 멤버, 커스텀 역할**은 **불투명 커서**를 사용합니다: 각 응답에서 `next_page`를 읽어 그대로 `page`로 다시 넘깁니다. `next_page`가 `null`이면 멈춥니다.

모든 Admin API 엔드포인트의 속도 제한은 **조직당 분당 100요청**을 공유하며, 초대 생성만 예외로 **시간당 1,200요청** 자체 예산을 가집니다. 어느 쪽이든 초과 시 429를 반환합니다.

## 자주 쓰는 레시피

### 모든 멤버 조회 (페이지네이션)

```python
import os, requests

API = "https://api.anthropic.com/v1/organizations/users"
H = {"anthropic-version": "2023-06-01", "x-api-key": os.environ["ANTHROPIC_ADMIN_KEY"]}

after = None
while True:
    params = {"limit": 1000}
    if after:
        params["after_id"] = after
    page = requests.get(API, headers=H, params=params).json()
    for m in page["data"]:
        print(m["email"], m["role"])
    if not page["has_more"]:
        break
    after = page["last_id"]
```

### 분기별 그룹 감사 (Enterprise)

Console을 노려보지 않고도, 있어서는 안 되는 사람이 민감 그룹에 있는지 찾아냅니다.

```python
import os, requests

H_BETA = {"x-api-key": os.environ["ANTHROPIC_ADMIN_KEY"],
          "anthropic-beta": "ce-user-management-2026-07-13"}

groups = requests.get("https://api.anthropic.com/v1/organizations/rbac_groups?limit=1000",
                     headers=H_BETA).json()["data"]

for g in groups:
    if "prod" not in g["name"].lower():
        continue
    members = requests.get(
        f"https://api.anthropic.com/v1/organizations/rbac_groups/{g['id']}/members?limit=1000",
        headers=H_BETA).json()["data"]
    print(f"{g['name']} ({len(members)} members)")
    for m in members:
        print(f"  {m['email']}")
```

이 출력을 IdP 명부와 diff하고, 오래된 사람은 `DELETE /rbac_groups/{group_id}/members/{user_id}`로 제거하세요. SCIM으로 프로비저닝된 그룹(`source_type: "scim"`)은 수정 시 400을 반환합니다 — 그것은 당신의 IdP에서 처리하세요.

## SSO + Admin API

당신의 IdP가 어떤 영역을 담당하고 있다면 API는 그것에 위임합니다:

| 당신의 IdP가 하는 일 | 차단되는 API 작업 | HTTP |
|---|---|---|
| JIT 또는 SCIM 사용자 프로비저닝 | 초대 생성 | 400 |
| 고급 SSO / SCIM 역할 프로비저닝 | 멤버 역할 업데이트 | 400 |
| SCIM 멤버십 프로비저닝 | 조직에서 멤버 제거 | 400 |
| SCIM 그룹 프로비저닝 (`source_type: "scim"`) | 그룹 이름 변경, 그룹 삭제, 그룹 멤버 추가/제거 | 400 |

읽기는 항상 동작합니다. 이것은 의도된 설계입니다: IdP가 소유한 것에 대해서는 IdP가 진실의 원천이며, Admin API는 스크립트가 조용히 그것과 어긋나게 되는 것을 거부합니다.

## 시트, 초대, 그리고 한 번쯤 맞닥뜨릴 400

유한한 시트 풀을 가진 플랜에서는:

- **대기 초대는 시트를 소비합니다**. 시트를 반환하려면 철회하거나 만료되게 두세요.
- 초대 생성은 **티어 파라미터를 받지 않습니다**. 서버가 여유가 있는 가장 낮은 티어를 고릅니다.
- 여유 시트가 없으면 초대 생성은 **400**을 반환합니다 — 구매가 아닙니다. 플랜 설정에서 시트를 구매한 뒤 재시도하세요.
- 초대는 **21일** 후 만료되며 연장할 방법이 없습니다. 대기 초대의 이메일이나 역할을 바꾸려면 철회 후 다시 생성하세요.

## Admin API vs Compliance API vs Inference Hooks

자주 혼동되는 세 가지 거버넌스 표면:

- **Admin API**(이 페이지)는 **누가 조직에 있는지**와 **무엇을 할 수 있는지**를 관리합니다.
- **[Compliance API](https://platform.claude.com/docs/en/manage-claude/compliance-api)**는 **무엇을 했는지**를 노출합니다: 감사 이벤트, 활동 피드, 그리고 (Enterprise에서) 법적 보존을 위한 콘텐츠 조회 및 삭제.
- **[Inference Hooks](/docs/api/inference-hooks)** — 셋 중 가장 최신(2026년 8월 5일 베타) — 은 Claude가 보기 전에 **각 프롬프트를 실시간으로** 허용하거나 거부하도록 당신의 DLP 서버가 결정하게 해줍니다, chat, Claude Code, Cowork 전반에서.

보안 도구용으로는 `read:org_audit` 스코프의 단일 키가 양쪽 API 읽기를 모두 커버합니다. Inference Hooks는 admin console에서 별도로 구성됩니다.
