## 60 秒概念对照

如果你只读一节，就读这节。下面是你在 Claude 中所熟悉的东西如何对应到 ChatGPT：

| 在 Claude 里你称它为…… | 在 ChatGPT 里它是…… | 同一个概念吗？ |
| --- | --- | --- |
| Claude Projects（工作区 + 文件 + 项目指令） | **Projects** | 是——几乎是同一个概念 |
| Custom Style / 一段你反复复用的已保存系统提示 | **Custom GPTs**——正被 **Plugins**（skills + apps）取代 | 接近，但有一处转折（见下文） |
| 你的账户级偏好 / “我希望你如何回应” | **Custom instructions** | 是 |
| Claude 对过往对话的记忆 | **Memory** | 是——同一个概念，经常演进 |
| Artifacts（用于文档/代码的侧边栏） | **Canvas** | 是——同一个概念 |
| 模型选择器（Opus / Sonnet / Haiku） | **模型选择器**（速度 vs 推理的层级） | 是——同一个概念，名字不同 |
| 工具使用 / 函数调用（API） | **Function calling** | 是——形态相同，JSON 细节不同 |

要点：几乎没有*新概念*要学。它主要是把你已经理解的东西**重新命名和重新安置**。

## Projects vs Custom GPTs——唯一值得搞清楚的区别 {#projects-vs-custom-gpts}

这是 Claude 用户最常犯迷糊的一个点，因为 ChatGPT 有**两样**东西都让人感觉像“定制版的 Claude”，而它们针对的是不同的用途。

- **Projects** 是*组织性*的——一个工作区，把围绕某项持续工作的多个对话、上传的文件和共享指令捆绑在一起。跨多个对话保持连续性正是它的意义所在。当你会去打开一个 Claude Project 时，就该选 Project：一条长期的研究线索、一篇不断演进的文稿、一条带参考文档的工作流。<VerifyNote lastVerified="2026-10-07" source="https://learn.chatgpt.com/docs/projects">OpenAI 自己的措辞是：“用一个 project 把相关的对话、文件、指令和来源放在一起”（"Use a project to keep related chats, files, instructions, and sources together"）——适用于那些“会持续一段时间、产出不止一个结果，或者依赖同一批文件和来源”（"will continue over time, produce more than one output, or depend on the same files and sources"）的工作。它在免费和付费套餐中的可用性会随时间变化——请查阅最新页面。</VerifyNote>

- **Custom GPTs** 是*打包好的助手*——一份已保存的配置（一段系统提示、可选的知识文件、启用的工具，有时还有 API actions），你可以把它作为一个全新的、带固定人设的单次对话来调用。它们生来就是为了复用和分享，所以由一个人构建专业能力，供许多人使用。**它们正在被退役。**

- **Plugins** 就是那个替代品：用 OpenAI 的话说，它是“一个面向某条工作流的可复用打包件，可以包含 skills、apps 或两者兼有”——*skills* 承载如何完成工作的指令，*apps* 则把 ChatGPT 连接到其他服务。和 Custom GPT 是同一种直觉，但覆盖面更大。<VerifyNote lastVerified="2026-10-07" source="https://learn.chatgpt.com/codex/migrate-custom-gpts">OpenAI 表示：“我们正在把 custom GPTs 迁移到 plugins。请用下面的里程碑来规划你的迁移，趁 custom GPTs 尚未退役。”（"We're transitioning custom GPTs to plugins. Use the milestones below to plan your migration before custom GPTs are retired."）已公布的里程碑依次是：管理员通知 → 迁移 → Custom GPT 退役，到那时“custom GPTs 停止运行并离开 GPT 目录”（"custom GPTs stop running and leave the GPT directory"）。原始的 GPT“在退役前仍可使用”（"remains usable until retirement"），而且即便退役之后不再运行，一个 GPT 仍然可以被迁移。具体日期按工作区而定（这份指南是写给 ChatGPT Enterprise 管理员和 GPT 创建者的），并且可能变化——请到所链接的页面上读里程碑，而不要相信这里的某个日期。</VerifyNote>

心智捷径：

- **需要跨多个对话共享上下文并保持连续性？** → Project。
- **需要一个可复用、可分享、每次表现都一致的专家？** → 一个 Plugin（并把你手上已有的 Custom GPT 迁移过去）。

给 Claude 用户的两个陷阱：

- 一次 Custom GPT 或 Plugin 对话往往每次都**从头开始**，只带着它预设的指令加上当前这次对话——别指望它像一条持续进行的 Project 线索那样记得你上一次会话的内容。
- 迁移**并非**无损。Custom actions 必须单独重建——对接某个受支持的连接器，或你自己的 MCP server——所以一个重度依赖它们的 GPT 需要实打实的工作量，而不是一键转换。如果重建的人是你，[Codex Agent Plugins](/docs/models/codex-agent-plugins-catalogs) 讲的就是那层打包机制。

## Custom instructions 与 memory——同一个概念，层次略有不同

在 Claude 里你设置全局偏好，并让它记住上下文。ChatGPT 做的是同样的事，只是有更明确的、可供你设置指令的层次：

<Steps items={[
  {title: "账户级 custom instructions", body: "你长期不变的偏好——语气、详略程度、要关注什么。应用于所有对话，就像你的 Claude 账户偏好。"},
  {title: "Project 指令", body: "限定于某个 Project 主题范围内的上下文——相当于 Claude 的 Project 指令。"},
  {title: "Plugin（或 Custom GPT）指令", body: "烘焙进一个打包助手里的“系统提示”——可以是某个 Plugin 的 skill，也可以是你还没迁移的 Custom GPT 的指令字段。这是构建者完全掌控其行为的地方。"},
  {title: "对话内、一次性", body: "当你需要单条消息的调整时，直接在对话里说出来即可——和 Claude 完全一样。"},
]} />

**Memory** 是它自成一体、不断演进的系统：ChatGPT 可以在不同对话之间携带上下文。请把它*记住什么*、*记多少*，以及*在哪里可用*（例如是否在一个打包助手内部）都视为**易变的**——它经常变，所以要核实当前行为，别想当然。<VerifyNote lastVerified="2026-10-07" source="https://learn.chatgpt.com/codex/personalize">OpenAI 表示：“对于你希望 ChatGPT 跨对话一直遵循的偏好，比如你偏好的回应风格，请使用 custom instructions。”（"Use custom instructions for preferences you want ChatGPT to follow across chats, such as your preferred response style."）分层是真实存在的——在 Codex 里，个人层位于你的全局 `AGENTS.md`，而且“项目和代码仓库也可以提供它们自己的指令”（"projects and repositories can also provide their own instructions"）。细节和可用性会变化——请查阅最新页面。</VerifyNote>

## Canvas 就是 ChatGPT 的 Artifacts

如果你喜欢 Claude Artifacts——一个侧边栏，让文档或代码块变成一个实时、可编辑的对象——那你会觉得 **canvas** 很亲切。它为写作和编码打开一个专门的编辑界面，让你和模型可以就地修改，而不必重新生成整条消息。同样的直觉，不同的名字。

有一点要留意（也是我们为什么不把具体细节写死的一个好例子）：**你能拿到什么样的编辑界面，取决于你身处哪个端**，而不只取决于你提了什么要求。OpenAI 的最新文档把预览与编辑行为描述为按端而异——桌面应用会在对话旁边预览生成的文档，CLI 则完全没有可视化预览，而 IDE 扩展是在编辑器里审阅文件。所选的模型也可能有影响。如果侧边栏没有出现，先怀疑你所在的端或所选的模型，再怀疑是 bug。<VerifyNote lastVerified="2026-10-07" source="https://learn.chatgpt.com/codex/artifacts-viewer">OpenAI 的文件预览文档按端来界定可用性：桌面应用“在对话旁边预览生成的文档、演示文稿、电子表格和 PDF 文件”（"previews generated documents, presentations, spreadsheets, and PDF files alongside the chat"），CLI“不包含可视化文件预览”（"doesn't include a visual file preview"），而 IDE 扩展是在编辑器里审阅文本和代码文件。该页面并未声称存在按模型的门控，所以请把关于模型的那句提醒当作保险说法，而非有文档依据的规则。Canvas 本身在 OpenAI 的帮助中心另有文档（在“来源”中已链接）。</VerifyNote>

## 模型选择器——按任务而非按名字来选

正如你在 Opus、Sonnet 和 Haiku 之间做选择，ChatGPT 也要你选一个模型——通常沿着一条**速度 ↔ 推理**的光谱（快速/即时选项用于快速轮次，更强推理的选项用于难题，最高层级则对付费套餐开放）。*名字和层级数量经常变动*；持久的技能和你在 Claude 上早已使用的是同一个：**让模型与任务难度以及你对延迟/成本的容忍度相匹配。**

这正是 [选择一个模型](/docs/models/choosing-a-model) 和 [我该用哪个 Claude？](/docs/start-here/which-claude) 里的框架——它与厂商无关。别去背某个模型名字；学会读懂“快 vs 深”，据此选择。

下面这段是为了把道理讲具体，而不是让你去背：截至 **2026 年 10 月 7 日**，选择器里跑的是 **Astra**（能力最强）、**GPT-6.1 Sol**（“以低于 Astra 的成本，在复杂工作上提供接近 Astra 的表现”，正在向 Plus、Pro、Business、Enterprise 和 Edu 推送）以及 **GPT-6 Luna**（面向聚焦、高吞吐工作的高效模型）——与此同时，**GPT-5.5 将于 2026 年 10 月 14 日从 ChatGPT、ChatGPT Work 和 Codex 退役**，但仍可在 API 上使用。如果你读到这段的时间已经远远晚于那个日期，这一段里的每一个名字很可能都已经变了。这恰恰就是重点。<VerifyNote lastVerified="2026-10-07" source="https://learn.chatgpt.com/docs/models">模型阵容、套餐可用性和 GPT-5.5 的退役日期读取自 OpenAI 的最新模型页面。该页面上列出的更早的退役：GPT-5.3-Codex-Spark 于 2026 年 9 月 14 日，GPT-5.4 和 GPT-5.4-mini 于 2026 年 8 月 31 日。这份清单按设计就会很快过时——请重新去读原始来源，而不要相信这里的内容。</VerifyNote>

## Function calling——形态相同，JSON 细节不同

如果你在 Claude 上做过 [工具使用](/docs/api/tool-use)，OpenAI 的 **function calling** 会让你立刻感到熟悉，因为*那个循环是一样的*：

<Steps items={[
  {title: "声明工具", body: "你用一个名称、一段描述，以及其参数的 JSON schema（哪些必填、各自的类型）来描述每个工具。和 Claude 的工具定义是同一个概念。"},
  {title: "模型请求一次调用", body: "给定提示和可用工具，模型会返回一个结构化的工具调用——工具名称加参数——而不是（或除了）文本。"},
  {title: "由你来执行", body: "你的应用运行实际的函数，用上那些参数。模型自己从不运行任何东西。"},
  {title: "返回结果", body: "你把工具的输出反馈给模型。"},
  {title: "模型作答", body: "它用结果产出最终回应——并且在结束前可能请求更多调用。"},
]} />

完全相同的是：描述 → 模型请求 → 你执行 → 返回结果 → 作答这个循环、多次/并行调用，以及*模型提议、你的代码定夺*这一原则。<VerifyNote lastVerified="2026-10-07" source="https://developers.openai.com/api/docs/guides/function-calling">已逐字对照 OpenAI 的指南核实：该指南把“一个 function”定义为“一种特定类型的工具，由 JSON schema 定义”，带有 `type`、`name`、`description`、`parameters` 和 `strict`，并列出了同样的五个步骤：带着模型可以调用的工具去发起请求 → 收到一次工具调用 → 在应用侧执行代码 → 带着工具输出发起第二次请求 → 收到最终回应（或更多工具调用）。确切的字段名和选项会变化——请查阅最新的 API 指南。</VerifyNote>

**不同的**、并且在你复制粘贴时会绊倒你的是：确切的 JSON 字段名、工具调用和结果在消息列表中如何表示、“strict”/结构化输出选项，以及具体的 API 端点形态。作为跨厂商的一条通则，**提示和架构可以迁移；线路格式的细节不能**——始终重新核对各厂商的 schema。

## 哪些能迁移（剧透：几乎全部）

你辛苦练就的 Claude 习惯不会白费。以下这些基本上原封不动地沿用：

- **提示结构**——清晰的角色、明确的任务、示例、所要求的输出格式 → [提示基础](/docs/prompting/basics)
- **有意识地给上下文**——粘贴正确的材料、界定范围、别一股脑全倒进去
- **要求特定的输出格式**——表格、JSON、步骤；用法相同
- **就地迭代**——通过追问来打磨（现在还可以通过 canvas）
- **工具使用循环**——描述工具、让模型调用它们、返回结果 → [工具使用](/docs/api/tool-use)
- **按任务难度选模型**——快 vs 深，同样的判断

## 哪些确实要调整

一份简短而诚实的、确实不同的清单：

- **两个“定制化”对象，而不是一个。** 一开始就决定好：是持续的工作区（Project），还是可复用的打包助手（一个 Plugin——或者一个正在变成 Plugin 路上的 Custom GPT）？选错是最常见的早期错误。
- **Custom GPTs 是迁移的起点，不是终点。** OpenAI 正在把它们转移到 Plugins 并让它们退役。如果你继承了一个，就规划它的迁移；不要新建一个。
- **功能 ↔ 端的搭配。** 在 ChatGPT 里，某个预览/编辑面板（或某个工具）是否可用，可能取决于你在哪里运行它——有时还取决于所选的模型。当某样东西缺失时，先检查这些，再看其他。
- **工具的线路格式。** function calling 这个*概念*是一样的；JSON 细节不是——绝不要原封不动地复用 Claude 的确切工具 JSON。
- **易变的具体细节。** 模型名称、层级、限制和价格变得很快。养成到源头去确认的习惯，就像你对 Claude 也应该这么做一样。

## 各自通常在什么场景下最出彩

两者都是出色的通用助手，在任何一项具体任务上的差距往往很小且不断变化——所以把这当作*倾向*，而非定律，并让你自己[在你自己的数据上做评估](/docs/models/choosing-a-model)来决定：

- **在以下情况选 ChatGPT：** 你需要它特有的生态——某个团队已在维护的 Custom GPT、某位协作者已搭好的 Project，或你在那里依赖的某个内置工具/集成。如果你的客户或同事扎根在 ChatGPT 里，去那里与他们会合，胜过制造摩擦。
- **在以下情况选 Claude：** 你已经身处本站围绕其构建的 Claude 工作流——Projects、Artifacts，以及 AILmanac 通篇记录的提示/智能体模式——并想在这些上面深入钻研。

大多数时候诚实的答案是：**你（或你的团队）已经搭建好的那一个。** 技能是可迁移的；搭建成本才是真正的切换成本。
