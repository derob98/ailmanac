Claude を[ヘッドレス](/docs/claude-code/headless-and-agent-sdk)や[スケジュール](/docs/claude-code/background-tasks)で実行する場合 — CI、cron ジョブ、pre-commit フック — 本来なら不適切な操作を止めてくれる人間がいなくなります。この便利さこそ、こうした実行に最も厳しいガードレールが必要な理由です。

## 無人実行に固有のリスク

- 危険なツール呼び出しをその場で**止める人がいない**。
- **環境に存在する認証情報。** CI には強力なトークン(デプロイ、パッケージレジストリ、クラウド)があることが多く、そこで動くエージェントはそれらを継承します。
- **信頼できない入力。** PR や issue をきっかけに起動した実行は、攻撃者が書いたコンテンツを処理する可能性があります([インジェクション](/docs/security/prompt-injection))。

<Callout type="warning">
設計で防ぐべき失敗モードは、悪意あるモデルではありません。持たせるべきでないトークンを握った普通のモデルが、攻撃者の書いたテキストに従って動くことです。以下の各項目は、この 3 つの要素のどれかを取り除きます。
</Callout>

## deny は取り除き、allow は事前承認するだけ

堅牢化した実行で最もよくある間違いは、使うレバーを間違えることです。allow リストは鍵のように見えますが、そうではありません。リストに載せなかったものもエージェントは使え続けられ、セッションの権限モードにフォールスルーするだけです。

<PromptCard title="機能を取り除く — リクエストからツールが消える">{`claude -p "run the test suite" \\
  --disallowedTools "Bash(curl *)" "Read(//.ssh/**)" "Edit(//etc/**)"`}</PromptCard>

<PromptCard title="事前承認リストを厳密にする — それ以外は確認ではなく拒否される">{`claude -p "run the test suite" \\
  --permission-mode dontAsk \\
  --allowedTools "Bash(npm test)" "Read"`}</PromptCard>

CI で使いたいのは後者の形です。`dontAsk` は確認プロンプトになるはずのものをすべて拒否に変えるため、想定外の事態に遭遇した実行は、ハングしたり、緩いデフォルトに黙ってフォールバックしたりせず、はっきりと失敗します。

## 呼び出しごとに走るチェック

allow ルールと deny ルールはパターンにマッチします。呼び出しの*内容* — 引数に含まれるシークレットらしき文字列や、想定外のホスト名 — を検査するチェックが必要なら、`PreToolUse` [フック](/docs/claude-code/hooks)に置きます。フックは他のすべての権限ステップより先に実行され、フックによる拒否は bypass モードでも有効です。

<PromptCard title="シークレットを含むツール呼び出しをすべて拒否する">{`# .claude/settings.json -> hooks.PreToolUse
# Exit code 2 blocks the call and tells Claude why.
jq -e '.tool_input | tostring | test("AKIA|BEGIN PRIVATE KEY|ghp_")' >/dev/null \\
  && { echo "secret material in tool input" >&2; exit 2; } || exit 0`}</PromptCard>

## 例: 安全な CI レビュアー

PR レビューボットは、コードを読み取り専用でチェックアウトし、デプロイやシークレットへのアクセスを**持たず**、コンテナ内で動き、発見事項を**コメント**する — 保護されたブランチは決して変更しない、という形であるべきです。[PR レビューのウォークスルー](/docs/walkthroughs/pr-review-action)を参照してください。
