**2026年11月5日**、Apiiroの研究者**Shmulik Cohen**と**Matan Giladi**は、公開GitHubをあるファイル名に絞って調査した結果を公表しました。`.claude/settings.local.json`です。**103,617のリポジトリで104,185件のコピー**が見つかり、そのうち**1,122件**(約**1.1%**)に**本物の秘密1,379件**がありました。

4日後、Hacker Newsのスレッドは622ポイント、422コメントでトップページに到達しました。続いたのはいつもの助言です。設定ファイルをコミットするな。

その助言は正しいものの、仕組みをまったく捉えていません。このページに独立した価値がある理由は3つあります。

1. **誰も設定ファイルに秘密を貼り付けてはいません。** データベースのデバッグでよくあるように、認証情報をシェルコマンドに入力し、それから**「Yes, and don't ask again」**をクリックしただけです。Claude Codeは承認されたコマンドを*権限ルールとして*保存しました。認証情報は、次回そのコマンドを許可する記録の一部になりました。
2. **漏洩ファイルのうち215件が、業界標準の2つの秘密スキャナの両方を破りました。** スキャナが悪いからではなく、`PGPASSWORD=`や`sshpass -p`の後ろにあるパスワードには、プロバイダ固有の接頭辞も、鍵の形式も、際立ったエントロピーもないからです。普通のコマンドラインにある普通の単語に見えます。
3. **Claude Codeは守ろうとしていますが、その保護は構造的に持ち運べません。** 除外ルールを**グローバルな**git除外ファイルに書きます。このファイルはホームディレクトリにあります。リポジトリの中にはないので、チームメイトのクローンにも、CIランナーにも、次のノートPCにも届きません。

これはプロンプトインジェクションの話ではなく、エクスプロイトもありません。承認された正規のワークフローで、監査証跡がたまたま秘密情報のファイルになっているという話です。はるかに根の深い種類の問題で、承認を永続化するあらゆるエージェントに当てはまります。

## 第1部 — 仕組みを正確に

Claude Codeは、ほとんどのシェルコマンドを実行する前に確認します。プロンプトには永続的な選択肢**「Yes, and don't ask again」**があり、これを選ぶとリポジトリのルートにある`.claude/settings.local.json`に`allow`ルールが書き込まれます。承認は**そのリポジトリとそのコマンドについて永続的**で、将来のセッション(worktreeを含む)にも適用されます。

ファイルの形は普通です。

<PromptCard title="安全な形 — Claude Code自身のドキュメントにあるパターンルール">{`{
  "permissions": {
    "allow": ["Bash(npm run test *)"],
    "deny": ["Read(./.env)", "Read(./.env.*)"]
  }
}`}</PromptCard>

ここが要です。**保存されるルールがパターンのときもあります**。上のように。**入力されたとおりの正確なコマンドのときもあります。** 正確なコマンドの場合、コマンドの全文字、インラインで渡したパスワードも含めて、ルール文字列の一部になります。

つまりこの障害には、ミスも攻撃者も要りません。普通の午後があれば足ります。

## 第2部 — なぜ215件のファイルが両方のスキャナを破ったのか

Apiiroは、漏洩ファイルを最も広く使われている2つのオープンソース秘密スキャナにかけました。秘密を含む**1,122**件のうち:

| スキャナ | 検出したファイル数 |
|---|---|
| gitleaks | **564** |
| TruffleHog | **643** |
| **どちらも検出しなかった** | **215** |

つまり**漏洩ファイルの19%が、両方のツールから見えません**。理由は先ほどの636/743の内訳です。

スキャナは2つの方法で秘密を見つけます。**既知の形式**(`AKIA…`の接頭辞、`ghp_…`のトークン、SupabaseのJWTの形)に一致させるか、怪しい位置にある**高エントロピーの文字列**を検出するかです。どちらの手法も、見分けがつくように設計された*発行済みの認証情報*に対して機能します。

**人間が選んだパスワード**がシェルコマンドの引数位置にある場合、どちらも機能しません。`PGPASSWORD=Summer2024!`には、一致させるべきベンダー接頭辞がありません。エントロピーも平凡です。構造的に、設定値やテストフィクスチャや単なる単語と区別できません。見逃しの大多数はまさにこの種類で、`PGPASSWORD=`、`sshpass -p`、`mysql -p`の後ろのインラインパスワードでした。

<Callout type="note" items={[
  "564/643の内訳についての注意点(単一の報道機関による)。両スキャナは、候補の認証情報が有効かを確かめる検証ステップなしで実行されました。検証が主に改善するのは再現率ではなく適合率で、そもそもどのルールにも一致しないパスワードには役立ちません。だから215という数字がそれによる副産物である可能性は低いです。ただし、スキャナごとの数字を引用する場合は、この注意点も併せて引用してください。",
]} />

一般化できる教訓は、この事件とは独立しています。**あなたの秘密スキャンは発行済みトークンに合わせて調整されており、コマンド引数に含まれる選ばれたパスワードにはほぼ盲目です。** エージェントの設定ファイルと保存されたトランスクリプトは、コマンド引数だらけです。スキャナのルールを何も変えずにパスに`.claude/`を足すだけでは、この問題の約5分の4しか捕まえられません。

## 第3部 — 持ち運べないgitignore保護

Claude Codeはこれに無関心ではありません。まだ無視されていないリポジトリに初めて`settings.local.json`を書くとき、除外ルールを追加します。ただしプロジェクトの`.gitignore`ではなく、**グローバルなgit除外ファイル**にです。

自分のマシンで2つのコマンドで確認できます。

<PromptCard title="保護が存在することを確認し、どこにあるかを見る">{`# Where Git looks for your personal excludes.
# If this prints nothing, Git uses the XDG default: ~/.config/git/ignore
git config --get core.excludesFile

# The rule Claude Code writes:
grep -n 'claude' ~/.config/git/ignore`}</PromptCard>

2026年11月10日にこのマシンで実行したところ、`core.excludesFile`は未設定で、`~/.config/git/ignore`の最初の行はちょうど`**/.claude/settings.local.json`でした。保護は実在し、機能しています。

それでも十分ではありえません。理由は4つあり、すべてバグではなく構造的なものです。

- **グローバル除外ファイルはコミットされません。** ホームディレクトリにあります。チームメイトのクローンはそれを見たことがありません。CIランナーも、devコンテナも、次のノートPCも同じです。
- **後からリポジトリになったフォルダには遡って効きません。** エージェントの作業の多くは作業用ディレクトリで始まり、あとから`git init`されます。
- **除外ルールは、すでに追跡されているファイルには何もしません。** これはClaude Codeの制限ではなくGitの文書化された挙動です。パスがインデックスに入ると、`.gitignore`は無関係になります。
- **保護するのは1つのファイル名だけです。** *共有*の`.claude/settings.json`はチームが意図的にコミットするファイルで、その公開コピー298件にも秘密がありました。

だから自分の側の修正は小さく、省略できません。パスを**リポジトリ自身の**`.gitignore`に入れ、プロジェクトと一緒に持ち運ばれるようにします。

<PromptCard title="除外ルールをプロジェクトと一緒に持ち運べるようにする">{`# In the repo, not in your home directory.
printf '%s\\n' '.claude/settings.local.json' >> .gitignore

# Or ignore the whole agent config directory, which also covers
# transcripts and anything future versions add:
printf '%s\\n' '.claude/' >> .gitignore

git add .gitignore && git commit -m "chore: ignore local agent permission settings"`}</PromptCard>

## 第4部 — 自分のリポジトリを監査する

5つのチェックを順番に。3番目は人が飛ばしがちで、最も重要です。

<PromptCard title="5コマンドの監査">{`# 1. Is the file tracked RIGHT NOW?
git ls-files .claude/settings.local.json

# 2. Has it EVER been committed, on any branch?
#    An empty result from step 1 means nothing without this.
git log --all --oneline -- .claude/settings.local.json

# 3. Look for the secrets the scanners miss: inline passwords
#    in command arguments, across all of history.
git log --all -p -- .claude/ | grep -nE 'PGPASSWORD=|sshpass -p|mysql .*-p|MYSQL_PWD=|--password[= ]'

# 4. Confirm an ignore rule actually applies, and see which file it came from.
git check-ignore -v .claude/settings.local.json

# 5. Run the scanners over history too, not just the working tree.
gitleaks git -v          # gitleaks 8.19+; older: gitleaks detect -v
trufflehog git file://.`}</PromptCard>

Claude Codeのセッション内では、`/permissions`コマンドが有効なルールすべてと、**それぞれがどのファイル由来か**を一覧にします。何もコミットされていないマシンの許可リストにあるリテラルのコマンドを見つける最速の方法です。

そのうえで検索を広げます。Apiiro自身の推奨は、組織全体で`.claude/settings.local.json`**と**`.claude/settings.json`の両方を、履歴も含めて、ファイルがすでに消えているリポジトリでも掃き出すことです。承認を永続化するエージェントはどれも同じ形のファイルを持つので、兄弟もスキャンしてください。`.claude/`、`.cursor/`、`.gemini/`、`.specstory/`です。

<Callout type="warning" items={[
  "ファイルを削除しても秘密は消えません。git履歴、すべてのフォーク、同僚がすでに持っているすべてのクローンに残ります。Apiiroは、ファイルの古いバージョンにのみ存在した秘密734件と、秘密を引き継ぐ74リポジトリの211フォークを見つけました。コミットされたファイルに一度でも触れた認証情報は、公開されたものとして扱ってください。",
]} />

## 第6部 — 知っておくべき食い違い

Anthropicは公に回答しました。Claude CodeチームのBoris Chernyは2026年11月7日にHacker Newsに書いています。

> Historically Claude Code has not done secret scrubbing (there are many good tools for that), but we are looking into what we can do to prevent this.

(訳: これまでClaude Codeは秘密のスクラブをしてきませんでした。そのための優れたツールは多くありますが、これを防ぐために何ができるかを検討しています。)

彼はさらに、`settings.local.json`はソース管理にチェックインするファイルではないこと、そして露出したコピーは**「手動で作られてチェックインされた」**ものだと述べました。論旨は、Claude Codeはファイルを作るときに除外ルールを追加するのだから、コミットされたコピーは別の場所から来たはずだ、というものです。彼は[auto mode](/docs/claude-code/permissions)を推奨しました。許可ルールを積み上げる代わりに、分類器でアクションを選別する仕組みで、さらにgitホストでの秘密スキャンも勧めています。検討中のプロトタイプは、auto modeがこうしたコマンドを捕まえるようにすること、基本的な秘密スキャンを組み込むことですが、完全には直らないかもしれないという但し書きつきです。同じ露出がauto modeでも起こりうるとコメント投稿者に指摘されたとき、彼の返事は「Yeah good catch.」でした。

**その説明とApiiroのデータは噛み合いません。** Apiiroは、追跡した**1,105のうち539**のリポジトリで、Claudeが共著者のコミットがファイルに触れていたと報告しています。共著だからといって、Claudeが個々の認証情報を持ち込んだ、あるいはプッシュしたことの証明にはならない、とApiiroは慎重に述べています。コミットがすでに存在したファイルを巻き込んだ可能性があるからです。それでも「手動で作られてチェックインされた」と、サンプルの半数にあるエージェント作成のコミットとは両立しにくいのです。

行動に移すのにこれを解決する必要はなく、どちらの説明でも工学的な結論は同じです。

- Anthropicが正しいなら、保護はホームディレクトリのファイルに依存しており、第3部の4つの構造的な隙間はすべてあなたのチームに当てはまります。
- Apiiroが正しいなら、エージェントが作成したコミットがファイルをリポジトリに入れる現役の経路であり、保護はさらに弱いことになります。

いずれにせよ、除外ルールはリポジトリに置き、リテラルではなくパターンを承認し、インラインパスワードをスキャンしてください。また、2026年11月8日時点で**修正が確認されたものは何もない**(バージョンも、変更履歴の項目も、CVEも、深刻度評価もない)ことにも注意してください。
