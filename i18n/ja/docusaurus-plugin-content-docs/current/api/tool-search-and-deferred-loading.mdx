## 2つの問題、そしてお金に関係するのはそのうち1つだけである理由

すべてのツール定義を最初にまとめて読み込むと、カタログが大きくなるにつれて2通りの形で行き詰まります。

1つ目は分かりやすいものです。Anthropic 自身の例を挙げると、5つのサーバー(GitHub、Slack、Sentry、Grafana、Splunk)を使う MCP 構成では、**Claude が何も作業を始める前にツール定義だけで約5万5千トークン**を消費します。これは会話のターンごとに毎回支払う税金のようなものです。

2つ目こそ、アーキテクチャを実際に変えるものです。**利用可能なツールが30〜50個を超えると、ツール選択の精度が低下します。** その先ではツールが増えても能力は増えず、モデルが混雑したメニューから選ぶことになるだけです。遅延読み込みは、モデルが現在のリクエストに関連する3〜5個のツールしか目にしないため、コストの問題と精度の問題を同じ一手で解決します。Anthropic は、そのマルチサーバー構成でコンテキストが **85パーセント以上**削減されたと報告しています。

経済性や公表されている精度の差分を知りたい場合は、AILmanac の [MCP のトークンコスト](/docs/claude-code/mcp-token-cost)で扱っています。このページは配線(実装)の話です。

## 誰もが誤解しているメンタルモデル

コードを書く前に、正しておくべき誤解があります。

> `defer_loading` は送信する内容を減らす**わけではありません**。遅延対象のツールも含め、すべてのツールの完全な定義(名前、説明、完全な `input_schema`)を、**リクエストのたびに毎回** `tools` 配列に入れる必要があります。

HTTP リクエストボディは小さくなりません。アップロード帯域も変わりません。API は検索を実行して見つかった参照を展開するために、サーバー側でそれらの定義を必要とするからです。

変わるのは**コンテキストウィンドウ**に入る内容であり、したがって課金対象となる内容です。遅延対象の定義はシステムプロンプトのプレフィックスから除外されます。Claude がその1つを発見すると、API は会話の中に `tool_reference` ブロックをインラインで追加し、モデルが目にする前に完全な定義へ展開します。

このインライン追加という詳細が、2つ目の分かりにくい点です。展開はプレフィックスではなく*会話の中で*行われるため、**キャッシュされたプレフィックスが無効化されることはありません**。遅延読み込みとプロンプトキャッシュは両立します。[strict ツール使用](/docs/api/tool-use)も同様です。ツール呼び出しの出力を制約する文法は完全なツールセットから構築されるので、会話の途中でツールが追加されても再コンパイルは発生しません。

## regex か BM25 か

どちらのバリアントも同じ4つのフィールド、つまり**ツール名、説明、引数名、引数の説明**を検索し、この機能をサポートするすべてのモデルで利用できます。違いは、Claude がクエリに何を書くかだけです。

| | `tool_search_tool_regex_20251119` | `tool_search_tool_bm25_20251119` |
|---|---|---|
| Claude が書くもの | Python の `re.search()` パターン | 自然言語クエリ |
| 入力フィールド | `pattern` | `query` |
| 最大長 | 200文字 | 500文字 |
| マッチング | 大文字小文字を区別しない | BM25 ランキング |
| 向いている場合 | 名前に名前空間がある(`github_`、`slack_`) | 説明が文章のように書かれている |

regex 版は設定を誤りやすいバリアントです。名前からキーワード検索のように思えますが、そうではないからです。Claude は本物のパターンを書きます。`"weather"`、`"get_.*_data"`、`"database.*query|query.*database"` といった具合です。期待するツールがモデルに見つけられない場合は、モデルのせいにする前に、自分でパターンを試してください。

<PromptCard title="失敗した regex マッチをローカルで再現する">
{`import re
# Claude writes broad patterns, e.g. ".*weather.*" — not exact names.
# Search the same four fields the API searches.
haystacks = ["get_weather", "Get the weather at a specific location", "location", "unit"]
print(any(re.search(r"weather", h, re.IGNORECASE) for h in haystacks))`}
</PromptCard>

マッチ漏れへの実践的な対処は、より巧妙なパターンではほぼありません。**説明文にキーワードを入れる**ことです。ユーザーが実際に使う言葉を書いてください。ツール名はサービスごとに名前空間を付け、1つのパターンでグループ全体を拾えるようにします。

## レスポンスを読む

検索が成功すると、アシスタントのターンに3種類の新しいブロックが次の順で現れます。

```json
{
  "role": "assistant",
  "content": [
    { "type": "text", "text": "I'll search for tools to help with the weather information." },
    {
      "type": "server_tool_use",
      "id": "srvtoolu_01ABC123",
      "name": "tool_search_tool_regex",
      "input": { "pattern": "weather", "limit": 10 }
    },
    {
      "type": "tool_search_tool_result",
      "tool_use_id": "srvtoolu_01ABC123",
      "content": {
        "type": "tool_search_tool_search_result",
        "tool_references": [{ "type": "tool_reference", "tool_name": "get_weather" }]
      }
    },
    {
      "type": "tool_use",
      "id": "toolu_01XYZ789",
      "name": "get_weather",
      "input": { "location": "San Francisco", "unit": "fahrenheit" }
    }
  ],
  "stop_reason": "tool_use"
}
```

扱いのルールは3つです。

1. **`srvtoolu_...` の ID に対して `tool_result` を返してはいけません。** 検索はすでに Anthropic のサーバー上で実行済みです。それに応答すると API はリクエストを拒否します。`tool_result` を返すのは `toolu_...` の ID に対してだけで、そこからは通常のツール使用になります。
2. **`tool_reference` ブロックを自分で展開してはいけません。** 対応する定義が `tools` にある限り、API が展開します。
3. **`tool_search_tool_result` は履歴にそのまま残してください。** 後続のターンが、どのツールがすでに発見済みかを知る手がかりになります。

何にもマッチしなかった検索はエラー**ではありません**。`tool_references` 配列が空の `tool_search_tool_search_result` が返り、次にどうするかは Claude が判断します。

`limit` についてもう1つ見落としやすい点があります。デフォルトは **5** 件ですが、Claude は自身の検索入力で 1 から 10,000 までの任意の値を設定できます。あなたが直接制御することはできません。大量の定義が流れ込む数に厳格な上限が必要なら、それは後述のカスタム実装を選ぶ理由になります。

実行*中*の検索失敗は異なります。HTTP **200** で返り、エラーは `tool_search_tool_result_error` オブジェクトの中に入ります。

| `error_code` | 何が起きたか |
|---|---|
| `invalid_tool_input` | 不正な正規表現、または200文字の制限を超えたパターン |
| `unavailable` | 検索を実行できなかった(タイムアウトまたはサービス利用不可) |
| `too_many_requests` | ツール検索操作に特化したレート制限 |
| `execution_time_exceeded` | 検索が実行時間の上限を超えた |

これらは回復可能なものとして扱ってください。会話は損なわれておらず、ターン全体を失敗させるよりも、Claude に別のパターンで再試行させるのが誠実な対応であることがほとんどです。周辺のリトライ方針は[エラーとレート制限](/docs/api/errors-and-rate-limits)を参照してください。

## プロンプトキャッシュ

結論は良好です。遅延定義はキャッシュされたプレフィックスの外にあるため、会話の途中でツールを追加・発見してもキャッシュは無効化されません。プレフィックスのルールは[プロンプトキャッシュ](/docs/api/prompt-caching)を、ヒットを実証する必要がある場合は[キャッシュ診断](/docs/api/cache-diagnostics)を参照してください。

落とし穴は上に挙げたものです。`defer_loading: true` と `cache_control` は1つのツールに対して相互排他です。現在ブレークポイントが長い配列の最後のツールにあり、その配列を遅延させると、気づかないうちに「キャッシュあり」から「400」へ移ってしまいます。ブレークポイントは、常に読み込んでおくつもりのツールに固定してください。

## MCP コネクタ:ツールではなくツールセットに設定する

[MCP コネクタ](/docs/api/mcp)を通じてリモートサーバーからツールが届く場合、個々の定義には触れません。定義はあなたのものではないからです。`mcp_toolset` エントリで設定します。サーバー全体には `default_config` で一度に、ツールごとには `configs` で指定します。

<PromptCard title="常に必要な1つのツールを除いて、MCP サーバー全体を遅延させる">
{`{
  "type": "mcp_toolset",
  "mcp_server_name": "observability",
  "default_config": { "defer_loading": true },
  "configs": {
    "search_events": { "defer_loading": false }
  }
}`}
</PromptCard>

これは実際に最も早く効果が出る形です。複数のサーバーを集約すると、まさにこの機能が想定する200個以上のツールという状況になり、常に使える状態にしておく価値のある入口ツールが1つか2つはほぼ確実にあります。

## 検索を独自のものに置き換える

組み込みのバリアントはどちらも字句ベースです。ツールが表現ではなく意味で見つけやすい場合は、検索を自分で実装してください。通常のカスタムツールを定義し、通常の `tool_result` の中で `tool_reference` ブロックを返します。

<PromptCard title="API が展開してくれるクライアント側の検索結果">
{`{
  "type": "tool_result",
  "tool_use_id": "toolu_your_tool_id",
  "content": [
    { "type": "tool_reference", "tool_name": "discovered_tool_name" }
  ]
}`}
</PromptCard>

参照する名前はすべて、トップレベルの `tools` 配列に完全な定義が必要で、通常は `defer_loading: true` を付けます。展開の経路は同一で、入れ替えるのは検索(取得)の部分だけです。形式の違いに注意してください。`tool_search_tool_result` は*サーバー側*の形式で、組み込みバリアントの内部用です。カスタムツールは、上に示した標準の `tool_result` 形式を返します。Anthropic は[エンベディングを使った実践的なレシピ](https://platform.claude.com/cookbook/tool-use-tool-search-with-embeddings)を公開しています。

これは `limit` の問題からの逃げ道でもあります。いくつの参照を返すかは、自前の検索が決めます。

## 使わないほうがよい場合

前提が成り立たないとき、遅延読み込みは何も得をもたらさず、検索の往復分のコストだけがかかります。次の**いずれか**に当てはまる場合に使ってください。

- 利用可能なツールが10個以上
- ツール定義が合計でおよそ1万トークンを超える
- カタログの拡大に伴い、選択精度が目に見えて低下している
- 複数の MCP サーバーを集約している(200個以上のツール)
- ツールライブラリが増え続けている

ツールが10個未満の場合、すべてのツールが毎回のリクエストで使われる場合、またはカタログ全体が約100トークン未満の場合は、通常のツール呼び出しのままにしてください。課金の形にも注意してください。**ツール検索は独立したサーバーツールとしては計測されません。** `usage.server_tool_use` にツール検索用のフィールドはありません。かかるトークンは、コンテキストに取り込まれる定義の分だけで、他のツール定義と同じ価格です。

キャパシティプランニング用のハードな上限は次のとおりです。**1リクエストあたり遅延ツール10,000個**、regex パターン200文字、BM25 クエリ500文字。
