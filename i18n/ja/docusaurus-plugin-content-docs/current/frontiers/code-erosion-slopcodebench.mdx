あなたが読んだことのあるほぼすべてのコーディング・ベンチマークは、同じ問いを立てています。*タスクが与えられたとき、エージェントはそれを解けるか？* 1つのプロンプト、1つのパッチ、1つの判定です。この設定は便利ですが、実際にお金を失わせる失敗モードを隠してしまいます。現実のソフトウェアは一度で書き上がることがないからです。仕様は動きます。先週作ったものを拡張します。そして本当に興味深い問いは、エージェントがその機能を書けるかどうかではなく、**すでに動いていたコードにエージェントが何をするか**です。

[SlopCodeBench](https://www.scbench.ai) はまさにそれを測るために存在し、その結果は世間の議論が示唆するよりも悪いものです。論文自身の言葉では、*「ソフトウェア開発は反復的だが、エージェント型コーディング・ベンチマークは、単発の設定によって設計上の問題を覆い隠している。」*

今週このページを書く価値があった理由は2つあります。第一に、第三者によるキャンペーン報告 *"SlopCodeBench 10/2026 – Opus 5.5, Astra wins overall, xhigh considered harmful"* が、2026年10月15日に Hacker News で**260ポイント・101コメント**に達しました。7月の同じベンチマークに関する405ポイントの投稿に続くものです。第二に、その中で最も重要な数字をほとんど誰も引用していません。見出しは広まりましたが、リグレッションの統計、合格1件あたりのコストの計算、そして清潔さと正しさの逆転は広まりませんでした。

## ベンチマークが実際にやっていること

SlopCodeBench の作業単位はタスクではなく**軌跡（trajectory）**です。エージェントは問題を与えられて解答を書き、次に新しい要件を受け取り、*自分自身の既存コード*を修正しなければなりません。これを繰り返します。仕様は、実装の詳細は開いたまま、アーキテクチャ上の判断を迫る形で進化します。そして — これがこのベンチマークを効かせる仕組みですが — **以前のチェックポイントのテストは引き継がれます**。チェックポイントを通過するには、新しい要件を満たし、*かつ*以前のすべての要件を動作させ続けなければなりません。

論文によれば規模は次のとおりです。**36問題**が合計**196チェックポイント**に分解され、オープンとクローズドのモデルファミリーにわたる**15のコーディングエージェント**が評価されています。

2つの指標が得られます。

- **Strict pass** — すべてのテストが通ること。以前のすべてのチェックポイントのリグレッションテストをすべて含みます。
- **Core pass** — より緩い基準で、現在の要件を満たしたことに点を与えます。

そして論文は、追跡する2つの劣化モードに名前を付けています。**構造的エロージョン**は複雑さが集中すること、つまりコードが少数の過負荷な箇所に固まっていくことです。**冗長性（verbosity）**は重複したコードが増殖することです。これらは雰囲気ではなく、測定されています。

### 見出しになるべき結果

論文より：**1つの問題でもエンド・ツー・エンドで完全に解いたエージェントはありませんでした。** 15のエージェントのどれも、36の問題のどれもです。最良のエージェントでも**チェックポイントの14.8%**に到達しただけでした。

構造的エロージョンは**軌跡の77%**で、冗長性は**75.5%**で増加しました。**473のオープンソースリポジトリ**のコーパスと比べると、エージェントが書いたコードは**2.3倍の冗長性**と**2.0倍のエロージョン**を示しました。

つまり基本的な主張は「エージェントは人間より少し散らかったコードを書く」ではありません。長期的な軌跡の4分の3で、エージェントが作業するほどコードは構造的に悪化し、最終状態は人間が出荷するものの約2倍エロージョンが進んでいる、ということです。

HumanLayer は、固定された v1.0 カタログに対し、標準の `just-solve` プロンプト、シード42、`any-case` ランナーの合格ポリシー、Python 3.12 と uv を使った Docker 上で、10の完全なキャンペーンを実行しました。モデルと労力の組み合わせごとに1回の実行です。

まず strict の列を見てください。フロンティア全体が**12.24%〜16.33%**の間に収まっています。最良と最悪の差は196件中8チェックポイントです。これらのモデルの1つが長期的な保守で決定的に優れていると言う人がいれば、それはノイズを読んでいるのです — とりわけ、各セルが1回の実行であることを踏まえれば。

### 引用する指標によって順位が入れ替わる

これは、どれかを引用する前に身につけておくべき部分です。

- **GPT-6 Astra XHigh** は **strict で1位**（16.33%）、**core で5位**（69.39%）。
- **Opus 5.5 Medium** は **strict で5位**（14.29%）、**core で1位**（73.98%）— 表の中で最良の core 率です。
- **GPT-6.1 SOL Medium** は **strict で4位タイ**（14.80%）、**core では最下位**（65.82%）。

同じ10回の実行、同じデータで、表彰台が入れ替わります。2つの指標は本当に異なるものを測っています。core 率は「新しいことをどれだけ達成したか」、strict 率は「古いものを壊さずに新しいことをどれだけ達成したか」です。一方が得意で他方が平凡なモデルもあり、これらの大半がそうです。

このページから1つだけ覚えるなら：**コーディングエージェントの数字が、どちらの合格率を指しているのかを尋ねてください。** 同じデータセット上の1つのモデルで14.29%と73.98%という差があること、それが議論のすべてです。

## 「xhigh は有害とみなされる」

さて、この投稿をトップページに押し上げた発見です。3つのモデルが medium と xhigh の両方の労力で実行されました。

| モデル | Strict：Medium → XHigh | Core：Medium → XHigh | コスト倍率 |
|---|---:|---:|---:|
| Opus 5.5 | 28 → **25** | 145 → 141 | **4.22×** |
| GPT-6 SOL | 30 → **26** | 133 → 134 | 2.11× |
| GPT-6 Astra | 29 → **32** | 130 → 136 | 2.91× |

3モデル中2つは、労力を上げると strict の合格数が**悪化**し、しかもコストは2.11倍〜4.22倍かかりました。著者の言葉では、*「opus 5.5 は xhigh よりも medium の労力のほうが良かった。」*

大いに評価すべきことに、著者は過大に主張しません。報告は、この発見が*「推論を増やすとコーディングが悪化することを証明するものではない」*とし、示すのは*「高い労力は、より多くの strict 合格を買う確実な方法ではなかった」*ことだけだと述べています。そして方法論上の注意点もはっきり述べられています：*「各モデルと労力の設定を1回ずつ実行した…… これらの単発の実行では、労力を原因として切り分けられない。」*

その注意点は本物であり、手放さないでください。196件中3チェックポイントの揺れは、同じ構成を2回実行した間に予想される分散の範囲内に十分収まります。**生き残るのは弱い主張です：長期的な作業において、労力は正しさを確実に買えるダイヤルではない。** 強い主張 — xhigh が積極的にコーディングを損なう — は、このデータでは確立されておらず、著者もそう主張していません。

## クリーンになったのに、動く頻度は下がるコード

これは本当に言い逃れしにくい結果であり、報告の中で最も興味深いものです。

xhigh の Opus 5.5 は、medium の Opus 5.5 より strict で通過したチェックポイントが**少なく**、それでいてスロップ指標では明らかに**優れた**コードを書きました。一致する28問題で、スロップのカバレッジは xhigh が **77.75%**、medium が **94.25%**（フィルタ後 92.90%）でした。著者は xhigh の出力を*「約5倍クリーン」*と特徴づけています。

その数字については、引用の仕方に関わるので注記します。約5倍というのは、著者による複合スロップ指標の特徴づけです。上の2つのカバレッジ率からは**導出できません**。それらの差は約16ポイントであって、5倍ではないからです。検証可能なものが必要なら、カバレッジの数値を引用してください。「約5倍クリーン」は、内部を見ていない指標についての方向性の主張として扱ってください。

いずれにせよ方向は一貫しており、含意は不都合です：**推論の労力を増やすと、見た目は良くなり、機能は悪くなるコードが買えた。** 労力は部分的にアーキテクチャ上の趣味 — リファクタリング、抽象化、整頓 — を買っているようで、それらの編集こそが、すでに動いていたコードを壊すものです。整頓はリグレッションのリスクです。醜くても動いているものをそのままにするモデルは、以前に何が通っていたかを覚えているベンチマークでは、より良いスコアを取ります。

合格率とコード指標のあいだの乖離についての報告の推測は、繰り返す価値があります。新しいモデルは、既存のリンターがまだ検出できない新しい種類のスロップのパターンを生成している可能性があります。これは、エージェントの出力に対するクリーンなリント報告は、あなたのコードについてと同じくらい、あなたのリンターについての証拠でもある、という良い注意喚起です。

### 指標に表れる、正反対の2つのアーキテクチャ・スタイル

もう1つ、見落としやすく、静かに多くを物語る詳細があります。関数・メソッド全体の平均循環的複雑度：

- **Fable 5.1**：8,967 個の callable、平均複雑度 **3.57**
- **GPT-6 SOL Medium**：1,083 個の callable、平均複雑度 **11.70**

同程度の問題で、書かれた関数の数には**8.3倍の差**があります。Fable は多数の単純な単位へ積極的に分解し、GPT-6 SOL ははるかに少数で、はるかに密度の高いものを書きます。平均複雑度だけで順位づけすれば Fable が3倍で勝ちます。callable の数で順位づけすれば話は逆転します — それらの小さな関数の山こそ、冗長性が住む場所でもあるからです。

どちらの数字も、単独では何も意味しません。これはエージェントの出力に対するコード品質指標についての一般的な教訓です：どの指標もアーキテクチャ・スタイルによって操作可能なので、ペアで読んでください。

## 実際に何をすべきか

論文は明白な介入を試しており、その結果はもっと知られるべきです：**品質を明示する指示は、初期の問題を最大3分の1減らしたが、劣化のパターンには影響しなかった。**

クリーンなコードを書けとエージェントに伝えるのは、一度は効きます。最初のコミットを改善します。腐敗は止めません。エロージョンはエージェントの最初の意図ではなく*反復的な編集プロセス*の性質なので、意図に向けた指示はそれに触れないのです。

つまり修正は、プロンプトよりも居心地の悪い場所にあります。
