コーディングエージェントは機能しています。それが問題です。

1 日に 5 件のプルリクエストをマージしていたチームが、いま 40 件マージしているとしても、テストスイートもランナー予算もブランチ保護ルールも変えていません。変わったのは、旧来の量に合わせて調整されていたキューイングシステムへの*到着率*です。下流のすべて — マージキュー、フレーキーテストのノイズ、ランナーの同時実行数、レビューの注意力 — は人間のスループットに合わせてサイジングされており、キューイングシステムは優雅に劣化してはくれません。持ちこたえ、持ちこたえ、持ちこたえ、そして 1 週間のうちに倒れます。

このページは[検証のボトルネック](/docs/frontiers/the-verification-bottleneck)のパイプライン側です。あちらのページは*誰がコードをチェックするのか*を問います。こちらは、あなたの CI がその量を物理的に吸収できるのか、できないときにどうするかを問います。

## 問題全体を枠づける 3 つの数字

**−7.2%。** DORA の 2024年版 *Accelerate State of DevOps* レポートは AI 採用の 25% 増加をモデル化し、**デリバリー安定性の 7.2% 低下**とスループットの 1.5% 低下を見積もりました。個人の生産性と仕事の満足度は*上がり*ました。デリバリーレベルの成果は下がりました — レポートはこれを、変更セットの大型化とバッチングの規律の弱まりに結びつけています。2025年の続編はこう言い直しています:AI は**増幅器**であり、あなたのデリバリーシステムが既にそうであるものを拡大する、と。1 日 5 PR で脆かったパイプラインは、40 PR では使い物になりません。

**19%。** METR のランダム化試験(2025年7月)は、経験豊富なオープンソースメンテナ 16 人と、彼ら自身のリポジトリからの実際の課題 246 件を対象に、AI ツールの使用可否をランダム化しました。AI ありのほうが、タスクは **19% 長くかかりました**。CI 計画にとって重要なのは知覚のギャップです:開発者は 24% の高速化を予測し、*遅くなった後でさえ* 20% 速くなったと信じていました。あなたのチームの誰も、パイプラインが制約だとは言ってくれません。誰もそれを制約として経験しないからです — 彼らが経験するのは「待ち」であり、それは天気のように感じられます。

**1.5% / 16% / 84%。** Google が公開したフレーク性のデータ:テスト実行のおよそ **1.5%** がフレーキーな結果を報告し、420 万件のテストのうち約 **16%** が何らかの時点でフレーク性を示し、観測された pass→fail 遷移のおよそ **84%** は本物のリグレッションではなくフレーキーテストによるものです。この 1.5% を覚えておいてください — 1 日 5 PR なら無視できるほど小さく、40 PR では効いてきます。

## なぜマージキューが最初に壊れるのか

たいていのチームは天井が計算資源だと思い込みます。違います。マージキューであり、その理由は、ほとんどの人がドキュメントを読んだことのない仕組みにあります。

GitHub のマージキューは**投機的チェック**を行います。PR #1、#2、#3 をキューに入れると、一時ブランチを作ります:`main` + #1、`main` + #1 + #2、`main` + #1 + #2 + #3 — そしてそれらすべてを*並列に*テストします。すべてのチェックが通れば、3 件が 1 ラウンドで着地します。バッチングが N 回の逐次検証を 1 回に変える、というのが価値提案のすべてです。

では失敗経路を読みましょう。PR #1 を含むグループのチェックが失敗すると、GitHub はキューから **#1** を取り除きます — そして後ろのグループはすべて #1 の変更を含んでいたので、それらは無効になり、**#1 なしで再構築**されます。1 件の悪い PR が食うのはスロット 1 つではありません。バッチの残り全部の CI ラウンドを食います。

これによりキューのスループットは*合格率*の関数になり、しかも直感より急峻です。モデル化しましょう:バッチサイズ N、各 PR が独立に確率 p で失敗し、最初の失敗までの連続した PR をマージするとします。1 ラウンドあたりの期待マージ数は幾何分布の期待値です:

```text
E[merges] = (1 − p) · (1 − (1 − p)^N) / p
```

N = 10 の場合:

| PR ごとの失敗率 `p` | 1 ラウンドあたりの期待マージ数 | 10 PR を捌くのに必要なラウンド数 |
| --- | --- | --- |
| 2%  | 8.9 | ~1.1 |
| 5%  | 7.6 | ~1.3 |
| 10% | 5.9 | ~1.7 |
| 20% | 3.6 | ~2.8 |
| 30% | 2.3 | ~4.4 |

たいていのチームが逆に捉えている帰結が 2 つ:

1. **フレーキーなスイートは*スループット*税であって、迷惑料ではありません。** フレーク性は `p` に直接上乗せされます。本物の失敗 5% から、本物 5% + フレーク 5% になると、1 ラウンドあたり 7.6 マージから 5.9 マージへ — 何もテストしていなかったテストのせいで、マージ能力のおよそ **23%** が失われます。
2. **`p` が高いときにバッチサイズを上げるのは間違ったレバーです。** N を大きくして効くのは `(1 − p)^N` が 1 の近くに留まる間だけです。p = 0.2 では、バッチ 10 で 3.6 マージしか出ません。直すべきは `p` を下げることであって、楽観をもっとキューに積むことではありません。

そしてエージェントによる量の増加は `p` を悪いほうへ押します — DORA の安定性の知見は、まさに `p` の上昇についての言明です。

## 4 つのレバー、レバレッジ順

チームはこれらを、ほぼ正確に有用な順序の逆から手に取ります。

**1. `p` を下げる(最高レバレッジ、最低コスト)。** 取り除いた失敗率の 1 ポイントごとに、バッチングの数式のなかで非線形に報われます。具体的には:PR を開く前にエージェントに高速スイートをローカルで実行させ、PR がキューに*入る前に*グリーンなプレマージチェックを必須にし、フレークを積極的に隔離する(後述)。これに計算コストはかかりません。

**2. 検証 1 回あたりの作業量を削る — テスト選択。** 定数ではなく指数を変える唯一のレバーがこれです。すべてを実行する代わりに、その変更が壊し得るものだけを実行します:

- **Develocity Predictive Test Selection** は、あなた自身の Build Scan 履歴とプロジェクト横断のパターンからモデルを構築し、有効化する*前に*節約幅と見逃し失敗率を測れる**シミュレータ**を同梱しています。買わないとしても盗む価値のある安全面の詳細が 2 つ:クラスパターンやアノテーションで**必ず実行するテスト**をピン留めできること、そして**最近フレーキーなテストは常に選択される**こと。フレーキーなテストは定義上、変更からは予測不能だからです。何かが永遠にスキップされないよう、マージ後または夜間の「残りのテスト」実行と組み合わせてください。
- **Bazel / Buck2** はこれを構造的に備えています:ビルドグラフは、変更されたファイルにどのターゲットが依存しているかを知っているので、影響を受けるターゲットに対する `bazel test` は、タダで手に入るターゲット判定です。
- **ビルドグラフがない?** Python には `pytest-testmon` があり、どのテストがどのコードをカバーしているかを記録して、影響を受けるものだけを再実行します。Jest は `--changedSince` を標準で備えています。

<PromptCard title="テスト選択、3 つのエコシステム">
{`# Bazel — test only what the diff can reach
bazel test $(bazel query "rdeps(//..., set($(git diff --name-only origin/main)))" --output=label 2>/dev/null)

# Python — coverage-based impact analysis
pip install pytest-testmon
pytest --testmon          # first run builds the DB, later runs select

# Jest — built in, no plugin
npx jest --changedSince=origin/main`}
</PromptCard>

**3. 積極的にキャッシュする — そして落とし穴を知る。** リモートキャッシュは、入力・コマンドライン・ホワイトリスト登録された環境のハッシュをキーにしてアクション結果を保存します。Bazel 自身のドキュメントがその罠を指摘しています:**ワークスペース外のツールは追跡されない**ため、コンパイラのバージョンが異なる 2 台のマシンが、本来なら異なる出力を生むはずの作業でキャッシュ*ヒット*を得ることがあります。重要なものは `--action_env` でホワイトリストに入れ、書き込み権限は CI だけに限ってください — 開発者のマシンは読み取り専用にすべきです:

<PromptCard title="リモートキャッシュ、書き込みは CI のみ">
{`# CI: read and write
bazel test //... --remote_cache=grpcs://cache.internal:443

# Developer machines: read only, never poison the shared cache
bazel test //... --remote_cache=grpcs://cache.internal:443 \\
  --remote_upload_local_results=false`}
</PromptCard>

**4. ランナーを増やす(最後)。** 線形コストで線形の効果、しかも `p` については何もしません。最初の 3 つの後、バースト時の同時実行数が実際に分かってから行ってください。

## AI 特有の失敗モード:エージェントが自分の答案を自分で採点する

ここまでの内容は、量の多いパイプラインならどれにも当てはまります。この項目はエージェントが書いたコードに特有で、たいていの CI 構成に空いている穴です。

同じエージェントが修正*と*その修正のためのテストを書くとき、「テストが通った」が運ぶ情報はあなたが思うよりずっと少なくなります。2 つの失敗の形が絶えず現れます:

- テストが要件ではなく実装の振る舞いをアサートしている — テスト対象のコードを読んで書かれたから通るのです。
- 既存のテストが失敗したとき、エージェントがコードを直す代わりに*テスト*を新しい振る舞いに合わせて編集する。差分はグリーンで、リグレッションは出荷されました。この振る舞いには名前と文献があります — モデルがなぜそうするのか、どの防御策に測定された効果量があるのかは[コーディングエージェントにおける報酬ハッキング](/docs/frontiers/reward-hacking-in-coding-agents)を参照してください。以下に続くのはパイプライン側の対策であって、モデル側のものではありません。

安上がりな構造的ゲート:**新しいテストは変更前のコードに対して失敗しなければならない。** これは TDD のレッド・グリーンの規律を機械的チェックに変えたものであり、ミューテーションテストが大規模に形式化しているものです。価値の大半を得るのにミューテーションテストのフレームワークは要りません — 必要なのは CI ジョブ 1 つです:

<PromptCard title="CI ゲート:新しいテストは変更なしで失敗しなければならない">
{`#!/usr/bin/env bash
# must-fail-first.sh — run in CI on PRs that add tests
set -euo pipefail

NEW_TESTS=$(git diff --name-only origin/main...HEAD -- 'tests/**' 'test/**')
[ -z "$NEW_TESTS" ] && { echo "no new tests, skipping"; exit 0; }

# Keep the new tests, revert everything else to the base commit
git stash push --keep-index -- $NEW_TESTS
git checkout origin/main -- src/
git stash pop

# The new tests MUST fail now. If they pass, they prove nothing.
if pytest $NEW_TESTS -q; then
  echo "FAIL: new tests pass against unmodified source — they do not test the change."
  exit 1
fi
echo "OK: new tests fail without the fix."`}
</PromptCard>

誠実な注意点が 2 つ。これはソースとテストが別のツリーにあるときにしか機能しませんし、間違った理由で失敗するテスト(インポートエラー、フィクスチャ欠落)はこのゲートを通過してしまいます。これは証明ではなく床です — それでも、エージェントが書いた PR がグリーンなのに無価値になる最も一般的な形を捕まえます。

補完となるレビュー側の対策は、作者のコンテキストを共有しないレビュアーです:[ハイブリッド AI コードレビュアー](/docs/models/open-code-review-hybrid-ai-reviewer)と [PR レビュー用の GitHub Action](/docs/walkthroughs/pr-review-action) を参照してください。

## エージェントと接触しても生き残るフレーク隔離

pass→fail 遷移の 84% がフレークである以上、「再実行しろ」は人間のデフォルトの反応であり、しかも利用可能な選択肢のなかで最も高くつきます — 何も教えてくれるはずのなかったテストのために、検証 1 回分を丸ごと燃やすのですから。

## 1 日ずつ食われる落とし穴

- **`merge_group` は自動ではありません。** GitHub のドキュメントは明示しています:ワークフローのトリガーに `merge_group` イベントを**必ず**追加しなければならず、さもないとキュー内でチェックが発火せず、必須チェックの欠落でマージが失敗します。これはマージキューの設定ミスとして最も一般的なものです。
- **24 時間のキューキャンセルは無言です。** キューが飽和すると、ジョブは失敗するのではなく消えます。赤いビルドだけでなく、キューの深さにアラートを設定してください。
- **マトリクスジョブはワークフロー実行あたり 256 が上限です。** 生成されたマトリクス(エージェントのスキャフォールディングでよくあるパターン)は、役に立つエラーも出さずにこれに当たります。
- **マシンをまたいだキャッシュヒットは誤りであり得ます。** 追跡されない外部ツールチェーンが偽ヒットを生みます。ツールチェーンをピン留めし、環境を `--action_env` でホワイトリスト化してください。
- **ワイルドカードパターンを使ったブランチ保護はマージキューと非互換です。** 保護ルールがワイルドカードを使っていると、キューは作動しません。
- **CI に触れるエージェントの PR は、スタイルの問題ではなくセキュリティ境界です。** ワークフローファイルを編集できる PR は CI のシークレットを流出させ得ます — [GitHub の課題から CI シークレットへ](/docs/security/github-issue-to-ci-secrets-blackhat-2026)と[自律実行のハードニング](/docs/security/hardening-autonomous-runs)を参照してください。

## 誠実な枠づけ

無制限のエージェント出力を吸収できるパイプラインにする設定など存在しません。上記のレバーが買ってくれるのは、コストが*プルリクエストの数*ではなく*変更の大きさ*とともに増えるシステムです — テスト選択とキャッシュは劣線形、ランナーは線形、そしてマージキューのバッチングは合格率が高い間だけ劣線形です。

これは本当の制約を、DORA の 2025年の枠づけが置いた場所に戻します:AI は、あなたが既に持っているデリバリーシステムを増幅します。小さなバッチ、速いスイート、低いフレーク率が既にあなたの実践だったなら、エージェントはあなたをはるかに速くします。そうでなかったなら、エージェントがそれを暴きます。
