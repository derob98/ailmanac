## 仕組み

Claude Code には**すべてのフラグにコード上のデフォルト値**が組み込まれており、そのうえで実際の値の取得を試みます。プロバイダーは GrowthBook です。専用の `DISABLE_GROWTHBOOK` 環境変数があり、変更履歴にも「GrowthBook のフィーチャーが null と評価されたときのクラッシュ修正」(v2.1.214)のようなエントリがあります。

このシステムの4つの性質を理解すれば、遭遇する奇妙なケースのほとんどを説明できます。

## 取得が行われなくなる4つのケース

ドキュメントはこの点を明記しています。Claude Code は次のセッションでフラグの取得をスキップします。

- **4つの環境変数のいずれかを設定している**:`DISABLE_GROWTHBOOK`、`DISABLE_TELEMETRY`、`DO_NOT_TRACK`、`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`。
- **サードパーティのプロバイダーを使っている**:Amazon Bedrock、Claude Platform on AWS、Google Cloud の Agent Platform、Microsoft Foundry。ただし、Claude Code を組み込むホストプラットフォームが `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST` を設定している場合を除きます。
- **Claude apps ゲートウェイのセッションである。**
- **新規インストールまたはアップグレード後の最初のセッションである**:フラグがまだ届いていません。詳細は後述します。

最初の2つの共通点に注目してください。どちらも**セキュリティ意識の高い企業**が選ぶ構成です。テレメトリを無効にして Bedrock 経由にする可能性が最も高い層が、黙って最も小さい機能セットを受け取ることになります。

<Callout type="warning" items={["テレメトリの無効化は、プライバシーの選択であるだけでなく、機能のスイッチでもあります。ドキュメントには、DISABLE_TELEMETRY は『DISABLE_GROWTHBOOK と同じ効果でフィーチャーフラグの取得も無効にする』と書かれています。", "機能を失わずにプライバシーを確保したい場合、両立する組み合わせはありません。ドキュメント化されたテレメトリの停止方法はどれも、フラグの取得も止めます。", "HOME が一時的な CI ランナーは、毎回が新規インストールと同じなので、毎回フラグなしのケースになります。"]} />

## 値の罠:3つの変数、3つの解析ルール

ここで多くの人が午後を丸ごと失います。これらの変数は同じファミリーに属し、同じことをするように読めますが、値は**3つの異なるルール**で解析されます。

| 変数 | 値の読み方 | したがって `=0` の意味 |
| --- | --- | --- |
| `DISABLE_TELEMETRY` | 空でない値ならオンになる | **それでもオプトアウトになる。**再び有効にするには unset する |
| `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` | 空でない値ならオンになる | **それでもトラフィックは無効のまま。**再び有効にするには unset する |
| `DISABLE_ERROR_REPORTING` | 空でない値ならオンになる | **それでもオプトアウトになる。**再び有効にするには unset する |
| `DISABLE_GROWTHBOOK` | 標準的な真偽値。`1` か `true` を設定する | 取得は**オンのまま** |
| `DO_NOT_TRACK` | 標準的な真偽値。`1` を設定する | テレメトリは**オンのまま** |

この表を2回読んでください。`DISABLE_TELEMETRY=0` はテレメトリを無効にします。`DO_NOT_TRACK=0` は無効にしません。どちらもドキュメントに記載された意図的な仕様で、しかも正反対です。

<Callout type="info" items={["ドキュメントはルールを直接述べています。一部の変数は『設定されているかどうかだけを読み、0 を含む空でない値はすべてその挙動をオンにする』。", "そうした変数を元に戻すには、変数を unset するか空の値に設定する必要があります。0 や false を代入してもオフスイッチにはなりません。", "これが最も効いてくるのは、誰かが 1 を 0 に変えて『オフにした』Dockerfile や CI 設定です。"]} />

## 実際に何を失うのか

フラグの取得をオフにすると、ドキュメントに記載された15の機能が使えなくなります。失うものごとにまとめると次のとおりです。

**権限と起動**
- Pro、Max、Team プランで、セッションがデフォルトで auto モードで始まらない
- VS Code 拡張機能が、開始時の権限モードのために設定ファイルを読めない
- `/auto-mode-setup` が `autoMode.environment` のエントリを下書きできない

**ローカルのセッションの外に及ぶすべてのもの**
- Remote Control
- 他のマシン上のセッションへのメッセージ送信(同一マシン内のメッセージ送信は引き続き動作)
- claude.ai アカウントで有効なスキルとプラグインをターミナルのセッションに同期すること
- アーティファクトへのコメントの読み取りまたは返信
- アドバイザーツール

**コマンドと診断**
- `claude import` と `/import` コマンド
- `/skill-doctor` と、`/plugin` の Stats タブにあるそのレポート

**黙って起きる挙動の変化(危険なグループ)**
- MCP:API が拒否するであろう入力スキーマを持つ MCP ツールを、Claude Code が除外しなくなります。スキーマはそのまま送信され、リクエストは、位置でツールを指す 400 で失敗します
- MCP:`MCP_PROTOCOL_NEGOTIATION=auto` を設定しない限り、claude.ai コネクタサーバーに対してプロトコルリビジョン 2026-07-28 のプローブが行われません
- 大きなペーストが、入力されたテキストではなくペーストされたテキストとして扱われなくなります。`[Pasted text #N]` というプレースホルダーの背後にある内容が、マークなしで Claude に届きます
- Git Bash がインストールされた Windows では、claude.ai と Console のアカウントにデフォルトで PowerShell ツールが提供されません。`CLAUDE_CODE_USE_POWERSHELL_TOOL=1` を設定してください
- Claude が下書きするフィードバックがオフになります

最後のグループこそ、肝に銘じておくべきものです。スラッシュコマンドがなければ、そのこと自体が分かります。しかし、**配列内の位置**でツールを指す 400 エラーは、テレメトリの設定のようには見えず、環境変数を確認しようと思いつくまでに、MCP サーバーを1時間デバッグすることになります。

### 影響範囲には前例がある

フラグやテレメトリの設定は、誰も予測しない場所に波及してきました。変更履歴から、修正済みですが示唆に富む例を2つ挙げます。

- **v2.1.108** では、`DISABLE_TELEMETRY` を設定した購読者が、プロンプトキャッシュの TTL が **1時間ではなく5分**にフォールバックする問題が修正されました。プライバシーのための変数が、長いセッションのたびに黙ってお金を余計に使わせていました。キャッシュ期間が12分の1になっていたわけです。
- **v2.1.105** では、*あるプロジェクトの*設定に `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` を設定すると、そのマシン上の**すべてのプロジェクト**で使用状況メトリクスが恒久的に無効になる問題が修正されました。

どちらも修正済みです。どちらもリスクの形を示しています。これらのスイッチは、無関係に見えるサブシステムを横断して効いてしまいます。

## インストールまたはアップグレード後の最初のセッション

これは独立した見出しに値します。典型的な「再現できない」バグ報告を生み出すからです。

Claude Code をインストールした直後の最初のセッションや、機能が追加されるバージョンへのアップグレード後の最初のセッションでは、フラグ制御の機能が**単に欠けている**ことがあり、通常は auto モードで始まるプランでも、セッションが Manual モードで始まることがあります。Claude Code はそのセッション中にフラグを取得するので、次回は両方とも揃います。

ここから2つの帰結が導かれます。

- **自然に直ります**。だからこそ報告しにくいのです。誰かが調べる頃には、2回目のセッションでフラグが揃っています。
- **一時的な環境では決して直りません。**CI ランナー、新しいコンテナ、使い捨てのホームディレクトリを使うあらゆる構成は、毎回が最初のセッションです。

ドキュメントは1つの緩和策にも触れています。新規インストール後、`claude -p`、Agent SDK、VS Code 拡張機能のような非対話型のセッションは、開始時の権限モードを選ぶ前にフラグを取得できる場合があります。

## 2分で診断する

推測する必要はありません。3つのチェックを、手軽なものから順に行います。

**1. そもそも設定が存在するかを確認する。**AGENTS.md サポートが利用できない場合、`/config` パネルに **Project instructions** の行がまったく表示されません。設定がないこと自体が診断です。機能がオフなのではなく、存在しないのです。

**2. 対話セッションが教えてくれることを見る。**動作しているとき、Claude Code は会話の中に `no CLAUDE.md found; AGENTS.md loaded: /home/you/repo/AGENTS.md` のような行を表示します。行がなければ、読み込まれていません。

**3. カナリアを走らせる。**元の報告を解決した手法です。ファイルの中に、他のどこにも現れない単語を入れ、クリーンな非対話型セッションでその単語を尋ねます。単語が返ってくれば、ファイルはモデルに届いています。これはどの指示ファイルでも、どのバージョンでも使えます。

## フラグに頼らず挙動を固定する

根本的な解決策は、ゲートに依存するのをやめることです。2つのパターンがあります。

**設定を明示的に固定する。**指示ファイルについては、**Project instructions** の値をデフォルトに任せず、組み込みプラグインの ID の下で設定ファイルに書けます。重要な制限が1つあります。Claude Code は、プロジェクト設定ファイルとローカル設定ファイルでは**このキーを無視し**、`~/.claude/settings.json`、`--settings` ファイル、または管理設定からしか読みません。リポジトリの `.claude/settings.json` に書いても何も起きません。

<PromptCard title="CLAUDE.md と AGENTS.md を一緒に読み込む:ユーザー設定または管理設定のみ">{`{
  "pluginConfigs": {
    "agents-md@builtin": {
      "options": { "instructionFiles": "claude-md-and-agents-md" }
    }
  }
}`}</PromptCard>

**ゲートされたことのない経路を使う。**`AGENTS.md` をインポートする `CLAUDE.md` は、すべてのバージョン、すべてのプロバイダー、テレメトリがオフの状態でも動作してきました。フラグ付きのコードパスではなく、通常の `@path` インポート展開だからです。これは、Bedrock、Vertex、Foundry のセッションに対してドキュメント自身が推奨している方法です。

<PromptCard title="フラグを一度も必要としなかった、1行の CLAUDE.md">{`@AGENTS.md`}</PromptCard>

この方法を採る場合の微妙な点が1つあります。*設定*を通じて読み込まれた `AGENTS.md` は、*インポート*で取り込まれたものとは少し挙動が異なります。`InstructionsLoaded` フックは、設定経由のパスでは**発火しません**が、`CLAUDE.md` がインポートまたはシンボリックリンクしている `AGENTS.md` では通常どおり発火します。指示の読み込みにフックを設定している場合は、インポートのほうが安全な経路です。
