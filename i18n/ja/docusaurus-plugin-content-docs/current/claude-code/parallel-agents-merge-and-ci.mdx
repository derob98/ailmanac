2026年9月21〜22日、2つの記事が1日違いでHacker Newsのトップページに載った。1つはLinearのエンジニアリング記事で、タイトルは*「AI coding has made CI a bottleneck, so we reworked ours to keep up」*。もう1つは**Foremerge**のShow HNで、売り文句は「コードの競合の前に、意図の競合を捕まえる」だ。

両者は同じことを反対側の端から描いている。エージェントによって、diffを作ることはほぼ無料になった。diffより下流のすべて、つまりそれが正しいと証明すること、そして他のエージェントがいままさに書いている4つの他のdiffと両立すると証明することは、相変わらず従来どおりのコストがかかる。だから行列ができるのはそこだ。

AILmanacはこの問題の人間側の半分をすでに[検証のボトルネック](/docs/frontiers/the-verification-bottleneck)で、ファイル単位の分離を[Gitワークツリー](/docs/claude-code/worktrees)で扱っている。このページはその間にある仕組みを扱う。複数のエージェントが1つのリポジトリで同時に作業すると何が壊れるのか、そして実際に何をすべきか。

## Part 1 — Gitはdiffを比較する。計画は比較できない。

ワークツリーは、各セッションに専用のディレクトリと専用のブランチを与える。それが解決するのはちょうど1つの問題、つまり2つのプロセスが同時に同じファイルに書き込むことだ。より高くつく失敗、すなわち同時には成り立たない2つの*計画*には何の役にも立たない。

Foremergeの作者が挙げる典型例はこうだ。あるセッションが`PaymentService`をStripe専用の実装に置き換え、別のセッションが元の抽象化の上にPayPalのサポートを追加した。Gitは両方のブランチをきれいにマージした。ところが2つ目の変更は、1つ目が削除した拡張ポイントに依存することになった。

マージの仕組みのなかに、これを捕まえられるものはなかった。マージの仕組みは、どちらのエージェントが*何をしようとしていたのか*を知らないからだ。

| 失敗モード | 見え方 | 分離が役に立たない理由 |
| --- | --- | --- |
| **破壊的 vs 追加的** | エージェントAが、エージェントBが拡張しているものを置き換えるか削除する | 両方のdiffは異なる行、場合によっては異なるファイルに触れている。マージはきれいだが、設計は壊れている |
| **重複作業** | 2つのエージェントが同じ問題を別の角度から解く | どちらのブランチも競合しない。二重に支払い、さらにそれを調整するために再び支払う |
| **契約のドリフト** | 1つのエージェントがAPI、スキーマ、設定を変更し、別のエージェントが古い形に対してコードを書く | コンパイルは通る。出荷もされる。実行時に失敗する |

作者は、2つのジョブが「同じマッチングスキーマを反対側から並べ替え始めた」本番での事例を報告しており、データ損失が表面化したのは3日後の本番だったという。これがこのバグクラスの形だ。マージ時には静かで、後になって高くつく。

<Callout type="key" items={["ワークツリーはファイルを分離する。マージキューは統合を直列化する。どちらのレイヤーにも意図の表現がないため、2つの計画の間にだけ存在する競合を検出できない。"]} />

## Part 2 — 調整レイヤーは実際に何をするのか

**[Foremerge](https://github.com/naw103/foremerge)**は、検討する価値のある具体例だ。採用すべきだからではなく、その設計判断が、チームがこの問題を社内で解こうとすれば必ず突き当たるものだからである。Apache-2.0、Rust製、リポジトリは2026年8月21日に開設、9月18日時点でv0.4.3、9月22日時点で491スター。

考え方はこうだ。エージェントは、**何かをする前に、これから何をするかを**機械が比較できる形で**宣言する**。同時には成り立たない2つの計画は、マージの場ではなく、問い合わせ可能なストアの中で衝突する。

### ファイルパスではなくセマンティックスコープ

スコープは小さな構造化オブジェクトで、パスではなく、種別、キー、操作から成る:

```json
{ "kind": "symbol", "key": "PaymentService", "operation": "replace" }
```

認識される種別:`symbol`、`api`、`schema`、`config`、`infra`、`test`、`migration`、`env`、`file`、`component`、`contract`、`domain`。種別とキーはどちらも、正規化された比較のために小文字化される。

肝心な区別は操作にあり、これは自分でこれを設計しようとしたとき、ほとんどの人が間違える部分だ:

- **保存的** — `add`、`extend`、`modify`。このものに依存する他のものは動き続ける。
- **非保存的** — `replace`、`remove`、`rename`、`migrate`。動き続けない。

この二値分類だけが、「2つのエージェントが`PaymentService`に触れた」(役に立たず、しょっちゅう起こる)を、「一方のエージェントが、もう一方が土台にしている拡張ポイントを削除しようとしている」(対処可能)に変える。

### 5つのルール、挙動のまま

| ルール | 発火条件 | 重大度 |
| --- | --- | --- |
| **FM-C001** 破壊的 vs 追加的 | 重なるスコープで、一方が非保存的、もう一方が保存的 | 両方の操作が明示的に宣言されていればHIGH、推論されたものならMEDIUM |
| **FM-C002** 分岐する書き換え | 同じスコープで両方が非保存的 | HIGH(確定)/ MEDIUM(提示)— まずどの設計を目標にするか選ぶようエージェントに求める |
| **FM-C003** 共有契約 | 重なるスコープで両方が保存的 | MEDIUM、確定されることはない — 調整メモであり、変更は十分に両立しうる |
| **FM-C004** 重複作業 | 要約の類似度(トークン化、CamelCase分割、ストップワード除去)でJaccard ≥ 0.62、または操作が一致しスコープが重なり0.42超 | MEDIUM、確定されることはない |
| **FM-C005** 重複するクレーム | 同じ正規化スコープに既にアクティブなクレームがある | MEDIUMのソフトな警告 — 新しいクレームは作成される |

そこには、このツールを一度もインストールしなくても盗む価値のある細部が2つある。第一に、**正規化されたスコープが完全に一致した場合のみ、所見を確定(assert)できる**。推論されたもの、ゆるい一致のものはMEDIUMに格下げされ、提示(surface)されるだけだ。第二に、HIGHの所見を上書きするには空でない文章による正当化が必要になる。抜け道はあるが、記録が残る。

### 状態の置き場所 — 優雅な部分

状態は、WALモードのSQLiteファイル1つで、`.git/foremerge/state.sqlite3`にある。サーバーなし、デーモンなし、インフラなし。そして、リポジトリのすべてのワークツリーはすでに共通のGitディレクトリを共有しているので、**ワークツリー間で共有される調整状態は無料で手に入る**。分離を可能にしたものが、そのまま調整も可能にする。

### 誰にも工学的に解消できないコンプライアンス問題

このプロトコルは、エージェントが実際に意図を公開してはじめて機能する。MCPが介在していれば、意図の宣言はエージェントのループにおける単なるもう1つのツール呼び出しにすぎず、他の[MCPサーバー](/docs/claude-code/mcp)と同じ仕組みであるため、遵守率は高いと作者は主張する。Foremergeは、`publish_intent`、`publish_changeset`、`run_verification`を含む18のライフサイクルツールをこの方法で公開し、セットアップ時にネイティブスキルをインストールする。

MCPがなければ、遵守はシステムプロンプトでモデルを説得できる範囲に依存する。つまり、フリートが忙しくなったまさにその瞬間に当てにならない。

<Callout type="warning" items={["公開されたベンチマークはまだなく、検証コマンドはサンドボックス化されておらず、プロジェクトは1.0前で、執筆時点で生後3週間だ。プロトコルを教訓として、バイナリは実験として扱うこと。","調整レイヤーは、すべてのエージェントのループに1ステップを追加する。フリートが2セッションなら、そのオーバーヘッドは見合わない。ワークツリーと短命ブランチの方針のほうが依然として優れている。"]} />

## Part 3 — CIの壁、数字とともに

では反対側の端へ。Linearのエンジニアリングチームは、エージェントが生産的になったときに何が起こるかの算術を公開した。テストスイートは**年初から4倍近くになり**、**週に約2,000件のテスト**のペースで増えている。

彼らの正直な見出しはこうだ。以下のすべての取り組みを経て、プルリクエストの待ち時間の中央値は**6分超から5分強**になった。最適化がなければ、同じスイートは今ごろ開発者を**およそ11分**待たせていただろう。この捉え方こそが本当の教訓であり、労力の大半は、倍に膨らむスイートに対して現状維持を買うために使われたのだ。

### クリティカルパスは短いジョブである

直感は、長いテストシャードを最適化せよと言う。計測は逆を示す。すべての実行は、PRがどのパスに触れたか、そして同じ入力に対してそれらのテストがすでに通っているかをチェックするゲートジョブから始まる。8つのAPIテストシャードは、これらが終わるまで1つも開始できない。つまり、小さなジョブで数秒を失えば、下流のすべてのジョブが同じ数秒を失う。

| ゲート作業 | 前 | 後 |
| --- | --- | --- |
| 変更検出、最も遅い実行 | 138 s | 37 s |
| 変更検出、中央値 | 26 s | 8 s |
| 最も遅いゲートでのチェックアウト | 94 s | 20 s |
| チェックアウトが一切ないゲートジョブ | 27 s | 7 s |
| APIプルリクエストあたりのマージパス短縮 | — | 42 s |

具体的な工夫が2つある。変更検出には、**履歴を限定したスパースでblobなしのチェックアウト**で十分だった(さらに約11秒短縮)。そして`actions/checkout`は、バックオフ付きでリトライし、`GIT_HTTP_LOW_SPEED_LIMIT` / `GIT_HTTP_LOW_SPEED_TIME`を設定するコンポジットアクションに置き換えられ、停止した接続が実行をハングさせずに約30秒で中断されるようになった。

次に、盤上で最も安い勝ち筋:**7つの独立したチェック**が、それぞれ数秒の実作業のためにランナーを起動し、リポジトリをチェックアウトし、依存関係をインストールしていた。これらをバッチ化することで、**月あたり約8万7,000ランナー分、CI総使用量の11.8%**を節約した。

<Callout type="key" items={["最も遅いジョブを最適化すると、テールが短くなる。ゲートジョブを最適化すると、全員の待ち時間が短くなる。テストスイートに手を付ける前に、クリティカルパスを計測すること。"]} />

### セットアップのオーバーヘッドが、どこまでシャードできるかを決める

シャード数を倍にしても実時間は半分にならない。各シャードがセットアップを再び支払うからだ。Linearが4シャードから8シャードに移行できたのは、シャードごとのセットアップが安くなってからだった:

| セットアップ項目 | 前 | 後 |
| --- | --- | --- |
| シャードごとのセットアップ | 110–140 s | 67–73 s(−44%) |
| `pnpm install` | 44–73 s | 16–18 s |
| データベースセットアップ(スナップショット) | コンテナあたり12 s | コンテナあたり1–2 s |

成果:4シャードではセットアップが合計**8.3分**を消費していた。削減後は、合計セットアップ**7.5分**で**8シャード**を動かせた。より少ない総オーバーヘッドで、より多くの並列性が得られた。クリティカルなジョブは、およそ**19%高速化し19%安くなり**、最も遅いシャードは**5.25分から4.33分**に、APIシャードの合計ランナー時間は実行あたり**32.8分から22分**になった。

### ルールを書き換える前にツールを替える

最大の個別の成果は、気の利いたものではなかった。遅い実装を、同じ仕事をする速いものに置き換えたのだ。

| 変更 | 測定された効果 |
| --- | --- |
| GitHubホストのランナー → サードパーティのランナー | ジョブは平均**34%高速化**。`tsc`ワークロードは**−52%** |
| `tsc` → `tsgo` | TypeScriptチェックの週次中央値が**−73%** |
| 型を考慮するカスタムlintルール → ASTのみの静的解析 | APIのlintが**−68%**、リポジトリ全体のlintが**−55%**(Oxlintによるさらなる削減を除く) |
| `isolate: false`のVitestオプトインプロジェクト | シャード時間が**300–379 sから約195 s**、月間CI費用の約**17%**に相当 |

最後のものは、ただでもらえるものではなく、本物のトレードオフだ。分離をオフにすると、安全なテストファイルが各ワーカー内でモジュールレジストリを共有できる。プロジェクトごとのオプトインなのは、まさにモジュール状態を書き換えるテストが、隣のテストを汚染するようになるからだ。テストは速くなるが、保証は弱くなる。意図して決めること。

### スレッドからの反論

Hacker Newsの議論は前提をそのまま通さなかった。その異論は携えておく価値がある:*エージェントが週に2,000件のテストを追加しているからといって、2,000件分のシグナルが増えているとは限らない。*複数のコメント投稿者が、エージェントが価値の低いテストを非効率な方法で大量に書くと述べており、それはCIコストを永遠に膨らませ、将来の変更を難しくする。そうしたテストはすべて、後のリファクタリングが満たすか削除しなければならないものだ。

CIを19%高速化するために四半期を費やす前に、スイートの一部がそもそも存在すべきかを問う価値がある。本当の理由で失敗することのないテストは、純粋な保有コストである。
