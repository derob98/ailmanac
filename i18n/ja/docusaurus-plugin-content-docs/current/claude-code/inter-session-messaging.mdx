## 問題: あなたが橋渡し役である

**ターミナルA**で`libfoo/`のClaude Codeを開き、**ターミナルB**で`app-that-uses-libfoo/`を開きます。ターミナルBがライブラリから型エラーを受け取ります。今日、あなた — 人間 — がルーティングを行います: エラーを読み、ターミナルを切り替え、Aに貼り付け、修正を待ち、切り替えて戻り、ビルドを再実行します。各コンテキストスイッチは両側で状態を失います。

これはまさに、クローズされたAnthropic RFE [claude-code#36181](https://github.com/anthropics/claude-code/issues/36181)（2026年3月にオープン）の痛点です: *「複数のターミナルにまたがる相互依存プロジェクトで作業する場合、ユーザーは現在、セッション間で手動でコンテキストを切り替える必要があります。」* このissueはクローズされていますが — Claude Codeにはまだネイティブのセッション間チャネルはありません。そのため、コミュニティが独自のものを構築しました。

## 3つのパターン

3つの独立したオープンソースプロジェクトが、2026年初頭に同じ問題に収束し、それぞれ異なるトランスポートを選択しました。トレードオフはトランスポートの選択に組み込まれており、特定のプロジェクトに組み込まれているわけではないため、これらは重要です。

| パターン | トランスポート | 提供形式 | レイテンシ | マルチマシン | デバッグ性 |
| --- | --- | --- | --- | --- | --- |
| **ファイルベースの受信箱** | `~/.claude/session-bridge/sessions/<id>/{inbox,outbox}/`配下のJSONファイル | 9つのbashスクリプト + `jq` | 約5〜10秒（3秒ポーリング） | ❌ 単一マシン | ✅ `cat message.json` |
| **ローカルWebSocketバス** | localhost WebSocket、セッションデーモン | Claude Codeプラグイン | ミリ秒レベル | ❌ 単一マシン | ⚠️ バスダンプが必要 |
| **MCPチャネル** | Slack風チャネル + セマンティック検索を備えたMCPサーバー | `npx claude-slack` | ネットワークホップ | ✅ ネットワーク経由で動作 | ✅ MCPをクエリ |

すでにデバッグしている方法と、実際にエージェントを実行しているマシン数に一致するトランスポートを選択してください。

### 1. ファイルベースの受信箱 — [`PatilShreyas/claude-code-session-bridge`](https://github.com/PatilShreyas/claude-code-session-bridge)（MIT、65★）

各セッションにはディレクトリがあります: `~/.claude/session-bridge/sessions/<6文字ID>/`。メッセージは`status`フィールドを持つJSONファイルで、原子的に`pending → read`に反転します。受信者は3秒ごとに受信箱をポーリングします。作者自身がWebSocketとMCPをスキップした理由: *「デバッグ可能だから。文字通り`cat`メッセージができる。」*

<PromptCard title="セッションAがリスナーになり、セッションBが質問する">{`# In session A (the library repo)
/bridge listen
# → prints A's 6-char session id, e.g. a1b2c3

# In session B (the app that consumes the library)
/bridge connect a1b2c3
/bridge ask "Which version of libfoo exports the parseDate() helper, and did its signature change?"`}</PromptCard>

セッションAは*ライブコンテキストから*答えます — 読み込まれたファイル、最近のツール結果、そのプランモードから。セッションBは、信頼できる人間に類する入力として扱うメッセージとして返信を受け取ります。その最後の文がこのパターンにおけるセキュリティの全体像です。読み続けてください。

### 2. ローカルWebSocketバス — [`yilunzhang/claude-code-inter-session`](https://github.com/yilunzhang/claude-code-inter-session)（MIT、27★）

ローカルデーモンがループバックインターフェイスでWebSocketをバインドします。接続された各セッションは名前を登録し、`send`、`broadcast`（ペイロード上限256 KB）、または`list`ピアが可能です。配信にはClaude CodeのMonitorツールを使用するため、アイドルセッションはトークンを消費せず、ポーリングループも実行されません。Claude Code **≥ 2.1.105**とPython **≥ 3.10**が必要です。

プラグインマーケットプレイスとしてインストールし、そのスラッシュコマンドを使用します:

<PromptCard title="セッション間プラグインをインストールして2つのターミナルを接続する">{`# In any Claude Code session (run once per machine)
/plugin marketplace add https://github.com/yilunzhang/claude-code-inter-session
/plugin install inter-session

# Terminal A
/inter-session:inter-session connect libfoo

# Terminal B
/inter-session:inter-session connect app
/inter-session:inter-session send libfoo "Does parseDate() still accept a string?"

# Broadcast to everyone
/inter-session:inter-session broadcast "About to bump libfoo to 2.0 — hold merges."`}</PromptCard>

### 3. MCPチャネル — [`theo-nash/claude-slack`](https://github.com/theo-nash/claude-slack)（MIT、8★）

Slack風の抽象化を公開する完全なMCPサーバー: `#general`、プロジェクトごとのチャネル、DM、およびQdrantを基盤とするセマンティック検索の知識層。メッセージは再起動をまたいで永続化されます — 他の2つはそうではありません。トレードオフ: ネットワークサービスとその依存関係を実行するようになり、メッセージは各ターンでツール呼び出しの往復を経由しなければなりません。

<PromptCard title="MCPサーバーを起動し、エージェントのターンから使用する">{`# Start once (in its own terminal)
npx claude-slack

# In any Claude Code session, once claude-slack is added to your MCP config:
Post to #libfoo-consumers that parseDate() moved from utils to date-helpers in v2.0.
Then search the channel for prior questions about parseDate to make sure I answered them.`}</PromptCard>

**永続性**が必要な場合（明日開始したセッションが昨日のセッションが言ったことを検索できる）や、ピアが異なるマシン上に存在する場合はMCPチャネルを使用してください — 他の2つは単一マシンのみです。

## 絶対に省略してはいけない信頼境界

これは誰も明確に語っていない部分です。上記のすべてのパターンで、メッセージは受信セッションに**デフォルトでエージェントが指示として扱うテキスト**として届きます。つまり、別のセッション — またはあなたのマシン上で受信箱/ソケット/MCPに書き込めるあらゆるもの — があなたのエージェントにプロンプトを注入できるということです。

<Callout type="warning" items={["ピアメッセージは信頼できない入力であり、ユーザーのターンではありません。自分のマシン上でも、送信者は別の自律エージェントであり、それ自体が読んだファイルによってプロンプト注入されている可能性があります。","広く開かれたツールセットでセッション間メッセージングを実行しないでください。破壊的なシェル、任意のWebフェッチ、シークレットパスをブロックするClaude Codeの権限プロファイルと組み合わせてください。","WebSocketとファイルベースのパターンには、デフォルトで送信者の認証がありません。ループバックソケットにバインドできる、または~/.claude/session-bridge/に書き込めるローカルプロセスは、ピアを装うことができます。","ブロードキャストを爆発半径として扱ってください。接続された5つのセッションへの毒された1つのメッセージは、5つの侵害されたエージェントであり、1つではありません。","疑問がある場合は、仲介してください: 受信セッションに、行動する前に受信メッセージを承認のためにあなたに要約させてください — 軽量なフックやプラグインのフロントマターにおけるプロンプトガードレールが仕事をします。"]} />

これが当てはまる一般的な脅威モデルについては、[プロンプトインジェクション](/docs/security/prompt-injection)と[エージェントのセキュリティ確保](/docs/security/securing-agents)を参照してください。MCP固有のバスリスクについては、[不可視コメントMCP攻撃](/docs/security/invisible-comment-mcp-attacks)が直接関連しています — 「メッセージが隠された指示とともに届く」バグの同じクラスが、ツール結果と同じようにSlack風チャネルにも当てはまります。

## サブエージェントに勝る場合 — と勝らない場合

ピアセッションとサブエージェントは*異なる*問題を解決します。[サブエージェント](/docs/claude-code/subagents)は、メインコンテキストを保護するかタスクを専門化するために生成する、スコープされたツールセットを持つ新鮮なClaudeです; 空で始まり、結果を返します。ピアセッションは、独自のファイルが読み込まれ、プランモードがアクティブで、状態の会話全体を持つ*長時間実行される、人間主導の*Claude Codeインスタンスです — あなたはそのコンテキストを借りているのであって、新しいものを作成しているのではありません。

価値が**他のセッションのライブ状態**にある場合は、セッション間メッセージングを検討してください: それがすでに推論しているライブラリ、実行したばかりの失敗したテスト、ステージしたばかりのコミット。価値が**分離して1つの制限されたタスクを実行すること**にある場合は、サブエージェントを検討してください。ピアのコンテキストに依存しないワンショットの質問を発火するためにセッション間メッセージングを使用している自分に気付いた場合、おそらくサブエージェント — または共有ワークツリー — が必要です。

両方のパターンを超える長期間の複数エージェントワークフローについては、[長時間実行エージェントハーネス](/docs/frontiers/long-running-agent-harnesses)と[ネイティブマルチエージェントAPI](/docs/models/native-multi-agent-apis)を参照してください。
