## ソフトキャップとハードキャップ:唯一重要な区別

宣伝文句を取り除くと、あらゆる支出管理は 2 つのうちのどちらかです。

**ソフトキャップ** は観察します。コストのシグナルを監視し、あなたの設定値と比較して、通知します。メール、Webhook、ダッシュボードのバッジなどです。トラフィックは流れ続けます。AWS Budgets、Anthropic の利用状況ダッシュボード、これまでに設定したあらゆる「課金アラート」はソフトキャップです。確かに役に立ちますが、保護ではありません。ソフトキャップの唯一の効果は人間に介入を促すことであり、そのレイテンシはシステムのものではなく *あなたの* 対応時間です。

**ハードキャップ** は強制します。上限に達した時点で新しいリクエストをブロックします。コードがそれを知るのは、受信トレイではなくエラーを通じてです。

実用的なテスト:*チームの全員が寝ているとき、支出は止まるか?* 答えが「いいえ」なら、UI がどう呼んでいようと、それはソフトキャップです。

以下はすべてハードキャップについてです。ソフトキャップも残しておいてください。作動した上限はインシデントであり、100% でのブロックだけでなく 60% での警告も欲しいはずです。

## 罠:1 つの出来事に 4 つのステータスコード

ここは 4 か所に別々に文書化されていながら、どこにもまとまっていない部分で、最も噛みつきやすい点です。

Anthropic の挙動は注意深く読んでください。実際には 2 つの異なる挙動だからです。

**ティア** の月次上限を超えると、API は HTTP 429 を、エラータイプ `rate_limit_error` で返します。通常のレート制限と同じタイプですが、**`retry-after` ヘッダはありません**。Anthropic 自身のドキュメントは、その帰結をはっきり述べています。*「Retrying, including the SDK's automatic retries, fails until access resumes.」* アクセスは、上限を引き上げない限り、翌月 1 日の 00:00 UTC に再開します。つまり、指数バックオフを備えたお行儀の良いクライアントが、一時的に見えるエラーをログに出し続けながら、最大 31 日間リトライのループに居座ることになります。見分けるためのフィールドは `error.details.error_code` で、値は `enforced_spend_limit_reached` です。

**あなた自身が** 設定した上限(組織またはワークスペース)を超えると、API は HTTP **400** を、タイプ `invalid_request_error` で返します。これは通常の想定を逆転させます。400 は「リクエストが不正なのでリトライするな」を意味するため、ほとんどのクライアントはこれをバグとしてログに記録し、クラッシュするか、黙って作業を捨ててしまいます。これはバグではありません。あなた自身の上限が、仕事をしているだけです。

さらに Claude Code のワークスペースは、また別にチェックされます。そのワークスペースの上限を超えたリクエストには、`retry-after` を *含む* 429 が返ることがあります。

OpenRouter は 3 つ目の道を取ります。プリペイドクレジットのモデルなので、残高切れは支払いの問題であり、HTTP **402 Payment Required** を返し、`error.metadata.limit_source` が、アカウント残高、キー単位の上限、実行中の予算ホールドの 3 つのうちどれに達したかを示します。知っておく価値のある細部として、アカウント残高がマイナスになると、**無料** モデルへのリクエストも失敗します。

OpenAI のドキュメントは、ハード支出上限の影響を受けたリクエストは `429` を返すと述べています。強制の遅延については述べておらず、混同しやすい 2 つを区別しています。OpenAI があなたの組織に設定する承認済みの月次利用上限と、組織またはプロジェクトにあなた自身が設定する支出上限です。両方が 1 つのリクエストに適用されうるため、余裕のあるプロジェクトでも、その上にある組織の天井によってブロックされることがあります。

1 つの出来事に 4 つの形。つまり、欲しいハンドラは「429 ならリトライ」ではありません。

<PromptCard title="Classify a cap error instead of retrying it">
{`# The three signals that mean "stop, this is a budget wall" — not "wait and retry"
#
#   Anthropic tier cap   -> 429, type=rate_limit_error, NO retry-after,
#                           error.details.error_code == "enforced_spend_limit_reached"
#   Anthropic own limit  -> 400, type=invalid_request_error,
#                           message startswith "You have reached your specified API usage limits"
#   OpenRouter           -> 402, error.metadata.limit_source present
#   OpenAI hard limit    -> 429  (no documented discriminator field)

def is_budget_wall(status, body, headers):
    err = (body or {}).get("error", {}) or {}
    detail_code = (err.get("details") or {}).get("error_code")

    if status == 429 and detail_code == "enforced_spend_limit_reached":
        return True                      # month-long wall; do NOT back off
    if status == 429 and "retry-after" not in {k.lower() for k in headers}:
        return True                      # 429 with no retry-after is not a rate limit
    if status == 400 and err.get("message", "").startswith(
        "You have reached your specified API usage limits"
    ):
        return True                      # your own cap, wearing a 400
    if status == 402 and (err.get("metadata") or {}).get("limit_source"):
        return True                      # prepaid balance or key cap

    return False

# Page a human, mark the work as blocked, and stop the loop.
# Retrying a budget wall just burns your own CPU until the first of the month.`}
</PromptCard>

どのプロバイダがリファクタリングしても生き残る一般則は、**`retry-after` ヘッダのない 429 はレート制限ではない** ということです。レート制限は構造上一時的なもので、どれだけ待つべきかを教えてくれます。待ち時間を教えることを拒む 429 は、別の生き物です。

## なぜ上限は正確になりえないのか、そしてそれは怠慢ではない

市場のあらゆるハードキャップは、請求済みのコストではなく *推定* コストで作動します。近道のように見えますが、実際には唯一成り立つ設計です。使用量を集計し、料金を適用し、割引を反映し、突き合わせる課金パイプラインには、数分から数時間かかります。それを待つ上限は、まさに止めるべき障害モードに対して役に立ちません。

Google Cloud はそのトレードオフを率直に述べています。*「For faster enforcement, spend caps use gross, estimated costs to trigger alerts and enforce the spend cap」*。そして正直に、*「Due to latency in usage and cost reporting, spend cap enforcement isn't instantaneous. Consider setting your budget slightly below your absolute limit.」* と続けます。さらに責任については、*「any cost overages are billed as normal」* です。レポートの遅延の間にすり抜けた分については、引き続きあなたに責任があります。

設計時に織り込むべき帰結が 3 つあります。

**上限は、本当の天井より低く設定する。** 本当に痛い金額が 500 ドルなら、400 ドルで上限を設定します。その差が超過分の予算です。どれだけ必要かは、プロバイダではなくピーク時の消費速度で決まります。毎分 50 ドル使えるエージェント群は、1 日 50 ドルを使うチャットアプリより広いマージンが必要です。

**実行中のリクエストは完了する。** 上限がブロックするのは *新しい* 利用です。すでに実行中のものは終了まで走り、課金されます。長時間動くエージェントのターンでは、これは丸め誤差ではありません。

**事後より、プリフライト。** 超過を構造的に避けられる唯一の仕組みは、呼び出しの *前に* 推定コストを確保しておくことです。LiteLLM のプロキシはこれをデフォルトで行います。リクエストボディとモデルの料金から最大コストを推定し、該当するすべての予算に対してその額を確保し、確保によって予算を超過するならリクエストを拒否し、レスポンスが返ったら確保分を実際のコストに置き換えます。OpenRouter の実行中の予算ホールドは、同じ考え方をプリペイド残高に適用したものです。どちらも事後に測定するよりはるかに強力ですが、逆方向には近似にすぎません。多めに確保するため、本来は払えたはずのリクエストを拒否することがありえます。

## Anthropic のティアと、ネットが消える場所

Anthropic は、求めなくてもハードキャップを提供します。Start、Build、Scale の各ティアには月次の支出上限があり、これは組織が暦月に API に使える最大額です。

| 利用ティア | 月次支出上限 |
| --- | --- |
| Start | $500 |
| Build | $1,000 |
| Scale | $200,000 |
| Custom | **なし** — アカウントチームと取り決める |

<VerifyNote lastVerified="2026-10-05" source="platform.claude.com/docs/en/api/rate-limits — Spend limits" />

最後の行をもう一度読んでください。デフォルトのセーフティネットは、最も多く支出する組織が属するティア *以外の* すべてのティアに存在します。Custom に移行すると自動の天井が失われるため、人々が気にしなくなるまさにその時点で、明示的に設定した上限が任意ではなく必須になります。

設定画面にいる間に、さらに 2 つ設定しておく価値があります。

**ティア上限より低い、自分用の上限を設定する。** Billing ページでは、ティアの上限より小さい数字を指定できます。自分で選べるので、実際に欲しいのはこの制御です。ただし、429 ではなく 400 として現れることを忘れないでください。

**ワークスペースを被害範囲の境界として使う。** ワークスペースにはそれぞれ独自の支出上限とレート制限を設定できるので、実験的なエージェントと本番トラフィックが同じプールを共有しません。組織全体の上限は、ワークスペースの上限の合計がそれを上回っていても、常にその上に適用されます。1 つ制約があります。デフォルトのワークスペースには上限を設定できないため、大事なものはそこに置かないでください。

## Enterprise 層:API としてのメンバー単位の上限

Claude Enterprise の組織には、Console が公開していないものが提供されます。**Spend Limits API** で、個人ごとの予算を、プログラムから読み書きできるリソースとして扱います。この話の中で、ほとんどどこにも書かれていない部分なので、何をするものかを知っておく価値があります。

2 つのリソースにまたがる 8 つのエンドポイントがあります。1 つ目は、「各メンバーにどの上限が適用され、それはどこから来ていて、どれだけ近づいているか」に答えます。

<PromptCard title="Read every member's effective cap and month-to-date spend">
{`curl "https://api.anthropic.com/v1/organizations/spend_limits/effective?limit=20" \\
  --header "x-api-key: $ANTHROPIC_ADMIN_KEY" \\
  --header "anthropic-version: 2023-06-01"

# Each row carries:
#   amount                -> the effective cap, in MINOR UNITS ("50000" = $500.00)
#                            null = unlimited;  "0" = included plan usage only
#   source.type           -> user | seat_tier | rbac_group | organization
#   period_to_date_spend  -> spend since the period started, same minor-unit format
#   spend_limit_id        -> the configured row this resolved from
#
# Requires an Admin API key with the read:spend_limits scope.`}
</PromptCard>

見落とすと午後が丸ごと潰れる細部が 4 つあります。

- **金額は、請求通貨の最小単位による 10 進文字列です。** `"50000"` は $500.00 です。10 進数としてパースし、100 で割ってください。ドキュメントは、大きな値に対する 2 進浮動小数点の使用を明示的に警告しています。
- **`null` と `"0"` は同じではありません。** メンバーの有効行(effective row)では、`null` は *無制限*、`"0"` はプランに含まれる利用分を超えて Claude を使えないことを意味します。`"0"` はすでに上限に達しているものとして扱ってください。
- **`period_to_date_spend` は、単に値が取得できないだけのときも `"0"` と表示されることがあります。** ドキュメントはこれを取引用ではなく参考情報と呼んでいるため、ゼロの値を「支出なし」として扱うゲートを作ってはいけません。
- **グループの上限は、メンバーごとのデフォルトであり、共有の予算プールではありません。** それを継承する各メンバーは、自分自身の支出に対してゲートされます。

2 つ目のリソースはレビューキューです。メンバーが claude.ai で「Request more usage」をクリックすると、支出上限の引き上げリクエストが作成されます。保留中のものを一覧でき、各リクエストにはそのメンバーの現在の上限と期間内累計支出を示す最新の `spend_summary` が付いているので、ポリシーエンジンが追加の検索なしに判断できます。承認すると、同じ呼び出しで新しいユーザー単位の上限が書き込まれます。知っておくべき非対称性が 2 つあります。`POST /spend_limits` で上限を直接設定しても、保留中のリクエストは解決 **されません**(承認用のエンドポイントを使います)。また、8 つのエンドポイントはすべて、組織ごとに 1 分あたり 60 リクエストという 1 つの予算を共有します。

この API で書き込めるのは **ユーザー単位のオーバーライド** だけです。シート階層、グループ、組織のデフォルトは claude.ai の設定で構成します。また、この API は Enterprise 専用で、Claude Platform(Console)の組織では利用できません。

強制ではなくレポート用には、Admin API のコストレポートが相棒になります。`GET /v1/organizations/cost_report` は日次のバケット(デフォルトは `1d`、1 ページあたり最大 31)を最小単位の金額で返し、`description` または `workspace_id` でグループ化でき、`cost_type`(`tokens`、`web_search`、`code_execution`、`session_usage`)ごとに内訳が出ます。この最後の区分を見れば、請求の大半が推論ではないことに気づけます。

## クラウド層と、それがカバーしないもの

Google Cloud は、2026 年 7 月 27 日の課金リリースノートで **spend cap budgets** を出荷しました。Preview としてで、10 年にわたって課金関連の機能要望のトップだった機能にしては、驚くほど静かな発表でした。仕組みはよく読む価値があります。範囲が「Google Cloud のハードキャップ」という言葉より狭いからです。

- **対象サービスは短いリストです。** 文書化されているところでは、Gemini API、Gemini Enterprise Agent Platform、Cloud Run、Cloud Run functions。頼る前に最新のリストを確認してください。対象外のサービスに対する上限は存在しません。
- **1 つの上限がカバーするのは 1 プロジェクト × 1 サービスです。** アカウント全体のキルスイッチではありません。
- **月次の期間のみ。**
- **自動では再開しません。** *「When a spend cap is enforced, the usage block is reversed only when you manually lift the spend cap」*。さらに、その後サービスが完全に再開するまで最大 1 時間かかることがあります。本番サービスにとっては、意図的な請求の代わりに、意図的な停止を選ぶことになります。上限を設定する *前に* どちらが欲しいかを決めておいてください。
- **永続的なリソースは課金され続けます。** コンピュートとストレージに紐づく固定的な利用は有効なままで、課金も累積し続けます。上限が止めるのは新しいリクエストであり、稼働中のインフラではありません。
- **サブスクリプションの費用は対象外です。** たとえば Gemini Enterprise のライセンスなどです。

AWS は逆のアプローチを取り、サインアップ時点でこの問題に取り組みました。2026 年 9 月 17 日に報じられたところでは、新しい AWS アカウントは *プロジェクト* として構成され、$100 の無料利用枠クレジットから始まり、有料に移行するとプロジェクトごとの月次支出上限が $20 から設定され、AWS が過去の利用状況から金額を提案します。上限に達すると、プロジェクトは課金が累積する代わりに一時停止され、オーナーが上限を引き上げると再開します。注意点が 2 つあります。ロールアウトは段階的で、**新規顧客のみ** が対象であること。そして、一時停止されたプロジェクトが稼働中の公開エンドポイントにどう作用するかは明記されていないこと。ユーザー向けのものであれば、最初に答えを得るべき疑問です。

## 上限が守ってくれないもの

ハードキャップは、*1 つの層* における *従量計測された利用* の天井です。次の 4 つは、しばしばその外側にあります。

**シートとサブスクリプション。** シート単位のライセンスやプラン料金は従量計測された利用ではないので、利用上限では制限されません。

**永続的なインフラ。** アイドル状態の GPU インスタンス、プロビジョニング済みのデータベース、ストレージは、API の上限が適用されている間も課金され続けます。エージェントは止まっても、それが動いていたマシンは止まりません。

**独自の時計で動くコーディングエージェント。** Claude Code はコストのテレメトリをエクスポートします。USD 建ての `claude_code.cost.usage` とトークン数の `claude_code.token.usage` で、どちらも各 API リクエストの後に加算され、モデル、クエリソース(main / subagent / auxiliary)、速度、effort ごとに属性が付きます。これは確かに優れた可観測性ですが、何も強制しません。メトリクスは、各リクエストの完了 *後に* 発行される読み取り専用のエクスポートだからです。強制は、その下にある API またはゲートウェイの層で行う必要があります。Claude Code のワークスペース上限を設定し、そのワークスペースが組織の他の部分とは別にチェックされることを忘れないでください。

**層と層の間のすき間。** サービスがプロバイダに直接到達できるなら、ゲートウェイの予算は役に立ちません。プロバイダレベルの上限は、迂回できない唯一の上限であり、だからこそ最初に設定するのです。
