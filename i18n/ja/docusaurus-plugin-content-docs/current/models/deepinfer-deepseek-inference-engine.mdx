**2026 年 10 月 20 日** の 09:08 UTC、*「DeepInfer: High-performance inference framework for DeepSeek models」* というタイトルのリンクが Hacker News に載り、**2,251 ポイント、856 コメント**に落ち着きました — その週のサイトで最大の AI の話題です。リポジトリ `deepseek-ai/DeepInfer` はその 4 日前に作られ、翌朝までに **16,337 スターと 1,620 フォーク**を集めました。Apache 2.0、Python で書かれています。

どこでも見られた枠組みは *「DeepSeek が DeepSeek を動かすエンジンをオープンソース化した」* でした。この枠組みは正しく、ほとんど役に立ちません。856 件のコメントのスレッドは、そのギャップのほぼ完璧な実例です。フロンティアラボにとって推論が儲かるのかをめぐる長い議論で、**コードが何をするかの議論は実質的にありません**。実際に動かしてみたと報告している人もいません。

そこでこのページは、地味な部分を担当します。DeepInfer 自身のドキュメントには、このリリースから何を結論づけるべきかを大きく変える 4 点があり、そのどれも報道には載りませんでした。

1. 自身の謝辞によれば、これは **vLLM のフォーク**であり、クリーンルームで作られたエンジンではありません。
2. **「NVIDIA SM100」** は、すべての H100 とすべてのコンシューマー向けカードを除外します。読者のほとんどはこれをまったく動かせません。
3. 見出しのデコードスループットは **全受理の集計(full-acceptance accounting)** で計算されており、*真の受理率にかかわらず*投機的ドラフトトークンを数えます。
4. 最も長く残る貢献である**バッチ不変の推論**は、DeepInfer 自身の投機的デコーダーを*オフ*にするフラグでオンになります。ここでは速度と再現性は二者択一です。

## 一段落で言うと

DeepInfer は、DeepSeek の本番スタックのうち**オフライン推論**の経路を取り出して公開したものです。モデルファミリーは `DeepSeek-V4.1-Flash` の 1 つだけ、ハードウェアは 2 種類で動作し、DeepSeek 自身のカーネルライブラリが組み込まれています。マルチヘッド潜在アテンション用の [FlashMLA](https://github.com/deepseek-ai/FlashMLA)、行列積用の [DeepGEMM](https://github.com/deepseek-ai/DeepGEMM)、エキスパート並列の通信用の [DeepEP](https://github.com/deepseek-ai/DeepEP)、スパースアテンションとサンプラーの top-k 用の [DeepSelect](https://github.com/deepseek-ai/DeepSelect)、そして残りを担う [TileKernels](https://github.com/deepseek-ai/TileKernels) とツリー内の TileLang カーネルです。これら 5 つのリポジトリは新しくありません。FlashMLA、DeepGEMM、DeepEP はいずれも 2025 年 2 月のもので、それぞれ 13.1k、9.1k、10.3k スターを持ち、DeepSelect は 2026 年 9 月のもので 510 スターです。DeepInfer は、ずっと欠けていたもの、つまりそれらを組み立てる**スケジューラーとランタイム**です。

### 誰も引用しなかった系譜

謝辞にはっきり書かれています。DeepInfer は「当初は主に **vLLM** の上に構築され、**SGLang** と **TensorRT-LLM** からも追加の着想を得ました」。

これはじっくり考える価値があります。このリリースの支配的な読み方は、*フロンティアラボがオープンソースのサービングスタックを退け、自前のものを作った*、というものでした。真実はむしろその逆に近いです。DeepSeek は vLLM を取り、1 種類のアクセラレーター上の 1 つのアーキテクチャに向けて徹底的に特化させ、同じ寛容な条件で成果を返しました。すでに vLLM を動かしているなら、DeepInfer は、汎用性をすべて削ぎ落としたときの vLLM 派生物がどうなるかを示す宣言であって、評価しなければならない競合ではありません。

### 意図的に除外されている 3 つの部品

README には、ほとんどの要約が飛ばした節があり、「Required for a complete inference service (not included in this release)」と題されています。

- **KV キャッシュシステム**
- **VE/prefill/decode の分離**(DeepSeek は、エンジン側の機能の大半は実装されているが、オーケストレーションは含まれていないと述べている)
- プリフィルとデコードの両方における、**データ並列レプリカ間のロードバランシング**

クライアントを向ける OpenAI 互換の HTTP サーバーはここにありません。すべての例は `python examples/offline_inference.py` です。「vLLM を外して DeepInfer を入れれば、同じエンドポイントで動く」というイメージだったなら、サービングプラットフォームのうち最も難しい 3 つの部品を自分で書くことになります。

## ハードウェアの一行を読み解く

README は 2 つの対象を挙げています。**NVIDIA SM100 GPU** と **Huawei Ascend 950 NPU** です。たった一行で、ほとんどの人を静かに除外しています。

`SM100` は CUDA の演算能力 **10.0** で、*データセンター向け* Blackwell、B100/B200 クラスです。次のものではありません。

| お使いのハードウェア | アーキテクチャ | 記載あり? |
|---|---|---|
| H100 / H200 | SM90(Hopper) | **なし** |
| RTX 5090 / 50 シリーズ | SM120(コンシューマー向け Blackwell、cc 12.0) | **なし** |
| B200 / B100 | SM100 | あり |
| Ascend 950 | CANN 9.2 | あり |

そして 2 つの Blackwell は互換ではありません。`sm_100` と `sm_120` のあいだにバイナリ互換性はなく、データセンター向け Blackwell のカーネルは `tcgen05` 命令と TMEM(コンシューマー向け Blackwell にはまったくない専用のテンソルメモリ)を使うからです。SM100 向けに書かれたカーネルは RTX 5090 で「遅く動く」のではなく、動きません。

固定された依存関係のリストも、別の言い方で同じことを語っています。`requirements-nvidia.txt` は 3 行で、`torch==2.13.0+cu132`、`flash-attn-4==4.0.0b34`、開発用の要件です。そして `build.sh` は Torch に付属してきたものの上から `nvidia-nccl-cu13==2.32.3` を強制的に再インストールします。ベータ版の FlashAttention-4、CUDA 13.2、手作業でパッチを当てた NCCL。DeepSeek 自身のラックにある正確なマシンに固定されたスタックです。

## バッチ不変性: temperature 0 が決して決定的でなかった理由

DeepInfer のうち、実際には使わなくても注目する価値があるのがここです。

`temperature=0` に設定して、同じプロンプトを 2 回送ると、異なる答えが返ってくる。誰もが目にしています。おそらく読んだことのある説明、つまり[この記事のサンプリング制御のレッスン](/docs/foundations/sampling-controls)(このページはそれを補強します)でも、「サーバー側のバッチ処理と浮動小数点の非決定性」とされています。それは近いところを指していますが、メカニズムは誤りで、その違いこそがバグを直せるものにします。

### 説明の誤った半分

「GPU は並列で、浮動小数点の加算は結合則を満たさないから、結果が揺れる」というのは、揺れが*本質的*であることを意味します。そうではありません。同じ GPU で、同じデータに対して同じ行列積を何度実行しても、**ビット単位で同一**の結果が毎回得られます。カーネルは決定的です。並行性は犯人ではありません。

### 実際のメカニズム

犯人は**バッチ不変性**、より正確にはその欠如です。GPU カーネルは、与えられた作業の形に基づいてリダクションの戦略を選びます。1 行(バッチ 1)を掛けると加算は 1 つの順序で行われ、同じ行を 32 行のバッチの一部として掛けると、カーネルはリダクションを別の分け方にするので、浮動小数点の加算が別の順序で行われ、結果が最後の数ビットで異なります。各実行は決定的です。*形*が決定的ではないのです。

そして不気味に感じられる部分が来ます。**バッチサイズは他人のトラフィックによって決まります。** 共有の推論サーバーは、あなたのリクエストを同じ時間枠に届いた他のものと一緒にバッチ化します。あなたは何も変えていません。負荷が変わり、あなたの数値が動いたのです。順伝播は決定的で、それをあなたが体験する結果は決定的ではありません。

Transformer では、リダクションに基づく 3 つの演算を修正する必要があります。**RMSNorm、行列積、アテンション**です。手順は、可能な限り各リダクションを 1 つのコア内に収め、形がバッチサイズに依存するリダクションの分割を拒否し、性能を犠牲にしてでも単一のカーネル構成を使う、というものです。

### 気になるはずの数字

Thinking Machines Lab は、`Qwen3-235B-A22B-Instruct-2507` でこれを測定しました。同じプロンプト(「Tell me about Richard Feynman」)、temperature 0、1,000 トークン、**1,000 回の実行**です。

結果: **80 通りの異なる出力**。最も多かったものは 78 回現れました。そして分岐の形が示唆に富みます。1,000 件すべてが*最初の 102 トークンまでは同一*で、103 トークン目で分かれ、992 回が「Queens, New York」、8 回が「New York City」と言いました。

LLM のテストスイートで等価性のアサーションが非常に危険なのはそのためです。短いスモークテストは千回通っても何も教えてくれません。分岐は 103 トークン目で待っていたのです。

直すのはタダではありません。Qwen-8B で 1,000 シーケンスを処理したとき、Thinking Machines は vLLM のデフォルトで **26 秒**、素朴な決定的ビルドで **55 秒**、アテンションカーネルを改良した後で **42 秒**と測定しました。ビット単位の再現性に、およそ **1.6 倍の遅さ**です。

80 通りの出力という結果、103 トークン目での分岐、26 秒 / 55 秒 / 42 秒という数値は、Thinking Machines Lab が自社のハードウェアとカーネルで測定したもので、DeepInfer のものではありません。DeepSeek は自社のバッチ不変の経路について、比較可能な前後のコストを公開していません。約 1.6 倍は、見込むべきオーダーとして扱い、DeepInfer について引用する数値としては扱わないでください。

### なぜ 1.6 倍を払う人がいるのか

4 つの理由があり、金額の大きさの順におおよそ並べています。

- **オンポリシーの RL が嘘でなくなる。** サンプラーとトレーナーが異なる数値を計算するなら、「オンポリシー」の強化学習は静かにオフポリシーになっています。Thinking Machines は、決定的な推論がなければ、報酬の崩壊を避けるためにオフポリシーの補正が必要になり、ビット単位で同一の結果があれば、真のオンポリシー RL が得られ、サンプリングと学習のポリシー間の KL ダイバージェンスがゼロになることを示しました。大きなモデルで RL を行う人にとって、これは脚注ではなく主役です。
- **回帰テストで等価性をアサートできる。** DeepInfer はこれに強く依拠しています。`tests/models/offline_decode_ppl.json` はプラットフォームごとのパープレキシティのベースラインを保存し、それが**サンプルごとに厳密に**比較されます。このテスト設計は、決定的なエンジンでのみ可能です。
- **エージェントの実行のデバッグが扱いやすくなる。** ビット単位で再現できる失敗はバグで、できないものは怪談です。
- **監査とコンプライアンス。** 「同じ入力、同じ出力、証明可能」は、一部の規制対象の環境では要件であり、これがなければ不可能です。

2 つ目のモードに、DeepInfer の最も巧妙なアイデアがあります。通常の投機的デコードは *n* 個のトークンをドラフトして、すべてを検証します。**信頼度スケジューリングによる検証**は、モデル自身の信頼度の推定を使って、どれだけの検証予算を使うかを決めます — ドラフトが明らかに正しいところは安く、そうでないところは高く。これはカーネルのアイデアではなくスケジューリングのアイデアで、ドラフトの経路を持つあらゆるエンジンに転用できます。

## DeepInfer 自身のベンチマーク数値を読む

DeepSeek は、見出しの秒あたりトークン数ではなく、2 本のパレート曲線を公開しています。プリフィルのスループット対レイテンシ、デコードのスループット対ユーザーごとの速度です。その抑制は称賛に値しますが、**引用できる単一の数字がない**ということでもあります。また、真実は `examples/README.md` に書かれた方法論の中にあるということでもあります。その中の 3 点が、グラフの読み方を変えます。

### 1. デコードのスループットは、すべてのドラフトトークンが受理されたと仮定している

これが最大の点です。公開されているデコードのスループットは次のように計算されます。

```text
decode_throughput = avg_SPS × decode_num_requests × (1 + nextn) / cp
```

そしてドキュメントは、これが「**full-acceptance accounting** — 真の受理率にかかわらず、リクエストあたりステップあたり `1 + nextn` トークン」のもとにあると、はっきり述べています。

`nextn` のデフォルトは 5 です。したがって、投機的デコーダーの 5 つのドラフトが検証を通ったかどうかにかかわらず、各リクエストはデコードの 1 ステップあたり 6 トークンとして計上されます。デフォルトの 64 リクエストでは、「デコードの 1 ステップの 64 リクエストは合計 384 トークンになります」— 64 × 6 です。

マルチトークン予測の実際の受理率は 100% をかなり下回ります。したがって、そのグラフのデコードのスループットは、**どの実ワークロードも到達しない上限**で、グラフと現実のギャップは、まさにあなたの棄却率です。ここに不誠実なものはなく、リポジトリに書かれています。しかしパレート曲線をちらっと見た読者が想定するものではなく、856 件の Hacker News のコメントの誰も触れませんでした。

### 2. 数値は GPU ごとで、あなたが持たない規模のもの

プリフィルは **SM100 GPU 4 枚**、デコードは **64 枚**で測定され、「それぞれ 1 つのスケールアップドメイン内」、つまりイーサネットのクラスターをまたぐのではなく、単一の NVLink ファブリック内です。どちらのスループットも、デバイス数で割って、トークン/秒/**GPU** にされます。

GPU ごとの正規化は公開の仕方として正しく、同時に誤読しやすさでもこの上ありません。64 GPU が 1 つのファブリックを共有して得られた GPU ごとのデコードの数値は、あなたの 8 GPU ノードに掛け戻しても成り立ちません。それを可能にしたエキスパート並列の通信パターンが、ファブリックそのものだったからです。

### 3. プロファイラーのトレースはスループットのデータではない

ほかでは見たことがなく、自分のエンジンをプロファイルする人には本当に役立つ警告です。ドキュメントによると、`PROFILE=1` のトレース内のステップ時間にはプロファイラーのオーバーヘッドが含まれ、「**bsz=1 でほぼ 50% の水増し**」があり、プロファイラーが終了した後も約 **7〜11%** の残存する遅延があります。そのため、プロファイラーの区間の後に測定をスケジュールすることは許されません。明示的な指示は、トレースはカーネル構成の確認に使い、秒あたりのステップ数の導出には**決して**使わない、というものです。

ハーネスは多くのものより徹底しています。MoE のロードバランサーの統計フラッシュ(数ミリ秒のジッターを伴うエキスパート並列の `all_gather`)と重なる測定区間はすべて捨て、測定ウィンドウを 2 回実行します。1 回目はロードバランサーの値を取得するためにログをオンにし、2 回目は実際の数値のためにログなしで。

### 評価ハーネスが実際に測るもの

このリポジトリの精度の数値を引用する前に知っておく価値があります。3 つのベンチマークを扱い、すべて Pass@1 で報告されます。**AIME 2026**(30 問 × 32 サンプル、平均精度)、**HLE**(2,500 問 — テキスト 2,158 問と画像 342 問 — 単一サンプル)、**GPQA Diamond**(198 問 × 8 サンプル)です。スクリプトは意図的に**データセットをダウンロードしません**。それぞれを自分で取得して JSONL に変換する必要があり、HLE は Hugging Face でゲート付きです。自前のテストセットを自動ダウンロードしないベンチマークのハーネスは、汚染への真剣さの小さな現れです。

## 痛い目に遭う 2 つの設定値

**SWA のバウンデッドリプレイ。** DeepInfer は、コンテキストの有限な末尾だけを再生することで、デコーダーのプリフィルの作業量を減らします。V4.1 のデフォルトでは `DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact` と `DEEPINFER_YOCO_PREFILL_KEEP_TOKENS=140` で設定されます。制約が興味深い部分です。保持される末尾は、**スライディングウィンドウアテンションのウィンドウに最大のバックトラック長を足した範囲を覆わなければなりません**。この妙に具体的な `140` はチューニングの好みではなく、アーキテクチャから導かれる下限です。メモリを節約しようと下げれば、品質と速度のトレードオフではなく、モデルがまだ必要とするコンテキストを切り捨てることになります。

**EPLB の冗長エキスパート。** エキスパート並列のロードバランシングは `DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS` で設定され、デフォルトは **32** です。これは*下限*にすぎません。エンジンは `num_routed_experts + num_extra_experts` を `ep_size` で割り切れるまで切り上げ、バックボーンと DFlash を別々に丸めます。そのため、設定した値が実際に有効な値とは限らず、ディスクに書かれる記録やプロットでは、実際に有効になった丸め後の値が使われます。2 つの実行を比較するなら、環境の値ではなく、ログに出た値を比較してください。

## 動かせなくても、この 3 つは持ち帰れる

- **スループットの数値がどんな集計を使っているか尋ねる。** 投機的デコーダーが介在する「秒あたりトークン数」は、棄却されたドラフトが数えられているかどうかを誰かが教えてくれるまで曖昧です。使っているエンジンも含め、すべてのエンジンに尋ねてください。
- **決定性を勝ち取っていない限り、LLM の出力で等価性をアサートするのをやめる。** temperature 0 はほぼ決定的であって、決定的ではありません。失敗のモードは、スモークテストが到達しない、100 トークン先の分岐です。エンジンをバッチ不変にしてビット単位でアサートするか、評価と分布でテストするかのどちらかです。中間は、チームに赤を無視させる不安定なスイートです。
- **「エンジンをオープンソース化した」は、めったに「サービスをオープンソース化した」を意味しない。** *欠けているもの*、つまりキャッシュシステム、分離、ロードバランシングを読んでください。公開されたエンジンと動いているサービスのギャップに、プラットフォームの作業のすべてがあり、どの部品が欠けているかを正直に伝える README は、あなたに親切にしてくれています。
