**2026年6月13日**、Z.ai(旧 Zhipu AI)は **GLM-5.2** をリリースした — **7530億パラメータ**の Mixture-of-Experts モデルで、**100万トークンコンテキスト**、地域制限のない平易な **MIT ライセンス**で Hugging Face に公開。続く 2 週間で、ローンチそのものより無視しにくい 3 つのことが起きた:長ホライズンのコーディングベンチマークで **Claude Opus 4.8 の約 1 ポイント差**に着地し、API がフロンティア価格を約 **6 倍**下回り、Semgrep のセキュリティチームが GLM-5.2 がほとんどスキャフォールディングなしで **Claude Code を実世界の IDOR 脆弱性ベンチマークで上回った**と静かに報告した。

このページは GLM-5.2 について実際に非自明な点をカバーする — 1M トークン推論を扱いやすくする IndexShare アーキテクチャ変更、Claude と GPT-5.5 に対する誠実なベンチマーク像、今日セルフホストにかかるコスト、そしてクローズドフロンティアモデルに手を伸ばすより真に優れたツールとなる場面。

## 一文サマリー

GLM-5.2 は **オープンウェイト**(MIT)、**753B 総 / ~40B アクティブ**のスパース Mixture-of-Experts モデルで、Z.ai 製、**1M トークンコンテキスト**、**131,072 トークン最大出力**、長ホライズンのエージェンティックコーディング向けに構築 — クローズドフロンティア API の約 6 分の 1 の価格で、独立評価では自律エージェント作業に重要なコーディングベンチマークで Claude Opus 4.8 から 1 ポイント差にある。

## 見出しからは自明ではない GLM-5.2 の 3 点

### 1. IndexShare が本当のアーキテクチャストーリー

GLM-5.2 の見出しの変更は「より大きな MoE」ではなく **IndexShare** だ。スパースアテンションは、各クエリが過去のどのトークンにアテンドするかを決める*インデクサ*を必要とする。1M トークンコンテキストで層ごとにそのインデクサを実行するのは高価だ。Z.ai の IndexShare は **同じインデクサを 4 つのスパースアテンション層すべてで再利用**し、1M ウィンドウ全体でトークンあたり FLOPs を **~2.9×** 削減する。

実用的な結果:GLM-5.2 は、完全な二次アテンションモデルで同じ仕事をすると経済的に不合理な価格で、実世界の長コンテキストワークロードを提供できる。これはまた、FP8 チェックポイント(`zai-org/GLM-5.2-FP8`として公開)が **8× H200** で 131K トークンセッションの余地を持って動作する理由でもある;IndexShare なしなら、同じハードウェアはそこに至る前に KV キャッシュで詰まる。

GLM-5.2 は投機的デコード用の改善された **Multi-Token Prediction (MTP) 層**も出荷し、Z.ai は **~20% の受容長アップリフト**を報告 — これは論文メトリックだけでなく、実際の推論での速いトークン/秒として現れる。

<VerifyNote lastVerified="2026-07-29" source="https://huggingface.co/zai-org/GLM-5.2">
アーキテクチャ詳細(IndexShare、MTP 受容アップリフト、753B/40B 構成)は公式 Hugging Face モデルカードと Z.ai のローンチ資料から。計算節約主張(2.9×)はベンダー報告;1M コンテキストでの独立した推論コスト測定は 2026年7月末時点でまだ疎です。
</VerifyNote>

### 2. ベンチマークストーリーは「GPT-5.5 に勝つ」より強く「Opus に勝つ」より弱い

ベンダー表とニュース報道はこれをサウンドバイトに圧縮する。誠実な読み:

| ベンチマーク | GLM-5.2 | Claude Opus 4.8 | GPT-5.5 | 注記 |
|---|---|---|---|---|
| **Terminal-Bench 2.1** | 81.0 | ~85.0 | — | 長ホライズン shell/エージェント作業;4 ポイントギャップ |
| **SWE-bench Pro** | 62.1 | — | 58.6 | 自律的なリポレベルの修正;GPT-5.5 の先、GLM-5.1 (58.4) の先 |
| **GPQA Diamond** | 91.2 | — | — | 難しい科学 QA;強い |
| **AIME 2026** | 99.2 | — | — | ベンダー報告;極端な数値、慎重に扱う |
| **Artificial Analysis Intelligence Index** | 51 | — | — | ローンチ時点で任意のオープンウェイトモデルの最高スコア |
| **Code Arena (グローバル)** | #2 | — | — | 一つのクローズドモデルに次ぐ |

内面化すべき 2 点:

- **エージェント作業に対応するコーディングベンチマーク**(SWE-bench Pro、Terminal-Bench 2.1、Code Arena)では、GLM-5.2 は *GPT-5.5 より Claude Opus 4.8 に近い*。任意のオープンウェイトモデルにとって初めてのことだ。
- **最も難しい推論タスクと開かれた知識**では、クローズドフロンティアモデルが依然リードする。AIME 99.2 見出しはベンダー報告で独立評価と並べて読むべき — Z.ai の Artificial Analysis Index スコア 51 の方がよりキャリブレーションされた要約だ。

<Callout type="tip">
誰かが「GLM-5.2 が Claude Opus に勝つ」または「GLM-5.2 が GPT-5.5 に勝つ」とリンクしたら、*どのベンチマーク*で*誰の測定*かを確認せよ。長ホライズンコーディングで:Opus から 1 ポイント差、GPT-5.5 より明確に先。一般推論で:依然クローズドフロンティアの後。両方とも真だ。
</Callout>

### 3. Huawei Ascend NPU で訓練され、Nvidia ではない

GLM-5.2 は Nvidia H100/H200 ではなく、報告によれば **Huawei Ascend アクセラレータ**で訓練された。それはベンチマーキングの詳細ではない — サプライチェーンの事実だ。Z.ai が米国 Entity List にあり、ホスト型 API が中国インフラを経由することと組み合わせると、3 つの実際の判断を形成する:

- **規制環境**は本番に配線する前に、ホスト型 API を輸出管理ポリシーに対して評価すべきだ。MIT ウェイトは制限がない;API はコンプライアンスレビューの代替にならない。
- **データ機密ワークロード**は、Z.ai の API エンドポイントにプロンプトを送るのではなく、セルフホストパス(下記)を優先すべきだ。
- **アグリゲータ**(OpenRouter、NVIDIA Build、OpenRelay)は非 Z.ai インフラを通じて GLM-5.2 を提供する — モデルは欲しいがオリジンルーティングは欲しくないなら、それがルートだ。

## 実効コスト計算

Z.ai 自身の API 価格は、プロバイダ全体で入力トークン 100 万あたり約 **$1.20–$1.40**、出力トークン 100 万あたり **$4.10–$4.40** 付近に位置する。Claude Opus 4.8 テリトリー($15/M 入力、$75/M 出力のフロンティア価格)と比較すると、比率は入力で約 **1:6**、出力で **1:15+** だ。Semgrep の IDOR ベンチマークは脆弱性あたりコストを **~$0.17 for GLM-5.2** に置き、フロンティア相当は数ドル。

見逃しやすい罠:GLM-5.2 はモデルレベルで「high」または「max」思考努力で動くので、同じタスクに対して**出力トークン数は非思考モデルより高い**。タスクあたりコストは依然低いが、比率はトークンあたり価格が示唆するほど極端ではない — 各々より低い価格で、答えあたりより多くのトークンを支払っている。

## API 経由で始める

GLM-5.2 は **OpenAI 互換 chat completions** を話す。エンドポイント URL とモデル ID はプロバイダによって変動する — 一つを選べ:

| プロバイダ | ベース URL | モデル ID | Env |
|---|---|---|---|
| Z.ai(直接) | `https://api.z.ai/api/paas/v4/` | `glm-5.2` | `ZAI_API_KEY` |
| OpenRouter | `https://openrouter.ai/api/v1` | `z-ai/glm-5.2` | `OPENROUTER_API_KEY` |
| NVIDIA Build | `https://integrate.api.nvidia.com/v1` | `z-ai/glm-5.2` | `NVIDIA_API_KEY` |
| OpenRelay | `https://inference.openrelay.inc/v1` | `openrelay/glm-5.2` | `OPENRELAY_API_KEY` |

## セルフホスティング:3 つの現実的パス

MIT ライセンスと公開された FP8 ウェイトは、多くのチームにとってセルフホスティングを全ポイントにする。3 つの実用的パス、最もハードウェアが必要なものから最も少ないものへ:

### パス A — vLLM で 8× H200 上の FP8(本番グレード)

リファレンスデプロイメント。公式 FP8 チェックポイントをダウンロードし、vLLM 0.23.0+(または SGLang 0.5.13.post1+)で提供する。これは Z.ai 自身の推論に最も近い config だ;完全な 131K トークン最大出力と安定したスループットを与える。

<PromptCard title="vLLM で 8× H200 上に GLM-5.2 FP8 をデプロイ">
{`# 1) Download the FP8 weights (~750 GB)
huggingface-cli download zai-org/GLM-5.2-FP8 \\
  --local-dir /models/glm-5.2-fp8

# 2) Serve with vLLM 0.23.0+
python -m vllm.entrypoints.openai.api_server \\
  --model /models/glm-5.2-fp8 \\
  --served-model-name glm-5.2-fp8 \\
  --tensor-parallel-size 8 \\
  --quantization fp8 \\
  --enable-expert-parallel \\
  --max-model-len 131072 \\
  --kv-cache-dtype fp8_e5m2 \\
  --gpu-memory-utilization 0.92 \\
  --enable-chunked-prefill \\
  --max-num-seqs 32 \\
  --port 8000`}
</PromptCard>

### パス B — Mac Studio または 24 GB GPU + 256 GB RAM 上の 2 ビット GGUF

Unsloth の動的 2 ビット GGUF は GLM-5.2 を ~1.51 TB から ~239 GB へ圧縮する — **256 GB Mac Studio (Ultra)** または **24 GB GPU に 256 GB システム RAM** を持つワークステーションに収まる小ささ(MoE ルーティングは一度に少数のエキスパートだけをホットに保つので、DRAM オフロードが機能する)。これは「実際に店で買えるハードウェアで動かす」パスだ。H200 ラックより遅いトークン/秒を予期せよ、しかし単独エージェントワークロードには使える。

### パス C — コミュニティからの AWQ/W4A16 量子化

サードパーティ量子化(例:`QuantTrio/GLM-5-AWQ`、`PhalaCloud/GLM-5.2-W4AFP8`)は vLLM の AWQ カーネルと互換な 4 ビット重みパスを狙う。これは FP8 より小さいメモリフットプリントを望むが 2 ビット GGUF より余裕を望むときに有用。Z.ai は 2026年7月末時点で公式 AWQ 版を公開していない — 本番で使う前にコミュニティ版のキャリブレーションを検証せよ。

<Callout type="warning">
任意のティアで GLM-5.2 をセルフホストする際、トークナイザとチャットテンプレートには依然注意が必要だ。Hugging Face モデルカードは両方を出荷する;プロンプトを手動で組み立てるのではなく `add_generation_prompt=True` で `apply_chat_template` を使え。テンプレートの不一致は「なぜ私のオープンウェイトモデルは API よりずっと悪いのか?」レポートの単一で最も一般的な原因だ。
</Callout>

## GLM-5.2 vs Claude をいつ選ぶか

真により良いツールとなる 2 つのタスク:

- **プライベートコードベース上の長ホライズン自律コーディング。** セルフホスト FP8 は、コードやコンテキストがインフラを離れずにフロンティア隣接の SWE-bench Pro スコアを与える。Claude Opus 4.8 は Terminal-Bench 2.1 で髪の毛ほど鋭いが、オンプレ推論のコンプライアンス勝ちがしばしば 4 パーセントポイントを上回る。
- **敵対的ペイロードでのセキュリティ研究。** Semgrep の IDOR 実験(裸プロンプトハーネスで F1 39%、Claude Code の 37% を先行)は、GLM-5.2 が Claude の安全訓練が偽陽性をトリガーする防御的セキュリティタスクで意味のある拒否率の低さを示唆する。

Claude が依然より良いツールである 2 つのタスク:

- **開かれた推論と事実知識の質問。** GLM-5.2 は一般知識と開かれた推論でクローズドフロンティアモデルに遅れる;Claude Opus/Sonnet 5 と Fable 5 がここで先行する。
- **拒否モードのニュアンスが重要な任意のもの。** Claude の害回避はよりニュアンスに富む(正当な作業での過剰拒否が少なく、真の害でよりシャープに停止)。GLM-5.2 の安全層はエッジケースに対してより薄くキャリブレーションが低い。

<Callout type="tip">
クロスリンク:より広いオープンウェイトランドスケープには [DeepSeek、Qwen とオープンウェイトの波](/docs/models/deepseek-qwen-open-models) と [Kimi K3:世界最大のオープンウェイトモデル](/docs/models/kimi-k3-open-weight-frontier) を参照。「これは全くローカルで実行すべきか?」判断には [Local vs Claude エージェント](/docs/models/local-or-claude-agent) を参照。
</Callout>

## Semgrep の IDOR 結果を一段落で

Semgrep は脆弱性データセット(実際のオープンソース IDOR 欠陥)、F1 スコアリング、システムプロンプトを一定に保ち、モデル + 周辺ハーネスを変えた。GPT-5.5 とのカスタム **Semgrep Multimodal** リグは **61% F1**;Opus 4.8 との同じリグは **53%**。GLM-5.2 を**プロンプトだけ**(裸の Pydantic AI ハーネス、エンドポイント列挙なし、案内付きナビゲーションなし)でテストしたとき、**39% F1** を記録 — 同じタスクで Claude Code (37% F1) を約 **脆弱性あたり $0.17** で上回った、フロンティアコストの約 6 分の 1。彼ら自身の見出し:*「私たちは家に Mythos がある。」* 重要な但し書き:一つのタスク、一つのデータセット、一つの実行 — 発見は方向性があり、SSRF、XSS、または他のクラスへの一般化を約束するものではない。
