**2026 年 9 月 22 日**、Anthropic は **Claude Opus 5.5**（`claude-opus-5-5`）をリリースし、ほとんどのワークロードで推奨される出発点に据えました。見出しになるのは価格です。**入力 $4 / 出力 $20 per MTok** で Opus 5 の $5/$25 より 20% 安く、**キャッシュ読み取りは $0.20**。さらに Anthropic 自身の見積もりでは、デフォルト設定の典型的なワークロードで**合計コストが約 40% 低下**します。トークン単価が下がった*うえに*、同じタスクをより少ないトークンで終えるからです。

面白いのは価格ではありません。**リクエスト/レスポンスの契約について 5 つのことが変わった**という点です。そのうち 4 つは `400` を返し、5 つ目は `200` を返しながら進捗 UI を静かに壊します。そして初日にいちばん高くつくミスは、直感とは正反対です。Opus 5 の `effort` 設定をそのまま持ち越すと、請求額が**上がる**可能性があるのです。

## 1 段落で言うと

Opus 5.5 は、**より安く、より速く、よりおしゃべりでない Opus 5 に、より厳格な API 契約を付けたもの**です。1M トークンのコンテキストも、同期 Messages API での 128k の最大出力も、Fable 5.1 と同じ 2026 年 6 月という信頼できるナレッジカットオフも、そのままです。価格は $4/$20 per MTok に、キャッシュ読み取りは $0.20 に下がりました — これは**基本入力価格の 0.05 倍**で、プラットフォームの標準は 0.10 倍です。長いエージェントセッションではキャッシュ読み取りが請求額を支配するため、見出しの値下げよりこちらのほうが効いてきます。アダプティブ thinking は**常時オンになり、どの effort レベルでもオフにできません**。強制 `tool_choice` は廃止。レガシーの `computer_20251124` ツールは Claude API と Google Cloud で拒否されます（Bedrock ではまだ動きます）。thinking ブロックは、モデル*と*会話のプレフィックスに暗号的に紐づけられます。デフォルトの effort は `high` から `medium` に下がり、Anthropic の報告では、コーディングとナレッジワークの評価で Opus 5.5 の `medium` が Opus 5 の `high` に匹敵するか上回ります。提供終了は**2027 年 9 月 22 日より前には行わない**とコミットされています。

## 正確な価格

| | Opus 5 | **Opus 5.5** | Fable 5.1 |
|---|---|---|---|
| 入力 / MTok | $5 | **$4** | $10 |
| 出力 / MTok | $25 | **$20** | $50 |
| キャッシュ読み取り / MTok | $0.50 | **$0.20** | $0.25 |
| キャッシュ読み取り倍率 | 0.10× | **0.05×** | 0.025× |
| キャッシュ書き込み、5 分 | $6.25 | **$5** | — |
| キャッシュ書き込み、1 時間 | — | **$8** | — |
| バッチ（50% 割引） | $2.50 / $12.50 | **$2 / $10** | — |
| デフォルトの `effort` | `high` | **`medium`** | `high` |
| コンテキスト / 最大出力 | 1M / 128k | **1M / 128k** | 1M / 128k |

じっと見るべき行は**キャッシュ読み取り倍率**です。Anthropic のプラットフォーム標準は基本入力の 10%、Fable 5.1 と Mythos 5.1 は 2.5%、そして Opus 5.5 は独自の **5% ティア**に座っています。同じリポジトリのコンテキストが毎ステップ再生される長いエージェントセッションでは、キャッシュ読み取りが最大の費目になります。したがって Opus 5 に対する実効的な節約は、定価 20% 引きを大きく上回ります。キャッシュ可能な最小プロンプトは 512 トークンです。これらのレートを実際の請求額に変える計算は、[プロンプトキャッシュの経済学](/docs/frontiers/prompt-caching-economics)のページにあります。

**Fast mode** はリサーチプレビューで、**Claude API 限定**です — Bedrock、Claude Platform on AWS、Google Cloud、Microsoft Foundry では使えません。`fast-mode-2026-02-01` ベータヘッダーとともに `speed: "fast"` を設定すると、入力 $8 / 出力 $40 per MTok（標準の 2 倍）を支払う代わりに、実時間でおよそ 2.5 倍の速度が得られます。

## まずここから:エラーにならない変更

Anthropic は 4 つの破壊的変更を挙げており、いずれも `400` を返します。それらは 2 番目に直してください。最初に直すべきはこちらです。`400` は CI の最初のリクエストで自ら名乗り出ますが、こちらは `200` を返し、ステータスコードを確認するテストをすべて通過し、ユーザーのもとへ届いてしまうからです。

Opus 5 では、モデルが**ツール呼び出しの合間**に書く短いメモは `text` ブロックとして返ってきました。Opus 5.5 では — Fable 5.1 と同様に — そのナレーションは**進捗更新（progress-update）の `thinking` ブロック**として返り、各ツール呼び出しの前に最大 1 つ入ります。`thinking.display` のデフォルトである `"omitted"` では、その `thinking` フィールドは**空**です。

何も失敗しません。しかし、そのテキストを進捗としてユーザーにストリーミングしていたアプリケーションは、**長いエージェント的ターンの全区間にわたって沈黙**します。ユーザーは「マイグレーションを確認しました。次はテストを更新します」の代わりに、スピナーを見ることになります。

## 4 つの 400 エラー

### 1. thinking は無効化できない — どの effort レベルでも

Opus 5 は `high` 以下の effort で `thinking: {"type": "disabled"}` を受け付けていました。Opus 5.5 はどこでも受け付けません。無効化の形も手動バジェットの形も、どちらも `400 invalid_request_error` を返します:

```text
"thinking.type.disabled" is not supported for this model. Use "thinking.type.adaptive" and "output_config.effort" to control thinking behavior.
```

```text
"thinking.type.enabled" is not supported for this model. Use "thinking.type.adaptive" and "output_config.effort" to control thinking behavior.
```

ベータヘッダーは関係なく、オプトアウトもありません。`thinking` フィールドをまるごと省略するか、`thinking: {"type": "adaptive"}` を送ってください — 両者は等価です。トークン節約のために thinking を無効化していた箇所では、**代わりに effort レベルを下げてください**。

<PromptCard title="thinking 無効化の削除 — Opus 5 から Opus 5.5 へ">
{`# Before — accepted on Opus 5, 400 on Opus 5.5
client.messages.create(
    model="claude-opus-5",
    max_tokens=16000,
    thinking={"type": "disabled"},
    messages=[{"role": "user", "content": "..."}],
)

# After — thinking is always on; effort is the only control
client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    output_config={"effort": "low"},
    messages=[{"role": "user", "content": "..."}],
)`}
</PromptCard>

Opus 5 の統合を thinking 無効で動かしていた場合、パラメータ変更に加えて 3 つの後続の編集が必要です。**thinking の代わりに推論をレスポンスへ書き出すよう求めていた指示はすべて削除してください** — その指示は、新しい `reasoning_extraction` 拒否カテゴリのもとで*そのまま拒絶されうる*ようになりました。代わりに `display: "summarized"` の thinking ブロックから推論を読んでください。**思考しないよう命じていたルールはすべて外してください**。いまや無意味です。そして、Opus 5 で追加した **thinking 無効時の緩和策を再テストしてください**（ツール呼び出し前に発話する許可、適合するツールがないときの振る舞い、内部タグの禁止）。それらは thinking をオフにしたときだけ現れるアーティファクトへの対処でした。

### 2. 強制ツール使用は廃止

`tool_choice: {"type": "any"}` と `tool_choice: {"type": "tool", "name": "..."}` はどちらも `400` を返します:

```text
tool_choice: type "tool" and "any" are not supported for this model.
```

同じバリデーションは**トークンカウントのエンドポイント**にも適用され、これは見落としやすいポイントです。実際のリクエストペイロードをそのまま写した事前のトークンカウントも失敗し始めます。

`auto`（デフォルト）と `none` は引き続きサポートされます。スキーマに適合する JSON を保証したい場合は、`tool_choice: {"type": "auto"}` のままにして、ツールに `strict: true` を設定するか、スキーマを[構造化出力](/docs/api/structured-output)に移してください。テキストで答えるのではなくツールに手を伸ばさせたい場合は、**そのツールがどんなときに当てはまるのかをプロンプトで述べてください** — かつてパラメータが担っていた仕事を、いまは指示が担います。

<PromptCard title="強制 tool_choice を strict なツール使用に置き換える">
{`# Before — 400 on Opus 5.5
tool_choice={"type": "tool", "name": "get_weather"}

# After — strict schema validation plus an instruction that names when the tool applies
client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    tools=[{**tool, "strict": True} for tool in tools],
    tool_choice={"type": "auto"},
    messages=[{
        "role": "user",
        "content": "What's the weather in Paris? Use the get_weather tool.",
    }],
)`}
</PromptCard>

### 3. thinking ブロックはモデルと会話に紐づけられる

これは 4 つのうち最も微妙で、ルーターや圧縮ステップ、コンテキスト編集のループを壊す可能性が最も高いものです。

すべての thinking ブロックは**どのモデルが生成したか**を記録しており、モデルは自分自身のブロックと、一部の他モデルのブロックしか読みません。そのグラフは非対称です:

- Opus 5.5 は Opus 5 およびそれ以前の Opus、Sonnet、Haiku モデルの thinking を**読めます** — **しかし** Fable や Mythos のいかなるモデルのものも読めません。
- Opus 5.5 の thinking ブロックを読めるのは **Fable 5.1 と Mythos 5.1** だけです。**他のモデルは読めません。**

したがって Opus 5 → Opus 5.5 → Fable 5.1 と登っていく会話は、最後まで推論を保持します。Opus 5.5 から Sonnet 5 へ*フォールバック*したり、安価なステップのために Haiku へ下りたりする[ルーター](/docs/models/model-routing-patterns)は、切り替え後のすべてのターンを**それ以前の推論なしで**実行します。これはエラーではありません — API はモデルに見せる前に読めないブロックを落とし、リクエストは成功し、**落とされたブロックは課金されません**。`thinking-binding-controls-2026-08-01` ベータヘッダーを送ると、その除去がトップレベルの `input_transformations` 配列で報告されます。これが観測する唯一の手段です。

第二に、API は **thinking ブロックより前にあるものが変更されていないか**をブロック生成時点と比較して検査します。対象は `system` プロンプト、`tools` 配列、そしてそれ以前のあらゆるメッセージです。これは **2026 年 8 月 31 日 00:00 UTC 以降に作成されたアカウントではデフォルトで強制**され、Claude API とクラウドプラットフォームの双方に適用されます。そうしたアカウントでは、このような編集の後にブロックを再送すると `400` が返ります。それより古いアカウントでは、この検査はオプトインです。

### 4. `computer_20251124` は拒否される — 5 つのプラットフォームのうち 2 つで

[コンピュータ使用](/docs/models/computer-use-agents)を使っている場合、レガシーのツールタイプは **Claude API と Google Cloud** で `400` を返します:

```text
'claude-opus-5-5' does not support tool types: computer_20251124.
```

メッセージはその後、`Did you mean one of` に続いて受け付けられるタイプを列挙します。**Amazon Bedrock ではレガシーの `computer_20251124` ツールが動き続け**、Opus 5.5 でも Opus 5 のときとまったく同じです。したがってマルチクラウドのデプロイには*プラットフォーム条件付きのツール宣言*が必要になります。片方のクラウドのステージングは通り、もう片方の本番で 400 を出す、という類のものです。

移行は文字列の入れ替え以上のものです。`{"type": "computer_toolset_20260801"}` を、**ベータヘッダーなし、`name` なし、表示サイズなし**で宣言してください。そのうえでエージェントループを更新します。**メンバーの `tool_use` ブロック**を扱い、**アクションは `input.action` ではなくブロックの `name`** であることを前提にし、**1 ターンに複数**来ることを想定し、**すべての結果に `toolset_name` を返す**必要があります。[ブラウザ使用ツール](/docs/models/browser-agents-shared-login)は影響を受けません。

## effort の罠:逆方向を向いた 2 つの変更

ここが実際にお金のかかる部分であり、本当に直感に反します。なぜなら**2 つの変更が同時に逆方向へ動いた**からです:

1. **デフォルトが下がった。** `effort` を省略したリクエストは、いまや `medium` で動きます。Opus 5 では `high` でした。つまり*何もしない*と、以前より 1 段階低くなります。
2. **各レベルの思考量は増えた。** 同じ `effort` 値でも、Opus 5.5 は Opus 5 より**1 ターンあたり多く思考する**傾向があり、「とりわけ `xhigh` と `max` で顕著」です。つまり*設定を明示的に持ち越す*と、以前よりターンが長くなり、出力トークンが増えます。

「放っておく」も「古い値を維持する」も、Opus 5 の挙動を再現しません。レベル名はモデルをまたいで安定した単位ではなく、Anthropic 自身がそう明言しています。自分の評価セットで effort のスイープをやり直してください。

朗報は、品質カーブが動いた方向です。Anthropic のテストでは、**Opus 5.5 のデフォルト `medium` が、コーディングとナレッジワークの評価で Opus 5 の `high` に匹敵するか上回り**、しかもより少ないステップと少ないトークンで達成しました。いくつかのコーディング評価では、**`low` でもかなり近い**ところまで、はるかに低いコストで到達します。コンピュータ使用では、デフォルトの effort が、Opus 5 がずっと高い設定でようやく届いた成功率に並びました。密度の高いチャートでは、**最も低い** effort の Opus 5.5 が、**最も高い** effort の Opus 5 より正確に値を読み取り、出力トークンはごく一部でした。

| レベル | Opus 5.5 における用途 |
|---|---|
| `low` | 単純なタスク、サブエージェント、最低コスト — 「thinking 無効」の代替 |
| `medium` | **デフォルト。** 速度・コスト・性能のバランスを取るエージェント作業 |
| `high` | 複雑な推論、難しいコーディング、エージェント的タスク（effort に対応する*他の*すべてのモデルではこれがデフォルト） |
| `xhigh` | 30 分ほどにわたる長期作業、トークン予算が数百万規模のもの |
| `max` | 可能な限り深い推論、トークン消費に制約なし |

実務的なルールが 3 つ。**`max_tokens` は thinking と返答の両方を賄える大きさにしてください** — thinking の内容が返されない場合でも thinking は `max_tokens` にカウントされるため、thinking を*オフ*にした Opus 5 向けに設定した上限は返答を切り詰めます。Anthropic は、モデルの最大値である 128,000 が長いエージェント的コーディングのターンでうまく機能すると報告しています。**`xhigh` と `max` は、効果を測定できた作業にだけ使ってください。** そして**思考を減らしたいなら、プロンプトで頼むのではなく effort レベルを下げてください** — そのほうが指示より確実に効きます。

キャッシュに関する落とし穴が 1 つ。リクエスト間で**トップレベル**の `effort` を変えると、**プロンプトキャッシュが無効化**されます。effort がレンダリング後のプロンプトを形づくるからです。Opus 5.5 は**メッセージ単位の effort**（ベータヘッダー `mid-conversation-output-config-2026-07-01`）をサポートします。`content` が空の `role: "system"` メッセージに新しい `output_config.effort` を載せると、次のユーザーターンから有効になり、**キャッシュも保たれます**。セッション内で effort を変えるにはこれを使ってください。[effort チューニング](/docs/api/effort-tuning)と [thinking と effort](/docs/api/thinking-and-effort) を参照してください。

## 発表時ベンチマークを正直に読む

Anthropic 自己申告の発表時の表を、スケール比較用の Fable 5.1 と Opus 5 とともに:

| ベンチマーク | **Opus 5.5** | Fable 5.1 | Opus 5 |
|---|---|---|---|
| Terminal-Bench 4.0（エージェント的コーディング） | **66.4%** | 55.8% | 52.3% |
| FrontierCode v1.1（コードのマージ可能性） | **54.4%** | 50.3% | 48.0% |
| CursorBench 4.0（曖昧な実タスク） | **57.8%** | 51.8% | 46.6% |
| GDPval-AA v2.1（ナレッジワーク、Elo） | **1846** | 1735 | 1708 |
| OSWorld 2.0（コンピュータ使用、部分点あり） | **81.8%** | 80.7% | 74.0% |
| Chartography（ビジュアルチャート、ツールあり） | **89.0%** | 88.4% | 83.4% |
| AutomationBench（業務ワークフロー） | **40.0%** | 31.4% | 26.9% |
| Humanity's Last Exam（ツールあり） | **67.7%** | 65.6% | 63.6% |

構造的に興味深い事実は、**Opus 5.5 が、より大きく高価な Fable 5.1 をすべての行で上回っている**ことです — しかも Fable の定価の 40% で。これは AILmanac の[フラッグシップガイド](/docs/models/fable-5-mythos-5-flagship)が前提にしていたサイズの序列を逆転させます。そして、Anthropic 自身のモデル選択ガイダンスが「Opus 5.5 から始めよ。Opus 5.5 を*より高い effort で*動かしても評価が届かないときに Fable 5.1 を使え」と読めるようになった理由でもあります。

表より価値のある注意点が 4 つ:

- **OSWorld の部分点スコアは 81.8%、厳密スコアは 48.7% です。** コンピュータ使用ベンチマークにおける部分点は、複数ステップの GUI タスクの大部分まで進めたことを評価します。厳密な評価は、やり切ったことを評価します。プロダクトがタスクの*完了*を必要とするなら、あなたの数字は 48.7% です。
- **セーフガードのフォールバックが一部のスコアを押し下げています。** サイバー系タスクは Opus 4.8 へ、生物学とフロンティア LLM 関連の作業は Opus 5 へフォールバックします。それらのフォールバックも結果に数え込まれているため、該当カテゴリでは見出しの数字が素のモデルを過小評価しています。
- **AutomationBench はフォールバックなしで実行され**、セーフガードによる介入は**失敗として数えられました** — 他の行とは異なる測定ルールです。
- **Anthropic 自身が、この差はギャップを誇張していると述べています。** 発表資料は「ベンチマークの差は、実世界の違いを示す指標としての信頼性が下がってきている」こと、そしてモデルが「自分が評価されていることをしばしば見抜く」ことに触れており、評価から実運用への推論を難しくしています。Terminal-Bench 4.0 には ±2.6 ポイントの標準誤差があります。

Anthropic が公開した逸話のほうが、パーセンテージより具体的です。**68 万行のコード移行を 1 日以内**で完了。**20 万行のコードベースを 3 時間以内で監査・修正**（Opus 5 では 20 時間超）。Web アプリの読み込み時間の最適化に **40 回中 39 回成功**。合併分析を **93 分に対して 63 分**、半分のコストで。これらはベンダーが選んだベストケースであって、期待値ではないものとして扱ってください。

## コードに触れなくても気づく挙動の変化

**報告のために立ち止まります。** 長い多段タスクでは、Opus 5.5 は作業しながらユーザーに状況を伝え続けます。そしてその更新の一部は、**ツール呼び出しではなくテキストでターンを終えます**（`stop_reason: "end_turn"`）。テキストだけのターン終了を「タスク完了」と見なす無人のエージェントループは、**そこで、タスクの途中で止まります**。これは、自律的なハーネスが Opus 5.5 で静かに成果不足に陥る、最も起こりやすい経路です。

**要点を先に出し、専門用語を減らします。** Opus 5.5 は専門用語を使いにくく、重要な情報をメッセージの冒頭に置きやすくなりました。Opus 5 の言い回しをパースしていた後処理や、冗長さと戦っていたプロンプトは、再テストすべきです。

**チャットでは、決着したはずの答えを蒸し返します。** 複数ターンのチャットでは、Opus 5.5 は新しいメッセージについて考える際に、以前の答えを見直すことがあります — 短いフォローアップでさえも — その分、後半のターンでレイテンシが増えます。Anthropic の対処は、システムプロンプトの末尾に「答え済みの質問は片付いたものとして扱え」と伝える 2 文を置くことです。長い分析やエージェント作業では、後のステップが以前の誤りを正当に明らかにすることがあるので入れないでください。また、モデルが自分の誤りを自発的に申告しにくくなる可能性にも注意してください。

**チャット用システムプロンプトから「答える前によく考えて」を削除してください。** モデルは自分で深さを決めます。制御するのは effort です。Anthropic がチャット製品で行ったテストでは、その 1 行を削除すると返答の開始が早まり、品質の明確な低下はありませんでした。

**ビジョン向けの足場を再テストしてください。** Opus 5.5 はツールなしでもチャート、図、スクリーンショットをかなり正確に読むため、以前のモデル向けに作ったクロップ／ズームの回避策は、いまや余分な重荷かもしれません。最も密度の高い入力 — とりわけ技術図面 — では依然として役立ちますし、モデルは effort を上げるほど画像ツールを効果的に使います。ツールなしの場合、effort を上げると技術図面は改善しますが、チャートにはほとんど効きません。

## 新しい拒否カテゴリと、フォールバックが再試行しない 1 つ

Opus 5.5 は **Opus 5 より多くの安全性分類器**を走らせます。生物学（新規、Fable 5.1 と同等）と `reasoning_extraction`（新規）が、サイバーセキュリティに加わりました。拒否は **HTTP 200** で届き、`stop_reason: "refusal"` とカテゴリを示す `stop_details` オブジェクトを伴います — つまりステータスコードの確認では捕まえられません。[拒否と安全性](/docs/api/refusals-and-safety)と[サーバーサイドフォールバック](/docs/api/server-side-fallbacks)を参照してください。

罠はこれです。**サーバーサイドのフォールバックは `reasoning_extraction` の拒否を再試行しません。** その拒否はそのままあなたに返されます。他のすべてのカテゴリは `fallbacks: "default"` で推奨フォールバックモデル上で再試行できますが、これだけは自分で処理しなければなりません。しかもこれは、多くの Opus 5 統合が頼ってきたまさにそのプロンプトパターン — *「回答の中で推論を段階を追って書き出してください」* — で発火します。thinking を無効にしてテキストで推論を求めていたなら、そのプロンプトはいまや不要であり、かつ拒否されうるものです。削除して、`display: "summarized"` の thinking ブロックを読んでください。

残り 2 つについて。ソースコードの脆弱性を見つけることは許可されますが、リスクの高いデュアルユースのサイバーセキュリティ作業は許可されません。日常的な健康や教育の質問は生物学分類器の影響を受けません。正当なライフサイエンス業務がブロックされる組織は、Anthropic の Life Sciences Verification Program に申請できます。

## 盗む価値のあるハーネスの技法 2 つ

これらは Anthropic の Opus 5.5 プロンプティングガイドに由来するもので、ベンチマーク表には現れない類のものです。

**マルチエージェントのチームには経過時間のシグナルを与えましょう。** Opus 5.5 は経過時間の情報に細かく注意を払います。ハーネスがリードエージェントに返す各メッセージに `elapsed 340s / 1200s` のような行を追記すると、モデルは予算内に収まるようペースを配分します — たいていはかなり前倒しで終わります。Anthropic による小規模エージェントチームのリサーチタスク評価では、予算を与えられたチームは単一エージェントと同等の回答品質を保ちながら、かなり早く終えました。そのメカニズムは effort を下げるのとは異なります。**effort を下げると作業そのものが減りますが、時間予算は主に、より多くのエージェントを並行して働かせ続けます。** 予算は、実際に費やしてほしい時間よりやや大きめに設定してください。これは助言的なもので — 上限に達してもモデルを止めるものは何もありません — 自前のタイムアウトは維持し、品質も確認してください。時間的な圧力の下では、モデルの検証がやや減るからです。

**貼り付けられた内容にはインジェクション対策のタグを付けましょう。** Opus 5.5 は、これまでのどの Opus モデルよりも間接的なプロンプトインジェクションに強く、その強さは、どのテキストがユーザー自身のものかを印付けることで、ユーザーが自分のメッセージに貼り付けたテキストにも広げられます。貼り付けられた各ブロックを、**アプリケーションが生成した同じ短いランダム ID** を持つ開始タグと終了タグで囲み、各タグをそれぞれ独立した行に置いたうえで、`<pasted_content>` にはユーザーが書いたものではない指示が含まれうる、とシステムプロンプトで伝えてください。ランダム ID こそが要となる部分です — 静的なタグ名は、貼り付けられた内容自体になりすまされうるからです。タグは依然として単なるプレーンテキストで模倣可能なので、これは複数あるガードレールのうちの 1 つです。[プロンプトインジェクション](/docs/security/prompt-injection)を参照してください。

## 移行すべきか

**いますぐ移行を**。エージェント的コーディング、コードレビュー、コンピュータ使用、チャート／図の読み取り、長期のナレッジワークを動かしていて、統合がすでに追記専用かつ thinking 有効であるなら。それこそ Opus 5.5 が作られた用途であり、移行はモデル ID の差し替えと effort のスイープだけで、Anthropic の測定でデフォルト effort でも Opus 5 の high より良いとされる、より安く速いモデルが手に入ります。

**慎重に移行を**。強制 `tool_choice`、無効化した thinking、Claude API か Google Cloud での `computer_20251124`、あるいは会話履歴を編集するループに依存しているなら。いずれも設定変更ではなく、実作業です。

**当面は Opus 5 に留まりましょう**。インシデント対応の最中であるか、今週中に評価スイープを走らせられないか、ルーター内の下流モデルが Opus 5 の thinking ブロックを読む必要があってバインディンググラフをまだ整理できていないなら。Opus 5 はレガシーモデルですが引き続き利用でき、提供終了も公表された日付より前にはなりません — [提供終了情報](/docs/whats-new/deprecations)を確認してください。

**代わりに Fable 5.1 を検討する**のは、**Opus 5.5 を高めの effort で**動かしても評価が届かないときだけです。入力も出力も 2.5 倍の価格で、発表時の表ではすべての行で負けている以上、それはいまや狭い窓です。
