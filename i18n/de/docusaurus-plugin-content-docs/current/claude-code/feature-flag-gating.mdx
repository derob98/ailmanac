Welche Funktionen hinter einem abgerufenen Flag stehen, ändert sich mit fast jedem Claude-Code-Release — Funktionen werden freigeschaltet, sobald ein Rollout abgeschlossen ist. Verstehe die Feature-Liste unten als Gestalt des Problems und prüfe die aktuelle Dokumentation auf die heutige genaue Zusammensetzung.
</VerifyNote>

Zwei Entwickler installieren dieselbe Claude-Code-Version, auf demselben Betriebssystem, im selben Repo. Einer von beiden hat eine Funktion, die der andere nicht hat, und keiner bekommt eine Fehlermeldung. Das ist keine Folklore — es ist das dokumentierte Design. Claude Code schaltet einige Funktionen über **Feature-Flags** frei, **die es beim Start von Anthropic abruft**, und mehrere gewöhnliche, gut gemeinte Konfigurationen schalten diesen Abruf vollständig ab.

Die Folge, die Leute überrascht: **Eine rein lokale Operation kann von einem Netzwerkaufruf abhängen.** Im September 2026 wurde daraus ein Hacker-News-Thread mit 437 Punkten, weil sich zeigte, dass schon das Lesen einer Markdown-Datei von deiner eigenen Festplatte einen solchen brauchte.

## Der Mechanismus

Claude Code wird mit einem **Code-Standardwert für jedes Flag** ausgeliefert und versucht dann, die echten Werte abzurufen. Der Anbieter ist GrowthBook — es gibt eine eigene Umgebungsvariable `DISABLE_GROWTHBOOK`, und das Changelog enthält Einträge wie einen Absturz-Fix für „when a GrowthBook feature evaluates to null“ (v2.1.214).

Vier Eigenschaften dieses Systems erklären fast jeden seltsamen Fall, auf den du stoßen wirst:

## Die vier Wege, auf denen der Abruf ausfällt

Die Dokumentation ist hier eindeutig. Claude Code überspringt den Flag-Abruf in diesen Sitzungen:

- **Du hast eine von vier Umgebungsvariablen gesetzt**: `DISABLE_GROWTHBOOK`, `DISABLE_TELEMETRY`, `DO_NOT_TRACK` oder `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`.
- **Du nutzt einen Drittanbieter**: Amazon Bedrock, Claude Platform on AWS, die Agent Platform von Google Cloud oder Microsoft Foundry — es sei denn, eine Host-Plattform, die Claude Code einbettet, setzt `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST`.
- **Du bist in einer Sitzung über ein Claude-Apps-Gateway.**
- **Es ist deine erste Sitzung nach einer frischen Installation oder einem Upgrade** — die Flags sind noch nicht angekommen. Mehr dazu weiter unten.

Beachte, was die ersten beiden gemeinsam haben: Es sind die Konfigurationen, die ein **sicherheitsbewusstes Unternehmen** wählt. Genau die Gruppe, die am ehesten Telemetrie abschaltet und über Bedrock routet, bekommt stillschweigend den kleinsten Funktionsumfang.

## Die Wertefalle: drei Variablen, drei Parsing-Regeln

Das ist der Teil, der Leute einen Nachmittag kostet. Diese Variablen gehören zur selben Familie, lesen sich, als täten sie dasselbe, und parsen ihre Werte nach **drei verschiedenen Regeln**.

| Variable | Wie sie den Wert liest | `=0` bedeutet also |
| --- | --- | --- |
| `DISABLE_TELEMETRY` | Jeder nicht leere Wert schaltet es ein | **Meldet dich trotzdem ab.** Zum Wiedereinschalten die Variable entfernen |
| `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` | Jeder nicht leere Wert schaltet es ein | **Deaktiviert den Traffic trotzdem.** Zum Wiedereinschalten die Variable entfernen |
| `DISABLE_ERROR_REPORTING` | Jeder nicht leere Wert schaltet es ein | **Meldet dich trotzdem ab.** Zum Wiedereinschalten die Variable entfernen |
| `DISABLE_GROWTHBOOK` | Standard-Boolean — auf `1` oder `true` setzen | Lässt den Abruf **an** |
| `DO_NOT_TRACK` | Standard-Boolean — auf `1` setzen | Lässt die Telemetrie **an** |

Lies diese Tabelle zweimal. `DISABLE_TELEMETRY=0` deaktiviert die Telemetrie. `DO_NOT_TRACK=0` tut es nicht. Beides ist dokumentiert, beabsichtigt und gegensätzlich.

<Callout type="info" items={["Die Dokumentation nennt die Regel direkt: Manche Variablen „read only whether you set them at all, so any non-empty value including 0 turns the behavior on“.", "Um eine davon rückgängig zu machen, musst du die Variable entfernen oder auf einen leeren Wert setzen — 0 oder false zuzuweisen ist kein Ausschalter.", "Am härtesten trifft das in einem Dockerfile oder einer CI-Konfiguration, in der jemand es „abgeschaltet“ hat, indem er 1 in 0 geändert hat."]} />

## Was du tatsächlich verlierst

Bei abgeschaltetem Flag-Abruf entfallen fünfzehn dokumentierte Fähigkeiten. Gruppiert danach, was sie dich kosten:

**Berechtigungen und Start**
- Sitzungen können in den Tarifen Pro, Max und Team standardmäßig nicht im Auto-Modus starten
- Die VS-Code-Erweiterung kann keine Einstellungsdateien für den Start-Berechtigungsmodus lesen
- `/auto-mode-setup` kann keine `autoMode.environment`-Einträge entwerfen

**Alles, was über die lokale Sitzung hinausreicht**
- Remote Control
- Nachrichten an Sitzungen auf anderen Maschinen (Nachrichten auf derselben Maschine funktionieren weiter)
- Das Synchronisieren der für dein claude.ai-Konto aktivierten Skills und Plugins in Terminalsitzungen
- Kommentare zu einem Artefakt lesen oder beantworten
- Das Advisor-Tool

**Befehle und Diagnose**
- `claude import` und der Befehl `/import`
- `/skill-doctor` und sein Bericht im Reiter „Stats“ von `/plugin`

**Stille Verhaltensänderungen — die gefährliche Gruppe**
- MCP: Claude Code schließt MCP-Tools nicht mehr aus, deren Eingabeschema die API ablehnen würde. Es sendet das Schema trotzdem, und die Anfrage scheitert mit einem 400, der das Tool nach seiner Position benennt
- MCP: kein Abtasten von claude.ai-Connector-Servern auf Protokollrevision 2026-07-28, es sei denn, du setzt `MCP_PROTOCOL_NEGOTIATION=auto`
- Große Einfügungen werden nicht mehr als eingefügter, sondern als getippter Text behandelt — der Inhalt hinter einem `[Pasted text #N]`-Platzhalter erreicht Claude ohne Markierung
- Unter Windows mit installiertem Git Bash bekommen claude.ai- und Console-Konten das PowerShell-Tool nicht standardmäßig; setze `CLAUDE_CODE_USE_POWERSHELL_TOOL=1`
- Von Claude entworfenes Feedback ist aus

Die letzte Gruppe ist die, die du verinnerlichen solltest. Ein fehlender Slash-Befehl macht sich bemerkbar. Ein 400-Fehler, der ein Tool **nach seiner Position im Array** benennt, sieht nicht nach einer Telemetrie-Einstellung aus, und du debuggst deinen MCP-Server eine Stunde lang, bevor du auf die Idee kommst, eine Umgebungsvariable zu prüfen.

### Der Wirkungsradius hat Präzedenzfälle

Flag- und Telemetrie-Einstellungen sind an Stellen durchgesickert, die niemand erwartet hätte. Zwei behobene, aber lehrreiche Beispiele aus dem Changelog:

- **v2.1.108** behob, dass Abonnenten, die `DISABLE_TELEMETRY` gesetzt hatten, auf eine **Prompt-Cache-TTL von 5 Minuten statt 1 Stunde** zurückfielen. Eine Datenschutzvariable kostete bei jeder langen Sitzung unbemerkt Geld — ein 12-mal kürzeres Cache-Fenster.
- **v2.1.105** behob, dass `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, in den Einstellungen *eines* Projekts gesetzt, die Nutzungsmetriken dauerhaft für **alle Projekte auf der Maschine** abschaltete.

Beides ist behoben. Beides zeigt die Gestalt des Risikos: Diese Schalter greifen durch Subsysteme hindurch, die scheinbar nichts miteinander zu tun haben.

## Die erste Sitzung nach einer Installation oder einem Upgrade

Das verdient eine eigene Überschrift, weil es den klassischen nicht reproduzierbaren Fehlerbericht hervorbringt.

In deiner ersten Sitzung nach der Installation von Claude Code — oder nach einem Upgrade auf eine Version, die eine Funktion hinzufügt — **kann eine flaggebundene Funktion schlicht fehlen**, und die Sitzung kann im Manual-Modus starten, in einem Tarif, der sonst im Auto-Modus startet. Claude Code ruft die Flags während dieser Sitzung ab, sodass beim nächsten Mal beides vorhanden ist.

Zwei Folgerungen:

- **Es behebt sich von selbst**, und genau deshalb ist es schwer zu melden. Bis jemand nachsieht, hat die zweite Sitzung die Flags.
- **In flüchtigen Umgebungen behebt es sich nie.** Ein CI-Runner, ein frischer Container oder jedes Setup mit einem Wegwerf-Home-Verzeichnis befindet sich jedes Mal in seiner ersten Sitzung.

Die Dokumentation nennt eine Abhilfe: Nach einer frischen Installation kann eine nicht interaktive Sitzung wie `claude -p`, das Agent SDK oder die VS-Code-Erweiterung die Flags trotzdem aufnehmen, bevor sie den Start-Berechtigungsmodus wählt.

Die Lehre geht über diesen einen Fehler hinaus. Frage bei jeder neuen Claude-Code-Funktion: *Ist sie gegated?* Wenn ja, werden deine Telemetrie-Haltung, dein Anbieter und wie kürzlich du installiert hast alle zu Eingaben dafür, ob sie funktioniert.

## In zwei Minuten diagnostizieren

Du musst nicht raten. Drei Prüfungen, die günstigste zuerst.

**1. Frage, ob die Einstellung überhaupt existiert.** Wenn die AGENTS.md-Unterstützung nicht verfügbar ist, erscheint die Zeile **Project instructions** im `/config`-Panel gar nicht. Eine fehlende Einstellung ist selbst die Diagnose — die Funktion ist nicht aus, sie ist nicht vorhanden.

**2. Sieh nach, was dir eine interaktive Sitzung sagt.** Wenn es funktioniert, gibt Claude Code in der Unterhaltung eine Zeile aus wie `no CLAUDE.md found; AGENTS.md loaded: /home/you/repo/AGENTS.md`. Keine Zeile, kein Laden.

**3. Führe einen Canary aus.** Die Technik, die den ursprünglichen Bericht geknackt hat: Schreibe ein Wort in die Datei, das sonst nirgends vorkommt, und frage dann in einer sauberen, nicht interaktiven Sitzung danach. Kommt das Wort zurück, hat die Datei das Modell erreicht. Das funktioniert für jede Anweisungsdatei, auf jeder Version.

<PromptCard title="Canary-Test — wurde die Anweisungsdatei tatsächlich geladen?">{`mkdir -p /tmp/canary && cd /tmp/canary
echo 'The project codeword is PERIWINKLE.' > AGENTS.md
claude -p 'What is the project codeword? Answer with one word.'`}</PromptCard>

Führe ihn einmal mit deiner normalen Umgebung aus, dann einmal mit gelöschten Datenschutzvariablen, und vergleiche. Beachte die Zuweisung mit leerem String — denk daran, dass `DISABLE_TELEMETRY=0` sie **nicht** löschen würde.

<PromptCard title="Derselbe Test mit erlaubtem Flag-Abruf — beachte die leeren Werte, keine Nullen">{`cd /tmp/canary
env DISABLE_TELEMETRY= CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC= DISABLE_GROWTHBOOK=false \\
  claude -p 'What is the project codeword? Answer with one word.'`}</PromptCard>

**4. Wenn du Details brauchst, schalte das Debug-Logging ein.** Starte mit `--debug` oder `/debug`, und die Logs landen in `~/.claude/debug/<session-id>.txt`. Ein Haken: Die Umgebungsvariable `DEBUG` akzeptiert nur die Wahrheitswerte `1`, `true`, `yes` und `on` — ein Namespace-Muster wie `DEBUG=express:*`, das von einem anderen Tool übrig ist, schaltet es nicht ein.

## Verhalten festnageln, statt sich auf ein Flag zu verlassen

Die dauerhafte Lösung ist, nicht mehr vom Gate abzuhängen. Zwei Muster.

**Die Einstellung explizit festnageln.** Bei Anweisungsdateien kann der Wert **Project instructions** in einer Einstellungsdatei unter der ID des eingebauten Plugins stehen, statt dem Standard überlassen zu bleiben. Eine wichtige Grenze: Claude Code **ignoriert diesen Schlüssel in Projekt- und lokalen Einstellungsdateien** — es liest ihn nur aus `~/.claude/settings.json`, einer `--settings`-Datei oder verwalteten Einstellungen. Ihn in die `.claude/settings.json` deines Repos zu legen, bewirkt nichts.

<PromptCard title="CLAUDE.md und AGENTS.md gemeinsam laden — nur Benutzer- oder verwaltete Einstellungen">{`{
  "pluginConfigs": {
    "agents-md@builtin": {
      "options": { "instructionFiles": "claude-md-and-agents-md" }
    }
  }
}`}</PromptCard>

**Einen Pfad nutzen, der nie gegated war.** Eine `CLAUDE.md`, die `AGENTS.md` importiert, hat auf jeder Version, bei jedem Anbieter und mit abgeschalteter Telemetrie funktioniert — weil es gewöhnliche `@path`-Import-Expansion ist, kein geflaggter Codepfad. Das ist die Empfehlung, die die Dokumentation selbst für Bedrock-, Vertex- und Foundry-Sitzungen gibt.

<PromptCard title="Die einzeilige CLAUDE.md, die nie ein Flag brauchte">{`@AGENTS.md`}</PromptCard>

Eine Feinheit, wenn du diesen Weg gehst: Eine `AGENTS.md`, die über die *Einstellung* gelesen wird, verhält sich etwas anders als eine, die per *Import* eingezogen wird. `InstructionsLoaded`-Hooks **feuern nicht** für den einstellungsbasierten Pfad, wohl aber wie gewohnt für eine `AGENTS.md`, die eine `CLAUDE.md` importiert oder auf die sie per Symlink verweist. Wenn du Hooks auf dem Laden von Anweisungen hast, ist der Import der sicherere Weg.
