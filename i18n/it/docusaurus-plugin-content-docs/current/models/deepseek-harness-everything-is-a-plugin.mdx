**DeepSeek Harness** — il comando è `dsh` — è l'harness per agenti open source di
DeepSeek. È comparso su GitHub il 13 agosto 2026, a oggi conta 242.626 stelle e
29.081 fork, è con licenza MIT ed è scritto in TypeScript. Il 1° ottobre 2026
DeepSeek ha aggiunto installer desktop firmati, ed è ciò che lo ha riportato
sulla prima pagina di Hacker News.

Il suo slogan in una riga è la descrizione del repository: *"Everything is a
Plugin."* Quella frase compare nel README di praticamente ogni framework per
agenti mai pubblicato, e quasi sempre significa «abbiamo una cartella dei
plugin». Qui significa qualcosa di molto più forte e più strano, enunciato senza
mezzi termini in `docs/architecture.md`: l'adattatore del modello, il registro
degli strumenti, il log di sessione **e il loop dell'agente stesso** sono
plugin, «così ciascuno è sostituibile da configurazione». Puoi eliminare il loop
dell'agente da un file YAML e inserire il tuo senza fare alcun fork.

Questo design ha conseguenze — alcune eccellenti, altre costose. Questa pagina
parla di quelle che non si leggono sulla landing page.

## «Tutto è un plugin» è un'affermazione portante

Sotto `dsh` c'è **Cordis**, un framework di plugin incluso nel repository
(`vendor/`) e descritto in un paper su arXiv che il progetto cita — *A
Programming Paradigm for Spatiotemporal Composability*, arXiv:2608.25512,
inviato il 26 agosto 2026, da autori della Peking University e di DeepSeek-AI.
Le due idee del paper corrispondono direttamente al comportamento dell'harness a
runtime:

- **Componibilità temporale** — gli effetti collaterali di un componente possono
  essere annullati *completamente* quando lo si rimuove. Nell'harness questo è
  `ctx.effect()`: sezioni di prompt, schemi degli strumenti, adattatori di
  modello, provider e listener sono tutti installati come effetti reversibili,
  quindi scaricare un plugin ne annulla le registrazioni in ordine, senza
  lasciare orfani.
- **Componibilità spaziale** — le dipendenze si risolvono in modo reattivo. Un
  plugin dichiara i servizi di cui ha bisogno tramite `inject`, e Cordis
  semplicemente non lo avvia finché quei servizi non esistono. Non c'è una
  sequenza di boot da mantenere; l'ordine di caricamento è una conseguenza dei
  requisiti dichiarati.

Un **servizio** rivendica una chiave stabile sul contesto condiviso. I nomi sono
l'architettura:

| Chiave del servizio | Chi la possiede |
|---|---|
| `ctx.llm` | il registro degli adattatori LLM — il punto di giunzione del modello |
| `ctx.tools` | il registro degli strumenti e la sua pipeline di esecuzione con ambito |
| `ctx.agentLoop` | il driver predefinito del loop dell'agente |
| `ctx.agents` | il registro degli agenti attivi |
| `ctx.sessions` | il log `SessionEvent` append-only |
| `ctx.systemPrompt` | l'assemblaggio del prompt di sistema |
| `ctx.fs` | l'accesso al filesystem |
| `ctx.subprocess` | l'esecuzione dei sottoprocessi |
| `ctx.sandbox` | il confinamento dei sottoprocessi |
| `ctx.subagents` | la delega ai sottoagenti |
| `ctx.ptcRuntime` | l'esecuzione dei programmi per `run_code` |
| `ctx.credentials` | il punto di giunzione delle credenziali |

Il repository le chiama **capability seam** (punti di giunzione delle
capacità), e divide ciascuna in tre ruoli: il pacchetto che *dichiara* il
servizio, i pacchetti che lo *implementano* e i pacchetti che lo *consumano*.
`ctx.sandbox` è dichiarato da `packages/sandbox/sandbox`, implementato da
`sandbox-local` e `sandbox-windows-acl`, consumato da `tool-bash` e dal runtime
PTC. Sostituisci l'implementazione e ogni consumatore la segue, senza modificare
i consumatori.

La comunicazione tra plugin avviene tramite eventi tipizzati con **cinque
modalità di dispatch dichiarate**, e la modalità fa parte del contratto pubblico
di un evento:

| Modalità | Attesa | Ordine | Restituisce un valore |
|---|---|---|---|
| `emit` | no | ordine di registrazione | no |
| `waterfall` | no | ordine di registrazione | sì |
| `parallel` | sì | tutti insieme | no |
| `serial` | sì | ordine di registrazione | sì |
| `bail` | no | ordine di registrazione, si ferma al primo bail | sì |

`waterfall` è la più interessante: è un middleware «around». Un listener
riceve `(...args, next)`, chiama `next()` per passare lungo la catena un
risultato eventualmente avvolto, oppure ritorna senza chiamare `next()` per
interrompere la catena. Per gli eventi a decisione singola — «questo strumento
può essere eseguito?» — l'interruzione *è* il design: un listener di policy che
possiede la decisione ritorna senza delegare, mentre un listener che si limita
ad annotare deve delegare. Se hai scritto un hook di Claude Code che restituisce
una decisione di blocco, conosci già questa forma; la differenza è che qui è il
meccanismo di estensione nativo anziché una chiamata a una shell esterna.

Il loop dell'agente esegue **turni** (zero o più passi) e **passi** (una
richiesta al modello più le sue chiamate agli strumenti), e la sequenza di
estensione pubblicata è `agent/pre-step → agent/request → llm/stream → tools/* →
step/end`. Quelli sono i punti di aggancio. Non applichi patch al loop: lo
ascolti.

## Tre cose che contano se usi già Claude Code

### 1. Eseguirà il tuo `hooks.json` esistente di Claude Code

Questo è il fatto su `dsh` meno riportato in assoluto. `packages/hooks` include
tre pacchetti: `hook-protocol` (il motore condiviso), **`hooks-claude-code`** e
**`hooks-codex`**. Punta il bridge di Claude Code a un `hooks.json` esistente e
i tuoi hook girano dentro `dsh` quando le sessioni iniziano, arrivano i prompt,
gli strumenti vengono eseguiti e le esecuzioni terminano. Il README del gruppo è
esplicito su ciò che possono fare: bloccare prompt o chiamate agli strumenti
**con messaggi visibili al modello**, aggiungere contesto alla conversazione o
richiedere che l'esecuzione prosegua.

Il limite è altrettanto esplicito, ed è la cosa da controllare prima di
pianificare una migrazione: *ogni integrazione supporta solo il sottoinsieme di
hook di tipo command documentato dallo strumento di origine.* Quindi i tuoi hook
di tipo `command` vengono portati. Tutto ciò che dipende da comportamenti di
Claude Code al di fuori di quel sottoinsieme, no. Se hai un livello di hook di
cui ti fidi — vedi [Hook di Claude Code](/docs/claude-code/hooks) — questa è una
vera strada per «portarti dietro le tue protezioni», non una riscrittura.

### 2. Puoi puntarlo su Claude — ma non con il tuo abbonamento

L'elenco dei provider incluso nel catalogo installato comprende `anthropic` e
`openai` per nome. Per tutto ciò che non è nel catalogo — un relay, un gateway
aziendale, un server self-hosted — il modulo del provider personalizzato chiede
un Provider ID, un URL di base, una credenziale e un **protocollo API**, e ne
offre esattamente tre: OpenAI Chat Completions, OpenAI Responses e Anthropic
Messages. In `cordis.patch.yml` sono memorizzati come `openai-completions`,
`openai-responses` e `anthropic-messages`.

Due conseguenze su cui si inciampa:

- **Un provider parla un solo protocollo.** Un gateway che serve sia la forma
  OpenAI sia quella Anthropic richiede *due* voci di provider, non una.
- **L'accesso OAuth non è supportato.** La guida ai provider lo dice
  direttamente, usando Codex come esempio: i provider che si autenticano con
  OAuth «are not supported here yet». Significa fatturazione a chiave API, non un
  posto che già paghi. Se speravi di far funzionare `dsh` con un abbonamento
  esistente a un assistente, metti in conto token a consumo — i calcoli sono in
  [quanto costa l'AI tra i vari provider](/docs/models/what-ai-costs-across-providers).

C'è anche un pulsante di scoperta dei modelli che chiede al tuo endpoint quali
modelli serve. Utile, con un'avvertenza da interiorizzare: un provider
**integrato** viene sempre servito dal catalogo installato, anche quando il suo
URL di base punta a un gateway. Quindi, se vuoi vedere che cosa serve davvero un
gateway, devi aggiungerlo come provider *personalizzato*. Altrimenti stai
rileggendo a te stesso l'elenco incluso da DeepSeek.

### 3. `run_code` è codemode, ed è un runtime di prima classe

`packages/ptc-runtime` è la famiglia di capacità dietro ciò che il registro
degli strumenti presenta al modello come `run_code`. Il contratto: il modello
scrive **un solo programma** che chiama funzioni fornite dall'host come normali
chiamate async, e tornano indietro solo l'output stampato e il valore di
ritorno del programma. Non i risultati intermedi degli strumenti. Non venti
andate e ritorno.

I dettagli:

- Il backend TypeScript esegue ogni programma in un **nuovo processo Node
  gestito**, sotto la policy di sandbox risolta.
- **Ogni esecuzione parte senza stato dai programmi precedenti.** Non c'è una
  sessione REPL implicita su cui contare; porta lo stato tramite file o valore
  di ritorno.
- I fallimenti tornano come *risultati*, non come eccezioni, così il chiamante
  può diagnosticarli o passarli al modello.
- Esiste un **backend Python** sperimentale, che gestisce un protocollo wire su
  fd-3 tra l'host Node e un sottoprocesso CPython, per quando ti serve davvero
  CPython.

Se questo schema ti è nuovo, la spiegazione più chiara del *perché* fa risparmiare
così tanto contesto è in [Pi 1.0 e il trucco del codemode](/docs/models/pi-1-0-minimal-agent-harness):
i risultati degli strumenti che non entrano mai nella trascrizione non possono
gonfiarla. La stessa logica vale qui. La differenza è che in `dsh` il runtime
dei programmi è un punto di giunzione sostituibile (`ctx.ptcRuntime`) anziché una
scelta di sandbox fissa.

## La sandbox: tre modalità, tre primitive del kernel, un'avvertenza onesta

Le tre modalità ti sembreranno familiari se hai configurato Codex:

| Modalità | Che cosa può fare un sottoprocesso ai file |
|---|---|
| `read-only` | solo lettura |
| `workspace-write` | scrittura solo sotto il workspace della sessione |
| `danger-full-access` | senza restrizioni |

Più interessante è la tabella dei backend, perché ti dice che cosa applica
davvero la policy sulla tua macchina:

- **Linux** — bwrap, poi Landlock come gradino di ripiego.
- **macOS** — Seatbelt.
- **Windows** — un token ristretto, con `sandbox-windows-acl` come backend di
  restrizione delle scritture: i figli confinati possono scrivere solo nel
  workspace e in una directory temporanea privata.

Una chiamata negata può essere ritentata tramite una **escalation una tantum
approvata dall'utente**, quindi la policy è un confine «chiedi e procedi» e non
un muro invalicabile.

E poi l'avvertenza, che il README del pacchetto enuncia da solo e che dovresti
citare a chiunque ti dica che questo è «in sandbox»: **il confinamento è solo
same-world.** Condivide il kernel dell'host e il filesystem dell'host. Un
isolamento reale — container, microVM, esecutori remoti — qui non si registra
affatto; sostituisce intere capacità.

`SAFETY.md` è insolitamente schietto per un repository da 242k stelle, e vale la
pena leggerlo prima della prima esecuzione anziché dopo. Dice che l'harness può
eseguire codice generato dal modello, caricare plugin di terze parti,
raggiungere la rete e toccare processi, credenziali e file; che **non c'è alcuna
garanzia intrinseca** che sandbox, richieste di approvazione e controlli dei
permessi impediscano danni a qualsiasi cosa raggiungibile; e che il software
«must not be treated as secure or production-ready». Le sue raccomandazioni sono
quelle noiose e giuste: VM o container usa e getta, backup di tutto ciò che sta
dentro l'ambito del progetto e nessuna credenziale sensibile a meno che tu non
accetti il rischio. Lo stesso ragionamento vale per qualsiasi harness che esegui
in locale — vedi
[proteggere gli agenti locali e ibridi](/docs/models/securing-local-and-hybrid-agents)
e [sandbox e mascheramento delle credenziali](/docs/claude-code/sandbox-credential-masking).

C'è anche un piccolo gruppo di **guard** da conoscere: `timeout-policy` e
`repeat-tool-reminder` — quest'ultimo è un promemoria per la modalità di
fallimento in cui un modello chiama lo stesso strumento in loop.

## Il log di sessione è il prodotto

`dsh` persiste le sessioni come file JSONL versionato —
`session.vN.jsonl[.zstd]` — con catene di migrazione tra le versioni, tramite un
punto di giunzione `ctx.sessionPersistence` la cui implementazione inclusa è
`session-persistence-jsonl`. Gli eventi committati comprendono `turn/start`,
`step/start`, `user/message`, `assistant/message`, `tool/result` e `turn/end`.

L'invariante alla base è la parte da rubare anche se non userai mai `dsh`:
**«model-visible means logged»** (ciò che il modello vede viene registrato).
Ogni input che il modello ha visto deve essere ricostruibile dal log. Gli eventi
live esistono separatamente, per pilotare la UI in tempo reale; non sono
esplicitamente la fonte di verità.

Questa singola regola è ciò che rende possibili i pacchetti circostanti:

- `session-query-sqlite` — interrogare le sessioni da SQLite invece di fare grep
  sul JSONL.
- `dsh-session-projection` con `ctx.sessionProjections` — ripiegare lo stato
  della sessione in modo incrementale invece di rigiocarlo da zero.
- `llm-replay` più `token-meter` («replay token measurement») — rigiocare una
  sessione registrata e *misurarne* il costo in token, che è il modo in cui
  confronti due modifiche a prompt o modello su input identici anziché a
  sensazione.
- `compaction-tool-result-pruner` — descritto come potatura dei risultati degli
  strumenti **senza modello**, cioè ridurre la trascrizione senza pagare un
  modello per riassumerla. Confrontalo con l'approccio di Claude in
  [compattazione del contesto](/docs/api/compaction).

Se hai mai provato a fare debug di un'esecuzione di un agente scoprendo che i
tuoi log registravano la *UI renderizzata* anziché i byte ricevuti dal modello,
sai già perché questa invariante vale più della maggior parte delle funzionalità.

## MCP qui è un plugin per server, non un registro globale

`dsh` parla MCP sia su stdio sia su Streamable HTTP, usando l'SDK ufficiale per
negoziazione, scoperta, validazione e cancellazione. Le scelte di design sono
abbastanza insolite da elencarle:

- **I server sono opt-in, una voce di plugin per server.** Configuri una voce
  `@deepseek-ai/dsh-mcp-client` per server, nell'ambito Cordis in cui vuoi che
  sia visibile. Deliberatamente **non esiste un servizio condiviso `ctx.mcp`**:
  il client è un plugin di connessione e un *consumatore* del registro degli
  strumenti.
- **Nessun server configurato significa nessuna tassa MCP.** Un chiamante senza
  alcun server configurato visibile non riceve né testo di prompt MCP né
  strumenti MCP, in modalità nativa o PTC. Zero byte, non «una piccola
  sezione». Conta più di quanto sembri — vedi
  [il costo reale degli strumenti MCP](/docs/claude-code/mcp-token-cost).
- **I nomi pubblici degli strumenti includono il nome del server**, quindi
  strumenti con lo stesso nome di due server restano distinti. Un `serverName`
  deve essere unico all'interno del suo ambito di registrazione, ma ambiti di
  agente separati possono riusarlo.
- **Le istruzioni del server entrano nel prompt di sistema registrato**, entro il
  limite di `maxInstructionBytes` del client. Un server prolisso non può annettersi
  di nascosto il tuo prompt — ma nota che questo è anche il canale attraverso cui
  un server malevolo parla al tuo modello. È la superficie d'attacco descritta in
  [tool poisoning e rug pull di MCP](/docs/security/mcp-tool-poisoning-and-rug-pulls).
- **Un aggiornamento fallito dell'elenco degli strumenti mantiene la generazione
  precedente** anziché far sparire i tuoi strumenti a metà sessione, e non esiste
  alcuna impostazione di prodotto che forzi una revisione del protocollo — la
  negoziazione segue le revisioni supportate dall'SDK.

## Cinque trappole che ti costeranno un'ora

1. **Un override di configurazione Cordis sostituisce l'intera configurazione
   della voce.** La guida ai provider lo scrive chiaramente: quando modifichi un
   override esistente, devi preservare tu stesso gli altri campi e gli altri
   provider. Modifica un provider con disattenzione e hai cancellato tutti gli
   altri. È l'errore singolo più costoso possibile in `cordis.patch.yml`.
2. **Un Provider ID è permanente.** Richieste, sessioni salvate, modelli
   predefiniti e riferimenti alle credenziali dipendono tutti da esso. Rinominarlo
   significa aggiungere un nuovo provider ed eliminare il vecchio. Nome
   visualizzato, URL di base, protocollo, credenziale ed elenco dei modelli
   restano modificabili.
3. **`--dump-config-schema` importa codice dei plugin.** A differenza degli altri
   flag di dump, carica gli schemi dei plugin dichiarati dall'albero composto per
   stampare JSON Schema — quindi puntarlo su plugin non fidati esegue il loro
   codice in fase di import. La guida di riferimento della CLI ha una nota di
   sicurezza dedicata. Trattalo come
   [la revisione di codice di terze parti](/docs/security/reviewing-third-party-code),
   non come `--help`.
4. **La compatibilità delle versioni dei plugin è imposta, e la via di fuga è
   esplicita.** L'installazione e l'avvio del profilo controllano gli intervalli
   di peer DSH dichiarati rispetto alla versione del runtime di `dsh --version`;
   un plugin incompatibile richiede un'esenzione riconosciuta a versione esatta
   (`allow-version`, `revoke-version`). Buona igiene, sorprendente la prima volta
   che un plugin si rifiuta di caricarsi.
5. **Una sessione che ha già inviato una richiesta mantiene il modello registrato
   nel proprio log.** Cambiare il modello predefinito non sposta retroattivamente
   una sessione attiva, e se un default salvato nomina un provider eliminato il
   composer blocca l'input finché non ne scegli un altro. Entrambi sono
   comportamenti corretti; entrambi sembrano bug all'una di notte.

## Dove si colloca

Se stai scegliendo un harness anziché studiarne uno, il riassunto onesto è:
`dsh` è l'harness open source più interessante dal punto di vista
*architetturale* oggi in circolazione e il meno pronto a diventare portante. Lo
dice il suo stesso file di sicurezza. Il modello a plugin è davvero più forte di
quello dei concorrenti — avere `ctx.agentLoop` sostituibile non è una cosa che
si può fare nella maggior parte degli harness a nessun prezzo — e i bridge degli
hook fanno sì che adottarlo non sia una scommessa tutto o niente.

Dall'altra parte: un tag `latest` che è una release candidate, nessun audit di
sicurezza, modifiche incompatibili annunciate e una storia dei provider che
presuppone chiavi API. Per un confronto sull'intero panorama, vedi
[CLI di coding agent a confronto](/docs/models/coding-agent-clis-compared) e
[coding agent locali](/docs/models/local-coding-agents). Per i modelli con cui lo
piloteresti più plausibilmente, vedi
[DeepSeek-V4.1-Flash](/docs/models/deepseek-v4-1-flash-open-weight-1m).
