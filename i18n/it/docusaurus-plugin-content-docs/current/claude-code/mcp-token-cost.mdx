Su Hacker News e su X ricorre una discussione: *perché bruciare decine di migliaia di token per una sola operazione MCP quando la stessa cosa via CLI ne costa un paio di centinaia?* Sembra un attacco a MCP. Non lo è. Chi protesta più forte è proprio chi ama gli agenti — ha solo incontrato il conto. Questa pagina è la guida pratica a quel conto: dove vanno davvero i token, i due costi che quasi nessuno distingue e le tre soluzioni che trasformano un flusso da 150.000 token in uno da 2.000.

## Due costi, non uno

Quando colleghi un server MCP, il client gli chiede `tools/list` e riceve indietro **ogni strumento con il suo schema JSON completo**. L'intero blocco viene iniettato nel contesto del modello. La maggior parte delle persone ferma qui il proprio conto mentale. Ma le tasse sono due, distinte, e la seconda di solito è la più pesante.

**Costo 1 — Definizioni degli strumenti.** Nome, descrizione e schema dei parametri di ogni strumento collegato stanno nel contesto. La formulazione di Anthropic: *«Nei casi in cui gli agenti sono collegati a migliaia di strumenti, dovranno elaborare centinaia di migliaia di token prima di leggere una richiesta.»* Un singolo server aziendale può pubblicare da decine a centinaia di strumenti; analisi di terze parti stimano che un server da 400 strumenti pesi circa 400.000 token di soli schemi — il doppio di una finestra da 200k, e ancora il 40% di una da 1M, spesi prima della prima richiesta. (Dimensioni delle finestre per modello: [Modelli e prezzi](/docs/whats-new/models-and-pricing).)

**Costo 2 — Risultati intermedi.** Quando il modello chiama direttamente uno strumento, **ogni risultato rifluisce attraverso il contesto del modello**, anche le parti che non volevi che leggesse. L'esempio di Anthropic: estrai da uno strumento la trascrizione di una riunione di due ore e passala a un altro, e la trascrizione completa attraversa il modello *due volte* — potenzialmente ~50.000 token — solo per produrre un riassunto di una riga.

<Callout type="warning" items={["Il Costo 1 si paga A OGNI turno finché non interviene il prompt caching — gli schemi vengono rinviati a ogni richiesta della conversazione, non caricati una volta sola. Un grande catalogo di strumenti è una tassa sull'intera sessione, non una commissione una tantum. Questo è il costo di uno strumento la cui definizione è CARICATA; rimandarne il caricamento (vedi sotto) è ciò che lo toglie dal conto per turno.", "Il Costo 2 cresce con i tuoi DATI, non con il numero di strumenti. Dieci strumenti minuscoli possono costare meno di uno strumento che restituisce un blob gigantesco."]} />

Tutte e tre le righe sono cifre pubblicate da Anthropic. La parte sorprendente non è il costo — è l'**accuratezza**: con il Tool Search Tool, l'accuratezza nella scelta degli strumenti è *salita* (Opus 4.5 è passato dal 79,5% all'88,1%; Opus 4 dal 49% al 74%). Meno strumenti che affollano il contesto significa che il modello sceglie quello giusto più spesso. Qui costo e qualità vanno nella stessa direzione, il che è raro.

## Soluzione 1 — Carica gli schemi degli strumenti su richiesta

Invece di iniettare tutti gli schemi in anticipo, contrassegnali con `defer_loading: true`. Claude vede allora solo un indice leggero; quando gli serve GitHub, chiama il **Tool Search Tool**, che restituisce *solo* gli schemi GitHub corrispondenti — non i 50+ strumenti di tutti gli altri server. Anthropic riporta che questo preserva ~191.300 token di contesto contro i ~122.800 con tutto precaricato.

### In Claude Code è già attiva

Stai già osservando questo schema se usi Claude Code con server MCP. **La ricerca degli strumenti è attiva per impostazione predefinita**: all'avvio della sessione si caricano solo i *nomi* degli strumenti e le istruzioni dei server, e Claude recupera lo schema completo tramite una chiamata `ToolSearch` quando un compito lo richiede. Aggiungere un altro server ti costa quindi i nomi dei suoi strumenti, non i suoi schemi — Claude Code non fissa alcun tetto di strumenti per server e dice che il limite pratico è il budget della tua finestra di contesto.

Vale la pena correggere un'affermazione molto ripetuta, perché è giusta solo a metà. La soglia del «~10% della finestra di contesto» è reale, ma **non** è il trigger predefinito — è una modalità opt-in della variabile d'ambiente `ENABLE_TOOL_SEARCH`:

| `ENABLE_TOOL_SEARCH` | Comportamento |
| --- | --- |
| *(non impostata)* — il predefinito | Ogni strumento MCP rimandato, caricato su richiesta |
| `true` | Come non impostata |
| `auto` | Modalità a soglia. Gli strumenti rimandabili si caricano **in anticipo** finché le loro definizioni totalizzano meno del 10% della finestra di contesto; al 10% o oltre, la ricerca degli strumenti si attiva |
| `auto:N` | Modalità a soglia con una percentuale a tua scelta (`N` va da 0 a 100), ad esempio `auto:5` |
| `false` | Ogni strumento MCP caricato in anticipo, nessun rinvio |

Quindi, se contavi sul caricamento anticipato sotto il 10%, hai il predefinito al contrario — non si carica nulla in anticipo a meno che tu non chieda `auto`. E `auto` è **persistente**: una volta che il totale supera la soglia e la ricerca degli strumenti si attiva, quegli strumenti possono restare rimandati anche dopo che il totale è tornato sotto di essa.

Anche negare lo strumento ToolSearch nei permessi fa caricare tutto in anticipo.", "Esiste un modello minimo: Claude Code usa la ricerca degli strumenti su Claude Opus 4, Sonnet 4, Haiku 4.5 e successivi. Sui modelli precedenti tutto si carica in anticipo e ENABLE_TOOL_SEARCH=true NON lo scavalca. Sull'Agent Platform di Google Cloud la soglia è più alta — Opus 4.5, Sonnet 4.5, Haiku 4.5 e successivi."]} />

Se scrivi server MCP, il rinvio cambia anche il tuo budget per le descrizioni, in modo asimmetrico: uno strumento caricato **in anticipo** viene troncato a 4.096 caratteri (lo stesso tetto delle istruzioni del server), uno caricato **tramite la ricerca degli strumenti** a 16.384. Ma la ricerca stessa confronta solo il limite più corto, quindi le parole che Claude cercherebbe devono comunque stare all'inizio.

## Soluzione 2 — Tieni i risultati fuori dal contesto con l'esecuzione di codice

La soluzione più profonda punta al Costo 2. Invece di far chiamare al modello gli strumenti uno alla volta, con ogni risultato che lo attraversa, il modello **scrive codice** che chiama gli strumenti, e i dati intermedi restano nell'ambiente di esecuzione. Anthropic espone i server MCP come un **albero di file di strumenti** che l'agente esplora come un filesystem, caricando solo le definizioni che gli servono — e *«i risultati intermedi restano per impostazione predefinita nell'ambiente di esecuzione… l'agente vede solo ciò che registri o restituisci esplicitamente.»*

Questa singola scelta di progetto è ciò che riduce il flusso Drive→Salesforce da 150.000 a 2.000 token: i record si muovono attraverso il codice e al modello torna solo il conteggio finale. Sulla Developer Platform la stessa idea arriva come **Programmatic Tool Calling** — Claude scrive Python che orchestra più strumenti e filtra gli output prima che raggiungano il suo contesto.

<Callout type="tip" items={["Regola pratica: se uno strumento RESTITUISCE qualcosa di grosso (una trascrizione, un dump di query, un file), vuoi l'esecuzione di codice, così il blob viene elaborato fuori dal contesto. Se uno strumento si limita a FARE qualcosa di piccolo (creare una issue, inviare una riga), una chiamata diretta va bene."]} />

## Soluzione 3 — Sapere quando una chiamata CLI vince e basta

A volte la risposta giusta non è una configurazione MCP migliore — è nessun MCP. La discussione su HN/X ha un punto fondato: un comando di shell come `gh pr list` o `psql -c '…'` costa un paio di centinaia di token di andata e ritorno, mentre il percorso MCP equivalente paga gli schemi più un risultato strutturato. Se l'agente ha già un terminale e la CLI esiste, quella è spesso la strada più snella.

<PromptCard title="Preferisci la CLI quando lo strumento è già una CLI">
{`# Instead of connecting a GitHub MCP server for read-only work,
# let the agent use the gh CLI it already has:
gh pr list --state open --json number,title,author

# ~200 tokens of command + compact output, no schema tax,
# no server to keep connected across the session.`}
</PromptCard>

MCP si guadagna il suo overhead quando ti serve una capacità **tipizzata, con permessi, valida su più superfici** — un database con un ruolo di sola lettura, un browser da pilotare, un'API SaaS con OAuth — oppure quando gli stessi strumenti sono riusati su molti turni, così la cache ammortizza il costo degli schemi. Usa una CLI quando la capacità è occasionale, già scriptabile e restituisce qualcosa di piccolo. Nessuna delle due è «migliore»: sono punti diversi di una curva dei costi.
