<LevelBadge level="advanced" />

Per tutto il suo primo anno MCP è stato un **protocollo testuale**: una tool call restituiva JSON o Markdown e il client renderizzava come voleva. **MCP Apps** — la prima estensione ufficiale, finalizzata il **26 gennaio 2026** e integrata nella **[core spec del 2026-07-28](/docs/api/mcp-2026-07-28-stateless)** — aggiunge un canale UI. Un server può ora inviare un blocco di HTML, il client lo renderizza in un **iframe sandboxed** e l'iframe risponde tramite **JSON-RPC 2.0 su `postMessage`**. Ogni scrittura continua a passare per lo stesso audit path di qualsiasi altra tool call. Pensa a un report interattivo + conferma-prima-di-eseguire, non a "esegui una webapp completa dentro Claude."

Identificatore dell'estensione `io.modelcontextprotocol/ui`; MIME type `text/html;profile=mcp-app`; schema URI `ui://`. Il testo congelato dell'estensione vive nel [repo `ext-apps`](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx) e viene distribuito come estensione ufficiale insieme alla release core del 2026-07-28. Nomi dei campi, forma delle capability e default dell'host si muovono ancora ai bordi — verifica sulla SEP e sulle release notes del tuo SDK prima di andare in produzione.
</VerifyNote>

## La versione in un paragrafo

Il server dichiara una o più **risorse UI** su URI `ui://<server>/<name>` con MIME type `text/html;profile=mcp-app`. Un tool segnala "ho una UI" mettendo `_meta.ui.resourceUri` nel suo schema. Su una `tools/call` il server può restituire il solito testo/dato **più** un riferimento alla risorsa UI; il client scarica l'HTML con `resources/read`, lo mette in un `<iframe>` sandboxed, e ora iframe e host chiacchierano via `postMessage` usando JSON-RPC 2.0. **Le tool call originate dalla UI richiedono comunque la stessa approvazione utente di qualsiasi altra tool call** — l'App può renderizzare, può proporre, non può eseguire in silenzio.

## Forme sul filo che scriverai davvero

Dichiarazione di capability su una richiesta client:

```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": { "name": "get_weather", "arguments": { "location": "Milan" } },
  "_meta": {
    "capabilities": {
      "extensions": {
        "io.modelcontextprotocol/ui": {
          "mimeTypes": ["text/html;profile=mcp-app"]
        }
      }
    }
  }
}
```

Lo schema del tool, lato server:

```json
{
  "name": "get_weather",
  "description": "Get current weather and a 7-day forecast for a location.",
  "inputSchema": {
    "type": "object",
    "properties": { "location": { "type": "string" } },
    "required": ["location"]
  },
  "_meta": {
    "ui": {
      "resourceUri": "ui://weather-server/dashboard-template",
      "visibility": ["model", "app"]
    }
  }
}
```

La risorsa UI dichiarata accanto:

```json
{
  "uri": "ui://weather-server/dashboard-template",
  "mimeType": "text/html;profile=mcp-app",
  "_meta": {
    "ui": {
      "connectDomains": [],
      "permissions": []
    }
  }
}
```

E il primo messaggio che l'iframe rimanda indietro:

<PromptCard title="UI → host: JSON-RPC 2.0 su postMessage">{`window.parent.postMessage(
  {
    jsonrpc: "2.0",
    id: 1,
    method: "ui/initialize",
    params: {
      toolName: "get_weather",
      toolArguments: { location: "Milan" },
      toolResult: /* whatever the server returned alongside the UI */
    }
  },
  "*"
);`}</PromptCard>

Tutto ciò che segue — chiedere all'host di chiamare un altro tool, sottoscriversi a una risorsa, inviare un evento lato UI — è altro JSON-RPC 2.0 sullo stesso canale, strutturato in modo identico al protocollo sul filo che già parli lato server. È tutto il punto: **gli sviluppatori UI possono usare l'`@modelcontextprotocol/sdk` standard** invece di imparare uno shim custom.

## Quando ricorrere davvero a un App

L'asticella è alta di proposito — ogni App è superficie client per te e superficie d'attacco per l'utente. Ricorri a uno solo quando una UI batte un turno di chat con un margine chiaro:

- **Conferme su data-grid.** "Ecco 47 righe che sto per aggiornare — deseleziona quelle che non vuoi." Un rendering in chat è o enorme o disonesto; una griglia con checkbox è onesta e veloce.
- **Approvazione guidata da grafici.** "Ecco il query plan / la proiezione di costo / il trace waterfall. Approva o rifiuta." I grafici costano poco in HTML e sono terribili come ASCII.
- **Picker strutturati** dove la forma dell'input non è testo. Date-range con mini calendario, tree-select su un filesystem o un organigramma, map picker con bounding box.
- **Editor in-place** per il piccolo passaggio in cui una vista diff + accetta/rifiuta batte il rigenerare tutta la risposta.

Se la tua idea è "fatemi embeddare un'intera dashboard", non è questo il posto — metti un link. Se la tua idea è "fatemi eseguire codice utente arbitrario nella sandbox", questo posto non fa proprio per te.

## Il contratto di compatibilità con 2025-11-25

MCP Apps cavalca il framework di estensioni introdotto nella core spec 2026-07-28, ma l'estensione in sé è **Final dal 2026-01-26**. Implicazione pratica: un client che parla solo la vecchia revisione 2025-11-25 più questa estensione può già renderizzare Apps; un client stateless 2026-07-28 la raccoglie come una entry nella sua mappa di capability per-richiesta. Poiché l'estensione è opt-in su entrambi i lati, un server che l'aggiunge non rompe mai un client vecchio — semplicemente salta il ramo UI. Questa è la forma che avrà ogni futura estensione MCP, quindi capire questo handshake ammortizza il debito per quelle che verranno.

- **[MCP 2026-07-28: la spec stateless](/docs/api/mcp-2026-07-28-stateless)** — il protocollo core su cui viaggia Apps; in particolare la sezione sul framework di Extensions (SEP-2133).
- **[MCP & connettersi ai tool](/docs/api/mcp)** — il connettore lato API. È il client che renderizzerà l'iframe; oggi il connettore astrae il trasporto, quindi Apps ci passa attraverso senza modifiche.
- **[MCP in Claude Code](/docs/claude-code/mcp)** — dove sta andando il supporto MCP di Claude Code; il rendering UI è una capability del client, non del server, quindi è la superficie che decide quali Apps verranno mai renderizzate per te.
- **[Mettere in sicurezza i server MCP](/docs/security/securing-mcp-servers)** — il pattern di hardening per i server dall'altra parte di quell'iframe.
