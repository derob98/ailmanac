<LevelBadge level="advanced" />

Il **28 luglio 2026** il Model Context Protocol ha chiuso la sua più grande revisione dal lancio. Il titolo: **MCP è stateless**. L'handshake `initialize` e l'header `Mcp-Session-Id` non esistono più; ogni richiesta porta la propria identità dentro `_meta`; qualsiasi istanza del server dietro un load balancer può rispondere a qualsiasi chiamata. MCP serverless non è più un workaround — è la forma del protocollo.

Specifica chiusa il **28 luglio 2026**. Le beta degli SDK stanno uscendo ora; la GA seguirà con un rollout progressivo nelle prossime settimane. Le funzionalità deprecate (Roots, Sampling, Logging, la vecchia API sperimentale Tasks) continuano a funzionare per **almeno 12 mesi** — rimozione al più presto il **28 luglio 2027**. Verifica i numeri di versione degli SDK e lo stato del rollout Claude sulle fonti primarie prima di fare un cutover netto.
</VerifyNote>

## La versione in un paragrafo

Prima: handshake `initialize` → cookie `Mcp-Session-Id` → coppia client/server sticky per tutta la durata della sessione. Dopo: nessun handshake, nessun session id, nessuna stickiness. Identità e capability del client viaggiano su ogni richiesta dentro un oggetto `_meta`. Un nuovo metodo `server/discover` sostituisce lo scambio iniziale di capability. Lo stato applicativo — un carrello, un task in corso — vive in **handle** che il tool restituisce e il client rimanda alla chiamata successiva, esattamente come un id di risorsa REST. Quel singolo cambiamento è ciò che sblocca deployment serverless ed edge, scaling orizzontale reale, e la possibilità che due implementazioni concorrenti stiano dietro lo stesso URL.

Le deprecazioni di Roots/Sampling/Logging sono quelle che la maggior parte dei server esistenti tocca davvero. Tutte e tre assumevano un canale server↔client persistente e bidirezionale. In un mondo stateless il client possiede l'LLM, i path, e il sink dei log — il server risponde solo alla chiamata del tool.

## L'unico cambio JSON che frega tutti

Il codice di errore per risorsa mancante è passato da **`-32002`** a **`-32602` (Invalid Params)**. Se il tuo client ha un ramo `if (err.code === -32002)` da qualche parte, smette silenziosamente di scattare il 28 luglio. È il bug di integrazione più comune nell'RC.

## Prima / Dopo

```jsonc
// PRIMA (2025-11-25): handshake stateful
POST /mcp     { "method": "initialize", "params": { "capabilities": {...} } }
              → imposta Mcp-Session-Id: abc123
POST /mcp     Mcp-Session-Id: abc123
              { "method": "tools/call", "params": { "name": "search", ... } }
// il server assume di "conoscerti" grazie al session cookie
```

```jsonc
// DOPO (2026-07-28): richiesta auto-descrittiva
POST /mcp     Mcp-Method: tools/call
              Mcp-Name: search
              MCP-Protocol-Version: 2026-07-28
              {
                "method": "tools/call",
                "params": { "name": "search", "arguments": {...} },
                "_meta": {
                  "clientInfo": { "name": "claude-code", "version": "..." },
                  "capabilities": { "extensions": { "com.anthropic.apps": "1" } },
                  "traceparent": "00-..."
                }
              }
// qualsiasi istanza può servirla; nessuna sessione, nessuna stickiness
```

## Multi Round-Trip Requests, in concreto

La parte elegante della specifica. Un server che deve chiedere "quale calendario?" mid-execution non deve tenere un socket aperto. Risponde:

```json
{
  "resultType": "input_required",
  "inputRequests": {
    "calendarId": { "type": "string", "prompt": "Which calendar?" }
  },
  "requestState": "base64(<opaque server-signed blob>)"
}
```

Il client mostra il prompt, raccoglie gli `inputResponses`, e rilancia la richiesta originale con entrambi i campi. Il server tratta `requestState` come autoritativo — spesso firmandolo — quindi non deve ricordare il tentativo precedente. Ecco tutto il trucco dietro l'elicitation stateless: **lo stato viaggia sul filo, non sul server**.

## Autorizzazione: la pulizia OAuth

La vecchia specifica era OAuth-ish. La nuova ha la forma OAuth 2.1 / OIDC:

- I client **devono** validare il parametro `iss` sulle risposte di autorizzazione secondo la **RFC 9207** — la fix per gli attacchi mix-up che hanno colpito i server MCP a inizio anno.
- La Dynamic Client Registration ora richiede ai client di dichiarare un `application_type` OpenID Connect, così un identity provider può applicare regole diverse per client native vs web vs machine.
- I refresh token seguono lo standard flow OIDC — il che significa che l'SSO enterprise (Entra, Okta, PingID) funziona senza middleware custom per la prima volta.

Lettura pratica: se stavi costruendo colla OAuth custom per far entrare MCP dentro Okta, puoi cancellarne la maggior parte.

## Dove atterra questo sulla mappa AILmanac

- **[MCP e connessione ai tool](/docs/api/mcp)** — il connector lato API. Ancora attuale; il connector astrae il transport, quindi il cambio di wire è invisibile a quella forma di richiesta. Solo i *server* con cui il connector parla migrano.
- **[MCP in Claude Code](/docs/claude-code/mcp)** — come Claude Code parla MCP con server locali + remoti. Il modello stateless è la ragione per cui puoi finalmente puntare Claude Code a un endpoint MCP serverless senza timeout strani.
- **[Il MCP Token Tax](/docs/claude-code/mcp-token-cost)** — il deferred loading è la leva token-side; il framework extensions è la leva *protocollo*-side per lo stesso problema.
- **[Securing MCP Servers](/docs/security/securing-mcp-servers)** — la guida NSA di maggio 2026 sulla sicurezza MCP e l'hardening di autorizzazione dell'RC si rinforzano a vicenda. Leggi entrambi.
