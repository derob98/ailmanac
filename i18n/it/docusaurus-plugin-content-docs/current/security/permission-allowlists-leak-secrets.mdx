Il **5 novembre 2026** i ricercatori di Apiiro **Shmulik Cohen** e **Matan Giladi** hanno pubblicato un'indagine su GitHub pubblico per un nome di file specifico: `.claude/settings.local.json`. Hanno trovato **104.185 copie in 103.617 repository**. In **1.122 di quei file**, circa l'**1,1%**, hanno trovato **1.379 segreti reali**.

Quattro giorni dopo il thread su Hacker News è arrivato in prima pagina con 622 punti e 422 commenti. È seguito il consiglio di sempre: non committare i file di configurazione.

Il consiglio è giusto e manca del tutto il meccanismo. Tre dettagli rendono questo argomento degno di una pagina a sé:

1. **Nessuno ha incollato un segreto in un file di configurazione.** Hanno digitato una credenziale in un comando di shell, la cosa ordinaria che si fa quando si fa debug di un database, e poi hanno cliccato **"Yes, and don't ask again."** Claude Code ha salvato il comando approvato *come regola di permesso*. La credenziale è diventata parte del record che autorizza il comando la volta successiva.
2. **215 dei file con perdite hanno battuto entrambi gli scanner di segreti standard del settore.** Non perché gli scanner siano scadenti, ma perché una password dopo `PGPASSWORD=` o `sshpass -p` non ha prefisso del provider, formato di chiave né entropia distintiva. Sembra una parola qualsiasi in una riga di comando qualsiasi.
3. **Claude Code cerca di proteggerti, e la protezione è strutturalmente incapace di viaggiare.** Scrive la regola di esclusione nel file di esclusioni git **globale**. Quel file sta nella tua home directory. Non è nel repository, quindi non arriva al clone del tuo collega, al tuo runner di CI né al tuo prossimo portatile.

Non è una storia di prompt injection e non c'è alcun exploit. È un workflow autorizzato il cui audit trail è per caso un file di segreti: una categoria di problema molto più durevole, che vale per ogni agente che rende persistenti le approvazioni.

## Parte 1 — Il meccanismo, con precisione

Claude Code chiede prima di eseguire la maggior parte dei comandi di shell. Il prompt offre un'opzione persistente, **"Yes, and don't ask again"**, e sceglierla scrive una regola `allow` in `.claude/settings.local.json` alla radice del repository. L'approvazione è **permanente per quel repository e quel comando** e vale per le sessioni future, worktree compresi.

La forma del file è ordinaria:

<PromptCard title="La forma sicura — una regola a pattern, dalla documentazione di Claude Code">{`{
  "permissions": {
    "allow": ["Bash(npm run test *)"],
    "deny": ["Read(./.env)", "Read(./.env.*)"]
  }
}`}</PromptCard>

Ecco il punto cruciale. **A volte la regola salvata è un pattern** come quello sopra. **A volte è il comando esatto come digitato.** Quando è il comando esatto, ogni carattere di quel comando, compresa una password passata inline, diventa parte della stringa della regola.

Quindi il guasto non richiede errori né attaccanti. Richiede un normale pomeriggio:

## Parte 2 — Perché 215 file hanno battuto entrambi gli scanner

Apiiro ha passato i file con perdite attraverso i due scanner open source di segreti più diffusi. Dei **1.122** file con segreti:

| Scanner | File segnalati |
|---|---|
| gitleaks | **564** |
| TruffleHog | **643** |
| **Segnalati da nessuno dei due** | **215** |

Cioè il **19% dei file con perdite è invisibile a entrambi gli strumenti**. Il motivo è la divisione 636/743 di prima.

Uno scanner trova i segreti in due modi: riconosce **formati noti** (un prefisso `AKIA…`, un token `ghp_…`, la forma di un JWT Supabase) oppure segnala **stringhe ad alta entropia** in posizioni sospette. Entrambe le tecniche funzionano su *credenziali emesse*, progettate per essere riconoscibili.

Nessuna delle due funziona su una **password scelta da un essere umano** che sta nella posizione di argomento di un comando di shell. `PGPASSWORD=Summer2024!` non ha un prefisso di vendor da riconoscere. La sua entropia è nella norma. Strutturalmente è indistinguibile da un valore di configurazione, da una fixture di test o da una parola. I falsi negativi erano in stragrande maggioranza di questo tipo: password inline dopo `PGPASSWORD=`, `sshpass -p` e `mysql -p`.

<Callout type="note" items={[
  "Un'avvertenza sulla divisione 564/643, riportata da una sola testata: entrambi gli scanner sono stati eseguiti SENZA il passo di verifica, la modalità in cui lo strumento tenta di confermare che una credenziale candidata sia attiva. La verifica migliora soprattutto la precisione più che la recall, e non può aiutare su una password che non corrisponde ad alcuna regola in partenza, quindi è improbabile che la cifra 215 sia un artefatto di ciò. Ma se citi i numeri per scanner, cita con essi anche quell'avvertenza.",
]} />

La lezione generalizzabile è indipendente da questo incidente: **la tua scansione dei segreti è tarata sui token emessi ed è in gran parte cieca alle password scelte negli argomenti dei comandi.** I file di configurazione degli agenti e le trascrizioni salvate sono pieni di argomenti di comandi. Se ti limiti ad aggiungere `.claude/` ai percorsi del tuo scanner senza cambiare nulla nelle sue regole, intercetterai circa quattro quinti del problema.

## Parte 3 — La protezione gitignore che non può viaggiare

Claude Code non è indifferente a questo. La prima volta che scrive `settings.local.json` in un repository che non lo ignora già, aggiunge una regola di esclusione, **nel tuo file di esclusioni git globale**, non nel `.gitignore` del progetto.

Puoi verificarlo sulla tua macchina con due comandi:

<PromptCard title="Verifica che la protezione esista — e vedi dove risiede">{`# Where Git looks for your personal excludes.
# If this prints nothing, Git uses the XDG default: ~/.config/git/ignore
git config --get core.excludesFile

# The rule Claude Code writes:
grep -n 'claude' ~/.config/git/ignore`}</PromptCard>

Eseguito su questa macchina il 10 novembre 2026, `core.excludesFile` non era impostato e la prima riga di `~/.config/git/ignore` era esattamente `**/.claude/settings.local.json`. La protezione è reale e funziona.

Ma non può essere sufficiente, per quattro ragioni tutte strutturali e non bug:

- **Un file di esclusioni globale non viene committato.** Vive nella tua home directory. Il clone del tuo collega non l'ha mai visto. Né l'ha visto il tuo runner di CI, il tuo dev container o il tuo prossimo portatile.
- **Non aiuta retroattivamente una cartella diventata repository più tardi.** Molto lavoro con gli agenti parte in una directory di prova e riceve il `git init` dopo.
- **Le regole di esclusione non fanno nulla sui file già tracciati.** È il comportamento documentato di Git, non un limite di Claude Code: una volta che un percorso è nell'indice, `.gitignore` è irrilevante per esso.
- **Protegge un solo nome di file.** Il file *condiviso* `.claude/settings.json` è un file che i team committano deliberatamente, e anche 298 sue copie pubbliche contenevano segreti.

Quindi la correzione dal tuo lato è piccola e non è opzionale: metti il percorso nel `.gitignore` **del repository**, dove viaggia con il progetto.

<PromptCard title="Fai viaggiare la regola di esclusione con il progetto">{`# In the repo, not in your home directory.
printf '%s\\n' '.claude/settings.local.json' >> .gitignore

# Or ignore the whole agent config directory, which also covers
# transcripts and anything future versions add:
printf '%s\\n' '.claude/' >> .gitignore

git add .gitignore && git commit -m "chore: ignore local agent permission settings"`}</PromptCard>

## Parte 4 — Fai l'audit dei tuoi repository

Cinque controlli, in ordine. Il terzo è quello che la gente salta, ed è quello che conta.

<PromptCard title="L'audit in cinque comandi">{`# 1. Is the file tracked RIGHT NOW?
git ls-files .claude/settings.local.json

# 2. Has it EVER been committed, on any branch?
#    An empty result from step 1 means nothing without this.
git log --all --oneline -- .claude/settings.local.json

# 3. Look for the secrets the scanners miss: inline passwords
#    in command arguments, across all of history.
git log --all -p -- .claude/ | grep -nE 'PGPASSWORD=|sshpass -p|mysql .*-p|MYSQL_PWD=|--password[= ]'

# 4. Confirm an ignore rule actually applies, and see which file it came from.
git check-ignore -v .claude/settings.local.json

# 5. Run the scanners over history too, not just the working tree.
gitleaks git -v          # gitleaks 8.19+; older: gitleaks detect -v
trufflehog git file://.`}</PromptCard>

All'interno di una sessione di Claude Code, il comando `/permissions` elenca ogni regola attiva **e da quale file proviene ciascuna**: il modo più rapido per trovare un comando letterale in un'allowlist su una macchina dove non è mai stato committato nulla.

Poi allarga la ricerca. La raccomandazione di Apiiro è di passare al setaccio l'intera organizzazione cercando sia `.claude/settings.local.json` **sia** `.claude/settings.json`, cronologia compresa, anche nei repository dove il file non c'è più. E dato che ogni agente con approvazioni persistenti ha lo stesso tipo di file, scansiona i fratelli: `.claude/`, `.cursor/`, `.gemini/`, `.specstory/`.

## Parte 6 — Il disaccordo che vale la pena conoscere

Anthropic ha risposto pubblicamente. Boris Cherny del team di Claude Code ha scritto su Hacker News il 7 novembre 2026:

> Historically Claude Code has not done secret scrubbing (there are many good tools for that), but we are looking into what we can do to prevent this.

(In italiano: storicamente Claude Code non ha fatto scrubbing dei segreti, esistono molti buoni strumenti per questo, ma stiamo valutando cosa possiamo fare per prevenire il problema.)

Ha aggiunto che `settings.local.json` non è un file da inserire nel controllo di versione e che le copie esposte erano state **"manually created and checked in"** (create manualmente e committate), l'argomento essendo che, dato che Claude Code aggiunge la regola di esclusione quando crea il file, le copie committate devono provenire da altrove. Ha raccomandato l'[auto mode](/docs/claude-code/permissions), che filtra le azioni con un classificatore invece di accumulare regole allow, più la scansione dei segreti sull'host git. Prototipi allo studio: insegnare all'auto mode a intercettare questi comandi e integrare una scansione di base dei segreti, con la riserva che potrebbe non risolvere del tutto. Quando un commentatore ha fatto notare che la stessa esposizione può verificarsi in auto mode, la sua risposta è stata "Yeah good catch."

**Quella spiegazione e i dati di Apiiro non combaciano.** Apiiro riporta commit co-firmati da Claude che toccano il file in **539 di 1.105** repository tracciati. Apiiro è attenta a precisare che la co-firma non prova che Claude abbia introdotto o pushato ogni credenziale: il commit può aver incluso un file preesistente. Ma "creato manualmente e committato" è difficile da conciliare con commit scritti da un agente in metà del campione.

Non serve risolverlo per agire, e la conclusione ingegneristica è la stessa in entrambi i racconti:

- Se ha ragione Anthropic, la protezione dipende da un file nella tua home directory, e ognuna delle quattro lacune strutturali della Parte 3 si applica ancora al tuo team.
- Se ha ragione Apiiro, i commit scritti dall'agente sono un percorso attivo del file verso il tuo repository, e la protezione è ancora più debole.

In ogni caso: metti la regola di esclusione nel repository, approva pattern e non letterali, e scansiona le password inline. Nota anche che **nulla risulta confermato come corretto**: nessuna versione, nessuna voce di changelog, nessun CVE, nessuna valutazione di severità, all'8 novembre 2026.
