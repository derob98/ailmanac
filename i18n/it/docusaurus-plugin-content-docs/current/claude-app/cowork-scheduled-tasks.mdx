Cowork ha smesso di essere un workspace solo desktop il **7 luglio 2026**. Ora gira su **web (claude.ai)**, **iOS e Android**, e — la parte che quasi tutti gli articoli seppelliscono — le sessioni vengono eseguite sui **server di Anthropic**, non sulla tua macchina. Questo singolo cambiamento architetturale è ciò che sblocca la feature principale: **task pianificati che girano con il portatile chiuso, il telefono in tasca e nessun dispositivo online**.

Questa pagina è la guida pratica sul campo: cosa funziona davvero su quale superficie, come configurare un task pianificato correttamente al primo colpo, e la manciata di imprevisti che ti accorgi di avere solo dopo che il briefing delle 6:00 del lunedì è fallito in silenzio perché serviva un file locale.

## L'unico cambio che conta: le sessioni si sono spostate sui server di Anthropic

Prima di luglio 2026, una sessione Cowork era un processo dentro l'app Claude Desktop sul tuo Mac o PC. Chiudi il portatile, la sessione muore. Uccidi l'app, la sessione muore. È il motivo per cui il loop pre-luglio di Cowork iniziava sempre con "apri il desktop, tienilo sveglio".

Il lancio di luglio introduce le **sessioni remote**: il loop di Cowork vive nel cloud di Anthropic, lo stato della tua sessione e i file persistono legati al tuo account Claude, e qualsiasi superficie (web, mobile, desktop) è solo un visualizzatore + dispositivo di input per la stessa sessione sottostante.

Due conseguenze dirette:

1. **I task pianificati sono possibili.** Un task ricorrente può svegliarsi alle 06:00 di lunedì, fare 45 minuti di lavoro e lasciare una bozza nel tuo account — con zero dispositivi online, perché non c'è un dispositivo nel loop.
2. **Il passaggio tra dispositivi è gratuito.** Avvia un task alla scrivania, chiudi il portatile e vedi la stessa sessione a metà run sul telefono. Non c'è nulla da sincronizzare — la sessione non è mai stata sul tuo portatile.

Il tradeoff è la matrice delle capacità qui sotto: qualsiasi cosa che debba toccare **la tua macchina locale** (file su disco, il tuo browser, il tuo OS) può girare solo su desktop, perché è l'unica superficie con un piede in entrambi i mondi.

## Matrice delle capacità per superficie

| Capacità | App Desktop | Web (claude.ai) | Mobile (iOS/Android) |
| --- | --- | --- | --- |
| Sessioni Cowork (interattive) | ✓ | ✓ (beta) | ✓ (beta) |
| Task Cowork **pianificati** | ✓ (crea + monitora) | ✓ (crea + monitora) | ✓ (monitora + approva) |
| Accesso a file locali | ✓ | ✗ | ✗ |
| Browser use (automazione browser locale) | ✓ | ✗ | ✗ |
| Computer use (controllo OS) | ✓ | ✗ | ✗ |
| Artifact live (anteprima in-sessione) | ✓ | ✗ | ✗ |
| Tool connessi (Gmail, Slack, GDrive, Calendar, web) | ✓ | ✓ | ✓ |
| **Skill** installate | ✓ | ✓ | ✓ |
| **Plugin** | ✓ | ✓ | ✓ |
| Push mobile per prompt di approvazione | (via telefono collegato) | (via telefono collegato) | ✓ (native) |
| Modello Fable 5 in Cowork | ✓ (solo ultimo Desktop) | vedi imprevisti | vedi imprevisti |

:::info La regola pratica
Se il task ha bisogno solo di **tool connessi + Skill + web** (triage email, "leggi questi tre doc e scrivimi un update", report settimanale da Google Sheets), gira ovunque — pianificalo. Se ha bisogno dei **tuoi file, del tuo browser o della tua macchina**, resta solo desktop-e-live.
:::

## Cowork interattivo vs Task pianificato vs Dispatch

I tre modi vengono confusi. Sono bestie diverse:

<Steps items={[
  {title: "Sessione Cowork interattiva", body: "La avvii tu, la guardi, Claude lavora su un orizzonte lungo sul tuo obiettivo attivo. Ora vive sui server di Anthropic, quindi puoi passarla tra dispositivi. Ideale per: lavori di più ore che vuoi guidare mentre accadono."},
  {title: "Task Cowork pianificato", body: "Definisci un prompt + una cadenza (orario / giornaliero / feriali / settimanale / manuale). Ogni run apre una sessione Cowork fresca con i tool, skill e plugin che hai specificato. Gira in remoto, secondo pianificazione, che ci sia o meno un dispositivo online. Ideale per: prep ricorrente — briefing del lunedì alle 06:00, triage orario dell'inbox, riepiloghi di fine giornata."},
  {title: "Dispatch (solo desktop)", body: "Forma legacy: avvia un task in background da una sessione desktop attiva che continua a girare mentre tu continui a chattare. Richiede che l'app desktop resti sveglia perché il processo vive ancora localmente. Ideale per: lavoro sulla macchina locale che vuoi mettere in background mentre continui a collaborare. NON confonderlo con un task remoto pianificato — Dispatch muore quando chiudi l'app."}
]} />

La scorciatoia mentale: **Dispatch = background locale, Task pianificato = cloud con una cadenza, Interattivo = sei al volante.**

## Configurare un task pianificato nel modo giusto

Un task pianificato ha bisogno di sei cose — cinque impostazioni e un prompt. Sbaglia una qualsiasi delle impostazioni e la run sembrerà "riuscita" ma farà la cosa sbagliata.

<Steps items={[
  {title: "Nome del task", body: "Corto, umano. È quello che vedrai nella lista dei task pianificati e nelle notifiche mobile. 'Prep cliente lunedì' batte 'briefing-v2'."},
  {title: "Prompt / istruzioni", body: "Scrivilo come se parlassi a un collega che entra da zero a ogni run — perché ogni run È una sessione fresca. Dichiara l'obiettivo, le fonti (quali connettori, quali skill, quali cartelle), la forma di output che vuoi, e ogni invariante (es. 'non inviare mai email, lascia sempre come bozza')."},
  {title: "Frequenza", body: "Scegli tra orario / giornaliero / feriali / settimanale / manuale. Non c'è sintassi cron e non ci sono opzioni sotto l'ora — se ti serve 'ogni 5 min', sei sul tool sbagliato (usa l'API + il tuo scheduler)."},
  {title: "Modalità di approvazione", body: "L'impostazione critica. Le opzioni sono auto-approve (Claude procede senza chiedere, buono per task read-only), ask-on-mobile (Claude si ferma a un punto di decisione e pinga il telefono — default sicuro per qualsiasi cosa scriva), o hold-for-review (il task finisce sempre con una bozza che rivedi dopo)."},
  {title: "Modello (opzionale)", body: "Default sul Cowork default del tuo piano. Scegli un modello più piccolo/economico per loop pesanti di lettura-riassunto; scegli top-tier solo quando la qualità del ragionamento sposta davvero il risultato."},
  {title: "Cartella di lavoro (opzionale)", body: "Limita le scritture su file della sessione a uno specifico progetto/cartella nel tuo account Claude. Salta questa impostazione e gli output finiscono in una posizione di default — che va bene per un task, un casino quando ne hai dodici."}
]} />

<PromptCard title="Template di prompt per task pianificato: briefing cliente lunedì 06:00">{`You are preparing my Monday morning brief for the Acme account.

Every Monday at 06:00 local:

1. Read the last 7 days of email in the "Acme" Gmail label. Group by
   thread; note anything that expects a reply from me.
2. Pull calendar events with "Acme" in the title or attendees from
   the coming week. Note prep needed for each.
3. Search the web for news about Acme (company name + "acquisition",
   "layoffs", "product launch") in the last 7 days. Cite sources.
4. Read the Google Doc "Acme - Running Notes" for open questions.

Produce a single briefing doc titled "Acme brief — <this-monday-date>"
in the "Client briefings" project folder. Structure:

- 3-bullet TL;DR at the top
- "Needs a reply from me" list (with links)
- "This week" list (calendar + prep)
- "News since last brief" (with sources)
- "Open questions" (from the running-notes doc)

DO NOT send any email. Leave a follow-up email as a DRAFT in Gmail
titled "Acme weekly check-in" pre-filled with the TL;DR — I'll edit
and send.`}</PromptCard>

Due cose da notare su questo prompt:

- L'**invariante** ("DO NOT send any email... leave as DRAFT") è scritta esplicitamente. In una run pianificata non puoi chiedere un follow-up "sei sicuro?" — gli invarianti devono stare nel prompt.
- La **posizione di output + naming** è precisa. Quando queste run girano settimanalmente per mesi, li vuoi trovare, non sparsi sotto titoli di default.

## Flusso di approvazione mobile — progettare per "sto dormendo"

`ask-on-mobile` sembra amichevole finché non scatta alle 03:00 e la run si blocca in silenzio in attesa di te. Due regole rendono questo affidabile:

<Steps items={[
  {title: "Abbina la modalità di approvazione al blast radius", body: "Azioni read-only o solo-bozza → auto-approve. Qualsiasi cosa invii, pubblichi, cancelli o spenda soldi → ask-on-mobile con un fallback nel prompt: 'se non ho risposto entro 30 minuti, salva come bozza e termina il task'. Il fallback a livello prompt conta perché la piattaforma non farà il timeout per te."},
  {title: "Fai in modo che il titolo della notifica ti dica cosa sta per succedere", body: "Nel prompt, incapsula i punti di decisione in una richiesta specifica: 'Prima di inviare qualsiasi cosa, richiedi approvazione con l'esatto subject e i primi 200 caratteri del body.' Le notifiche push tagliano — metti in testa le parti importanti così puoi approvare/negare dalla lockscreen senza aprire l'app."}
]} />

<Callout type="warning" items={[
  "Le approvazioni push bloccano il task finché non rispondi. Se non rispondi mai, la run resta lì — non ricade automaticamente su un default sicuro. Metti un timeout 'se nessuna risposta, fai X' dentro il prompt stesso, o usa hold-for-review invece."
]} />

## I quattro imprevisti che rompono le run Cowork pianificate

<Steps items={[
  {title: "1. I tool solo locali disabilitano silenziosamente la run", body: "Se il prompt chiede al task di 'apri la mia cartella downloads', 'automatizza il mio browser', o 'fai uno screenshot del mio schermo', la sessione remota non ha modo di farlo. La run non crasha — salterà o improvviserà. Fix: fai un audit dei tuoi prompt pianificati e sostituisci le azioni sulla macchina locale con equivalenti tool-connessi (Google Drive invece di file locali, web fetch invece del browser locale, ecc)."},
  {title: "2. Fable 5 in Cowork richiede ancora l'ultima versione di Desktop", body: "Al lancio di luglio 2026, eseguire il modello Fable 5 dentro una sessione Cowork richiede l'ultima app Claude Desktop. Se pianifichi un task che fissa Fable 5 e conti su di lui in remoto, verifica il supporto attuale — questo vincolo dovrebbe allentarsi ma controlla prima di fissarlo."},
  {title: "3. Dispatch NON è un task pianificato", body: "Il lavoro Dispatch messo in background da una sessione desktop attiva muore quando chiudi l'app. Se ti serve davvero 'lancia questo settimanalmente, comunque', non usare Dispatch — crea un task pianificato."},
  {title: "4. Il drift di autenticazione dei connettori uccide le run silenziose", body: "I token OAuth per Gmail, Slack, Google Drive possono scadere, essere revocati, o incappare in cambi di permesso. ## Quando prendere l'API invece

I task Cowork pianificati sono una feature di prodotto — ottimi per lavoro ricorrente personale / small-team che vuoi visibile nel tuo account Claude, con approvazione umana nel loop. Sono il tool sbagliato quando ti serve:

- **Cadenza sotto l'ora** — l'intervallo minimo dei task pianificati è orario.
- **Orchestrazione programmatica** — decine di run parallele, scheduling dinamico, o integrazione stretta con la tua infra. Prendi i [Managed Agents](/docs/api/managed-agents), o fai da te con l'[Agent SDK](/docs/claude-code/headless-and-agent-sdk) + un cron/queue che già giri.
- **Memoria server-side tra run** — i task Cowork passano stato via file nel tuo account, il che va bene per doc ma è grossolano per stato strutturato. Per memoria strutturata cross-run, usa i [Managed Agents Memory Stores](/docs/api/managed-agents-memory-stores).
- **Coordinamento profondo multi-agente** — per molti-agenti-che-collaborano, vedi [Cowork & Agent Teams](/docs/api/cowork-and-agent-teams) e [Native Multi-Agent APIs](/docs/models/native-multi-agent-apis).
