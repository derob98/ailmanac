Colibrì: Ein 744B-MoE von der SSD ausführen (und was es Sie wirklich kostet)

Experte
What you'll learn
  • Den Drei-Ebenen-Trick verstehen — dichte Gewichte im RAM, geroutete Experten auf der Platte, optionale VRAM-Ebene — und warum MoE ihn überhaupt erst möglich macht
  • Die Benchmark-Tabelle ehrlich lesen: welche Hardware 0,1 tok/s erreicht, welche ~2, welche ~6, und warum die NVMe-Bandbreite und nicht die CPU die Obergrenze ist
  • Die vier Fallstricke kennen, die Leute Tage kosten: int8-MTP-Heads, O_DIRECT auf der falschen Platte, spekulatives Decoding, das verliert, und SSD-Verschleiß
  • Von git clone bis zum ersten gestreamten Token auf GLM-5.2 oder DeepSeek V4.1 Flash kommen
  • Entscheiden, wann Colibrì einen GGUF-plus-Ollama-Offload schlägt, wann man stattdessen eine GPU mieten sollte und wann eine gehostete API schlicht die richtige Antwort ist

Am 1. Juli 2026 stellte ein Entwickler unter dem Namen JustVugg ein Repository mit einem Einzeiler als Versprechen online: Frontier-MoE-Modelle auf Hardware ausführen, die Sie bereits besitzen — reines C, keine Abhängigkeiten, Experten von der Platte gestreamt. Der Show-HN-Thread erreichte neun Tage später 453 Punkte. Mitte September steht das Projekt bei 30,8k Sternen, und Version 1.11.0, veröffentlicht am 13. September, fügte eine neunte Modellfamilie hinzu (DeepSeek V4.1 Flash, 552B), die den veröffentlichten Checkpoint nativ ohne Konvertierungsschritt liest. Während diese Seite geschrieben wird, ist es das führende KI-Repository in GitHubs täglicher Trending-Liste.

Der Pitch klingt wie ein Trick, und in gewissem Sinne ist er einer. Diese Seite erklärt den Trick präzise genug, dass Sie vorhersagen können, was er auf Ihrer Maschine tun wird, bevor Sie 370 GB herunterladen.

Die Ein-Satz-Version​

Ein Mixture-of-Experts-Modell berührt pro Token nur einen kleinen Ausschnitt seiner Gewichte, also hält Colibrì den immer genutzten Teil (Attention, Embeddings, geteilte Experten) resident im RAM und liest den selten genutzten Teil (die gerouteten Experten) bei Bedarf von NVMe — und tauscht Tokens pro Sekunde gegen die Fähigkeit, ein Modell mit 744 Milliarden Parametern auf einem Laptop auszuführen.

Warum MoE das möglich macht​

Nehmen Sie GLM-5.2 als Referenzfall, da es das Modell ist, um das das Projekt herum gebaut wurde:

GrößeWert
Parameter gesamt744B
Aktiv pro Token~40B
Dichte (immer aktive) Parameter~17B → ~9,9 GB resident als int4
Geroutete Expertenrund zwanzigtausend über alle Schichten → ~370 GB auf der Platte als int4
Expertengewicht, das sich von Token zu Token ändert (kalt)~11 GB
Minimaler RAM / komfortabler RAM16 GB / 24 GB

Jedes Token braucht die dichten 9,9 GB plus die Handvoll Experten, die der Router in jeder Schicht auswählt. Der dichte Teil passt ins RAM. Die Experten nicht — aber Sie brauchen nur wenige davon gleichzeitig, und das nächste Token nutzt oft viele derselben wieder. Also behandelt die Engine VRAM, RAM und NVMe als eine einzige Speicherhierarchie: einen LRU-Cache pro Schicht für kürzlich genutzte Experten im RAM, einen gelernten "Pinned Hot-Store" der am häufigsten genutzten Experten, eine optionale VRAM-Ebene, falls eine GPU vorhanden ist, und die Platte als Backing Store für alles andere.

Die Designentscheidung, die daraus eine einzige C-Datei pro Modell statt eines Frameworks macht: kein BLAS, kein Python zur Laufzeit, keine GPU erforderlich. Die GLM-Engine begann mit etwa 1.300 Zeilen C. Keine Abhängigkeiten bedeutet auch, dass der Page-Cache des Betriebssystems zu einer kostenlosen zweiten Cache-Ebene für Expertenlesezugriffe wird.

Vier Mechanismen, die man verstehen sollte​

1. Router-Lookahead: Routing ist eine Schicht voraus zu 71,6 % vorhersagbar​

Der teure Teil des Streamings ist das Warten auf die Platte. Colibrì betreibt einen Lookahead-Thread (aktiviert mit PILOT=1), der vorhersagt, welche Experten die nächste Schicht brauchen wird, und die Lesezugriffe früh startet. Die gemessene Zahl aus dem README lautet, dass Routing-Entscheidungen eine Schicht voraus zu 71,6 % vorhersagbar sind, was ausreicht, um einen großen Teil der I/O-Latenz hinter der Berechnung zu verstecken. Deshalb ist "tok/s nach dem Warmup" eine ganz andere Zahl als "kalte tok/s".

2. Dual-SSD-Streaming: zwei Platten, ein Modell, summierte Bandbreite​

Legen Sie eine vollständige Kopie des Modells auf eine zweite NVMe, und die Engine streamt von beiden gleichzeitig. Jeder Experte wird deterministisch einer Platte zugeordnet, gewichtet nach der gemessenen Bandbreite jeder Platte, sodass es kein doppeltes Caching gibt und die effektive Lesebandbreite ungefähr die Summe der beiden ist. Der DeepSeek-V4-Flash-Benchmark unten (RTX 5080 plus zwei NVMe-Platten, ~1,6 tok/s) ist eine Dual-Drive-Konfiguration.

3. Komprimierter KV-Zustand, der einen Neustart überlebt​

Modelle mit Multi-Head Latent Attention (MLA) erlauben Colibrì, einen komprimierten KV-Zustand zu speichern — 576 Floats pro Token statt 32.768, eine 57-fache Reduktion. Die Engine persistiert diesen Zustand in einer .coli_kv-Datei, sodass das Wiederöffnen einer Unterhaltung nach einem Neustart kein erneutes Prefill erfordert und byte-identisch mit einer Sitzung ist, die nie unterbrochen wurde. Auf einer Maschine, auf der das Prefill mit Streaming-Geschwindigkeit läuft, ist das Vermeiden eines erneuten Prefills eines langen Kontexts der Unterschied zwischen nutzbar und nicht nutzbar.

4. Die Semantik ist garantiert, die Geschwindigkeit nicht​

Der erklärte Vertrag des Projekts: Zu wenig schneller Speicher macht es nur langsamer; Präzision und Router-Verhalten ändern sich nie stillschweigend. Der Forward-Pass wird token-exakt gegen ein transformers-Orakel validiert. Das ist der gegenteilige Tausch zu den meisten "passt auf einen Laptop"-Quantisierungsgeschichten, bei denen man Geschwindigkeit bekommt, indem man ein anderes Modell akzeptiert.

Die Benchmark-Tabelle, ehrlich gelesen​

Zahlen aus dem README des Projekts (GLM-5.2, sofern nicht anders angegeben), warmer Cache wo vermerkt:

HardwareTok/sWas es bedeutet

Die Variable, die Ihre Zahl bestimmt, ist die Random-Read-Bandbreite der Platte, nicht die CPU. Ein kaltes Token braucht Expertenlesezugriffe in der Größenordnung von 11 GB; eine PCIe-5.0-NVMe mit 13–15 GB/s begrenzt ein kaltes Setup ohne Prefetch daher auf knapp 1 tok/s, und Lookahead plus Cache-Treffer sind das, was Sie darüber bringt. Kommentatoren im Launch-Thread berichteten von Cache-Trefferquoten um 23 % auf einem Apple M5 Max mit 128 GB und 0,091 tok/s auf einem alten Dual-Xeon mit 192 GB DDR3 — "brauchbar für Nachtjobs".

Die ehrlichen Anwendungsfälle sind also: nächtliche oder asynchrone Batches, private Offline-Experimente mit einem Modell der Frontier-Klasse, Forschung dazu, wie sich MoE-Inferenz tatsächlich verhält, und warmer Multi-Turn-Chat auf einer Maschine mit 100 GB+ RAM. Interaktives Pair-Programming auf einem 32-GB-Laptop steht nicht auf der Liste.

Wenn Sie bereits Kimi-K3- oder DeepSeek-V4.1-Flash-Gewichte aus einem vLLM-Deployment haben, liest Colibrì genau diese Dateien.

Vier Fallstricke, die Leute Tage kosten​

  1. MTP-Heads müssen int8 sein. Multi-Token-Prediction-Draft-Heads, die auf int4 quantisiert sind, liefern 0–4 % Draft-Akzeptanz — spekulatives Decoding tut stillschweigend nichts (Issue #8). Der vorkonvertierte GLM-5.2-Container auf Hugging Face ist genau aus diesem Grund int4 für das Modell und int8 für MTP.
  2. O_DIRECT hilft auf manchen Platten und schadet auf anderen. Das Umgehen des Page-Caches brachte gemessene +34 % auf NVMe-Platten mit DRAM-Cache und Bandbreitenreserve und war neutral bis negativ auf QLC-, DRAM-losen und virtualisierten Platten. Benchmarken Sie beides auf Ihrer Platte; kopieren Sie nicht das Flag von jemand anderem.
  3. Spekulatives Decoding ist bei echtem Chat oft ein Nettoverlust. In Multi-Turn-Unterhaltungen akzeptierten die MTP- und Grammatik-Drafter etwa 1–10 von je 24 Tokens, und das Wiederabspielen des rekurrenten Attention-Zustands der Engine für abgelehnte Suffixe kostete mehr, als die akzeptierten Drafts einsparten. Für DeepSeek V4 maß das Projekt 495 Sekunden Wiederabspielen abgelehnter Suffixe und liefert standardmäßig beide Drafter abgeschaltet aus (V4_DRAFT=0, V4_MTP=0). Schalten Sie sie nur ein, wenn Sie einen Gewinn messen.
  4. SSD-Verschleiß ist real. Intensive Expertenlesezugriffe treiben den Page-Cache-Umschlag; das README warnt vor Verschleiß auf Consumer-Platten, und der Rat aus dem Launch-Thread war, Swap zu deaktivieren und ein Read-only-Mount für das Modellverzeichnis in Betracht zu ziehen. Ein 370-GB-Modell, das stundenlang pro Tag gestreamt wird, ist eine Arbeitslast, für die Consumer-NVMe nicht verkauft wurde.

Noch einer, weniger ein Fallstrick als eine Einschränkung: Das gelernte Experten-Pinning kann an Ihre Routing-Historie überangepasst sein. Es hilft bei wiederholten Arbeitslasten; die Maintainer sagen, es brauche noch Held-out-A/B-Tests über Sitzungen hinweg, bevor man den Gewinnen bei neuen Prompts trauen sollte.

Vom Clone zum ersten Token​

Guided walkthrough1 of 5
  1. git clone https://github.com/JustVugg/colibri && cd colibri/c && ./setup.sh — dann make -C c glm für GLM-5.2 oder make -C c inkling / make -C c kimi_k3 für die anderen. Beginnen Sie mit OLMoE (7 GB), um den Build zu bestätigen, bevor Sie sich auf Hunderte Gigabyte Downloads einlassen.
  2. ./coli convert --model /nvme/glm52_i4 lädt herunter und konvertiert Shard für Shard, einmalig. Für GLM-5.2 existiert auf Hugging Face ein vorkonvertierter int4-Container mit int8-MTP-Heads (mastouri/GLM-5.2-colibri-int4-g64-with-int8-mtp). DeepSeek V4.1 Flash und Kimi K3 brauchen keine Konvertierung: Richten Sie die Engine auf den veröffentlichten Checkpoint.
  3. COLI_MODEL=/nvme/glm52_i4 ./coli plan zeigt, welche Tensoren auf Ihrer Maschine in VRAM, RAM und auf der Platte landen; ./coli doctor führt eine Bereitschaftsprüfung durch. Wenn plan sagt, dass die meisten Experten auf einer langsamen Platte kalt sein werden, kennen Sie jetzt Ihre tok/s, bevor Sie einen Abend darauf verwenden.
  4. COLI_MODEL=/nvme/glm52_i4 ./coli chat für einen Terminal-Chat. ./coli web --model /nvme/glm52_i4 startet einen API-Server plus ein Dashboard, das Ebenenplatzierung, Cache-Trefferquote und Platten-I/O live anzeigt; ./coli serve ist die Headless-Variante. Aktivieren Sie PILOT=1 für Router-Lookahead auf jedem Setup, das von der Platte streamt.
  5. Probieren Sie O_DIRECT ein- und ausgeschaltet auf Ihrer konkreten Platte. Lassen Sie spekulatives Decoding aus, bis ein Benchmark auf Ihren eigenen Prompts zeigt, dass es gewinnt. Wenn Sie eine zweite NVMe haben, spiegeln Sie das Modell darauf für Dual-Drive-Streaming.

Ein minimaler erster Lauf auf GLM-5.2 (Linux, eine NVMe)

git clone https://github.com/JustVugg/colibri && cd colibri/c
./setup.sh
make -C c glm
./coli convert --model /nvme/glm52_i4        # one-time download + convert
COLI_MODEL=/nvme/glm52_i4 ./coli plan          # see what lands where
COLI_MODEL=/nvme/glm52_i4 PILOT=1 ./coli chat  # first streamed tokens

Colibrì vs. die Alternativen, die Sie bereits kennen​

PfadWorin er gut istWo sich Colibrì unterscheidet
llama.cpp / Ollama mit GGUF-Offload (unser Ollama-Leitfaden)Riesiger Modellkatalog, GPU-Offload, ausgereiftes Tooling; die GLM-5.2-Seite behandelt die 239-GB-Route mit dynamischem 2-Bit-GGUFGGUF-Offload braucht das gesamte quantisierte Modell in RAM plus VRAM (256 GB für GLM-5.2 bei 2 Bit). Colibrì braucht 16–24 GB RAM und eine große Platte, bei derselben Präzision, die das Labor veröffentlicht hat, nicht 2 Bit.
vLLM / SGLang auf gemieteten GPUs (Kimi-K3-Deploy-Leitfaden)Dutzende Tokens pro Sekunde, Batching, mehrere NutzerSchnell, weil alles im HBM resident ist. Colibrì existiert für den Fall, dass diese Hardware nicht verfügbar oder nicht erlaubt ist.
Gehostete API (DeepSeek, Z.ai, Moonshot)Mit Abstand am günstigsten pro Token, keine HardwareDer einzige Grund, Colibrì vorzuziehen, ist, dass die Gewichte und die Prompts die Maschine niemals verlassen dürfen oder dass Sie MoE-Inferenz selbst studieren wollen.

Die richtige Art, über Colibrì zu denken, ist nicht "ein schnelleres llama.cpp". Es ist das Werkzeug, das ein offenes Modell in Frontier-Größe auf einer Maschine verfügbar macht, die es sonst nicht laden könnte, bei einer Geschwindigkeit, um die man herum plant, statt auf sie zu warten. Für einen Privacy-first-Stack, der ein kleines schnelles lokales Modell für interaktive Arbeit mit einem großen langsamen für Batch-Jobs kombiniert, siehe Ein privater lokaler KI-Stack.
