权限与权限模式

进阶
最后验证时间：2026-08-18。

具体的规则语法和模式名称会不断演进——请以 Claude Code 官方的权限与权限模式文档为准。自 v2.1.283 起： auto 是所有套餐和提供商下交互式终端及 VS Code 会话的内置起始模式（见下文）。

请对照以下来源核实： 官方来源.

权限决定了 Claude Code 无需停下来询问你就能做什么。调得好，你既能保持流畅又不失控；调得不好，你要么对一切无脑放行，要么被提示淹没。

三种裁决​

每个可能的操作最终都会得到以下之一：

按 Enter 或空格键翻转卡片。使用左右方向键在卡片之间切换。已显示术语。

规则通常将一个工具与一个模式匹配，例如 allow Bash(npm run test:*) 或 deny Read(./.env)。

允许某个工具 + 模式

Bash(npm run test:*)

拒绝某个工具 + 模式

权限模式​

模式决定一次会话的整体姿态。共有六种。常用的几种可用 Shift+Tab 循环切换，也可以在设置中指定 permissions.defaultMode。

模式无需询问即可执行适用场景
default（显示为 Manual）仅读取日常工作、敏感改动
acceptEdits读取、文件编辑、常见文件系统命令受信任且范围明确的编辑会话
plan读取，以及在 auto 模式可用时由分类器批准的命令；从不编辑你的源代码大型或有风险的任务——参见 Plan Mode
auto （自 v2.1.283 起为交互式会话的起始模式）一切操作，由安全分类器审查提示疲劳才是真正风险的长任务
dontAsk你工作目录中的文件读取以及预先批准的工具；任何会触发提示的操作都会被拒绝锁定的 CI 和脚本
bypassPermissions一切操作，不做任何检查仅限沙箱/容器——绝不要在存有机密的机器上使用

auto 模式现在是 Claude Code 的默认模式​

自 Claude Code v2.1.283 起，auto 是所有套餐和提供商下交互式终端及 VS Code 会话的内置起始模式。在更早的版本中，自 2026 年 8 月 14 日起，它仅是 Pro、Max 和 Team 套餐新会话的默认模式。Anthropic 给出的理由（来自其对 1,000 多名付费用户的自测）：分类器拦截了 89% 的有害操作，而人工审查仅为 13.6%——因为习以为常的用户在没读的情况下就接受了约 97% 的人工提示。

两项例外保留了你的意图：

  • 如果你在用户设置中指定了 permissions.defaultMode，它会保持不变，除非你接受一次性的应用内切换提示。
  • 如果默认值由你的组织管理（Team/Enterprise 托管设置），则不会自动更改。

你随时可以在会话中用 Shift+Tab 循环切换模式。这些套餐上已经生效的一项相关变更：auto 模式发起的分类器调用不再计入你的用量限额。

提前启用（8 月 14 日之前）——将 auto 设为默认

~/.claude/settings.json
{
"permissions": {
  "defaultMode": "auto"
}
}

8 月 14 日之后继续沿用旧的提示行为

~/.claude/settings.json
{
"permissions": {
  "defaultMode": "default"
}
}

auto 模式究竟如何运作​

auto 介于“凡事都提示”与“关闭安全机制”之间。它不再询问你，而是由一个独立的分类器模型在每个操作执行前进行审查，并拦截任何超出你所要求范围的操作、触及它不认识的基础设施的操作，或看起来由 Claude 刚读到的恶意内容驱动的操作。明确的 ask 规则仍会停下来询问你。

它会拦截 curl | bash、force push、生产环境部署和迁移、对未解析变量执行 rm -rf、篡改对话记录、会丢弃未提交工作的破坏性 git 命令，以及将机密发送到外部端点等操作——同时让日常工作（本地编辑、安装已声明的依赖、只读 HTTP、推送到你自己的分支）直接通过。如果同一操作被反复拦截，auto 模式会暂停，并把提示的决定权交还给你。

auto 模式并非安全保证——它减少提示，但并不免除审查敏感操作的必要。可用性取决于你的套餐、模型，以及（在 Team/Enterprise 上）管理员的开关。如果你要真正无人值守地运行（cron、云端会话、CI），请搭配 Hardening Autonomous Runs 使用——auto 仍然不是 bypassPermissions。

Watch out
  • bypassPermissions 只属于沙箱。在你的真实机器上关闭所有提示运行，正是代理最终碰到不该碰的东西的原因。请把它留给一次性环境——如果你真正想要的是减少提示，请改用 auto 模式。参见 /docs/security/hardening-autonomous-runs 上的 Hardening Autonomous Runs。

一份合理的初始 allowlist​

目标：预先允许安全且重复的操作；将破坏性操作保持在 ask 或 deny。

Guided walkthrough1 of 3
  1. 读取文件、运行你的测试/lint/构建命令、git status/diff。
  2. 安装依赖、在项目之外写入文件、网络调用。
  3. 读取机密文件（.env、密钥文件）、force-push、rm -rf。

将项目规则存放在 settings.json（共享），将个人覆盖存放在 settings.local.json。

Pro tip
  • 让它从你的提示中学习：把同一条安全命令批准几次，你就会清楚该往 allowlist 里加什么——把反复出现的提示变成一次性规则。
Key takeaways
  • 三种裁决：allow（不提示）、ask（默认——暂停并确认）、deny（绝不）。
  • 规则将工具与模式匹配，例如 Bash(npm run test:*) 或 Read(./.env)。
  • 六种模式决定会话姿态：default（Manual）、acceptEdits、plan、auto、dontAsk、bypassPermissions。
  • 自 v2.1.283 起，auto 是所有套餐下交互式终端和 VS Code 会话的起始模式；你自己设置的 defaultMode 保持不变，组织托管的默认值不受影响。
  • auto 模式用安全分类器审查每个操作，而不是提示你——这是应对提示疲劳的工具，而不是 bypassPermissions。
  • 建立 allowlist：安全且重复的用 allow，中等风险的用 ask，破坏性的用 deny。
  • 共享规则放在 settings.json；个人覆盖放在 settings.local.json。
