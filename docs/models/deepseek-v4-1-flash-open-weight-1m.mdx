At 04:00 UTC on **September 10, 2026**, DeepSeek flipped its API to a new model and published the weights the same day: **DeepSeek-V4.1-Flash**, served as `deepseek-flash`. It is the smallest member of a new architecture family, but it is not a small model: **552 billion parameters**, a **1-million-token context**, **native vision**, and a KV cache that costs **890 bytes per token**. On DeepSWE v1.1, the long-horizon software-engineering benchmark both Google and Anthropic now headline, DeepSeek reports **74.2**, one-fifth of a point above Claude Opus 5. On Terminal-Bench 4.0 it reports **31.2** against Opus 5's **51.8**. Both numbers are true, and the gap between them is the whole story.

This page is the field guide for a Claude user: what actually changed, the routing change that quietly re-pointed every `deepseek-v4-pro` request, the effort dial and what it does to your bill, how to run the weights, and the workloads where Claude is still the right call.

## The one-sentence version

V4.1-Flash is DeepSeek's first model on a **new architecture** (a "Causal Encoder-Decoder" with **Compressed Sparse Attention 2**), released MIT-licensed with **native vision**, a **1M-token window**, **384K max output**, and a **continuously controllable reasoning effort from 1 to 100**. It replaces every V4-era Flash endpoint immediately and, since **September 14**, also answers every `deepseek-v4-pro` call at Flash prices until V4.1-Pro lands.

## Three things a Claude user should not miss

### 1. DeepSWE parity and Terminal-Bench deficit are the same fact seen twice

DeepSeek's launch table, in the columns that matter for an agent shop:

| Benchmark | DeepSeek-V4.1-Flash | Claude Opus 5 | GPT-5.6 Sol |
| --- | --- | --- | --- |
| **DeepSWE v1.1** (resolved) | **74.2** | 74.0 | 73.0 |
| **Terminal-Bench 3.0** | 30.0 | **43.3** | — |
| **Terminal-Bench 4.0** | 31.2 | **51.8** | — |
| **CyberGym** | 88.1 | — | — |
| **AutomationBench** | 54.8 | — | — |

DeepSWE rewards a model that reads a repository, plans a patch, and lands it: long context, careful retrieval, a few large edits. Terminal-Bench rewards many short, adaptive shell turns where each decision depends on the last tool result. V4.1-Flash has 1M tokens of context and a cheap cache, so the first shape suits it. It runs **8B active parameters per token at prefill and 16B at decode**, which is a lot less "thinking per step" than a dense frontier model, so the second shape hurts. If your work looks like a pull request, the parity claim is credible and worth an eval. If your work looks like an interactive terminal session, the 20-point Terminal-Bench gap is the number to budget around. The same split shows up in Google's [Gemini 3.8 Flash](/docs/models/gemini-3-8-flash) launch a week earlier, and for the same architectural reasons.

The base-model rows tell a quieter story: **MMLU-Pro 74.1** (V4-Flash 68.3, V4-Pro 73.5), **HumanEval 79.4** (V4-Flash 69.5), **GSM8K 93.0** (V4-Flash 90.8). The new "Flash" is a better base than last month's "Pro", which is why DeepSeek was comfortable routing Pro traffic onto it.

### 2. The reasoning-effort dial is a real dial, and it is on your bill

Unlike Claude's `effort` (`low`/`medium`/`high`/`max`), V4.1-Flash exposes an **integer from 1 to 100**. DeepSeek's own ablation on DeepSWE v1.1: **effort 25 scores 66.0%, effort 100 scores 74.2%**, and the top setting emits **roughly 2.5× as many output tokens**. They also say the **60–80 band delivers most of the maximum-effort accuracy at less than half the token budget**. Every benchmark row above was run at `reasoning_effort=100`. So the parity number is the expensive number. Reproduce it at 100 first, then walk down to the cheapest setting your evals still pass at. That is the same discipline we recommend for `thinking_level` on Gemini and `effort` on Claude in [Reasoning models compared](/docs/models/reasoning-models-compared).

### 3. Two routing changes happened without a client-side change

- From **September 10**, `deepseek-v4-flash` and `deepseek-v4-flash-vision-exp` **route to V4.1-Flash**, billed at Flash rates. The [V4-Flash-Vision-Exp](/docs/models/deepseek-v4-flash-vision-open-multimodal) page's numbers now describe the open weights, not the hosted endpoint.
- From **04:00 UTC September 14**, every `deepseek-v4-pro` request **also routes to V4.1-Flash** at Flash rates, "until V4.1-Pro launches".

If you have evals pinned to `deepseek-v4-pro`, your production model changed under you on Sunday morning. Re-run the suite. The upside is that the same call now costs roughly a quarter of the Pro rate; the downside is that any Pro-specific behavior you tuned for is gone. This is exactly the failure mode [Porting prompts across models](/docs/models/porting-prompts-across-models) warns about when a provider aliases model IDs.

## Model card at a glance

| Spec | DeepSeek-V4.1-Flash |
| --- | --- |
| **API model ID** | `deepseek-flash` |
| **Release** | September 10, 2026 (API + open weights same day) |
| **Parameters** | 552B total; 8B active at prefill, 16B at decode |
| **MoE layout** | 384 routed + 1 shared expert per MoE layer; 6 routed experts active per token |
| **Architecture** | Causal Encoder-Decoder, Compressed Sparse Attention 2 (CSA2) |
| **KV cache** | 890 bytes per token (FP4, E2M1): ~1/4 of V4-Flash in HBM, ~1/8 in SSD storage; global KV cache lifetime at least 72 hours |
| **Context / max output** | 1M tokens / 384K tokens |
| **Vision** | Native; DeepSeek-ViT trained from scratch, 2D-RoPE, 3×3 pixel-unshuffle downsampling |
| **Reasoning control** | `reasoning_effort` integer 1–100 |
| **License** | MIT |
| **Weights** | Safetensors in BF16, F32, F8_E4M3, I8 |
| **Serving** | vLLM, SGLang, Docker Model Runner, Transformers; reference inference code in the `inference/` folder |
| **Recommended sampling** | temperature 1.0, top_p 0.95 or 1.0, context 1M |
| **API concurrency** | 2,500 |

The KV-cache line is the architectural headline. A 1M-token conversation at 890 bytes per token is under a gigabyte of cache, which is why DeepSeek can promise a 72-hour cache lifetime and price cache hits at fractions of a cent. Anthropic's answer to the same problem is a cheaper cache-read rate on [Claude Fable 5.1](/docs/models/fable-5-1-field-guide); DeepSeek's is to make the cache physically small. Both push you toward the same habit: put the stable prefix first and never edit it mid-run. See [Prompt caching](/docs/api/prompt-caching).

## Pricing: the peak-hour trap

DeepSeek keeps a two-rate schedule. **Peak hours are 01:00–04:00 and 06:00–10:00 UTC, Monday through Friday**; everything else is off-peak at exactly **half** the peak rate.

| Per 1M tokens | Peak | Off-peak |
| --- | --- | --- |
| Input, cache hit | $0.006 | $0.003 |
| Input, cache miss | $0.30 | $0.15 |
| Output | $1.20 | $0.60 |

Two things follow. First, the "$0.003 per million" headline is the *off-peak cache-hit* price, the cheapest of six cells; a cold, peak-hour agent run pays 100× that on input. Second, the peak window is defined in UTC and covers the European morning and the tail of the U.S. night. A batch job scheduled at 09:00 UTC pays double what the same job pays at 11:00 UTC. If you can shift, shift. For a framework that puts these cells beside Anthropic, OpenAI, and Google list prices, use [What AI costs across providers](/docs/models/what-ai-costs-across-providers); current Claude list prices live on [Models and pricing](/docs/whats-new/models-and-pricing).

## Running it yourself

Hosted is right for almost everyone: the model is enormous, and the API is the cheapest thing on this page. Self-host when data cannot leave your network or when you want the effort dial and 1M window without a rate limit.
