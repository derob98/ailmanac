Big tasks go better when you split them across focused [subagents](/docs/claude-code/subagents) instead of cramming everything into one context. Let's design a research → implement → review pipeline.

## The shape

```mermaid
flowchart TD
  G[Goal] --> R[Research subagent
  read-only, explores codebase]
  R --> P[Plan/Implement subagent
  scoped write access]
  P --> V[Review subagent
  read-only, adversarial]
  V -->|issues| P
  V -->|clean| D[Done]
```

Each subagent has its **own context** and a **tailored toolset** — and only the *result* flows back to the main session, keeping it clean.

## Step 1 — Define the agents

Via the `/agents` interface, define three, each with a tight `description` (so the main agent delegates correctly) and scoped tools:

<Steps items={[
  {title: "researcher — read and search only", body: "Maps the relevant code and returns findings. No write tools at all, which is what makes it safe to let it read widely. The heavy exploration happens here so it never lands in your main context."},
  {title: "implementer — can edit files and run tests", body: "Gets the researcher's findings as input, so it starts from a map instead of re-reading the codebase itself. Scoped write access: the narrower the set of files it can touch, the less it can surprise you."},
  {title: "reviewer — read-only, adversarial", body: "Looks for bugs, missing cases, and convention violations. Read-only on purpose: a reviewer that can fix what it finds stops reporting and starts patching, and you lose the signal."}
]} />

The `description` field is not documentation — it is the routing key the main agent reads when it decides whether to delegate. Vague descriptions are the single most common reason a subagent you defined never gets used.

<PromptCard title="A reviewer description that actually gets delegated to">{`Use this agent to review a completed code change adversarially before it ships.
Invoke it after the implementer reports done, and before telling the user the
task is finished. It reads the diff and the surrounding code and reports
problems; it does not fix them.`}</PromptCard>

## Step 2 — Orchestrate with handoffs

The main session passes each stage's output to the next: research → implement (using the research) → review (of the implementation). Add a **review gate**: if the reviewer finds issues, loop back to the implementer before finishing.

<PromptCard title="The handoff instruction that creates the gate">{`Run this as three stages, and do not skip the gate:

1. Delegate the exploration to the researcher. Wait for its findings.
2. Give those findings to the implementer as its starting context.
   Do not ask it to re-explore.
3. Give the implementer's result to the reviewer. If the reviewer reports
   any issue, hand the issues back to the implementer and review again.
   Only report the task complete after a review that found nothing.`}</PromptCard>

## Step 3 — Know when NOT to do this

:::warning[Parallel/multi-agent isn't free]
- **Sequential dependencies** (implement needs research) stay sequential — don't fan out where order matters.
- **Shared file writes** can conflict — isolate with [git worktrees](/docs/claude-code/worktrees) or serialize.
- For small tasks, the coordination overhead exceeds the benefit. Use this for **sizeable, decomposable** work.
:::

## Step 4 — Verify

A good multi-agent run shows: a focused main context (heavy reading happened in the researcher), an implementation that reflects the research, and a review that actually caught something (or credibly signed off). If the reviewer is a rubber stamp, make its prompt **adversarial** ("try to find what's wrong").
