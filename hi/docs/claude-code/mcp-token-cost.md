# MCP का टोकन टैक्स

> Source: https://derob98.github.io/ailmanac/hi/docs/claude-code/mcp-token-cost · AILmanac (CC BY 4.0) · last verified 2026-11-10

MCP सर्वर जोड़ने से आपके पहले अनुरोध से पहले ही 50k–150k टोकन क्यों खर्च हो सकते हैं — और तीन समाधान: Tool Search, कोड एक्ज़ीक्यूशन, और यह जानना कि CLI कॉल कब जीतती है।

टोकन के आँकड़े और फ़ीचर के नाम (`defer_loading`, Tool Search Tool, Programmatic Tool Calling) Anthropic की इंजीनियरिंग पोस्टों से लिए गए हैं। Claude Code का अपना टूल-सर्च व्यवहार — कि यह डिफ़ॉल्ट रूप से चालू है, `ENABLE_TOOL_SEARCH` के मान, मॉडल की न्यूनतम सीमा और विवरण की अधिकतम सीमाएँ — [Claude Code MCP डॉक्स](https://code.claude.com/docs/en/mcp#scale-with-mcp-tool-search) से है, और यही वह जगह है जहाँ यह हिस्सा बदलता है। सटीक संख्याएँ उद्धृत करने से पहले दोनों की पुष्टि कर लें।
</VerifyNote>

Hacker News और X पर एक बहस बार-बार उठती रहती है: *जब वही काम CLI से कुछ सौ टोकन में हो जाता है, तो एक MCP ऑपरेशन पर दसियों हज़ार टोकन क्यों जलाए जाएँ?* यह MCP की बुराई जैसा लगता है। पर ऐसा नहीं है। सबसे ज़ोर से बहस करने वाले वही लोग हैं जिन्हें एजेंट पसंद हैं — बस उनका सामना बिल से हो चुका है। यह पेज उसी बिल की व्यावहारिक गाइड है: टोकन असल में कहाँ जाते हैं, वे दो लागतें जिन्हें लगभग कोई अलग नहीं करता, और वे तीन समाधान जो 150,000 टोकन के वर्कफ़्लो को 2,000 टोकन का बना देते हैं।

## एक नहीं, दो लागतें

जब आप कोई MCP सर्वर जोड़ते हैं, तो क्लाइंट उससे `tools/list` माँगता है और **हर टूल अपने पूरे JSON स्कीमा के साथ** वापस पाता है। वह पूरा ब्लॉक मॉडल के कॉन्टेक्स्ट में डाल दिया जाता है। ज़्यादातर लोग अपना मानसिक हिसाब यहीं रोक देते हैं। पर दो अलग टैक्स हैं, और दूसरा आमतौर पर बड़ा होता है।

**लागत 1 — टूल की परिभाषाएँ।** जुड़े हुए हर टूल का नाम, विवरण और पैरामीटर स्कीमा कॉन्टेक्स्ट में बैठा रहता है। Anthropic का अपना कथन: *"जब एजेंट हज़ारों टूल से जुड़े होते हैं, तो उन्हें कोई अनुरोध पढ़ने से पहले सैकड़ों हज़ार टोकन प्रोसेस करने पड़ते हैं।"* एक अकेला एंटरप्राइज़ सर्वर दर्जनों से सैकड़ों टूल प्रकाशित कर सकता है; तीसरे पक्ष के विश्लेषण 400 टूल वाले सर्वर को अकेले स्कीमा में लगभग 400,000 टोकन का बताते हैं — यानी 200k विंडो का दोगुना, और 1M विंडो का फिर भी 40%, जो पहले अनुरोध से पहले ही खर्च हो जाता है। (हर मॉडल की विंडो का आकार: [मॉडल और कीमतें](/docs/whats-new/models-and-pricing)।)

**लागत 2 — इंटरमीडिएट नतीजे।** जब मॉडल सीधे किसी टूल को कॉल करता है, तो **हर नतीजा मॉडल के कॉन्टेक्स्ट से होकर वापस गुज़रता है**, उन हिस्सों समेत जिन्हें आप उसे कभी पढ़ाना ही नहीं चाहते थे। Anthropic का उदाहरण: एक टूल से दो घंटे की मीटिंग का ट्रांसक्रिप्ट निकालकर दूसरे टूल को दें, तो पूरा ट्रांसक्रिप्ट मॉडल से *दो बार* गुज़रता है — संभवतः ~50,000 टोकन — सिर्फ़ एक पंक्ति का सारांश बनाने के लिए।

### प्राथमिक स्रोतों से आँकड़े

| समाधान | टास्क | पहले | बाद में | कमी |
| --- | --- | --- | --- | --- |
| MCP के साथ कोड एक्ज़ीक्यूशन | Google Drive → Salesforce वर्कफ़्लो | 150,000 | 2,000 | **98.7%** |
| Tool Search Tool | काम शुरू होने से पहले परिभाषाएँ लोड करना | ~77,000 | ~8,700 | **85%** |
| Programmatic Tool Calling | जटिल रिसर्च टास्क | 43,588 | 27,297 | **37%** |

तीनों पंक्तियाँ Anthropic के प्रकाशित आँकड़े हैं। हैरान करने वाली बात लागत नहीं, **सटीकता** है: Tool Search Tool के साथ टूल चुनने की सटीकता *बढ़ी* (Opus 4.5 का 79.5% → 88.1%; Opus 4 का 49% → 74%)। कॉन्टेक्स्ट में कम टूल भीड़ लगाएँ तो मॉडल सही टूल ज़्यादा बार चुनता है। यहाँ लागत और गुणवत्ता एक ही दिशा में चलती हैं, जो दुर्लभ है।

## समाधान 1 — टूल स्कीमा ज़रूरत पड़ने पर लोड करें

सारे स्कीमा शुरू में ही डालने के बजाय उन्हें `defer_loading: true` से चिह्नित करें। तब Claude को सिर्फ़ एक हल्का इंडेक्स दिखता है; जब उसे GitHub चाहिए, तो वह **Tool Search Tool** को कॉल करता है, जो *सिर्फ़* मेल खाने वाले GitHub स्कीमा लौटाता है — बाकी हर सर्वर के 50+ टूल नहीं। Anthropic के अनुसार इससे ~191,300 टोकन का कॉन्टेक्स्ट बचता है, जबकि सब कुछ पहले से लोड होने पर ~122,800 बचते हैं।

### Claude Code में यह पहले से चालू है

अगर आप MCP सर्वर के साथ Claude Code इस्तेमाल करते हैं, तो आप अभी यही पैटर्न देख रहे हैं। **टूल सर्च डिफ़ॉल्ट रूप से चालू है**: सत्र की शुरुआत में सिर्फ़ टूल के *नाम* और सर्वर के निर्देश लोड होते हैं, और जब किसी टास्क को ज़रूरत होती है, तब Claude `ToolSearch` कॉल से पूरा स्कीमा लाता है। इसलिए एक और सर्वर जोड़ने की क़ीमत उसके टूल के नाम हैं, उसके स्कीमा नहीं — Claude Code प्रति सर्वर टूल की कोई सीमा तय नहीं करता और कहता है कि व्यावहारिक सीमा आपके कॉन्टेक्स्ट-विंडो का बजट है।

एक बहुत दोहराया जाने वाला दावा सुधारने लायक है, क्योंकि वह आधा सही है। "कॉन्टेक्स्ट विंडो का ~10%" वाली सीमा असली है, पर वह डिफ़ॉल्ट ट्रिगर **नहीं** है — वह `ENABLE_TOOL_SEARCH` एनवायरनमेंट वेरिएबल का एक ऑप्ट-इन मोड है:

| `ENABLE_TOOL_SEARCH` | व्यवहार |
| --- | --- |
| *(सेट नहीं)* — डिफ़ॉल्ट | हर MCP टूल डिफ़र्ड, ज़रूरत पड़ने पर लोड |
| `true` | सेट न होने जैसा ही |
| `auto` | थ्रेशहोल्ड मोड। डिफ़र किए जा सकने वाले टूल तब तक **पहले से** लोड होते हैं जब तक उनकी परिभाषाओं का कुल योग कॉन्टेक्स्ट विंडो के 10% से कम है; 10% या उससे ज़्यादा होने पर टूल सर्च चालू हो जाता है |
| `auto:N` | आपके अपने प्रतिशत के साथ थ्रेशहोल्ड मोड (`N` 0–100 है), जैसे `auto:5` |
| `false` | हर MCP टूल पहले से लोड, कोई डिफ़र नहीं |

इसलिए अगर आप मान रहे थे कि 10% से नीचे टूल पहले से लोड होंगे, तो आपने डिफ़ॉल्ट उलटा समझा है — जब तक आप `auto` न माँगें, कुछ भी पहले से लोड नहीं होता। और `auto` **चिपकू** है: कुल योग के सीमा पार करते ही टूल सर्च चालू हो जाता है, और योग के फिर सीमा से नीचे आ जाने के बाद भी वे टूल डिफ़र्ड रह सकते हैं।

अगर आप MCP सर्वर लिखते हैं, तो डिफ़र करना आपके विवरण के बजट को भी बदलता है, और असमान रूप से: **पहले से** लोड होने वाला टूल 4,096 अक्षरों पर कट जाता है (सर्वर के निर्देशों जितनी ही सीमा), जबकि **टूल सर्च के ज़रिए** लोड होने वाला 16,384 पर। पर सर्च खुद सिर्फ़ छोटी सीमा के विरुद्ध मिलान करता है, इसलिए जिन शब्दों से Claude खोजेगा, उन्हें दोनों ही स्थितियों में शुरुआत के पास होना चाहिए।

## समाधान 2 — कोड एक्ज़ीक्यूशन से नतीजों को कॉन्टेक्स्ट से बाहर रखें

गहरा समाधान लागत 2 को निशाना बनाता है। मॉडल के एक-एक करके टूल कॉल करने और हर नतीजे के उसके भीतर से गुज़रने के बजाय, मॉडल **कोड लिखता है** जो टूल को कॉल करता है, और इंटरमीडिएट डेटा एक्ज़ीक्यूशन एनवायरनमेंट में ही रहता है। Anthropic MCP सर्वरों को **टूल्स के फ़ाइल ट्री** के रूप में सामने रखता है, जिसे एजेंट फ़ाइलसिस्टम की तरह खंगालता है और सिर्फ़ ज़रूरी परिभाषाएँ लोड करता है — और *"इंटरमीडिएट नतीजे डिफ़ॉल्ट रूप से एक्ज़ीक्यूशन एनवायरनमेंट में रहते हैं… एजेंट सिर्फ़ वही देखता है जो आप स्पष्ट रूप से लॉग या रिटर्न करते हैं।"*

यही एक डिज़ाइन बदलाव Drive→Salesforce वर्कफ़्लो को 150,000 से 2,000 टोकन पर ले आता है: रिकॉर्ड कोड के भीतर घूमते हैं, और मॉडल के पास सिर्फ़ अंतिम गिनती लौटती है। Developer Platform पर यही विचार **Programmatic Tool Calling** के रूप में आता है — Claude Python लिखता है जो कई टूल को ऑर्केस्ट्रेट करता है और आउटपुट को उसके कॉन्टेक्स्ट तक पहुँचने से पहले ही फ़िल्टर कर देता है।

<Callout type="tip" items={["अँगूठे का नियम: अगर कोई टूल कुछ बड़ा लौटाता है (ट्रांसक्रिप्ट, क्वेरी डंप, फ़ाइल), तो आपको कोड एक्ज़ीक्यूशन चाहिए ताकि वह ब्लॉब कॉन्टेक्स्ट के बाहर प्रोसेस हो। अगर टूल बस कुछ छोटा करता है (इश्यू बनाना, एक पंक्ति भेजना), तो सीधी कॉल ठीक है।"]} />

## समाधान 3 — जानें कि CLI कॉल कब सीधे जीत जाती है

कभी-कभी सही जवाब बेहतर MCP सेटअप नहीं, बल्कि MCP का न होना है। HN/X की बहस में एक असली बात है: `gh pr list` या `psql -c '…'` जैसी शेल कमांड आने-जाने में कुछ सौ टोकन की पड़ती है, जबकि बराबर का MCP रास्ता स्कीमा के साथ एक संरचित नतीजे की भी क़ीमत चुकाता है। अगर एजेंट के पास पहले से टर्मिनल है और CLI मौजूद है, तो अक्सर वही सबसे हल्का रास्ता है।

<PromptCard title="जब टूल पहले से CLI हो तो CLI को प्राथमिकता दें">

MCP अपना ओवरहेड तब वसूल करता है जब आपको **टाइप्ड, अनुमति-नियंत्रित, कई सतहों पर चलने वाली** क्षमता चाहिए — रीड-ओनली रोल वाला डेटाबेस, एक ब्राउज़र जिसे वह चला सके, OAuth वाला SaaS API — या जब वही टूल कई टर्न में दोबारा इस्तेमाल होते हैं और कैशिंग स्कीमा की लागत को बाँट देती है। CLI तब चुनें जब क्षमता एक बार की हो, पहले से स्क्रिप्ट की जा सकती हो, और कुछ छोटा लौटाती हो। दोनों में से कोई "बेहतर" नहीं है; वे लागत-वक्र पर अलग-अलग बिंदु हैं।
