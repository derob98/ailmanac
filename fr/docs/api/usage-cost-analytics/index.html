L'API Usage & Cost Analytics : attribuer chaque dollar

Avancé
What you'll learn
  • Ce qui a remplacé usage_report et cost_report, et pourquoi la nouvelle forme est faite de lignes plutôt que de tranches de temps
  • Le contrat d'une ligne : starting_at / ending_at, group, et usage ou cost, et pourquoi une dimension vaut null sauf si vous avez groupé par elle
  • group_by[] accepte cinq dimensions, sauf les deux de l'endpoint cost qui ne comptent pas et n'obéissent pas à limit
  • Le modèle d'acteur : utilisateur, compte de service, identité cloud fédérée, ou la clé API elle-même, et pourquoi api_key_ids[] et actor_ids[] répondent à des questions différentes
  • Le piège des centimes : amount est une chaîne décimale en CENTIMES, donc "41280.000000" vaut 412,80 $ et un tableau de bord naïf se trompe d'un facteur 100
  • Les règles de fraîcheur des données qui invalident un tableau de bord du jour même, et l'astuce pour obtenir des résultats qui ne changent pas entre deux appels
  • La recette en une ligne du coût Claude Code par utilisateur
Dernière vérification : 2026-11-02.

L'API Usage and Cost Analytics est en bêta : envoyez anthropic-beta: analytics-usage-cost-2026-08-24 ainsi qu'un en-tête anthropic-version à chaque requête. Anthropic a classé l'ancienne API Usage and Cost et les endpoints Claude Enterprise Analytics comme legacy le 29 octobre 2026 : toujours pris en charge, pas supprimés. Les chemins d'endpoints, noms de dimensions, limites et le format d'amount en centimes viennent du guide officiel et des références d'API usage et cost. Les tarifs eux-mêmes se trouvent dans Modèles & tarifs actuels.

Vérifiez auprès de la source officielle.

Deux endpoints, un seul travail : vous dire où est réellement passée votre dépense Claude.

  • GET /v1/organizations/analytics/usage : nombres de tokens et de requêtes.
  • GET /v1/organizations/analytics/cost : coût en USD.

Pour une organisation Claude Console, c'est à peu près ce que montrent les pages Usage et Cost de la Console, avec les dimensions que vous choisissez plutôt que celles qu'elles ont choisies. La raison de s'y intéresser est la question à laquelle personne ne peut répondre depuis la Console : lequel de mes clients, agents ou clés API est responsable de la ligne qui a monté ?

C'est du reporting, pas de l'application de règles

Rien ici n'arrête une facture. Pour cela, voir Plafonds de dépenses stricts — et notez que les deux sont complémentaires : les plafonds décident si la dépense a lieu, cette API vous dit qui l'a causée.

Identifiants, selon le type d'organisation​

OrganisationQuoi utiliser
Claude ConsoleUne clé Admin API, ou un jeton bearer OAuth avec le scope org:admin (envoyé en authorization: Bearer, pas en x-api-key)
Claude EnterpriseUne clé avec le scope read:analytics, créée dans claude.ai par le propriétaire principal après l'activation de l'Analytics API pour l'organisation

Donnez au service collecteur sa propre clé, gardez-la dans un gestionnaire de secrets, et définissez une expiration de clé pour que la rotation soit imposée plutôt que mémorisée. Là où c'est disponible, une règle Workload Identity Federation avec org:admin est strictement meilleure : jetons de courte durée, aucun secret longue durée à faire fuiter. Même raisonnement que pour l'Admin API en général.

Démarrage rapide​

Daily token usage by model, one week

curl --globoff "https://api.anthropic.com/v1/organizations/analytics/usage?\
starting_at=2026-09-01T00:00:00Z&\
ending_at=2026-09-08T00:00:00Z&\
time_bucket_width=1d&\
group_by[]=model&\
limit=100" \
-H "anthropic-version: 2023-06-01" \
-H "anthropic-beta: analytics-usage-cost-2026-08-24" \
-H "x-api-key: $ANTHROPIC_API_KEY"

--globoff compte : sans lui, curl essaie d'interpréter le [] de group_by[] comme une plage de glob.

Le contrat d'une ligne​

C'est la partie qui piège ceux qui migrent depuis les anciens endpoints, car la réponse est volontairement structurée autrement.

Guided walkthrough1 of 6
  1. starting_at et ending_at donnent la période couverte par la ligne, group contient toutes les dimensions, et usage (ou cost sur l'endpoint cost) contient les métriques. Dimensions et métriques sont dans des objets séparés : elles ne sont pas côte à côte comme dans l'ancien rapport.
  2. group contient toujours toutes les dimensions, mais chacune vaut null sauf si elle apparaît dans group_by[]. Une dimension groupée est AUSSI null sur les lignes qui n'ont pas de valeur pour elle : l'usage d'exécution de code, par exemple, a model: null. group_by[] accepte jusqu'à cinq dimensions.
  3. Chaque ligne est une combinaison des dimensions groupées, et toute combinaison ayant de l'usage ou du coût apparaît exactement une fois sur l'ensemble des pages d'une requête. Les combinaisons sans rien ne produisent aucune ligne. Sans group_by[] ni time_bucket_width, vous obtenez une seule ligne totalisant toute la plage.
  4. Réglez time_bucket_width sur 1m, 1h ou 1d pour découper chaque combinaison par tranche UTC ; le starting_at et le ending_at de chaque ligne bornent alors sa tranche. Il n'y a pas de défaut : omettez-le pour des totaux sur toute la plage. Les tranches vides ne produisent aucune ligne.
  5. Par défaut, les lignes reviennent ordonnées selon la métrique order_by sur toute la plage, les plus grandes d'abord (order=asc inverse). Pour une série temporelle, réglez time_bucket_width ET order_by=time : les lignes arrivent alors tranche par tranche, la plus récente d'abord par défaut, avec les plus grosses lignes d'abord à l'intérieur de chaque tranche. Vous remplissez vous-même les tranches vides avec des zéros.
  6. La plupart des dimensions groupables ont un filtre de liste à notation par crochets correspondant, p. ex. models[]=claude-opus-5-5. Répétez le paramètre pour plusieurs valeurs, jusqu'à 100 par filtre. Plusieurs valeurs d'un même filtre sont un OR ; des filtres différents sont un AND. Vous pouvez filtrer par une dimension sans grouper par elle, ou l'inverse.

order_by sur l'endpoint usage accepte total_tokens (défaut), output_tokens, uncached_input_tokens, requests ou time. Sur l'endpoint cost : amount (défaut), list_amount ou time.

Le classement par défaut est le bug silencieux des tableaux de bord

Si vous demandez une plage et tracez les lignes dans l'ordre où elles arrivent, vous obtenez un diagramme à barres trié par taille qui ressemble à une série temporelle. Vous n'obtenez des lignes chronologiques que si vous réglez à la fois time_bucket_width et order_by=time.

Toutes les dimensions ne vous concernent pas​

model et actor s'appliquent à toutes les organisations. api_key_id n'existe que pour la Console. slack_channel_id n'existe que pour Enterprise. Une dimension qui ne s'applique pas vaut null sur chaque ligne et son filtre ne correspond à rien, silencieusement. La seule exception est rbac_group_id, qui renvoie plutôt une erreur quand les équipes ne sont pas disponibles pour votre organisation.

Et un changement de comportement à afficher au mur : dans l'ancienne API, un ID de clé API ou de workspace inconnu renvoyait une erreur. Ici, il ne correspond à rien, y compris une valeur models[] mal orthographiée. Un résultat vide est désormais la réponse normale à une faute de frappe.

Acteurs : qui reçoit la charge​

La dimension actor désigne à qui une requête est attribuée : un utilisateur, un compte de service, une identité cloud fédérée (un principal AWS ou Google Cloud, pour les organisations qui accèdent à Claude via leur plateforme cloud) ou, quand aucun de ceux-ci n'est derrière, la clé API elle-même. Groupez par actor et l'actor de chaque ligne est un objet dont le type dit de quel genre il s'agit. L'usage attribuable à aucune identité a actor: null.

Les règles de correspondance :

  • Les clés personnelles et les clés de compte de service agissent comme l'utilisateur ou le compte de service auquel elles sont liées : l'identité apparaît dans actor, la clé dans api_key_id.
  • Les clés de workspace legacy ne sont liées à aucune identité, donc la clé apparaît à la fois dans actor et dans api_key_id.
  • Une clé que Claude Code crée pour un membre à la connexion vit dans le workspace Claude Code, et son usage est attribué à ce membre.
  • Les requêtes sans aucune clé API (depuis la Console, depuis Claude Code après une connexion sans clé API, ou avec un jeton Workload Identity Federation) ont api_key_id: null. L'actor est toujours le membre connecté ou, pour une charge de travail fédérée, son compte de service.
Deux filtres, deux questions différentes

api_key_ids[]=apikey_… correspond à toutes les requêtes que cette clé a authentifiées, quelle que soit leur attribution. actor_ids[]=apikey_… ne correspond qu'aux requêtes attribuées à la clé elle-même. Ils ne sont pas interchangeables, et les confondre est la façon dont un audit revient incomplet. Pour inclure l'usage sans clé dans un filtre api_key_ids[], ajoutez une entrée vide : api_key_ids[]=.

L'endpoint cost, et le piège du facteur 100​

L'endpoint cost accepte les mêmes filtres, dimensions et tranches de temps que /usage. L'objet cost de chaque ligne contient :

ChampSignification
amountCoût après remises, avant application des crédits
list_amountCoût au tarif catalogue
currencyToujours "USD"
requestsNombre de requêtes
amount est en CENTIMES, pas en dollars

currency dit "USD", mais le nombre est une chaîne décimale en centimes avec six décimales. "41280.000000" vaut 412,80 $, pas 41 280 $. L'ancien rapport de coûts renvoyait des chaînes de type dollars comme "123.45" ; la même valeur est ici "12345.000000". Divisez par 100 avant d'afficher quoi que ce soit, et écrivez le test : c'est une erreur d'un facteur 100 qui passe la revue de code parce que le champ s'appelle amount et que le champ de devise dit dollars.

Deux dimensions n'existent que sur l'endpoint cost, et toutes deux enfreignent les règles habituelles en votre faveur : group_by[]=cost_type découpe chaque ligne par type de coût, et group_by[]=token_type découpe le coût des tokens par type de token. Aucune ne compte dans la limite de cinq dimensions, et aucune n'obéit à limit : une page peut donc légitimement contenir plus de lignes que limit.

Where the money went: cost by model, cost type, and token type for a month

curl --globoff "https://api.anthropic.com/v1/organizations/analytics/cost?\
starting_at=2026-09-01T00:00:00Z&\
ending_at=2026-10-01T00:00:00Z&\
group_by[]=model&\
group_by[]=cost_type&\
group_by[]=token_type" \
-H "anthropic-version: 2023-06-01" \
-H "anthropic-beta: analytics-usage-cost-2026-08-24" \
-H "x-api-key: $ANTHROPIC_API_KEY"

Cette unique requête est celle qui vaut la peine d'être lancée en premier sur toute organisation, car elle répond à la question que la plupart des équipes devinent : quelle part de la facture n'est pas de l'inférence du tout. Découper par cost_type sépare la dépense en tokens de l'outillage côté serveur ; découper par token_type sépare les lectures en cache de l'entrée non cachée et de la sortie. Si les lectures en cache dominent votre ligne d'entrée, Prompt Caching et Diagnostics du cache sont la prochaine étape ; si ce sont les tokens de sortie, c'est Réduire sa consommation de tokens.

Per-user Claude Code cost, in one query

curl --globoff "https://api.anthropic.com/v1/organizations/analytics/cost?\
starting_at=2026-10-01T00:00:00Z&\
ending_at=2026-11-01T00:00:00Z&\
products[]=claude_code&\
group_by[]=actor" \
-H "anthropic-version: 2023-06-01" \
-H "anthropic-beta: analytics-usage-cost-2026-08-24" \
-H "x-api-key: $ANTHROPIC_API_KEY"

Les organisations Console ont une seconde option pour cela : la Claude Code Analytics API dédiée, qui rapporte l'activité Claude Code par utilisateur avec un coût estimé.

Plages de dates, et l'arrondi que personne n'attend​

  • Les horodatages sont en RFC 3339 avec un décalage UTC (2026-09-01T00:00:00Z). starting_at est inclusif, ending_at est exclusif.
  • starting_at doit être à partir du 1er janvier 2026 et dans les 365 derniers jours.
  • Une requête couvre au plus 31 jours. ending_at vaut par défaut 31 jours après starting_at, ou maintenant, le plus tôt des deux. Découpez les plages plus longues en plusieurs requêtes.
  • ending_at est obligatoire dès que time_bucket_width est défini, et avec time_bucket_width=1m la durée est d'au plus 24 heures.
  • Les deux bornes sont arrondies vers le bas à une limite de tranche, ou à l'heure quand time_bucket_width n'est pas défini. Avec des tranches 1h, starting_at=2026-09-01T10:43:00Z devient 10:00:00Z et ending_at=2026-09-01T15:43:00Z devient 15:00:00Z, si bien que la réponse couvre 10:00–15:00 UTC. Une requête « les 90 dernières minutes » écrite naïvement renvoie une heure.

La fraîcheur des données est ce qui casse les tableaux de bord​

Chaque réponse porte un horodatage data_refreshed_at. L'usage postérieur à cette heure est manquant ou partiel. Quand aucune donnée n'existe encore pour une partie de la plage, data_refreshed_at vaut null et data est vide.

PropriétéValeur
Décalage de rafraîchissement typiqueSous 4 heures après l'usage sous-jacent
Pire casJusqu'à 24 heures
Fenêtre de révisionLes valeurs peuvent changer à mesure que des événements tardifs et la réconciliation arrivent, jusqu'à environ 7 jours après la fin du mois calendaire
PaginationChaque page d'une même requête paginée lit le même instantané, donc data_refreshed_at est identique d'une page à l'autre

En pratique : les chiffres du 1er octobre peuvent encore changer jusqu'au 7 novembre environ.

C'est une vraie régression par rapport à l'ancienne API, où les données apparaissaient typiquement en 5 minutes, et cela change ce que vous pouvez construire. Deux règles en découlent directement :

  • Pour des résultats qui ne changent pas entre deux appels, réglez ending_at à une valeur égale ou antérieure à un data_refreshed_at que vous avez déjà vu.
  • Pour des totaux définitifs, n'interrogez que des mois terminés depuis au moins 7 jours.
Ne construisez pas d'alerte temps réel là-dessus

Une alerte de pic de coût avec 4 à 24 heures de décalage n'est pas une alerte. Utilisez l'API pour l'attribution, la refacturation et le reporting de tendances ; utilisez les plafonds de dépenses pour ce qui doit réagir en quelques minutes, et le tracing OpenTelemetry pour une visibilité quasi temps réel par requête, en vous rappelant que les traces sont best-effort et at-least-once : le grand livre, c'est l'Analytics API, pas vos traces.

Migrer depuis usage_report et cost_report​

Ce qui se conserve : votre clé Admin API, l'en-tête anthropic-version, starting_at / ending_at, les valeurs de largeur de tranche (1m, 1h, 1d), la notation par crochets, les noms des champs de pagination, et les noms des champs de tokens et de coûts. Ce qui change :

Le workspace par défaut a cessé d'être null : mettez à jour votre code de regroupement

Les anciens consommateurs traitaient souvent workspace_id: null comme cas particulier « Default Workspace ». Cette correspondance est désormais fausse, et un null signifie ici « non groupé par cette dimension ». Le workspace par défaut a un ID wrkspc_ normal, mais List Workspaces l'omet sauf si vous passez include_default=true, donc un ID inconnu dans vos lignes peut ne pas apparaître dans votre table de workspaces. Résolvez-le avec Get Workspace : le workspace par défaut renvoie "name": "Default".

Cette dimension user_profile_id est la plus intéressante sur l'API Claude elle-même : combinée aux profils utilisateur, elle transforme cette API en refacturation par client final pour une plateforme ou un revendeur : la même attribution qui limite le rayon d'impact de votre application de règles vous dit aussi ce que chaque client vous coûte.

  • Deux endpoints, /v1/organizations/analytics/usage et /cost, exigeant tous deux anthropic-beta: analytics-usage-cost-2026-08-24.
  • Divisez amount par 100. Ce sont des centimes avec six décimales, bien que currency indique USD.
  • Une dimension vaut null sauf si vous avez groupé par elle, et une combinaison sans données ne produit aucune ligne : comblez donc les zéros côté client.
  • Classé par défaut : une vraie série temporelle exige time_bucket_width ET order_by=time.
  • La fraîcheur est de 4 à 24 heures avec des révisions pendant ~7 jours après la fin du mois. C'est une infrastructure d'attribution et de refacturation, pas d'alerte.
  • api_key_ids[] (ce que la clé a authentifié) et actor_ids[] (ce qui est attribué à la clé) répondent à des questions différentes : choisissez délibérément.
  • Les fautes de frappe ne provoquent plus d'erreur. Un workspace, une clé ou un nom de modèle inconnu ne correspond silencieusement à rien.

  • L'Admin API : automatiser votre organisation Claude — les identifiants, scopes et conventions de pagination dont ces endpoints héritent.

  • Profils utilisateur & application des règles — la dimension user_profile_id qui transforme cette API en refacturation par client final.
  • Tracing OpenTelemetry natif — la visibilité par requête quand 4 heures de décalage sont trop lentes.
