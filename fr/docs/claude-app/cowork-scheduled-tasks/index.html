Cowork Scheduled Tasks : agents qui tournent sans appareil allumé

Intermédiaire
Dernière vérification : 2026-08-05.

Cowork sur web + mobile lancé le 7 juillet 2026 (Max d'abord, autres plans payants roulant dans les semaines suivantes). Disponibilité, quotas et couverture exacte des connecteurs évoluent rapidement — confirmez contre l'article officiel du blog et l'article du centre d'aide Schedule recurring tasks in Claude Cowork avant de vous fier à un chiffre ici.

Vérifiez auprès de la source officielle.

Cowork a cessé d'être un espace de travail desktop uniquement le 7 juillet 2026. Il tourne maintenant sur web (claude.ai), iOS et Android, et — la partie que la plupart des articles enterrent — les sessions s'exécutent sur les serveurs d'Anthropic, pas sur votre machine. Ce seul changement architectural débloque la fonctionnalité phare : des tâches planifiées qui tournent avec votre portable fermé, votre téléphone en poche, et aucun appareil en ligne.

Cette page est le guide pratique de terrain : ce qui fonctionne réellement sur quelle surface, comment configurer une tâche planifiée correctement du premier coup, et la poignée de pièges que vous ne remarquez qu'après que votre briefing du lundi 6h a silencieusement échoué parce qu'il avait besoin d'un fichier local.

What you'll learn
  • Comprendre pourquoi déplacer l'exécution de Cowork hors de votre appareil change le produit (runs planifiés, handoff cross-device, prompts d'approbation mobile) — et où atterrissent les compromis
  • Choisir la bonne surface (desktop / web / mobile) pour un travail donné, avec la matrice des capacités
  • Configurer une tâche Cowork planifiée correctement du premier coup, avec le bon mode d'approbation, la fréquence et le dossier de travail
  • Concevoir un flux d'approbation mobile qui ne cale pas silencieusement quand vous dormez ou êtes dans un avion
  • Éviter les quatre pièges qui cassent les runs planifiés en production : outils locaux uniquement, Fable-5-desktop-only, Dispatch vs Remote, et dérive d'auth des connecteurs

Le seul changement qui compte : les sessions ont bougé vers les serveurs d'Anthropic​

Avant juillet 2026, une session Cowork était un processus dans l'app Claude Desktop sur votre Mac ou PC. Fermez le portable, la session meurt. Tuez l'app, la session meurt. C'est pourquoi la boucle Cowork pré-juillet commençait toujours par « ouvrir desktop, garder éveillé ».

Le lancement de juillet introduit les sessions distantes : la boucle Cowork vit dans le cloud d'Anthropic, l'état de votre session et vos fichiers persistent contre votre compte Claude, et toute surface (web, mobile, desktop) n'est qu'un visualiseur + périphérique d'entrée pour la même session sous-jacente.

Deux conséquences directes :

  1. Les tâches planifiées sont possibles. Une tâche récurrente peut se réveiller le lundi 6h, faire 45 minutes de travail et déposer un brouillon dans votre compte — avec zéro appareil en ligne, parce qu'il n'y a pas d'appareil dans la boucle.
  2. Le handoff cross-device est gratuit. Démarrez une tâche à votre bureau, fermez le portable, et voyez la même session en cours sur votre téléphone. Rien à synchroniser — la session n'a jamais été sur votre portable.

Le compromis est la matrice de capacités ci-dessous : tout ce qui doit toucher votre machine locale (fichiers sur disque, votre navigateur, votre OS) ne peut tourner que sur desktop, parce que c'est la seule surface avec un pied dans les deux mondes.

Cowork interactif vs Tâche planifiée vs Dispatch​

Les trois modes sont confondus. Ce sont des bêtes différentes :

Guided walkthrough1 of 3
  1. Vous la démarrez, vous regardez, Claude travaille sur un long horizon sur votre objectif actif. Vit sur les serveurs d'Anthropic maintenant, donc vous pouvez la passer d'un appareil à l'autre. Idéal pour : travail multi-heures que vous voulez piloter au fur et à mesure.
  2. Vous définissez un prompt + une cadence (horaire / quotidien / jours ouvrés / hebdomadaire / manuel). Chaque run lance une session Cowork fraîche avec les outils, skills et plugins que vous avez spécifiés. Tourne à distance, sur planning, qu'un appareil soit en ligne ou non. Idéal pour : travail de prep récurrent — briefings du lundi 6h, triage horaire de la boîte, rollups de fin de journée.
  3. Forme legacy : lancez une tâche en arrière-plan depuis une session desktop active qui continue de tourner pendant que vous continuez à discuter. Nécessite que l'app desktop reste éveillée parce que le processus vit encore localement. Idéal pour : travail sur machine locale que vous voulez mettre en arrière-plan pendant que vous continuez à collaborer. Ne le confondez PAS avec une tâche planifiée distante — Dispatch meurt quand l'app se ferme.

Le raccourci mental : Dispatch = arrière-plan local, Tâche planifiée = cloud sur cadence, Interactif = vous êtes au volant.

Configurer une tâche planifiée, la bonne méthode​

Une tâche planifiée a besoin de six choses — cinq paramètres et un prompt. Ratez un des paramètres et le run aura l'air « réussi » mais fera la mauvaise chose.

Guided walkthrough1 of 6
  1. Court, humain. C'est ce que vous verrez dans la liste des tâches planifiées et dans les notifications mobiles. 'Prep client lundi' bat 'briefing-v2'.
  2. Écrivez-le comme si vous parliez à un collègue qui rejoint à zéro à chaque run — parce que chaque run EST une session fraîche. Énoncez l'objectif, les sources (quels connecteurs, quelles skills, quels dossiers), la forme de sortie que vous voulez, et tout invariant (par exemple 'ne jamais envoyer d'email, toujours laisser en brouillon').
  3. Choisissez parmi horaire / quotidien / jours ouvrés / hebdomadaire / manuel. Il n'y a pas de syntaxe cron et pas d'options sous-horaires — si vous avez besoin de 'toutes les 5 min', vous êtes sur le mauvais outil (utilisez l'API + votre propre scheduler).
  4. Le paramètre critique. Les options sont auto-approve (Claude procède sans demander, bien pour les tâches en lecture seule), ask-on-mobile (Claude s'arrête à un point de décision et ping votre téléphone — défaut sûr pour tout ce qui écrit), ou hold-for-review (la tâche se termine toujours par un brouillon que vous relisez plus tard).
  5. Par défaut le Cowork par défaut de votre plan. Choisissez un modèle plus petit/moins cher pour les boucles lourdes de lecture-résumé ; choisissez top-tier seulement quand la qualité du raisonnement bouge vraiment le résultat.
  6. Scopes les écritures de fichiers de la session à un projet/dossier spécifique dans votre compte Claude. Sautez-le et les sorties atterrissent dans un emplacement par défaut — ce qui va pour une tâche, une pagaille avec douze.

Template de prompt pour tâche planifiée : briefing client lundi 6h

You are preparing my Monday morning brief for the Acme account.

Every Monday at 06:00 local:

1. Read the last 7 days of email in the "Acme" Gmail label. Group by
 thread; note anything that expects a reply from me.
2. Pull calendar events with "Acme" in the title or attendees from
 the coming week. Note prep needed for each.
3. Search the web for news about Acme (company name + "acquisition",
 "layoffs", "product launch") in the last 7 days. Cite sources.
4. Read the Google Doc "Acme - Running Notes" for open questions.

Produce a single briefing doc titled "Acme brief — <this-monday-date>"
in the "Client briefings" project folder. Structure:

- 3-bullet TL;DR at the top
- "Needs a reply from me" list (with links)
- "This week" list (calendar + prep)
- "News since last brief" (with sources)
- "Open questions" (from the running-notes doc)

DO NOT send any email. Leave a follow-up email as a DRAFT in Gmail
titled "Acme weekly check-in" pre-filled with the TL;DR — I'll edit
and send.

Deux choses à noter sur ce prompt :

  • L'invariant (« DO NOT send any email... leave as DRAFT ») est explicité. Dans un run planifié vous ne pouvez pas poser un « êtes-vous sûr ? » de suivi — les invariants doivent être dans le prompt.
  • L'emplacement de sortie + nommage est précis. Quand ceux-ci tournent hebdomadairement pendant des mois, vous les voulez trouvables, pas éparpillés sous des titres par défaut.

Flux d'approbation mobile — concevoir pour « je dors »​

ask-on-mobile semble amical jusqu'à ce qu'il tire à 3h et que le run cale silencieusement en vous attendant. Deux règles rendent cela fiable :

Guided walkthrough1 of 2
  1. Actions en lecture seule ou brouillon uniquement → auto-approve. Tout ce qui envoie, publie, supprime ou dépense de l'argent → ask-on-mobile avec un fallback dans le prompt : 'si je n'ai pas répondu dans les 30 minutes, sauvegarde en brouillon et termine la tâche'. Le fallback au niveau du prompt est important parce que la plateforme ne va pas vous timer out à votre place.
  2. Dans le prompt, enveloppez les points de décision dans une demande spécifique : 'Avant d'envoyer quoi que ce soit, demande l'approbation avec la ligne de sujet exacte et les 200 premiers caractères du corps.' Les notifications push tronquent — mettez les bits importants en tête pour que vous puissiez approuver/refuser depuis l'écran de verrouillage sans ouvrir l'app.
Watch out
  • Les approbations push bloquent la tâche jusqu'à ce que vous répondiez. Si vous ne répondez jamais, le run reste là — il ne retombe pas automatiquement sur un défaut sûr. Intégrez un timeout 'si pas de réponse, faire X' dans le prompt lui-même, ou utilisez hold-for-review à la place.

Les quatre pièges qui cassent les runs Cowork planifiés​

Guided walkthrough1 of 4
  1. Si le prompt demande à la tâche d'« ouvrir mon dossier téléchargements », « automatiser mon navigateur », ou « prendre une capture d'écran de mon écran », la session distante n'a aucun moyen de le faire. Le run ne plantera pas — il sautera ou improvisera. Correctif : auditez vos prompts planifiés et remplacez les actions machine locale par des équivalents outil connecté (Google Drive au lieu des fichiers locaux, web fetch au lieu du navigateur local, etc.).
  2. Au lancement de juillet 2026, exécuter le modèle Fable 5 dans une session Cowork nécessite la dernière app Claude Desktop. Si vous planifiez une tâche qui épingle Fable 5 et comptez sur son exécution distante, vérifiez le support actuel — cette contrainte devrait se relâcher mais vérifiez avant d'épingler.
  3. Le travail Dispatch en arrière-plan depuis une session desktop active meurt quand vous fermez l'app. Si vous avez vraiment besoin de 'tourner ceci hebdomadairement, coûte que coûte', ne Dispatchez pas — créez une tâche planifiée.
  4. Les tokens OAuth vers Gmail, Slack, Google Drive peuvent expirer, être révoqués, ou subir des changements de permissions. Une tâche planifiée sous un connecteur expiré produit une sortie vide et aucune erreur évidente. Correctif : pour tout ce qui tourne hebdomadairement ou moins souvent, ajoutez une première étape d'auto-vérification dans le prompt ('confirme que tu peux lire le label Gmail Acme ; sinon produis une erreur d'une ligne en haut du doc et arrête').

Quand se tourner vers l'API à la place​

Les tâches Cowork planifiées sont une fonctionnalité produit — excellentes pour du travail récurrent personnel / petite équipe que vous voulez visible dans votre compte Claude, avec l'approbation humaine dans la boucle. Elles sont le mauvais outil quand vous avez besoin de :

  • Cadence sous-horaire — le plus petit intervalle de tâche planifiée est horaire.
  • Orchestration programmatique — des dizaines de runs parallèles, planification dynamique, ou intégration serrée avec votre infra. Tournez-vous vers les Managed Agents, ou faites le vôtre avec l'Agent SDK + un cron/queue que vous exploitez déjà.
  • Mémoire côté serveur entre les runs — les tâches Cowork passent l'état via des fichiers dans votre compte, ce qui va pour des docs mais est grossier pour l'état structuré. Pour la mémoire structurée cross-run, utilisez les Managed Agents Memory Stores.
  • Coordination multi-agents profonde — pour la collaboration entre beaucoup d'agents, voir Cowork & Agent Teams et Native Multi-Agent APIs.
