Claude Sonnet 5.5: The Field Guide

Intermediário

On 28 September 2026 Anthropic released Claude Sonnet 5.5 (claude-sonnet-5-5) — the second model in the 5.5 family, after Opus 5.5 six days earlier. The rate card is the interesting part precisely because it did not move: $2 in / $10 out per MTok, byte-for-byte Sonnet 5's prices, same tokenizer, same cache and batch rates. Anthropic's claim is nonetheless output more than 30% faster and up to 30% less per task.

Both can be true at once, and understanding why is the whole point of this page: on Sonnet 5.5 the saving lives in the token count and the turn count, never in the price per token. That changes what you measure, and it changes which knob you reach for first.

The second thing worth knowing on day one: the cheap model is not uniformly behind the expensive one. On Terminal-Bench 4.0 Sonnet 5.5 scores 70.6% against Opus 5.5's 66.4% — the one published row where the half-price model is ahead. And on knowledge-work Elo the two are a statistical tie. The gap that remains is concentrated somewhere specific, and this page says where.

What you'll learn
  • Know the real numbers: $2/$10 per MTok unchanged from Sonnet 5, 1M context, 128K max output (300K on Batches), June 2026 cutoff, default effort high
  • Fix the five breaking changes that 400-error a Sonnet 5 codebase, and the sixth that returns 200 and makes your progress UI go silent
  • Use between_tools correctly — the replacement for thinking disabled, which is rejected at xhigh and max effort and rejects every companion field
  • Read the launch table honestly: where Sonnet 5.5 beats Opus 5.5, where it is 8 points behind, and why one row reads 10.3%
  • Calibrate effort from scratch instead of carrying a setting over, and recover the ~1/3 of session cost that max effort spends on self-started review
  • Handle the quieter failure modes: structured-output requests that think until max_tokens, tool names off by letter case, and real user messages mistaken for prompt injection

Four things in that table are genuinely new, and only one of them is a headline anywhere:

  1. The minimum cacheable prompt halved, 1,024 → 512 tokens. If your system prompt sits in the 600–1,000 token range it was silently uncacheable on Sonnet 5 and is cacheable now, at 10% of input price on reads. No code change, no beta header. This is the cheapest win on the whole page.
  2. thinking: {"type": "disabled"} is gone, replaced by between_tools. Sonnet 5.5 sits between Sonnet 5 (which accepted disabled) and Opus 5.5 (which accepts neither) — it can still skip up-front thinking, just under a new name and with new limits.
  3. Default effort stayed high — note that this is higher than Opus 5.5's medium default. The cheaper model thinks more per turn out of the box than the expensive one.
  4. temperature, top_p and top_k return 400 at any non-default value, as on the rest of the 5.x line. Sampling-parameter sweeps are not a tuning surface here; effort is.

The tokenizer is unchanged from Sonnet 5, so the same text produces the same token counts. Any change you measure in your bill is a change in how many tokens the model chose to emit.

Why the bill drops when the price does not​

This is the part most launch coverage compresses into "30% cheaper" and gets subtly wrong. The rate card is identical. Anthropic's claim decomposes into three separate effects, and they are not equally easy to capture:

Guided walkthrough1 of 3
  1. Output is the expensive side at $10/MTok against $2 input. Sonnet 5.5 reaches the same result in fewer output tokens than Sonnet 5, which includes thinking tokens — thinking is billed as output even when its text is never returned to you. This effect you get for free, on the same code.
  2. Each avoided tool call removes a whole request: the resent conversation prefix on input, the latency, and a turn of overhead. In an agent loop that is usually a bigger line item than the output tokens themselves. Anthropic's own framing of Terminal-Bench 4.0 is that this is where token efficiency pays.
  3. Latency is not cost, but it is a cost in every interactive product, and it is the effect most likely to survive your own measurement unchanged. Note the ceiling: at medium effort and above the model thinks briefly before nearly every reply, greeting included, which adds to time-to-first-token no matter how fast generation is.

Effects 1 and 2 are exactly what a carried-over effort setting can cancel out. Which is why the next section is the one to read before you change your model ID.

Effort: recalibrate, do not carry over​

Anthropic is explicit that effort levels are recalibrated — a level does not buy the same amount of thinking it bought on Sonnet 5. There is no conversion table, by design. Re-run your sweep.

The published starting points are not the default:

WorkloadStart atWhy
General / unsurehighThe API default.
Agentic coding, multistep tool use, well-specifiedmediumThen move to high for harder or longer tasks.
Chat, latency-sensitivemedium or lowHigher effort means a longer wait before the reply starts.
Anythingxhigh / maxOnly where you have measured a quality gain.

Three consequences that bite in production:

  • Changing the top-level effort between requests invalidates the prompt cache. If you want a cheap interactive session that escalates on hard turns, use the per-message effort beta (output_config.effort on one message), which keeps the cache. This beta is new on 5.5 and was not available on Sonnet 5.
  • max_tokens has to cover thinking plus the reply. Thinking counts against it even when the thinking text is omitted from the response. A limit sized for a no-thinking request will truncate. For agentic coding Anthropic's guidance is blunt: set max_tokens to 128,000 and stream.
  • Asking the model to think less does not reliably work. Lowering the effort level does. From medium up it thinks before almost every reply; at low it skips thinking on most simple requests.

The max-effort review tax​

At xhigh and max, Sonnet 5.5 does not stop when the task is done. It starts its own rounds of review and verification, and if your harness offers subagents it will launch reviewer subagents — unasked. Anthropic published the fix and, unusually, the size of it: in their testing on coding tasks at max effort, the paragraph below cut session cost by about a third with no change in quality.

Stop self-started review rounds at xhigh and max effort

When the work the user asked for is done and its checks pass, stop and report. Don't start extra
rounds of review or hardening on your own, and don't launch reviewer sub-agents unless the user
asked for a review. If you think a deeper review is worth doing, say so at the end.

It makes self-started reviews rarer rather than impossible. The mirror-image problem exists at the bottom of the range: at low and medium on long agentic tasks the model is more likely to stop and check in before finishing, and at low it sometimes reports a code change done without running a check that exercises it.

The five breaking changes​

Each of these returns HTTP 400 invalid_request_error on code that worked on Sonnet 5.

1. disabled → between_tools​

thinking: {"type": "disabled"} returns 400 with a message that names its replacement:

"thinking.type.disabled" is not supported for this model. Use "thinking.type.between_tools" for the
lowest thinking setting, or "thinking.type.adaptive" and "output_config.effort" to control thinking
behavior.

between_tools is the lowest thinking setting on Sonnet 5.5. It needs no beta header and works on every platform that offers the model. But it is fussier than disabled ever was:

  • Accepted at low, medium, high. At xhigh or max it returns 400 — those levels require adaptive thinking (omit thinking, or send thinking: {"type": "adaptive"}; they are equivalent).
  • Effort cannot change mid-conversation. A per-message output_config.effort that differs from the level in effect returns 400. Per-turn effort needs adaptive thinking.
  • It takes no companion field. display, budget_tokens or block_binding sent alongside it returns 400. Manual budgets (thinking: {"type": "enabled", "budget_tokens": N}) return 400 too.
  • With server-side fallback, a between_tools request that falls back to Sonnet 5 runs there with thinking: {"type": "disabled"} — the settings map across the fallback for you.

One more trap: with between_tools, remove any instruction telling the model not to think. Those lines make it more likely to write internal XML tags into its visible output.

Migrating a thinking-off integration — Sonnet 5 to Sonnet 5.5

# Before — accepted on Sonnet 5
client.messages.create(
  model="claude-sonnet-5",
  max_tokens=16000,
  thinking={"type": "disabled"},
  output_config={"effort": "xhigh"},      # fine with disabled on Sonnet 5
  messages=[{"role": "user", "content": "..."}],
)

# After — on Sonnet 5.5: rename the type AND drop effort to high or below
client.messages.create(
  model="claude-sonnet-5-5",
  max_tokens=16000,
  thinking={"type": "between_tools"},     # xhigh/max with this -> 400
  output_config={"effort": "high"},
  messages=[{"role": "user", "content": "..."}],
)

# If you need xhigh or max, use adaptive thinking instead of between_tools:
#   thinking={"type": "adaptive"}   (or omit the field entirely)

# SDKs that predate between_tools fail type checking on the literal.
# Update the SDK, or pass the value as raw JSON.

2. Forced tool use is rejected​

tool_choice set to {"type": "any"} or {"type": "tool", "name": "..."} returns 400:

tool_choice: type "tool" and "any" are not supported for this model.

auto (the default) and none still work. The same check applies on the token-counting endpoint, which is easy to miss in a test suite that only exercises /v1/messages.

Forced tool use was doing two jobs; split them:

  • Schema validity comes from strict tool use (strict: true on the tool) or from structured outputs.
  • Steering — making the model call the tool at all — comes from the prompt saying when the tool applies.

3. Thinking blocks are bound to the model, the conversation, and the account​

Every thinking block records which model produced it, and models only read some other models' blocks. The graph is asymmetric and not intuitive:

Blocks produced byCan Sonnet 5.5 read them?
Sonnet 5.5 itselfYes
Sonnet 5, Opus 4.8, Haiku 4.5 and earlierYes
Opus 5, Opus 5.5No
Any Fable or Mythos modelNo

And in the other direction: no other model reads Sonnet 5.5's thinking blocks. So a conversation that migrates up from Sonnet 5 to Sonnet 5.5 keeps its reasoning; a conversation that moves off Sonnet 5.5 to anything else — including Opus 5.5, a tempting escalation path — runs every subsequent turn without it. Unreadable blocks are dropped before the model sees them, the request succeeds, and dropped blocks are not billed. With the thinking-binding-controls-2026-08-01 beta header the drops are itemised in a top-level input_transformations array.

Two further bindings sit on top:

  • Conversation prefix. The API checks whether the system prompt, the tools list, or any earlier message changed since a Sonnet 5.5 thinking block was produced. It enforces this by default for accounts created on or after 31 August 2026, 00:00 UTC on the Claude API, Bedrock and Google Cloud — replaying a block after such an edit returns 400 there. To drop the affected blocks instead of failing, send thinking-binding-controls-2026-08-01 and set thinking.block_binding.prefix_mismatch_behavior to "drop_block". Note block_binding only works with adaptive thinking; under between_tools your only options are append-only history or stripping thinking blocks from the edited turn onward.
  • Account. Sonnet 5.5's thinking blocks work only in the account that produced them, or a linked one. Another account sending them gets them dropped, with reason: "organization_binding_mismatch" under the binding-controls beta. Blocks from earlier models are unaffected.
Guided walkthrough1 of 5
  1. Claude Code, claude.ai, Claude Managed Agents and the Claude Agent SDK already do this. Append-only integrations need no change.
  2. Appending a line to system mid-session edits the prefix and invalidates every earlier thinking block. A mid-conversation system message appends instead — and it is newly supported on Sonnet 5.5, not on Sonnet 5.
  3. Adding an entry to tools later edits the prefix too. If you must add one mid-session, the inline-tools-2026-09-15 beta lets a tool_addition block carry a full tool definition inside a mid-conversation system message, without touching tools and without losing the cache.
  4. The compact-2026-09-04 beta returns a signed compaction block summarising the conversation, which you send first in place of the messages it replaces. Thinking blocks in the turns you keep can stay valid across the swap — which matters far more here than on Sonnet 5, precisely because these blocks are conversation-bound.
  5. It cannot read Sonnet 5.5 blocks. If a hard turn needs more depth, raising effort with the per-message beta keeps the reasoning; switching models does not.

4. computer_20251124 is rejected — on two platforms out of three​

On the Claude API and Google Cloud, Sonnet 5.5 supports computer use only through the computer_toolset_20260801 toolset. Declaring the older computer_20251124 tool returns 400:

'claude-sonnet-5-5' does not support tool types: computer_20251124.

On Amazon Bedrock, Sonnet 5.5 still accepts computer_20251124. That asymmetry is the kind of thing that makes a multi-platform deployment pass CI on one cloud and fail on another. Migrating means: drop the old beta header, replace the tools entry with {"type": "computer_toolset_20260801"}, and update the agent loop for member tool_use blocks, batch actions, and toolset_name on results. Integrations already on the toolset, and anything using the browser use tool, need no change.

5. Advisor pairings narrowed​

With the advisor tool (beta), a Sonnet 5.5 executor accepts Mythos 5.1, Fable 5.1, Mythos 5, Fable 5, Opus 5.5, Opus 5, or Sonnet 5.5 itself as advisor. Opus 4.8, Opus 4.7 and Sonnet 5 are rejected with 400 — all three of which worked as advisors for a Sonnet 5 executor. Every advisor Sonnet 5.5 accepts returns its advice encrypted, as an advisor_redacted_result block, so your client cannot read the advice text.

The sixth change: HTTP 200, and your UI goes quiet​

This one fails nothing and is the most likely to reach your users before it reaches your logs.

Between tool calls, Sonnet 5.5 writes user-facing notes about what it just found and what it is doing next. Notes longer than a sentence or two now come back as progress-update thinking blocks; shorter remarks stay text. At the default display: "omitted" a progress-update block's text field is empty. A client that renders only text blocks therefore shows nothing at all during a long agentic turn — no error, no warning, just silence where narration used to be.

Three ways out, in order of how little work they are:

  1. Use between_tools. The notes come back with their summary text, no display field needed (and none accepted).
  2. Set display: "updates" with the thinking-display-updates-2026-08-18 beta header. You get a short summary of each progress update while the reasoning itself stays hidden.
  3. Give the model a tool for sending the user a message, for the cases where it needs to show exact text mid-turn — a code snippet, a question it needs answered. Tell it to use that tool only for such content, and declare the tool in the first request so tools never changes later.

Then clean up around it: delete instructions like "hold all findings for the final response", and if you want updates at predictable points, ask for them explicitly — a line before the first tool call, a recap at the end. The model follows that.

If long turns still go quiet, your harness can nudge — carefully. Count consecutive tool-calling steps that sent the user no text, and after several (say five) append a one-turn reminder after the latest tool results, as a turn-scoped system message:

Harness nudge for a silent agentic turn

The user hasn't heard from you in a while — say in a few words what you're doing, then continue.

Stop after the second or third if it does not take. Frequent harness text after tool results makes the model suspect a prompt injection — which is the next section. Because the reminder is appended rather than inserted and later removed, the prompt cache and the preserved thinking both survive. Anthropic's measurement: at high effort with a message-the-user tool available, this shortens the longest silent stretches with no measurable change in task quality.

  • Terminal-Bench 4.0 is the one row where the half-price model wins, 70.6% against 66.4%. That benchmark is the closest published proxy for "run an agent in a shell until the job is done," which is exactly where fewer tool calls and fewer tokens compound.
  • Treat Sonnet 5's 10.3% on Terminal-Bench 4.0 with suspicion, not awe. A 60-point generational jump on one benchmark version tells you at least as much about the harness and the scoring version as about the model. Use it to conclude "this version of this benchmark punishes Sonnet 5's agent behaviour," not "Sonnet 5.5 is seven times better at agentic coding."
  • Sources disagree on FrontierCode at the top of the effort range. Anthropic's table reports 46.2% at max effort; at least one aggregator reports a higher 52.1% at xhigh. We have not been able to confirm the second figure against the primary table, so read it as unverified — but note that "more effort scored lower" is consistent with the docs' own advice to reserve xhigh and max for cases where you have measured a gain, rather than assuming monotonic improvement.

Independent measurement, as always, lands lower than vendor measurement on agentic benchmarks. Run your own evals before you commit a number to a slide.

The quiet failure modes​

None of these throw. All of them cost you accuracy or trust.

Structured outputs that think until they run out​

Ask for a JSON answer to a task that needs a few steps of working out — totalling figures from a document, applying a rule, ranking items — and Sonnet 5.5 often answers without thinking first, especially at low and medium effort. With structured outputs the response text holds only the JSON, so the working has nowhere to go except the thinking; skip the thinking and accuracy drops.

  • With adaptive thinking, appending Think the problem through before you answer. to the system prompt brings high-effort accuracy close to xhigh for a modest increase in output tokens.
  • between_tools is the wrong setting for these requests: with no tools in play, it means no thinking at all, and that line has no effect.
  • At low and medium with structured outputs, the model occasionally keeps thinking until it hits max_tokens. Treat any response with stop_reason: "max_tokens" as failed and retry, even when its text happens to contain valid JSON. This is the single most likely way to ship a confidently wrong number.

If you cannot use structured outputs and ask for JSON in the prompt, the model tends to work the problem out in the response text and put the JSON at the end. Do not slice from the first { to the last } — it occasionally writes a draft before the final answer and you would capture both.

Extracting the final JSON value from a mixed response

# Read only text blocks. Treat stop_reason == "max_tokens" as a failure and retry.
# Starting at each { or [, try to parse a JSON value; continue from the END of a value
# that parses, so values nested inside it are not counted on their own. Keep the LAST one.

import json

def last_json_value(text):
  dec, best, i = json.JSONDecoder(), None, 0
  while i < len(text):
      if text[i] in "{[":
          try:
              value, end = dec.raw_decode(text, i)
          except ValueError:
              i += 1
              continue
          best, i = value, end          # jump past it: skip nested values
      else:
          i += 1
  return best

# Then check the fields you expect are present, and retry once if they are not.

Real user messages read as prompt injection​

Sonnet 5.5 is trained to resist indirect prompt injection — instructions arriving through tool results and other content it reads mid-task. Sometimes it misclassifies a genuine user message that way, tells the user the tool result contained text posing as a message from them, and either ignores it or asks for confirmation. The trigger is placement: text arriving immediately after tool results, especially on every step.

  • Never put user text inside a tool_result block. This is the placement it misreads most often.
  • Deliver mid-turn user input as a user turn: append their words as a text block in the user message that carries the tool_result blocks, after the last tool_result.
  • Keep harness notices in a separate mid-conversation system message, after the user's words. Never put a notice and the user's words in the same block.
  • Drop your own token/budget countdown after tool results in interactive sessions where users can type mid-turn. A per-step countdown is the classic cause. The Task budgets beta adds a similar countdown but has not been seen to cause this misread.

Tool names off by letter case​

Sonnet 5.5 occasionally calls a declared tool by a name differing only in case — bash for Bash — or passes a known parameter under a slightly different name. Do not treat that as fatal. Either accept the call when the match is unambiguous, or return a tool_result with is_error: true that states the exact expected name; the model usually corrects itself on the next turn.

Charts: give it tools before you give it effort​

For dense charts and technical drawings, give the model a way to crop, zoom, or run code on the image. The measured result is worth internalising: with tools at high effort it read charts more accurately than without tools at max effort, at a fraction of the cost. On technical drawings the tools only help from high up, and most at xhigh and max. Reach for the tool, not the dial.

Refusals: five categories, and only two get retried​

A declined request is HTTP 200 with stop_reason: "refusal" and a stop_details object naming the category. Sonnet 5.5 is the first Sonnet to ship with cyber safeguards comparable to Anthropic's most capable models, and the first with classifiers that block reasoning extraction.

Two practical notes. First, if your prompts ask the model to include its reasoning in the answer, remove those lines — they invite reasoning_extraction declines. Read reasoning from summarized thinking blocks (display: "summarized") instead. Second, whether a refusal that arrives before any output is billed depends on its category, and it counts against your rate limits either way.

Legitimate life-sciences work blocked by the bio classifier can apply to Anthropic's Life Sciences Verification Program.

So which model do you actually run?​

Guided walkthrough1 of 5
  1. Everyday tasks, bug fixes, multistep tool use, polished documents and spreadsheets. Start at medium effort for agentic coding, high for general work, and measure. At $2/$10 with 1M context it is the cheapest model in the lineup that is still frontier-adjacent on knowledge work.
  2. The FrontierCode row is where the 2x price buys something real — 54.4% against 46.2%. Also note it cannot read Sonnet 5.5's thinking blocks, so treat the choice as per-conversation, not per-turn.
  3. That is Anthropic's own stated criterion, and at $10/$50 it is 5x Sonnet 5.5's list price.
  4. Two exist: code that depends on forced tool_choice, and code that depends on thinking: disabled with xhigh or max effort — a combination between_tools does not allow. Both are migrations, not blockers.
  5. 200K context, $1/$5, no effort parameter. For classification, extraction and routing the 5.5 family is overkill.
