中級
What you'll learn
  • 仕組みを理解する。コマンドを承認すると、そのコマンドが認証情報ごと一字一句そのまま、リポジトリ内のファイルに永続的に書き込まれる
  • 漏洩ファイルのうち215件がgitleaksとTruffleHogの両方を破った理由と、それが自分の使うあらゆる秘密スキャナについて何を意味するかを理解する
  • Claude Code組み込みのgitignore保護が正確に何をするのか、なぜ自分のノートPCでは機能するのか、そしてなぜチームメイトやCIを守れないのかという構造的な理由を知る
  • 自分のリポジトリで5コマンドの監査を実行する。ファイルを削除しても何も変わらないgit履歴も含めて
  • 正しい修復の順序(先にローテーション、後で後始末)を適用し、逆にすると露出が残る理由を理解する
  • リテラルのコマンドを承認するのをやめ、パターンを承認する。問題のクラス全体を消すただ一つの習慣の変更
  • ApiiroのデータとAnthropicの説明の間にある未解決の食い違いを読み、どちらの前提に対して設計するかを決める

2026年11月5日、Apiiroの研究者Shmulik CohenとMatan Giladiは、公開GitHubをあるファイル名に絞って調査した結果を公表しました。.claude/settings.local.jsonです。103,617のリポジトリで104,185件のコピーが見つかり、そのうち1,122件(約1.1%)に本物の秘密1,379件がありました。

4日後、Hacker Newsのスレッドは622ポイント、422コメントでトップページに到達しました。続いたのはいつもの助言です。設定ファイルをコミットするな。

その助言は正しいものの、仕組みをまったく捉えていません。このページに独立した価値がある理由は3つあります。

  1. 誰も設定ファイルに秘密を貼り付けてはいません。 データベースのデバッグでよくあるように、認証情報をシェルコマンドに入力し、それから**「Yes, and don't ask again」**をクリックしただけです。Claude Codeは承認されたコマンドを権限ルールとして保存しました。認証情報は、次回そのコマンドを許可する記録の一部になりました。
  2. 漏洩ファイルのうち215件が、業界標準の2つの秘密スキャナの両方を破りました。 スキャナが悪いからではなく、PGPASSWORD=やsshpass -pの後ろにあるパスワードには、プロバイダ固有の接頭辞も、鍵の形式も、際立ったエントロピーもないからです。普通のコマンドラインにある普通の単語に見えます。
  3. Claude Codeは守ろうとしていますが、その保護は構造的に持ち運べません。 除外ルールをグローバルなgit除外ファイルに書きます。このファイルはホームディレクトリにあります。リポジトリの中にはないので、チームメイトのクローンにも、CIランナーにも、次のノートPCにも届きません。

これはプロンプトインジェクションの話ではなく、エクスプロイトもありません。承認された正規のワークフローで、監査証跡がたまたま秘密情報のファイルになっているという話です。はるかに根の深い種類の問題で、承認を永続化するあらゆるエージェントに当てはまります。

最終検証: 2026-11-10。

数値はすべてApiiro自身のもので、2026年11月1〜3日にわたるとされる公開GitHubの収集によります(この日付範囲はiTWireのみが出典)。Apiiroはフィルタ+LLMレビュアーによるルーブリックで候補を分類し、認証情報は一つもテストしていません。通知を受けた1つの組織は、自社の鍵が有効だったと確認しています。Apiiroはアプリケーションとエージェントのセキュリティ製品を販売しています。合計値は、独立した再現がなされていないベンダー調査として読んでください。CVEも深刻度評価も、誰からも割り当てられていません。 2026年11月8日時点で、確認された製品の修正もバージョン番号もありません。新しいClaude Codeで解決されているという流布した主張は検証できませんでした。以下のグローバルgit除外の挙動は2026-11-10にローカルで再現しました。core.excludesFileが未設定の状態で、~/.config/git/ignoreの最初の行はちょうど**/.claude/settings.local.jsonでした。スキャナの比較には、該当セクションに示す単一出典の注意点があります。

第1部 — 仕組みを正確に​

Claude Codeは、ほとんどのシェルコマンドを実行する前に確認します。プロンプトには永続的な選択肢**「Yes, and don't ask again」があり、これを選ぶとリポジトリのルートにある.claude/settings.local.jsonにallowルールが書き込まれます。承認はそのリポジトリとそのコマンドについて永続的**で、将来のセッション(worktreeを含む)にも適用されます。

ファイルの形は普通です。

安全な形 — Claude Code自身のドキュメントにあるパターンルール

{
"permissions": {
  "allow": ["Bash(npm run test *)"],
  "deny": ["Read(./.env)", "Read(./.env.*)"]
}
}

ここが要です。保存されるルールがパターンのときもあります。上のように。入力されたとおりの正確なコマンドのときもあります。 正確なコマンドの場合、コマンドの全文字、インラインで渡したパスワードも含めて、ルール文字列の一部になります。

つまりこの障害には、ミスも攻撃者も要りません。普通の午後があれば足ります。

Guided walkthrough1 of 5
  1. 認証情報をインラインに含めたものを、自分で入力するか、Claudeが読んだばかりの設定ファイルから提案します。PGPASSWORDの代入が前についたpsql呼び出し、sshpassのログイン、フラグにパスワードがついたmysql呼び出しなどです。これらのツールをシェルから操作する昔ながらのやり方です。
  2. この1時間にあと15回は実行します。権限プロンプトが15回目の表示をします。「Yes, and don't ask again」を選びます。それこそがこのオプションの用途であり、プロンプト疲れを減らすあらゆるガイドが勧めることです。
  3. Claude Codeは、コマンド全文を含むallowエントリを追記します。認証情報は、リポジトリ内のJSONファイルの1行になりました。何も警告しません。まだ何も間違っていないからです。
  4. 除外ルールが存在する前にクローンしたチームメイトかもしれません。後からリポジトリになったフォルダでの 'git add -A' かもしれません。CIかもしれません。Apiiroは、調べた1,105リポジトリのうち539で、Claudeが共著者のコミットがこのファイルに触れていたことを突き止めました。この数字はAnthropic自身の説明が異議を唱えています(後述)。
  5. 警報は鳴りません。監視していそうな2つのスキャナが、漏れたものを見られないからです。それが次のセクションです。
Watch out
  • これはどのモデルでもなく、Claude Codeの性質です。ApiiroはOpus 5.5とFable 5.1の両方で書き込みの挙動を再現しました。モデルを替えても何も変わりません。Apiiroは16のコーディングエージェントのドキュメントも比較し、承認されたコマンド全文をデフォルトでプロジェクトファイルに保存すると確認できたのはClaude Codeだけだと報告しています。ただしその文では「確認」が重い意味を持ちますし、承認を永続化する設計は一般的です。別のエージェントを使っているから安全だと決めつけず、使っているエージェントを監査してください。

第2部 — なぜ215件のファイルが両方のスキャナを破ったのか​

Apiiroは、漏洩ファイルを最も広く使われている2つのオープンソース秘密スキャナにかけました。秘密を含む1,122件のうち:

スキャナ検出したファイル数
gitleaks564
TruffleHog643
どちらも検出しなかった215

つまり漏洩ファイルの19%が、両方のツールから見えません。理由は先ほどの636/743の内訳です。

スキャナは2つの方法で秘密を見つけます。既知の形式(AKIA…の接頭辞、ghp_…のトークン、SupabaseのJWTの形)に一致させるか、怪しい位置にある高エントロピーの文字列を検出するかです。どちらの手法も、見分けがつくように設計された発行済みの認証情報に対して機能します。

人間が選んだパスワードがシェルコマンドの引数位置にある場合、どちらも機能しません。PGPASSWORD=Summer2024!には、一致させるべきベンダー接頭辞がありません。エントロピーも平凡です。構造的に、設定値やテストフィクスチャや単なる単語と区別できません。見逃しの大多数はまさにこの種類で、PGPASSWORD=、sshpass -p、mysql -pの後ろのインラインパスワードでした。

What you'll learn
  • 564/643の内訳についての注意点(単一の報道機関による)。両スキャナは、候補の認証情報が有効かを確かめる検証ステップなしで実行されました。検証が主に改善するのは再現率ではなく適合率で、そもそもどのルールにも一致しないパスワードには役立ちません。だから215という数字がそれによる副産物である可能性は低いです。ただし、スキャナごとの数字を引用する場合は、この注意点も併せて引用してください。

一般化できる教訓は、この事件とは独立しています。あなたの秘密スキャンは発行済みトークンに合わせて調整されており、コマンド引数に含まれる選ばれたパスワードにはほぼ盲目です。 エージェントの設定ファイルと保存されたトランスクリプトは、コマンド引数だらけです。スキャナのルールを何も変えずにパスに.claude/を足すだけでは、この問題の約5分の4しか捕まえられません。

第3部 — 持ち運べないgitignore保護​

Claude Codeはこれに無関心ではありません。まだ無視されていないリポジトリに初めてsettings.local.jsonを書くとき、除外ルールを追加します。ただしプロジェクトの.gitignoreではなく、グローバルなgit除外ファイルにです。

自分のマシンで2つのコマンドで確認できます。

保護が存在することを確認し、どこにあるかを見る

# Where Git looks for your personal excludes.
# If this prints nothing, Git uses the XDG default: ~/.config/git/ignore
git config --get core.excludesFile

# The rule Claude Code writes:
grep -n 'claude' ~/.config/git/ignore

2026年11月10日にこのマシンで実行したところ、core.excludesFileは未設定で、~/.config/git/ignoreの最初の行はちょうど**/.claude/settings.local.jsonでした。保護は実在し、機能しています。

それでも十分ではありえません。理由は4つあり、すべてバグではなく構造的なものです。

  • グローバル除外ファイルはコミットされません。 ホームディレクトリにあります。チームメイトのクローンはそれを見たことがありません。CIランナーも、devコンテナも、次のノートPCも同じです。
  • 後からリポジトリになったフォルダには遡って効きません。 エージェントの作業の多くは作業用ディレクトリで始まり、あとからgit initされます。
  • 除外ルールは、すでに追跡されているファイルには何もしません。 これはClaude Codeの制限ではなくGitの文書化された挙動です。パスがインデックスに入ると、.gitignoreは無関係になります。
  • 保護するのは1つのファイル名だけです。 共有の.claude/settings.jsonはチームが意図的にコミットするファイルで、その公開コピー298件にも秘密がありました。

だから自分の側の修正は小さく、省略できません。パスをリポジトリ自身の.gitignoreに入れ、プロジェクトと一緒に持ち運ばれるようにします。

除外ルールをプロジェクトと一緒に持ち運べるようにする

# In the repo, not in your home directory.
printf '%s\n' '.claude/settings.local.json' >> .gitignore

# Or ignore the whole agent config directory, which also covers
# transcripts and anything future versions add:
printf '%s\n' '.claude/' >> .gitignore

git add .gitignore && git commit -m "chore: ignore local agent permission settings"

第4部 — 自分のリポジトリを監査する​

5つのチェックを順番に。3番目は人が飛ばしがちで、最も重要です。

5コマンドの監査

# 1. Is the file tracked RIGHT NOW?
git ls-files .claude/settings.local.json

# 2. Has it EVER been committed, on any branch?
#    An empty result from step 1 means nothing without this.
git log --all --oneline -- .claude/settings.local.json

# 3. Look for the secrets the scanners miss: inline passwords
#    in command arguments, across all of history.
git log --all -p -- .claude/ | grep -nE 'PGPASSWORD=|sshpass -p|mysql .*-p|MYSQL_PWD=|--password[= ]'

# 4. Confirm an ignore rule actually applies, and see which file it came from.
git check-ignore -v .claude/settings.local.json

# 5. Run the scanners over history too, not just the working tree.
gitleaks git -v          # gitleaks 8.19+; older: gitleaks detect -v
trufflehog git file://.

Claude Codeのセッション内では、/permissionsコマンドが有効なルールすべてと、それぞれがどのファイル由来かを一覧にします。何もコミットされていないマシンの許可リストにあるリテラルのコマンドを見つける最速の方法です。

そのうえで検索を広げます。Apiiro自身の推奨は、組織全体で.claude/settings.local.jsonと.claude/settings.jsonの両方を、履歴も含めて、ファイルがすでに消えているリポジトリでも掃き出すことです。承認を永続化するエージェントはどれも同じ形のファイルを持つので、兄弟もスキャンしてください。.claude/、.cursor/、.gemini/、.specstory/です。

Watch out
  • ファイルを削除しても秘密は消えません。git履歴、すべてのフォーク、同僚がすでに持っているすべてのクローンに残ります。Apiiroは、ファイルの古いバージョンにのみ存在した秘密734件と、秘密を引き継ぐ74リポジトリの211フォークを見つけました。コミットされたファイルに一度でも触れた認証情報は、公開されたものとして扱ってください。

第5部 — 正しい順序で修復する​

多くの記事は後始末を先に置いています。それは逆で、理由は上の行にあります。履歴、フォーク、クローンはあなたの管理外なので、認証情報が無効になるまで、後始末では何も得られません。

Guided walkthrough1 of 6
  1. すべてのパスワード、トークン、鍵。git履歴にしか見えないものも含めます。ローテーションだけが実際に露出を終わらせる唯一のステップで、その後はすべて衛生管理です。Apiiroは見つけた認証情報を一つもテストしておらず、通知を受けた1つの組織は鍵が有効だったと確認しました。自分のものも有効だと想定してください。
  2. 各マシンの.claude/settings.local.jsonを開きます。何もコミットされていないマシンでも同じです。リテラルの認証情報を含むallowエントリをすべて削除します。セッション内で/permissionsを使うと、それらを列挙し、どのファイルが保持しているかが分かります。
  3. git rm --cached .claude/settings.local.json を実行し、.gitignoreのエントリをコミットします。ルールが誰かのホームではなくプロジェクトと一緒に持ち運ばれるようにするためです。
  4. シークレットマネージャーから変数で参照し、コマンドには値ではなく名前が入るようにします。ここには鋭い落とし穴があります。コマンドラインのインライン環境変数代入にパスワードを書くと、リテラルがコマンドの文面に入ってしまい、そこから派生するどのルールにも入ります。変数は別の場所からエクスポートし、承認するコマンドの中で代入してはいけません。
  5. 問題のクラス全体を消す習慣の変更です。ルールとしてのBash(psql *)は秘密を持ちません。いま実行した正確なpsql呼び出しは持っているかもしれません。プロンプトがコマンドを記憶するよう提案してきたら、パターンまで編集して縮めるほうを選んでください。
  6. 組織の.gitignoreテンプレートにパスを追加します。.claude/、.cursor/、.gemini/、.specstory/を、pre-commitとCIで履歴も含めてスキャンします。さらにスキャナのルールを拡張し、既知の鍵形式だけでなくコマンド引数内のパスワードも検出できるようにしてください。そうしないと、215件の盲点を自分のパイプラインで再現することになります。

denyルールは、上記に加える安価な保険

{
"permissions": {
  "allow": ["Bash(psql *)", "Bash(npm run test *)"],
  "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./**/*.pem)"]
}
}

第6部 — 知っておくべき食い違い​

Anthropicは公に回答しました。Claude CodeチームのBoris Chernyは2026年11月7日にHacker Newsに書いています。

Historically Claude Code has not done secret scrubbing (there are many good tools for that), but we are looking into what we can do to prevent this.

(訳: これまでClaude Codeは秘密のスクラブをしてきませんでした。そのための優れたツールは多くありますが、これを防ぐために何ができるかを検討しています。)

彼はさらに、settings.local.jsonはソース管理にチェックインするファイルではないこと、そして露出したコピーは**「手動で作られてチェックインされた」**ものだと述べました。論旨は、Claude Codeはファイルを作るときに除外ルールを追加するのだから、コミットされたコピーは別の場所から来たはずだ、というものです。彼はauto modeを推奨しました。許可ルールを積み上げる代わりに、分類器でアクションを選別する仕組みで、さらにgitホストでの秘密スキャンも勧めています。検討中のプロトタイプは、auto modeがこうしたコマンドを捕まえるようにすること、基本的な秘密スキャンを組み込むことですが、完全には直らないかもしれないという但し書きつきです。同じ露出がauto modeでも起こりうるとコメント投稿者に指摘されたとき、彼の返事は「Yeah good catch.」でした。

その説明とApiiroのデータは噛み合いません。 Apiiroは、追跡した1,105のうち539のリポジトリで、Claudeが共著者のコミットがファイルに触れていたと報告しています。共著だからといって、Claudeが個々の認証情報を持ち込んだ、あるいはプッシュしたことの証明にはならない、とApiiroは慎重に述べています。コミットがすでに存在したファイルを巻き込んだ可能性があるからです。それでも「手動で作られてチェックインされた」と、サンプルの半数にあるエージェント作成のコミットとは両立しにくいのです。

行動に移すのにこれを解決する必要はなく、どちらの説明でも工学的な結論は同じです。

  • Anthropicが正しいなら、保護はホームディレクトリのファイルに依存しており、第3部の4つの構造的な隙間はすべてあなたのチームに当てはまります。
  • Apiiroが正しいなら、エージェントが作成したコミットがファイルをリポジトリに入れる現役の経路であり、保護はさらに弱いことになります。

いずれにせよ、除外ルールはリポジトリに置き、リテラルではなくパターンを承認し、インラインパスワードをスキャンしてください。また、2026年11月8日時点で修正が確認されたものは何もない(バージョンも、変更履歴の項目も、CVEも、深刻度評価もない)ことにも注意してください。
