.pth バックドア: LiteLLM 1.107.0 と、import より先に実行されるコード

上級
What you'll learn
  • 誰も litellm を import していないホストでペイロードが実行された理由を理解する — Python の site モジュールは、import で始まる .pth の行を、インタープリタの起動のたびに、あなたのコードより先に実行する
  • 「wheel はインストール時にコードを実行しない」という安心できるルールが、完全に正しく、かつ完全に無関係だった理由を知る
  • AI ゲートウェイを運用する人にとって重要な根本原因をたどる: コーディングエージェントが GitHub の OAuth トークンをレスポンスボディに入れ、プロキシがレスポンスボディをログに記録していた
  • 3 月から導入済みだった Trusted Publishing、Docker イメージ署名、イミュータブルタグが、そっくりなリポジトリからビルドされたリリースを止められなかった理由を理解する
  • 攻撃者がこのプリミティブをリアルタイムで取り入れる様子を見る: 2026 年 3 月の litellm 1.82.7 はパッケージを使うことが必要だったが、次のリリースの 1.82.8 は .pth に切り替えた
  • 自分のマシンで実行可能な .pth の行を検証済みの方法で監査し、結果を正しく読む(setuptools は正当なものを 1 つ同梱している)
  • 対策表を適用する: 一般的なサプライチェーン防御 15 個のうち、実際にこれをブロックできたのはどれか、マルウェアに署名してしまったのはどれか、そして 2 件の LiteLLM インシデントの両方を止められたはずの 1 行の設定

2026 年 10 月 21 日、約 100 分間、pip install litellm は認証情報スティーラーと、1 時間ごとに動くリモートコードローダーをインストールしました。Hacker News のスレッドは 519 ポイントでフロントページに到達しました。お決まりのアドバイスが続きました: バージョンを固定せよ、鍵をローテーションせよ。

そのアドバイスは正しいのですが、このインシデントの中で最も面白くない部分でもあります。1 ページを割く価値があるのは、次の 3 点です。

  1. ペイロードは import される必要がなかった。 .pth ファイルとして配布され、Python の site モジュールがその環境でインタープリタの起動のたびに実行します。LiteLLM を共有 virtualenv にインストールし、その後に無関係なスクリプトを実行したホストでも、認証情報は漏れました。
  2. 最初のアクセスは AI ゲートウェイのログ経由だった。 LiteLLM 自身のポストモーテムによれば、Claude Code はユーザーの GitHub CLI の OAuth トークンをレスポンスボディに埋め込み、LiteLLM の社内デプロイはレスポンスボディをログに記録し、そのデプロイは公開インターネットから到達可能でした。攻撃者はプロキシのログから 3 人の開発者の GitHub 認証情報を読み取りました。
  3. リリースは署名され、Trusted Publishing で公開され、本物のリポジトリに帰属していた — 攻撃者はパブリッシャーを偽装しなかったからです。パブリッシャーのワークフローを編集して、BerriAI/litellm の代わりに Berri-AI/litellm からビルドさせました。

コーディングエージェントの前段に LLM プロキシを置いているなら、2 点目は二度読む価値があります。ゲートウェイのリクエストログとレスポンスログは、おそらく一度も認証情報ストアとして分類したことがないであろう認証情報ストアです。

最終検証: 2026-10-22。 このページには時間とともに変化する事実が含まれています — 上記の日付を情報の鮮度の目安としてください。 出典: LiteLLM's incident post (docs.litellm.ai/blog/security-incident-oct-21-2026), plus StepSecurity, SafeDep, JFrog and Wiz technical analyses, The Hacker News, and the Python 3 site module documentation. Timestamps, the credential-theft chain and the remediation steps are the maintainers' own account, which was still being updated at the time of writing — expect the root-cause wording to be refined. The sdist omitting the payload is SafeDep's and JFrog's finding; the March 2026 Trivy-driven first compromise is JFrog's. Independently verified on 2026-10-22: litellm 1.107.0 is absent from the PyPI JSON API and the newest release is 1.106.2 (7 wheels + 1 sdist, consistent with the maintainers' 'seven wheels'; Wiz's writeup counts eight distributions); PyPI's integrity endpoint returns 'No provenance available' for litellm 1.106.2; github.com/BerriAI/litellm returns 200 and github.com/Berri-AI/litellm returns 404. The .pth execution behaviour, the duplicate firing in a venv and the -S suppression were reproduced locally on CPython 3.14.6, as was setuptools shipping a legitimate executable .pth line. The claim that a provenance attestation would have verified correctly is this page's inference from the maintainers' description of the workflow change, not a published finding.

パート 1 — メカニズム: import より先に実行されるコード​

.pth ファイルとは何か、何ができるか​

site-packages の中の .pth ファイルは、通常は退屈なものです: sys.path に追加するディレクトリのリストです。editable インストールはこの仕組みで動きます。しかしこの形式には、あまり知られていないもう 1 つの動作があり、標準ライブラリのドキュメントに書かれています。

.pth ファイルの中で、import で始まり、その後にスペースまたはタブが続く行は、exec() で実行される。

攻撃者の cook.pth は 12 バイトです。内容全体が import cook だけ。それで十分です。インタープリタの起動時に自動的に import される Python の site モジュールがそのファイルを見つけ、import で始まっているのを確認して実行します — それが cook.py を import します。これは、スティーラーを含む 1 行の base64 と zlib の塊です。

同時に wheel は sitecustomize.py も配置しました。これは .pth を一切必要としません: site モジュールは、管理者向けのフックとして、設計上、起動のたびにまさにその名前のモジュールを import しようとするからです。そしてドキュメントには、攻撃者が直接恩恵を受ける細部があります — sitecustomize の import で、該当する ImportError 以外の例外が発生した場合、その失敗は黙って握りつぶされるのです。誤動作するペイロードは、トレースバックも警告も出しません。

つまり、誰も litellm を import する必要がありません。 その環境の Python プロセスはすべて、両方のペイロードを実行します。cron ジョブも。--version のチェックも。同じコンテナ内の無関係なスクリプトも。

自分で検証する​

これはドキュメント化された動作であり脆弱性ではないので、使い捨ての virtualenv で 30 秒で確認できます。CPython 3.14.6 で再現しました。

使い捨て venv で .pth のメカニズムを証明する

python3 -m venv /tmp/pthdemo
SP=$(/tmp/pthdemo/bin/python -c "import site;print(site.getsitepackages()[0])")
printf 'import sys; sys.stderr.write("[pth ran: no import needed]\n")\n' > "$SP/zz_demo.pth"

# A command that imports nothing at all:
/tmp/pthdemo/bin/python -c "print('hello')"
#   [pth ran: no import needed]
#   hello

# -S skips the site module entirely, so nothing runs:
/tmp/pthdemo/bin/python -S -c "print('hello')"
#   hello

rm -rf /tmp/pthdemo

実行して得られた有用な観察が 2 つあります。1 つ目、-S はメカニズム全体を抑制します — これは以下で重要になります。ペイロードを実行せずに監査したいからです。2 つ目、デモの行はインタープリタの起動ごとに2 回出力されました: virtualenv では同じ site ディレクトリが複数回列挙されることがあり、ドキュメントは、パスのエントリは重複が除去される一方で実行可能なエントリポイントは除去されないと明記しています。ペイロードは 1 プロセスあたり複数回発火しうるのです。

インシデントより長生きする部分​

このページから 1 つだけ長く使える事実を覚えるなら、これにしてください: .pth の import 行は Python 3.15 で非推奨となり、Python 3.20 で削除される予定です。 代替は明示的な .start エントリポイントファイルで、対応する .name.start ファイルが存在する場合、.pth の import 行は黙って無視されます。

これはこの特定の攻撃プリミティブの、日付のある現実的な終わりです — そして、環境内の実行可能な .pth の行を今のうちに見つけておく理由でもあります。その一部は、依存されていて壊れるものだからです。

知っておく価値のあるドキュメント化された動作がさらに 2 つあり、どちらも静かなペイロードに有利です: 3.15 以降は、1 つの .pth の行でのエラーが残りの行の処理を中断しなくなり、非推奨期間中は、実行された import 行についての診断が**-v のときにしか出力されません**。

「wheel はインストール時のコードを実行しない」が誰も救わなかった理由​

Python のパッケージングにおいて、広く繰り返され、実際に正しい知識があります: sdist は setup.py を通じてインストール時に任意のコードを実行できますが、wheel はインストーラーがファイルをコピーして展開するだけの zip アーカイブです。wheel のほうが安全な形式です。wheel を優先せよ。

これはすべて真実です。何の役にも立ちませんでした。ペイロードにインストール時の実行は不要だったからです。攻撃者は pyproject.toml の maturin ビルド設定に 1 行を追加しました —

[tool.maturin]
data = "cook"

— これはビルドバックエンドに、cook/ ディレクトリを wheel のデータとしてパッケージ化し、インストール時にその中身を site-packages のルートに配置するよう指示します。フックも、スクリプトも、setup.py もなし。ただ 3 つのファイルが所定の場所にコピーされ、そのうち 1 つを Python がその後の起動のたびに実行します。

この教訓はインシデントを超えて一般化できます: 「このパッケージはインストール時にコードを実行するか?」は誤った問いです。正しい問いは**「このパッケージは環境にどんなファイルを置き、ランタイムはそのうちのどれかを自動で実行するか?」**です。

Watch out
  • wheel の中の .pth ファイルは、インストール時スクリプトと同等のものとして扱うこと。それは厳密にはさらに強力だ: インストールスクリプトは、あなたが目にするかもしれないインストーラーの下で一度だけ実行される。.pth の行は、インタープリタが起動するたびに、永遠に、次に Python を起動したプロセスの下で実行される。

パート 2 — wheel とソースが食い違っていた​

リリースのレビューのしかたを変えるべき発見がここにあります。ソース配布物にはペイロードが含まれていませんでした。 SafeDep と JFrog によれば、cook/ ディレクトリは sdist にありません — しかし sdist の pyproject.toml には data = "cook" の行があり、その行は BerriAI/litellm のどの公開コミットにも現れません。それは改ざんの唯一の目に見える痕跡で、ビルド設定の中にあり、アーティファクトにしかありませんでした。

その帰結をたどりましょう。

  • v1.107.0 の git タグを v1.106.2 と diff した人は、何もおかしいところを見なかった — タグはクリーンだから。
  • GitHub のリリースページを読んだ人は、何もおかしいところを見なかった。
  • --no-binary :all: でインストールした人は、3 つのペイロードファイルを受け取れなかった。sdist がそれらを含んでいないから。
  • pip install litellm — wheel を優先する通常のやり方 — を実行した人は、スティーラーを受け取った。

JFrog は、知っておく価値のある法医学的な細部を付け加えています: ペイロードファイルの ZIP エントリのタイムスタンプは、wheel 内の正当なファイルのものと一致しており、これはマルウェアがアーカイブの後からの再パッケージではなく、通常の wheel ビルド中に含められたことを示します。アーティファクトは、毒入りのビルドが生み出したものそのままです — そして、居心地の悪い部分に話は移ります。

パート 3 — 堅牢化が役に立たなかった理由​

LiteLLM はリリースのセキュリティに無頓着だったわけではなく、無頓着でなかった理由そのものがストーリーの一部です。これは 2026 年の LiteLLM に対する 2 回目の侵害でした。 3 月に、JFrog によれば、プロジェクトのビルドパイプラインが悪意ある ピン留めされていない Trivy 0.69.4 のリリースを実行し、CI/CD と公開用の認証情報が露出して、バックドア入りのバージョン 1.82.7 と 1.82.8 につながりました。JFrog は 10 月のペイロードとインフラは別物であり、2 つのキャンペーンの間に明らかな関連はないと述べています。

3 月の堅牢化は、その最初のインシデントへの答えでした。メンテナー自身の説明では、その後リリースをプライベートリポジトリに移し、Trusted GitHub Publishers を採用し、Docker タグをイミュータブルにし、Docker イメージ署名を有効にしていました。これは同規模のほとんどのプロジェクトより良い態勢です — そして、最初の侵害はビルドパイプラインのピン留めされていない依存関係で始まったことに注意してください。これは、下の対策表の最後に行き着く教訓と同じです。

それらの対策はすべて、10 月のリリースによって満たされていました。理由はこうです。

Guided walkthrough1 of 6
  1. 悪意あるワークフローは、正規のリポジトリの中で、正規のリリースパイプラインを通じて、正規の公開用アイデンティティで実行された。変わったのは、どのソースをチェックアウトしたかだけ。Trusted Publishing はアーティファクトを、それを生み出したワークフローとリポジトリに結びつける。そのワークフローが何をビルドすると選んだかについては何も言わない。
  2. ワークフローは BerriAI/litellm の代わりに Berri-AI/litellm を指していた。ハイフン 1 つ。ワークフローファイルの diff では、ほとんど見えない — そしてレビューを強制したはずのブランチ保護のチェックは、それが発火した 5 秒後に、組織オーナーの認証情報で無効化された。
  3. イメージ署名は、アーティファクトが期待どおりのパイプラインから来て、その後改変されていないことを証明する。アーティファクトはそのとおりだった。署名は有効で、イメージは毒入り。この二つは矛盾しない。署名が証明するのは出所であって、意図ではないからだ。
  4. イミュータブルタグは、v1.107.0 が指すものを黙って差し替えられるのを防ぐ。ここでは、毒入りイメージがそのタグで最初に、そして唯一公開されたものだった — したがって不変性はマルウェアを固定した。浮動タグはもっとひどかった: latest、main-latest、main-stable がすべてそれを指すよう付け替えられた。
  5. 悪意あるコミットは Berri-AI <protonmail のアドレス> の名義で作成され、GitHub の Verified バッジが付いていた。そのバッジが意味するのは、GitHub が認証済みセッション(通常は Web エディタ)の代理でコミットに署名したということであり、名前の挙がった作者が見かけどおりの人物だということではない。もっともらしい組織名の隣の Verified バッジは、本人確認ではない。
  6. 2026-10-22 に確認: PyPI の integrity エンドポイントは litellm 1.106.2 に対して 'No provenance available' を返す。つまりインシデント後でさえ、現行リリースには利用者が検証できるものが何もない — これは PyPI 全体で一般的なケースであり、このプロジェクトに特有の批判ではない。

正直なまとめは、主流のソフトウェアサプライチェーンのツールチェーンは*「このアーティファクトはプロジェクトの本物のパイプラインから来たか?」に答えるために作られている、ということです。それははいと、正しく答えました。「プロジェクトの本物のパイプラインは、プロジェクトの本物のソースをビルドしたか?」*に答えるように作られたものはほとんどありません — そして、この攻撃が拠り所にしたのはその問いでした。

パート 4 — 根本原因: ゲートウェイのログは認証情報ストアである​

ここからは AI インフラ特有の部分で、このインシデントが、パッケージングのニュースレターだけでなくこのサイトにも属する理由です。

攻撃者はメンテナーをフィッシングしたり、パスワードを破ったりしたのではありません。メンテナーのポストモーテムによれば、連鎖はこうでした。

Guided walkthrough1 of 4
  1. 調査で、そのデプロイに「予期しない、無害そうな名前のユーザーアカウント」が見つかった。チームは、最近パッチされた脆弱性経由でアクセスされたと疑ったが、執筆時点でその経路は確認されていなかった。
  2. ポストモーテムを引用すると: Claude Code はユーザーの GitHub CLI の OAuth トークンをレスポンスボディに埋め込み、レスポンスボディがログに記録されている場合、それらのトークンが LiteLLM のログに現れうる。ゲートウェイは、ゲートウェイが設定されるとおりのこと — デバッグ、コスト按分、評価のためにリクエストとレスポンスのペイロードを保持すること — をしていた。
  3. そのうち 1 つは、組織の 2 人のオーナーの一人のものだった。その一点が、「ログテーブルへの読み取りアクセス」を「ブランチ保護を無効化してリリースワークフローを強制 push する」に変えた。
  4. 自らを privcollect と名乗るスティーラーは、16 のカテゴリを収集する: ブラウザのパスワードと Cookie、SSH 鍵と GPG 鍵、AWS/Azure/GCP の認証情報、Kubernetes の設定、CI のシークレット(GitLab Runner、Jenkins、Vault、Terraform)、シェルとデータベースの履歴、/proc/<pid>/environ 経由のすべてのプロセスの環境変数、AI コーディングツールのトークン(Claude、Cursor、Copilot、Gemini ほか)— そして DATABASE_URL が設定されていれば、LiteLLM プロキシのデータベース自体の Prisma ダンプ。そこには、それが仲介するために作られたプロバイダーの鍵が入っている。

最後の項目がループを閉じ、これが構造的なポイントです。LLM ゲートウェイは、構造上、あなたの環境の中で、すべてのプロバイダー鍵を持ち、すべてのプロンプトと補完を見る唯一のホストです。 レスポンスボディのログを加えれば、エージェントがたまたまそこを通したあらゆるシークレットも保持します。1 台を侵害することは、開発者のノート PC を侵害するより価値があり、マルウェアの買い物リストは、攻撃者がそれを知っていたことを示しています。

What you'll learn
  • AI ゲートウェイを運用しているなら、このインシデントから得るアクションアイテムは「litellm をピン留めする」だけではない。ゲートウェイがリクエストやレスポンスのボディを永続化しているかを調べ、そうすべきかを判断し、そうせざるを得ないなら認証情報の形をした文字列をリダクトすることだ。エージェントのトラフィックは普通の API トラフィックではない — コーディングエージェントは GitHub、クラウドプロバイダー、パッケージレジストリのトークンを帯域内で運ぶ。

ペイロードがホスト上で行ったこと​

念のため、2 つ目のファイルについて。sitecustomize.py は切り離されたデーモンを fork しました — setsid()、I/O は /dev/null、作業ディレクトリは / で、親が終了しても生き残ります — それは3,600 秒ごとに起き、デッドドロップ(その後削除された GitHub アカウントの domain.txt)から次のコマンド&コントロールのホストを解決し、そこから /codepy を平文の HTTP で取得して exec() で実行しました。持ち出しは www.litellm[.]dev/healthcheck へ、こちらも平文の HTTP で、ボディは RSA-4096 でラップした鍵による AES-256-CBC で暗号化されていました — これはプロジェクトの本物の litellm.ai に似せたドメインで、リリースの 8 日前の 2026 年 10 月 13 日に登録されました。(このページではドメインを無害化しています。名前解決しないでください。)

StepSecurity は、デーモン化のパスが fcntl と os.fork に依存するため Windows では黙って失敗すると指摘しています。Windows 向けの wheel は公開されていたので、スティーラーはそこで実行されたものとし、1 時間ごとのローダーはおそらく動かなかった部分として扱ってください。

Watch out
  • パッケージをアンインストールしてもインシデントは終わらない。理由は互いに独立した 4 つある。盗まれた認証情報はすでに出て行った。fork されたデーモンは別のプロセスで、パッケージとの関係はもう残っていない。その間にそのホストで Python が起動するたびに、スティーラーが新たに実行された。そして — JFrog が指摘するように — pip 自体が Python プロセスなので、修復コマンドは出ていく途中でもう一度ペイロードを実行する。メンテナー自身のガイダンスは、ホストを侵害されたものとして扱うこと: デーモンを kill し、ファイルを削除し、再構築し、すべてをローテーションする。

パート 5 — 7 か月前の同じパッケージと、攻撃者自身のエスカレーション​

3 月のインシデントはよく見る価値があります。2 つの悪意あるバージョンは、.pth の手法がたった 1 回のバージョンアップで取り入れられる様子を示しているからです。

Datadog Security Labs は、これを TeamPCP キャンペーンとして追跡しており、それによれば:

  • litellm 1.82.7 は、ペイロードを litellm/proxy/proxy_server.py の中に持っていた。発火させるには、被害者がパッケージをインストールし、さらに実際に使う必要があった。
  • litellm 1.82.8 — まさに次のリリース — は litellm_init.pth を追加した。同じプロジェクト、同じキャンペーン、数日違いで、今やペイロードはインタープリタの起動時に発火し、LiteLLM の import は不要になった。

これはまさに、このページ全体が扱うプリミティブを攻撃者が発見したということであり、10 月のペイロードが注入されたモジュールではなく 12 バイトの .pth で始まった理由です。自分の依存関係をトリアージするなら、「モジュールレベルのコード」から「.pth ドロッパー」へのエスカレーションは、一回限りの手口ではなく、予期すべきパターンです。

3 月のペイロードも、10 月のものと見まがうほど同じ手口です: RSA-4096 でラップした鍵による AES-256、プロジェクト自身の名前から作ったそっくりなドメインへの持ち出し(当時は models.litellm[.]cloud、10 月は litellm[.]dev)、環境変数、SSH 鍵、クラウドの認証情報、Kubernetes にわたる認証情報の収集 — さらに 3 月は、~/.config/sysmon/sysmon.py による systemd での永続化、checkmarx[.]zone/raw でのコマンドのポーリング、クラスタ全体に広がるための Kubernetes の Pod 作成機能もありました。3 月のキャンペーンは 3 月 19 日の Trivy から外へと連鎖し、npm(CanisterWorm)と Checkmarx のツールを経て、3 月 24 日(litellm)と 3 月 27 日(telnyx)に PyPI に達しました。

What you'll learn
  • 2 件の LiteLLM インシデントが関連しているかどうかについて、情報源の見解は割れており、このページはそれを解決しない。JFrog は、10 月のペイロードとインフラは別物で、3 月のキャンペーンとの明らかな関連はないと述べている。それに対して: 両方とも .pth ドロッパーを使い、両方とも RSA-4096 でラップした鍵による AES-256 を使い、両方ともプロジェクト名に由来するそっくりなドメインに持ち出した — 一方で Datadog のキャンペーン名(TeamPCP)と 10 月のスティーラーが自ら選んだ名前(privcollect、マーカー PRIVCOLLECT_ACTIVE)は、まだ誰も結論を公表していない比較を誘う。帰属は研究者に委ねられる。類似点は、発見ではなく、説明のつかないものとして扱うこと。

両方を止められたはずの 1 つの対策​

3 月に関する PyPI 自身のインシデントレポートに、最も有用な数字があります: LiteLLM は毎分約 1,700 回インストールされ、3 月の露出期間中に 119,000 回ダウンロードされました。PyPI は 3 月のリリースを、アップロードから 2 時間 32 分後に隔離し、10 月は wheel が約 1 時間 43 分で消えました。対応は速くなっています — そして、決して十分には速くなりません。そのインストール速度では、最初の 10 分がすでに大規模侵害だからです。

だからこそ、PyPI が利用者に向けて掲げる主要な推奨は「コードを読め」ではありません。依存関係のクールダウンです: N 日より新しいリリースは解決しない。LiteLLM の 2 回の侵害はどちらも数時間以内に検知されて取り下げられました。3 日間のクールダウンがあれば、どちらも、それを設定していた人にとっては何事もなく終わっていたでしょう。

これはリストの中で最も採用が少ない高価値の対策で、設定は 1 行です。

クールダウンをサポートする 3 つのツールでの依存関係クールダウン

# --- uv: pyproject.toml (or uv.toml at the root) ---
# exclude-newer accepts an RFC 3339 timestamp, a friendly duration,
# or an ISO 8601 duration. Relative durations landed in uv 0.9.17.
[tool.uv]
exclude-newer = "7 days"     # equivalently: "P7D"

# --- Renovate: renovate.json ---
# The oldest implementation of the idea (formerly stabilityDays).
{
"minimumReleaseAge": "7 days"
}

# --- Dependabot: .github/dependabot.yml ---
# Note: Dependabot already applies a DEFAULT 3-day cooldown to version
# updates even with no cooldown block at all -- and never to security
# updates. Configure it only to lengthen or target the window.
updates:
- package-ecosystem: "pip"
  directory: "/"
  schedule: { interval: "weekly" }
  cooldown:
    default-days: 7
    semver-patch-days: 3

トレードオフは明快で小さい: セキュリティ以外のアップデートを最大 1 週間遅れで受け取ります。その代わり、毒入りリリースがあなたに届きうる期間は、「誰かが気づくまでの長さ」から、「クールダウン内に誰かが気づくなら、ゼロ」へと縮みます — そして LiteLLM の両方のケースで、誰かが数時間以内に気づきました。

Pro tip
  • クールダウンはセキュリティパッチを遅らせてはならない。さもなければ、リスクを別のリスクと交換しただけになる。Dependabot はこれを構造的に正しく扱っている: クールダウンはバージョンアップデート専用のオプションで、セキュリティアップデートには適用されないと文書化されている。自分でクールダウンを実装する場合 — たとえば CI で uv の exclude-newer を使う — 既知のアドバイザリを修正するリリースのために、文書化された上書きの経路を残しておくこと。
  • 設定を追加する前に、すでに持っているものを確認する。Dependabot の 3 日間のデフォルトにより、誰かが選んだわけでもなく部分的にカバーされているリポジトリは多い。一方、浮動タグをプルする Dockerfile や、pip install -U を実行する CI のステップは、このどれにもカバーされない。

残しておく価値のある監査: どの .pth ファイルがコードを実行するか?​

このインシデントとは別に、気にかけているマシンで Python の起動時に何が実行されるかを把握しておくべきです。-S に注意 — 監査が、探しているものを引き起こしてはいけません。

環境内の実行可能な .pth の行をすべて列挙する (-S を付けて実行)

cat > /tmp/audit_pth.py <<'EOF'
import glob, os, site, sys
dirs = list(site.getsitepackages())
try:
  if site.ENABLE_USER_SITE:
      dirs.append(site.getusersitepackages())
except Exception:
  pass
seen, hits = set(), 0
for d in dirs:
  if d in seen or not os.path.isdir(d):
      continue
  seen.add(d)
  for p in sorted(glob.glob(os.path.join(d, "*.pth"))):
      for n, line in enumerate(open(p, encoding="utf-8", errors="replace"), 1):
          s = line.strip()
          if s[:6] == "import" and s[6:7] in (" ", "\t"):
              hits += 1
              print(f"{p}:{n}: {s}")
print(f"\n{hits} executable line(s) across {len(seen)} site dir(s): {sys.executable}")
EOF

python3 -S /tmp/audit_pth.py

出力を正しく読んでください。 ヒットは発見ではありません。setuptools だけが入った新品の virtualenv では、これは実行可能な行を 1 つ報告し、それは正当なものです。

.../site-packages/distutils-precedence.pth:1: import os; var = 'SETUPTOOLS_USE_DISTUTILS'; ...

これは setuptools が distutils のシムをインストールしているもので、このメカニズムの最も一般的な正当な使い方です。editable インストール(__editable__*.pth)もその一つです。探すべきシグナルは、自分が意図的にインストールしたパッケージに帰属させられない実行可能な行です — そして、名前が思いつくどの配布物にも一致しない、site-packages のルートにあるファイルは、そのシグナルの最も強い形です。侵害されたホストでは、その名前は cook でした。

短命で、狭くスコープされた GitHub トークン初期アクセスログに残っていた長命の組織オーナー用 OAuth トークンが、ピボットのすべて。

安価で退屈な対策が勝ちます。クールダウンを設定し、厳密に固定し、固定をロックし、イメージはダイジェストでプルし、ゲートウェイに必要のないものを持たせない。 これらのうちコードの検査を伴うものがどれほど少ないかに注目してください: 表の上位 3 つの対策は、誰も何にも気づく必要がないからこそ機能するのです。

Key takeaways
  • .pth ファイルはパスのリストではなく、コード実行のプリミティブだ。Python の site モジュールは、import で始まる行を、インタープリタの起動のたびに、パッケージの import なしで exec する。インストール時スクリプトより厳密に危険だと扱うこと。
  • 「wheel を優先」というアドバイスはインストール時の実行についてのもので、ランタイム起動時の実行はカバーしない。ビルド設定の 1 行 — data = 「cook」 — が、フックなしで site-packages のルートに 3 つのファイルを置いた。
  • ソースとアーティファクトは食い違いうる。git タグはクリーンで、sdist はペイロードを含んでいなかった。wheel だけが運んだので、リポジトリを diff しても何も見つからなかった。目に見える唯一の痕跡は、どの公開コミットにも存在しないビルド設定の 1 行だった。
  • サプライチェーンの署名は「これは本物のパイプラインから来たか?」に答える — そしてここでは、答えは正当に「はい」だった。それは「本物のパイプラインは本物のソースをビルドしたか?」には答えない。ハイフン 1 つのそっくりな組織がすり抜けたのはそこだ。
  • AI ゲートウェイは AI スタックの中で最も価値の高いホストだ: すべてのプロバイダー鍵、すべてのプロンプト、そして — レスポンスボディをログに残すなら — コーディングエージェントが帯域内で運ぶあらゆるトークン。そのログをシークレットとして分類するか、保持をやめること。
  • 実行可能な .pth の import 行は Python 3.15 で非推奨となり 3.20 で削除され、明示的な .start ファイルに置き換えられる。今、python -S で自分のものを監査し、setuptools が正当なヒットになると予想しておくこと。
  • これは 2026 年の LiteLLM に対する 2 回目の侵害で、最初のものはビルドパイプラインのピン留めされていない依存関係から始まった。固定は、毒入りリリースから身を守る方法であるだけでなく、プロジェクトがそれを公開しないための方法でもある。
  • 最良の単一の対策は依存関係のクールダウンだ。誰かが気づくことに依存しない唯一のものだから。LiteLLM の両方のリリースは数時間以内に取り下げられた。3 日間のクールダウンがあれば、どちらも何事もなく終わっていた。Dependabot はすでにデフォルトで 3 日間を適用し、セキュリティアップデートには決して適用しない。
