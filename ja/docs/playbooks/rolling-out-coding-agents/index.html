非エンジニアへのコーディングエージェント展開

中級
What you'll learn
  • 非エンジニアがコーディングエージェントに実際に頼む3つの仕事を切り分ける — コーディングはそのうち1つだけで、このずれが話のすべてである
  • 大規模展開の本当のコストセンターを見つける:席数でもトークンでもなく、出力を引き継ぐエンジニアのレビューキューである
  • マイクロモデル問題を理解する — トレーダーの40行のポジション用スクリプトがなぜ規制対象のモデルになり得るのか、米国の監督ガイダンスは今何と言っているのか
  • 2026年の銀行AI禁止の2件を混同しない:社内のコーディングツールと、顧客口座に触れる第三者エージェントは、別の問題で別の対処が要る
  • 人ではなく仕事に合わせて利用面を選ぶ — ケイパビリティラダーを使う
  • 本当に強制できる統制を展開する — そしてサーバー管理設定と既定の監査証跡がなぜ強制にならないかを知る
最終検証: 2026-11-09。

以下のゴールドマン・サックスに関する具体的内容(日付、人数、誰がアクセスを維持したか)は、2026年11月2日付の Bloomberg の報道とその続報、および実名の会社広報担当者の発言に基づきます。アクセスポリシーは告知なく静かに変わります。ゴールドマンの事例は、詳細が動いている可能性のある実例として扱い、同社の現状の説明とは考えないでください。このページで長持ちするのは、仕組みと統制の面です。

次の情報源で確認してください: 公式情報源.

何が起きたのか、1段落で​

2026年7月、ゴールドマン・サックスの CIO であるマルコ・アルジェンティ氏は、同社の非技術系スタッフの間で広がる「バイブコーディング」を公に称賛しました。エンジニアではない人々が AI ツールで作ったものを、約12,000人いる同社のエンジニアの誰かに渡して仕上げてもらっていたのです。2026年10月、社内ガイダンスが方針を転換しました。Claude Code と GitHub Copilot はエンジニアと「ストラット」(トレーディング・クオンツ・エンジニアリングを兼ねるハイブリッド人材)の手元に残り、バンカーとトレーダーからは引き上げられました。広報担当者はこれを試行の終了と位置づけ、「生産性とリスク管理を含む様々な要素」を評価したうえで、長期的に最も使いこなせる人々にツールを委ねたと述べました。11月2日に Bloomberg が報じ、Hacker News のスレッドは780ポイントを超えました。

報道の多くは AI への評決として扱いました。しかし展開設計のケーススタディとして読む方が有益です。ここで描かれる失敗の型は、エンジニアリング部門の外にコーディングエージェントを広げるほぼすべての組織が遭遇するもので、事前に織り込んでいる組織はほとんどありません。

3つの仕事、コーディングはそのうち1つだけ​

アクセスを外された利用者が実際に何をしていたかから始めます。報道で一貫して挙がる仕事は3つです。

トレーダーの用途それはコーディングか?実際には何か
顧客の取引動向を追ういいえ機微なフローデータの分析
市場や自分のポジションの変動をシミュレートするいいえ定量モデリング
文章やビジュアルの下書きを作るいいえ文書・アセットの生成

3つのどれもソフトウェアエンジニアリングではありません。コーディングエージェントは仕事そのものではなく、運搬手段でした。これがこの出来事から持ち帰るべき最も重要な点であり、「銀行は AI を恐れている」という枠組みが覆い隠している点です。

こうなるのは、ターミナルのコーディングエージェントが、たまたま、ほとんどの企業が導入した中で最も有能な汎用分析ツールだからです。データベースに到達し、Python を書き、実行し、グラフを描く — チケットなしに、ひと続きのループで。承認された分析経路がデータ依頼と2週間の待ち行列を要するなら、コーディングエージェントは毎回実力で勝ちます。人々は悪用していたのではありません。社内のボトルネックを迂回していたのであり、有能な人はそうするものです。

結論として、あなたが決めているのは、非エンジニアがコーディングしてよいかどうかではありません。決めているのは、バージョン管理もレビューもない分析を、下流の誰も保守に同意していない人々が本番データに対して作ってよいかどうかです。 そう言い換えれば、展開をめぐる議論の多くは自然に決着します。

誰も予算化しないコストセンター:レビューキュー​

7月の説明をもう一度見てください。非技術系スタッフが作ったものを、12,000人のエンジニアの一人に「改善してもらう」ために渡していました。

この受け渡しこそが展開の本当のユニットエコノミクスであり、ビジネスケースには現れません。席のコストは見えます。トークンのコストも見えますし、そのためのハードな支出上限もあります。コードを読めない人が作ったプロトタイプの流れをレビューし、堅牢化し、引き受け、保守するためのエンジニアリング時間は、席を承認した人には見えません。別のチームの四半期に落ちるからです。

計算は容赦ありません。仮に2,000人の非エンジニアがそれぞれ月に1件、エスカレーションに値する成果物を作るとします — 熱心な集団にとっては控えめな見積もりです。月に2,000件が、それを想定していなかったエンジニアリング組織に届きます。レビュー、堅牢化、引き受けに1件4時間かかるなら、月8,000エンジニア時間、つまりおよそ50人のフルタイムエンジニアが受け入れ業務に吸収されます。12,000人に対してなら耐えられますが、不意打ちでは耐えられず、しかもエンジニアリングのロードマップには何も載りません。

このキューを通常のバックログより悪くする性質が3つあります。

Guided walkthrough1 of 3
  1. 成果物はすでに作者にとっては動いており、作者はレビュアーより上位であることが多く、すでに自分のデスクに見せています。「No」はトリアージの判断ではなく政治的な行為になります。断れないバックログはバックログではなく、義務です。
  2. 通常のレビューは、どちらもdiffを読める二人の会話です。ここでは、あらゆる指摘が作者の手戻りではなくエンジニアリング作業に変わります。レビュアーは丁寧にレビューしても自分の負荷を減らせません — 増やすことになります。
  3. エンジニアが一度手を入れたら、それはそのエンジニアのものになります。元の作者は変更を依頼し続け、それに依存し続けますが、ポケベルも依存関係の更新もインシデントも「手伝った」チームのものです。エスカレーションされたプロトタイプはすべて、保守予算のない恒久的な負債です。

このページから行動を一つだけ持ち帰るなら、これです。アクセスを広げる前に、出力を引き継ぐエンジニアリング組織に、断る手段を含む受け入れ率を書面で合意してもらってください。 「この人たちが作ったものを誰が保守するのか、彼らが No と言ったらどうなるのか」に答えられない展開は、展開ではなく先送りされた議論です。

マイクロモデル問題​

規制業種の企業には、もう一つ、より鋭い問題があり、展開を突然終わらせる可能性が最も高いのはこちらです。

トレーダーがエージェントに「カーブが50bpスティープ化したら自分のブックがどう動くかシミュレートして」と頼むとき、書かれたのはスクリプトではありません。金融監督当局がこの言葉を使うときの、重みのある意味でのモデルです。米国の従来からの監督ガイダンスは、モデルを、統計的・経済的・金融的・数学的な理論を適用して入力データを定量的な推定値に変える、定量的な手法・システム・アプローチと定義しています。午後に書いたポジションシミュレーションのスクリプトは、この定義に楽に収まります。取引先の取引にフラグを立てるために重み付き基準を適用する承認ルーティングのヘルパーや、顧客がオファーに該当するかをスコア化する適格性チェックも同様です。

この意味でのモデルは、文書化、独立した検証、変更履歴とともにモデルインベントリに載っているべきものです。モデルリスク管理の実務は、モデルが個別で、高価で、数が少ない世界のために作られました — 検証部門が追いつける程度に遅いリリースサイクルで、特定できるクオンツチームが作る世界です。

2,000人の非エンジニアの手にあるコーディングエージェントは、これらの前提をすべて逆転させます。成果物は安価で、大量で、文書化されず、バージョン管理されず、「モデル」という言葉が自分にも当てはまると知らない人々が作ります。これがマイクロモデル問題です。規制上のモデルの定義を満たす意思決定ロジックが、どの検証部門がインベントリ化するよりも速く、問いを立てたことのない作者によって作られる。ガバナンスの穴は、出力が悪いことではありません。何が存在するのかを誰も列挙できないことです。

2026年には監督の地盤も動きました。条文を引用する人にはこれが重要です。2026年4月17日、連邦準備制度はSR 26-2「Revised Guidance on Model Risk Management」を発出し、SR 11-7(2011年4月4日)とSR 21-8(2021年4月9日)に取って代わりました。社内ポリシー、ベンダーのコンプライアンス資料、あるいは頼っているブログ記事がまだ SR 11-7 を現行として引用しているなら、半年以上古くなっています。

最終検証: 2026-11-09。

SR 26-2 の存在、日付、置き換えられるレターは、連邦準備制度自身の SR レター索引で確認済みです。複数の二次的な解説が、SR 26-2 が生成 AI やエージェント型 AI を適用範囲でどう扱うかについて具体的な主張をしていますが、一次のレターで確認できなかったため、意図的に省いています。適用範囲に関する主張に基づいて統制を作る前に、レターとその添付文書を自分で読み、法務にも同じことをさせてください — ここにある内容は法律やコンプライアンスの助言ではありません。

次の情報源で確認してください: 公式情報源.

混同されがちな2つの禁止​

2026年の銀行の AI 制限に関する報道を検索すると、2つの話が一つに混ぜられています。同じ問題ではなく、同じ対処も当てはまりません。

社内のコーディングエージェント顧客口座に触れる第三者エージェント
例ゴールドマン・サックスが Claude Code と Copilot をエンジニアに限定JPMorgan、Bank of America、Citi が外部 AI エージェントの顧客口座へのアクセスを制限

典型的な統制アクセスの範囲限定、管理ポリシー、レビューゲートAPI 境界での読み取り専用への限定 — たとえば Meta の Muse は Chase の残高は読めるが送金はできない
詳しくはこのページエージェントの保護 · エージェント決済と x402

Bank of America の CEO は、エージェントにさらされた脆弱性に対してソフトウェアを修正するために1,000人の契約者を雇ったと述べました — これは1列目ではなく2列目の話です。アナリストに Claude Code を渡すことについての社内メモでこれを引用したなら、引用先を間違えており、最初に気づいた人はあなたの信用を削ることになります。

もう一つ、安易な読みに反するので押さえておくべき背景があります。ゴールドマン・サックスは Anthropic の IPO のリード左幹事であり、S-1 は2026年10月26日に提出済み、ロードショーは2026年11月9日の週に予定されています。ある製品を上場させる引受を担いながら社内アクセスを絞ることは、矛盾ではありません。この判断が道具への評決ではなく展開範囲についてのものだったという証拠です — 自社のものを含め、この種の制限はまさにそう読むべきです。

ケイパビリティラダー:利用面を仕事に合わせる​

ここまでを読んだ後の本能は、職種で制限することです。ゴールドマンはそうしましたし、12,000人のエンジニアと監督当局の検査官を抱える企業には、粗くても擁護できる手段です。それ以外の企業にとっては、たいてい最初の一手として誤りです。能力は取り除かれても需要は取り除かれず、満たされない AI 分析への需要は消えずに、テレメトリがまったくない個人 PC の個人アカウントに移るからです。

代わりに仕事で制限してください。非エンジニアがコーディングエージェントに求めるものの大半は、レビューキューもマイクロモデルも生まない利用面で手に入ります。

このラダーには注目すべき性質があります。保守義務を生むのは最上段だけで、その下の5段が実需の大半を吸収します。ラダーを飛ばし、コーディングエージェントを汎用の AI 提供として展開する企業は、チャット画面なら無料で済む仕事に、エンジニアリングレビューの価格を払っています。

強制する統制と、そう見えるだけの統制​

コーディングエージェントを幅広い層に実際に展開するなら、以下の区別は、ドキュメントを読んだ人も含めて、展開計画で見落とされるものです。

Guided walkthrough1 of 5
  1. デバイス管理ツールで配布した managed-settings.json は優先順位スタックの最上位にあり、ローカルでは上書きできません。claude.ai の組織から配信される設定は、すでに組織に認証したセッションにしか届きません — つまり、個人アカウントでログインしたマシンには決して届かず、そこがまさに心配していたマシンです。Anthropic 自身のドキュメントは、サーバー管理のリストを、デバイス管理で到達できないマシンのための利便性として扱い、強制とは考えないよう述べています。それに従って計画してください。MDM が統制であり、サーバー側のコピーは代替です。
  2. これがないと、開発者は個人の claude.ai アカウントでサインインでき、組織には何も見えません。テレメトリも、ポリシーも、監査証跡もなく、データは一般消費者向けアカウント経由で外に出ます。管理設定で forceLoginMethod と forceLoginOrgUUID を設定すると、Claude Code は一覧にない組織のログインを拒否し、使用中の認証情報がそうした組織のものなら起動時に終了します。これはファイル内で最もレバレッジの大きいキーです。
  3. どのアカウントを使うかとは別の関心事です。許可された経路 — Anthropic API、Amazon Bedrock、ゲートウェイ — を列挙し、それ以外に設定されたセッションを起動時に、またはセッション中に切り替えた場合は次のリクエストで拒否します。Claude Code v2.1.285 以降が必要です。トラフィックが未承認のプロキシを静かに経由するのを防ぐキーです。なぜそれが重要かは[グレーマーケットの AI プロキシ](/docs/security/gray-market-ai-proxies)を参照してください。
  4. これらのキーのもとでは、Claude Code は ANTHROPIC_API_KEY、ANTHROPIC_AUTH_TOKEN、apiKeyHelper で認証するセッションをブロックします — 管理設定自身がそれらを供給している場合でも。環境変数の認証情報では組織への所属を検証できないからです。自分が管理するすべての CI ジョブからのサポートチケットで知る前に、知っておくと役立ちます。
  5. allow と deny のルールは、特定のプロジェクトでエージェントが何をしてよいかを決めるための適切な道具です。誰がそもそもエージェントを実行してよいかを決める道具としては不適切です。よく書かれた deny リストをアクセス判断の代わりにしてはいけません。権限と、設定の優先順位スタックを参照してください。

managed-settings.json — MDM で配布する強制の土台

{
"forceLoginMethod": "claudeai",
"forceLoginOrgUUID": ["00000000-0000-0000-0000-000000000000"],
"allowedProviders": ["anthropic", "bedrock"],
"env": {
  "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
  "OTEL_METRICS_EXPORTER": "otlp",
  "OTEL_LOGS_EXPORTER": "otlp",
  "OTEL_EXPORTER_OTLP_PROTOCOL": "grpc",
  "OTEL_EXPORTER_OTLP_ENDPOINT": "http://collector.internal.example.com:4317",
  "OTEL_LOG_TOOL_DETAILS": "1"
}
}

UUID は管理設定にある自社の組織 ID に、エンドポイントは自社のコレクターに置き換えてください。テレメトリの変数を管理された env ブロックに固定することが重要です。そこで設定された送信先はロックされ、Claude Code は起動時に開発者が設定した競合する変数を削除します。開発者が変更できる送信先は、監査証跡ではありません。

レビューで恥をかく監査証跡の落とし穴​

これは入場料に見合う内容です。展開計画が主張することと、データが実際に含むことの間の隔たりだからです。

Claude Code は、本当に有用な OpenTelemetry メトリクス群 — claude_code.session.count、claude_code.lines_of_code.count、claude_code.commit.count、claude_code.pull_request.count、claude_code.cost.usage、claude_code.code_edit_tool.decision、claude_code.active_time.total — をエクスポートし、user.email、user.account_uuid、organization.id などの属性を伴います。ユーザー単位のコスト帰属とユーザー単位のアクティブ時間は、最初から利用できます。全体像は OpenTelemetry トレーシングと利用量とコストの分析を参照してください。

ただし、メトリクスとイベントは既定で秘匿化されており、その程度は多くの人の予想より強力です。

  • MCP サーバー名とツール名は、OTEL_LOG_TOOL_DETAILS=1 を設定しない限り、ツール名なしの "custom" または "mcp" として表示されます。エージェントがどの社内システムに触れたかの記録があると信じている組織には、既定では mcp とだけ書かれた記録があります。
  • プロンプトの内容、アシスタントの応答、システムプロンプトには OTEL_LOG_USER_PROMPTS=1 が必要です。
  • ツールの出力 — ファイルの読み取り、コマンドの出力 — には OTEL_LOG_TOOL_CONTENT=1 が必要です。
  • Bash コマンドとファイルパスも OTEL_LOG_TOOL_DETAILS=1 の背後にあります。
  • 組み込みの管理ダッシュボードはありません。 自社のオブザーバビリティ基盤にエクスポートし、ビューは自分で作ります。予算を見込んでください。静かに実行されないのがこの工程です。

既定は正しい既定です — 従業員を日常的な監視から守り、claude_code.safety_event は内容を晒さずに権限チェックとブロックを記録します。しかしそれは、「完全に監査可能です」という文が既定のインストールでは偽であることを意味し、それを発見する最も安上がりなタイミングは、検査の最中ではなく今です。フラグをオンにすることはプライバシー上の重みを伴う判断です。何を記録するかを人々に伝え、保持期間を合意し、名指しできる義務が要求しない限り内容のフラグはオフにしておいてください。同じ問いの従業員側の見え方はエージェントが何をアップロードするかを参照してください。

アクセスを広げる前に答えるべき5つの質問​

成熟度モデルではありません。答えがないと、4か月後の撤回を予言する5つの質問です。

Guided walkthrough1 of 5
  1. 10人に聞いてください。答えが分析、下書き、問い合わせ — たいていそうです — なら、コーディングエージェントはラダーの誤った段であり、このページの大半は飛ばせます。
  2. それが落ちるチームのエンジニアリングリーダーから書面で。誰も同意していなければ、席は予算化したが、コストは予算化していません。
  3. 成果物がノート PC 上にあるなら、答えは No であり、規制された環境では No は指摘事項です。利用者層ごとに承認されたリポジトリまたはワークスペースを用意することが、列挙を可能にする最低条件です。
  4. forceLoginOrgUUID を含む managed-settings.json を配布したか、それとも wiki のページか。意志の強い個人アカウント利用者に耐えるのは前者だけです。
  5. メトリクス一覧が提供するものではなく、先週コレクターが受け取ったもの。主張する前にクエリしてください。MCP のツール名が 'mcp' で返ってくるなら、設定していないフラグが分かります。

Key takeaways
  • 非エンジニアがコーディングエージェントに持ち込む3つの仕事 — 分析、モデリング、下書き — はコーディングではない。職種ではなく、その仕事について決める。
  • 承認された分析経路が遅いため、コーディングエージェントはしばしば実力で勝つ。ボトルネックを直さなければ、禁止後も迂回は続く。
  • 展開の本当のコストはエンジニアリングのレビューキュー:断れず、差し戻せず、恒久的に積み上がる。アクセスを広げる前に、書面の受け入れ率と拒否権を得る。
  • マイクロモデル問題:その場限りのポジションや適格性のロジックは、監督上のモデルの定義を満たし得る。穴は品質ではなく、何が存在するか誰も列挙できないこと。
  • SR 26-2(2026年4月17日)は SR 11-7 と SR 21-8 に取って代わる。SR 11-7 を現行として引用するポリシーは更新し、適用範囲の主張は一次のレターで確認する。
  • 社内のコーディングツールと、顧客口座に触れる第三者エージェントは、2026年の別々の銀行の話。一方を他方の証拠として引用しない。
  • MDM 経由の管理設定は強制し、サーバー管理設定は明確に利便性。forceLoginOrgUUID は個人アカウントの穴を塞ぐキー、allowedProviders は経路を固定する。
  • テレメトリは既定で秘匿化される — MCP のツール名は 'mcp' と記録される。監査可能性を主張する前にコレクターをクエリし、内容のフラグはチェックボックスではなくプライバシー上の判断として扱う。
