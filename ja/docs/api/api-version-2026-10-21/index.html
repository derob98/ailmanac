API Version 2026-10-21 — 3年ぶりの破壊的変更を伴うバージョン

中級
最終検証: 2026-10-22。

API バージョン 2026-10-21 は、Anthropic 公式のバージョン履歴に 2023-06-01 と 2023-01-01 と並んで掲載されています。このページの破壊的変更、SDK のバージョン番号、フィールド名の変更はすべて公式の移行ガイドに基づいています。リリース前に必ず読み直してください — 移行ガイドは、公開後に編集される唯一の種類のドキュメントです。

次の情報源で確認してください: 公式情報源.

3年半のあいだ、「自分はどの API バージョンを使っているのか」という問いへの答えはちょうど1つでした — 2023-06-01 です。すべての SDK がそれを送り、すべてのチュートリアルがそれを貼り付け、誰も二度と考えませんでした。

2026年10月21日、それが変わりました。anthropic-version: 2026-10-21 が現在の推奨バージョンであり、本物の破壊的リリースです：ワイヤレベルの変更4件と SDK／CLI の変更9件、異なる認証ヘッダー、そしてすでに対応済みかもしれないモデル別の非推奨化よりも厳しいパラメーター削除があります。

チームが不意を突かれる部分、そしてこのページが存在する理由はここです：

このバージョンはヘッダーを編集して選ぶのではありません。依存関係をアップグレードして選ぶのです。

Anthropic の SDK は、そのメジャーバージョンが出荷された時点で最新だった API バージョンを送ります。古いメジャーは永遠に 2023-06-01 を送り続けます。新しいメジャーは 2026-10-21 を送ります。したがって、メジャーの境界をまたぐ通常の pip install -U anthropic や npm update が、アプリケーション全体の API バージョンを切り替えてしまい — 誰かが changelog を読んだかどうかに関わらず、すべての破壊的変更が1回のコミットで一緒にやってきます。

What you'll learn
  • 2026-10-21 をいつ採用するかを決めるのが、あなたが制御するヘッダーではなく SDK のメジャーバージョンである理由
  • 5分間のトリアージ：どの破壊的変更が実際にあなたのコードに影響するか
  • サンプリングパラメーターが既定値でも 400 になる理由と、残された唯一の抜け道
  • X-Api-Key から Authorization: Bearer への認証の変更と、それが静かに壊すプロキシ
  • エラーではなく誤った結果を返す2つの落とし穴（二重の認証情報、キーを抑制するヘッダー）
  • ワイヤ上で変わるものと、SDK の型でのみ変わるものの違い
  • 本番の統合を緑のまま保つアップグレード順序

★ Insight ───────────────────────────────────── このリリースには、性質のまったく異なる2種類の変更が同梱されており、混同すると丸一日を無駄にします。ワイヤの変更（削除されたパラメーター、拒否されるブロック配置、名前が変わったレスポンスフィールド）は anthropic-version ヘッダーによって決まるため、生の curl、あらゆる SDK、そして Message Batches のすべてに影響します。SDK の変更（MessageParam の共用体、削除された Text Completions、値が1つだけの enum の定数化）は、たまたま一緒についてくる通常のメジャーバージョンのリファクタリングで、ワイヤ上の JSON は変わりません。生の HTTP で API を呼んでいるなら、前者のリストだけが該当し、この移行は小さなものです。SDK を使っているなら、両方の移行を同時に行うことになり、実際より大きく感じるのはそのためです。 ─────────────────────────────────────────────────

まず：影響を受けますか？​

ほかのものを読む前にこれを実行してください。ヒットした項目は下のセクションに対応します。ヒットがなければ、アップグレードは単なるバージョンの引き上げです。

アップグレードを順番に​

Guided walkthrough1 of 6
  1. Amazon Bedrock では、2026-10-21 は Claude 4.7 以降のモデルでのみ利用できます。Bedrock で古いモデルを呼んでいる場合は、その呼び出しをまず 4.7+ のモデルに移すか、現在使っている SDK バージョンのままにする必要があります。それ以外のすべて — Claude API、Claude Platform on AWS、Microsoft Foundry、Google Cloud — では今すぐ利用できます。
  2. お使いの言語で 2026-10-21 を送る最初のメジャーバージョンをインストールします — 下の表を参照してください。Go と ant CLI はモジュールのインポートパスも変わるため、古いパスでの単純な "go install …@latest" は、エラーも警告もなく v1 を入れ続けます。生の HTTP で API を呼んでいる場合は、代わりに anthropic-version ヘッダーを 2026-10-21 に設定してください。
  3. temperature、top_p、top_k を削除します。ドキュメントをアシスタントメッセージの外へ、引用をユーザーメッセージの外へ移します。読み取っている Admin と Analytics のレスポンスフィールド名を変更します。これらは 400 を引き起こす変更であり、本番を止めるのはこれらです。
  4. SDK はキーを Authorization: Bearer として送るようになりました。あなたと Anthropic の間にある何か — ゲートウェイ、オブザーバビリティのシム、社内の送信プロキシ — が X-Api-Key を読んでいる場合、認証情報が見えなくなります。プロキシを変更するか、自分でヘッダーを付け直してください。
  5. MessageParam は共用体になり、Text Completions はなくなり、ツールランナーのクライアント側コンパクションはなくなり、betas は非ベータの Models メソッドから移動し、値が1つだけの enum は定数になりました。コンパイラーや型チェッカーがほとんどを見つけてくれます。
  6. Anthropic 自身の指示は、バージョンの引き上げと修正を同じデプロイでリリースすることです。引き上げだけを出荷すると、計画された移行がインシデントに変わります。

サンプリングパラメーターは既定値でも削除される​

これは、誰かがすでに「修正した」コードを壊す可能性が最も高い変更です。

AILmanac は以前からモデル別の非推奨化を記録してきました：Claude 4.7 世代以降のモデルでは、既定値でない temperature、top_p、top_k は 400 を返します。2026-10-21 では、ルールがより厳しくなります：

temperature、top_p、top_k を送るリクエストは、パラメーターの既定値であっても 400 エラーを返します。

したがって、以前は安全だった防御的パターン — 後で誰も「調整」できないように temperature: 1.0 を明示的に固定する — は、以前は任意の値を受け付けていた古いモデルを含め、すべてのモデルで確実に失敗するようになりました。新しいメジャーでは、このパラメーターは SDK の型と CLI フラグから消えているので、型付き言語ではコンパイラーが捕まえます。dict やハッシュで組み立てたリクエストボディでは、API まで届いてしまいます。

# Before — accepted under 2023-06-01 on every model
client.messages.create(model=MODEL, max_tokens=1024, temperature=1.0, messages=msgs)

# After — temperature: 1.0 is a 400 under 2026-10-21
client.messages.create(model=MODEL, max_tokens=1024, messages=msgs)

パラメーターを省略すると、それらを省略した 2023-06-01 のリクエストとまったく同じ既定値（temperature の 1.0 を含む）でサンプリングされます。したがって、すでに既定値以外を拒否していた現在のフロンティアモデルでは、出力はまったく変わりません — 純粋にリクエストの形の整理です。

本当の損失はより限定的で、正確に述べる価値があります。他の値を受け付けていた古いモデル — たとえば Sonnet 4.6 — では、より一貫した出力のために temperature を下げていたリクエストはその効果を失い、他のどの設定もそれを置き換えません。 Anthropic が文書化している選択肢は、そのパラメーターを送るのをやめるか、その特定のリクエストを 2023-06-01 に留めることです。

Pro tip
  • 新しい SDK のメジャーは3つのパラメーターを型から完全に削除したため、「そのリクエストを 2023-06-01 に留める」とは実際には、それらの呼び出しを以前の SDK メジャーに留めるか、古いヘッダーで生の HTTP 経由で発行することを意味します — これは文書化された2つの事実からの推論であり、文書化されたパターンではありません。決定性のために下げた temperature に依存しているなら、それをサポートされた構成ではなく、期限付きの技術的負債として扱ってください。
  • 現在のモデルで temperature に代わる持続的な手段はパラメーターではありません。システムプロンプトで挙動を固定し、effort 設定で計算量を意図的に使ってください — Extended Thinking & Effort と Effort tuning を参照。

認証が Authorization: Bearer に移動した​

SDK と CLI は、API キーを X-Api-Key: <key> ではなく Authorization: Bearer <key> として送るようになりました。

# Before
X-Api-Key: <key>

# After
Authorization: Bearer <key>

Claude API はどちらのヘッダーのキーも受け付けます。 したがって、プログラムが api.anthropic.com と直接通信しているなら、この変更は目に見えません — 何もする必要はありません。

壊れるのは、その間にある層です。X-Api-Key を読み取り、設定し、書き換え、ログに記録する何もかもが、認証情報を見失います：LLM ゲートウェイ、コスト配賦プロキシ、社内の送信フィルター、ヘッダーをアサートするテストダブル、テナントごとにキーを注入するカスタム fetch。症状は、Anthropic からではなくあなた自身のインフラからの明確な 401 であり、まさにキーのローテーションの問題と誤診されやすい種類のエラーです。

出口は2つ。プロキシを Authorization を読むように直す（正しい方法）か、古いヘッダーを自分で付け直す（手っ取り早い方法）：

Keep sending X-Api-Key to a proxy that needs it

// TypeScript — Authorization: null stops the key going out twice
const client = new Anthropic({
apiKey,
defaultHeaders: { "X-Api-Key": apiKey, Authorization: null }
});

Python は HTTP クライアントの auth 関数で行います（リトライ時にも実行されます）。Go は option.WithHeader と option.WithHeaderDel("Authorization")、Java は apiKey の代わりに putHeader、PHP と Ruby はリクエストミドルウェアで行います。C# は ExtraHeaders を使い、ApiKey と AuthToken の両方を null に設定する必要があります。そうしないと、環境で見つかった認証情報がそのまま送られます。

見落としやすい言語別の詳細が3つ：

  • AnthropicFoundry / @anthropic-ai/foundry-sdk / FoundryBackend は引き続き x-api-key を送ります。 そこでは変更は適用されません。
  • Bedrock Mantle クライアントはすでにベアラートークンを送っていました。 変更なし。
  • Ruby SDK は、別のオリジンへのリダイレクトをたどるときに Authorization を落とします — 同じホストでの http → https のリダイレクトも含みます。以前は X-Api-Key で運ばれていたキーが、そこでも落とされるようになりました。SDK を内部の http:// URL に向け、リダイレクトに頼っている場合、認証情報は静かに届かなくなります。
  • PHP では、このためにクライアントの extraHeaders を使わないでください。 独自の extraHeaders を持つリクエストは、クライアントのものを置き換えます — そしてベータヘッダーが必要な $client->beta 配下のすべてのエンドポイントがそれを持っています。ミドルウェアを使ってください。

例外を出さない2つの変更​

上記はすべて大きな音を立てて失敗します。この2つは動き続けながら誤ったことをするため、手作業で監査する価値があります。

1. かつてキーを抑制していたヘッダーは、もう抑制しません。 認証情報なしで、あるいはクライアントとは異なる認証情報でリクエストを送るための慣用法は、X-Api-Key を狙っていました。そのヘッダーはもうキーのある場所ではありません：

# Before — kept the client's key off this one request
client.messages.create(..., extra_headers={"X-Api-Key": omit})

# After — the key still goes out in Authorization. Suppress that instead.
client.messages.create(..., extra_headers={"Authorization": omit})

2. リクエストごとのキー上書きは、2つのキーを送るようになりました。 X-Api-Key に別のキーを渡すと、以前はクライアントのキーを置き換えていました。もうそうではありません：上書きは X-Api-Key で送られ、クライアント自身のキーは Authorization で送られるため、両方がワイヤ上に載ります。 1つのリクエストだけ別のキーを送るには、代わりに Authorization を設定するか（Python／TypeScript／PHP／Ruby）、Go では option.WithAPIKey(otherKey) を使います。

共有クライアント上にテナントごとのキールーティングを構築しているなら、これが行動すべき段落です：フォールバックはもはや「リクエストが失敗する」ではなく、「リクエストが誤ったキーのもとで成功する」です。

1つのクライアントは1つの認証情報を持つ​

API キーと認証トークンが1つのヘッダーを共有するようになったため、SDK クライアントは1つの認証情報しか保持できません。以前は2つ渡すと、それぞれ自分のヘッダーで両方が送られていました。今は構築時に例外を出します：

SDK2つの認証情報を渡したときの挙動
PythonValueError
TypeScriptTypeError
C#ArgumentException
Javabuild() から両方を名指しした IllegalStateException
PHPInvalidArgumentException
RubyArgumentError
GoNewClient はエラーを返さないため、代わりにクライアントが行うすべてのリクエストが失敗する

これと併せて、2つの挙動ルールが変わりました：

  • コードで渡した認証情報だけが使われます。 クライアントはもう環境やディスク上のプロファイルにフォールバックしません。以前は、環境内の ANTHROPIC_API_KEY が、渡したトークンと一緒に、あるいはその代わりに送られることがありました。
  • 何も渡さない場合、優先順位は固定されています： ANTHROPIC_API_KEY、次に ANTHROPIC_AUTH_TOKEN、次に ANTHROPIC_PROFILE で指定されたプロファイル、次にワークロード ID フェデレーションの変数、最後にディスク上のアクティブなプロファイル。この順序は変わりました： 複数の SDK は以前、ディスク上のアクティブなプロファイルをフェデレーション変数の前に置いていました。WIF で認証していてディスク上にもプロファイルがある場合、昨日とは別の認証情報を使っているかもしれません。以前の挙動に固定するには ANTHROPIC_PROFILE を設定してください。

ANTHROPIC_API_KEY と ANTHROPIC_AUTH_TOKEN の両方が設定されている場合は、キーが優先され、SDK はプロセスごとに1回警告をログに出します。PHP では、これはウェブリクエストごとに1回を意味します — 使わない変数を unset しないと、エラーログがあふれます。

これが壊す正当なパターンは「ゲートウェイにはトークン、その背後の API にはキー」です。明示的に作り直してください：トークンをクライアントの唯一の認証情報として渡し、デフォルトヘッダーまたはミドルウェアで X-Api-Key を設定し、ゲートウェイが転送前に自分の Authorization ヘッダーを取り除くようにします。Claude API は1リクエストにつき1つの認証情報を期待しています。

拒否される2つのブロック配置​

どちらも 2026-10-21 では 400 であり、どちらも Messages API、トークンカウント、そして新しいバージョンで作成された Message Batch 内の各リクエストに適用されます。

  • assistant メッセージ内に直接ある document ブロック。 ドキュメントは user メッセージで送ってください。別のブロックの内部にネストされたドキュメント — たとえば Claude が返した web-fetch ツールの結果 — は引き続き問題ないので、Claude 自身の出力を再生するのは安全です。
  • user メッセージ内の、空でない citations 配列を持つ text ブロック（search_result ブロック内を含む）。それらのブロックから citations を取り除いてください。assistant メッセージ内の text ブロック上の引用は引き続き受け付けられ、ドキュメントや検索結果上の設定としての "citations": [brackets with enabled true] も同様です。

2つ目は検索拡張パイプラインに固有の落とし穴です。Claude に検索結果を渡し、受け取った引用メタデータをそのまま返送すると、そのラウンドトリップは 400 になります — 表面的に似た、Claude の引用付き回答を再生するケースは動き続けます。この非対称性こそがバグのすべてです。

MessageParam は3つのロール型の共用体になった​

単一の MessageParam 型は UserMessageParam | AssistantMessageParam | SystemMessageParam になり、BetaMessageParam も同じように分かれます。SDK が送る JSON は変わりません。

まず良いニュース：ロールを明示した、プレーンな dict、ハッシュ、配列、オブジェクトリテラルとして書かれたメッセージは、まったく変更不要です。 [brackets: role user, content Hello] は今でもどこでも型チェックを通ります。ほとんどのコードベースにとって、この変更は何も起こしません。

壊れるパターンは4つ：

# 1. Calling the type as a constructor now raises TypeError
message = MessageParam(role="user", content="Hello")      # before
message: MessageParam = {"role": "user", "content": "Hello"}   # after
// 2. Spread-copying a message of unknown role — system messages differ
const copy: Anthropic.MessageParam = { ...message, content: blocks };          // before
const copy: Anthropic.MessageParam =
  message.role === "system" ? message : { ...message, content: blocks };       // after
// 3. Extending or implementing the type — you cannot extend a union
interface StoredMessage extends Anthropic.MessageParam { id: string }   // before
type StoredMessage = Anthropic.MessageParam & { id: string }            // after
// 4. Struct/builder literals name the role's type and drop Role
anthropic.MessageParam{Role: anthropic.MessageParamRoleAssistant, Content: blocks}        // before
anthropic.MessageParam{OfAssistant: &anthropic.AssistantMessageParam{Content: blocks}}    // after

5つ目はより微妙です：role が複数のロールを保持しうる変数から来る dict は、共用体のどのメンバーにも一致しないため、汎用の to_message(role, text) ヘルパーはロールごとに分岐する必要があります。また beta では、clear_at と output_config は BetaSystemMessageParam にのみ存在し、その content はオプションです — つまり message["content"] は undefined になりえます。

Go には、リファクタリングの陰に隠れた本物の挙動変化が1つあります：MessageParam のコピーは、同じ基底メッセージを指します。 duplicate.OfUser.Content を設定すると両方が変わりますが、v1 では duplicate.Content を設定するとコピーだけが変わりました。コピーで会話のバリエーションを作っているなら、それはコンパイルエラーではなく本物のエイリアシングのバグです。

SDK のみの5つの削除​

これらのどれもワイヤは変わらず、変わるのはあなたのコードだけです。

Admin API と Analytics API のフィールド名変更​

レスポンスフィールドの名前変更です。古い名前は 2026-10-21 では単に存在しないため、それを読むコードはエラーではなく undefined／nil を得ます — リクエストの経路ではなく、ダッシュボードを壊します。エンドポイント自体については The Admin API を参照してください。

エンドポイントグループ旧名称新名称
RBAC グループ（作成、一覧、取得、更新）rolesrole_ids
RBAC グループメンバー（一覧、追加、削除のレスポンス）group_idrbac_group_id
RBAC ロール（一覧、取得）namedisplay_name
組織・ワークスペースのレート制限group_typegroup.type

Analytics：アクティビティの要約summariesdata

レート制限エンドポイントの group_type クエリパラメーターと、API キー一覧エンドポイントの workspace_id フィルターは変わりません。動いたのはレスポンスフィールドだけです。

API キーの workspace_id は名前変更ではなく、セマンティクスの修正です。 2023-06-01 では、null の workspace_id は曖昧でした：「Default Workspace に紐づいている」または「単一のワークスペースに紐づいていない」（全ワークスペース対象のキー）のどちらかを意味し、この2つを区別できませんでした。2026-10-21 では：

  • ワークスペース（Default Workspace を含む）に紐づくキーは、scope.workspace_id にそのワークスペースの実際の ID が設定されます。
  • 全ワークスペース対象のキーは、scope が [type: organization] で、workspace_id はまったくありません。

曖昧さはなくなり、これは間違いなく改善です — ただし、workspace_id === null を「Default Workspace」と読んでいたコードは誤りになります。Default Workspace の実際の ID を一度取得し（include_default=true で List Workspaces を呼び、"Default" という名前のものを取る）、scope.workspace_id と比較してください。

今すぐアップグレードすべきですか？​

ほとんどのチームにとっての正直な答えは、計画的に、早めに、ただし偶然ではなくアップグレードすることです。2023-06-01 は廃止が告知されておらず、特定のバージョンに対する Anthropic の互換性の約束も依然として有効です — 既存の入力・出力パラメーターは保持されます。期限のプレッシャーはありません。リスクは古いバージョンが動かなくなることではなく、誰かがピン留めされていない依存関係の更新を実行し、気づかないまま一度にすべての変更を採用してしまうことです。

Watch out
  • このページから1つだけ行動を持ち帰るなら：ロックファイルとマニフェストで Anthropic SDK をメジャーバージョンに固定してください。それにより、この移行は自分に降りかかりうるものから、自分でスケジュールするものに変わります。

よくある間違い​

  • SDK の更新と、壊れたものの修正を2回のデプロイに分ける。 その間の時間は、サンプリングパラメーターを送るあらゆるコード経路にとって全面的な障害になります。Anthropic 自身のガイダンスは、両方を一緒にリリースすることです。
  • サンプリングのルールを、すでに対応したものと同じだと思い込む。 モデル別の非推奨化は既定値以外を拒否しました。このバージョンはパラメーターをそもそも拒否します。明示的に temperature: 1.0 を固定していたコードは以前は正しく、今は 400 になります。
  • 認証の変更を「API は両方のヘッダーを受け付けるので何もない」として扱う。 アプリケーションにとっては真、インフラにとっては偽です。API が両方を受け付けることこそ、障害が自分のプロキシから来たように見える理由です。
  • ヘッダー名を変えるだけで X-Api-Key の上書きを移行する。 X-Api-Key を認証情報の抑制や上書きに使っていたなら、名前を変えるだけでは足りません — どちらの挙動に頼っていたかを理解する必要があります。一方は今や2つのキーを送り、もう一方は送るべきでないキーを送るからです。
  • 古いモジュールパスでの go install …@latest。 最新の v1 をインストールし、何も教えてくれません。TypeScript のプラットフォームパッケージを v0 のままにして、npm にその下で2つ目のコア SDK を解決させるのと同じ種類の罠です。
  • Go クライアントに2つの認証情報を持たせる。 構築時に例外を投げません — NewClient はエラーを返さないため — すべてのリクエストが失敗して初めて気づきます。
  • Message Batches を忘れる。 ブロック配置とサンプリングパラメーターのルールは、2026-10-21 で作成されたバッチ内の各リクエストに適用されます。バッチ呼び出し自体だけではありません。

Key takeaways
  • 2026-10-21 は 2023-06-01 以来初めての新しい anthropic-version であり、ヘッダーの変更ではなく SDK のメジャーバージョンのアップグレードで採用する。SDK のメジャーを固定して、これを事故ではなく意思決定にする。
  • ワイヤの変更と SDK の変更を分ける。生の HTTP の呼び出し側は前者のグループだけを扱えばよく、移行は小さくなる。
  • temperature、top_p、top_k は、すべてのモデルで既定値でも 400 になる。本当に必要な下げた temperature の、文書化された唯一の抜け道は、そのリクエストを 2023-06-01 に留めること。
  • 認証は Authorization: Bearer に移った。アプリケーションは気づかないが、プロキシは気づく。
  • 2つの変更は大きな音を立てずに静かに失敗する — もう抑制しなくなったキー抑制ヘッダーと、今ではワイヤ上に2つのキーを載せるキー上書き。手作業で監査する。
  • ブロック配置とサンプリングのルールは、新しいバージョンで作成された Message Batch 内の各リクエストにも適用される。
  • Amazon Bedrock では新しいバージョンは Claude 4.7 以降のモデルのみが対象。それ以外のすべての場所では完全に利用できる。
