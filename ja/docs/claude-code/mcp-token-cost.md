# MCPトークン税

> Source: https://derob98.github.io/ailmanac/ja/docs/claude-code/mcp-token-cost · AILmanac (CC BY 4.0) · last verified 2026-11-10

MCPサーバーの接続が、最初のリクエストの前に5万〜15万トークンを燃やしかねない理由 — そして3つの対策：Tool Search、コード実行、そしてCLI呼び出しが勝つ場面を知ること。

Hacker NewsとXでは、繰り返し論争が起きています。*同じことがCLIなら数百トークンで済むのに、なぜ1回のMCP操作に数万トークンも燃やすのか？* MCP叩きに聞こえますが、そうではありません。最も声高に議論しているのは、エージェントを愛する人たち — ただ請求書を突きつけられた人たち — です。このページは、その請求書についての実践ガイドです。トークンが実際どこに消えるのか、ほとんど誰も切り分けていない2つのコスト、そして15万トークンのワークフローを2千トークンに変える3つの対策を扱います。

## コストは1つではなく2つ

MCPサーバーを接続すると、クライアントはそれに`tools/list`を要求し、**全ツールを完全なJSONスキーマ付きで**受け取ります。そのブロック全体がモデルのコンテキストに注入されます。多くの人はそこで精算を止めます。しかし税は2つあり、2つ目のほうが通常は大きいのです。

**コスト1 — ツール定義。** 接続された各ツールの名前、説明、パラメータスキーマがコンテキストに載ります。Anthropic自身の言い回し：*「エージェントが数千のツールに接続されている場合、リクエストを読む前に数十万トークンを処理する必要がある」*。単一のエンタープライズサーバーが数十から数百のツールを公開することがあり、サードパーティの分析では400ツールのサーバーはスキーマだけで約40万トークン — 20万トークンのウィンドウの2倍であり、100万トークンのウィンドウでもなお40%に当たります。最初のリクエストの前に消費されます。（モデルごとのウィンドウサイズ：[モデルと料金](/docs/whats-new/models-and-pricing)）

**コスト2 — 中間結果。** モデルがツールを直接呼び出すと、**すべての結果がモデルのコンテキストを通って戻ってきます**。読ませたくなかった部分さえもです。Anthropicの例：あるツールから2時間の会議の文字起こしを取り出して別のツールに渡すと、全文がモデルを*2回*通過し — 1行の要約を作るためだけに、およそ5万トークンにもなり得ます。

<Callout type="warning" items={["コスト1はプロンプトキャッシュが効くまで毎ターン支払われる — スキーマは一度ロードされるのではなく、会話の各リクエストで再送される。大きなツールカタログは、一度きりの手数料ではなくセッション全体への税である。これは定義が**ロードされている**ツールのコストです。遅延させること（後述）が、毎ターンの請求からそれを外します。", "コスト2はツール数ではなく、あなたのデータに応じてスケールする。小さなツールが10個あるほうが、巨大なブロブを返すツール1個より安いこともある。"]} />

### 一次ソースから見た数値

| 対策 | タスク | 前 | 後 | 削減率 |
| --- | --- | --- | --- | --- |
| MCPでのコード実行 | Google Drive → Salesforceワークフロー | 150,000 | 2,000 | **98.7%** |
| Tool Search Tool | 作業開始前に定義をロード | ~77,000 | ~8,700 | **85%** |
| Programmatic Tool Calling | 複雑な研究タスク | 43,588 | 27,297 | **37%** |

3行すべてAnthropicの公表数値です。驚くべきはコストではなく、**精度**です。Tool Search Toolでは、ツール選択の精度が*上がりました*（Opus 4.5は79.5% → 88.1%、Opus 4は49% → 74%）。コンテキストを混雑させるツールが減ると、モデルは正しいものをより頻繁に選びます。ここではコストと品質が同じ方向に動く — これは稀なことです。

## 対策1 — ツールスキーマをオンデマンドでロードする

全スキーマを最初に注入する代わりに、`defer_loading: true`とマークします。するとClaudeは軽量なインデックスだけを見て、GitHubが必要になったときに**Tool Search Tool**を呼び出し、それが*一致するGitHubスキーマだけ*を返します — ほかのすべてのサーバーの50以上のツールは返しません。Anthropicの報告では、これによりすべてをプリロードした場合の約122,800トークンに対し、約191,300トークンのコンテキストが保たれます。

### Claude Codeでは、すでにオン

MCPサーバーでClaude Codeを使っているなら、今まさにこのパターンを見ています。**ツール検索はデフォルトで有効**です。セッション開始時にロードされるのはツールの*名前*とサーバーの指示だけで、タスクが必要とするとき、Claudeは`ToolSearch`呼び出しを通じて完全なスキーマを取得します。つまり、サーバーを1つ増やしても、かかるのはそのツール名であってスキーマではありません。Claude Codeはサーバーごとのツール数の上限を設けておらず、現実的な限界はコンテキストウィンドウの予算だと述べています。

広く繰り返されている主張に、訂正しておくべきものがあります。半分だけ正しいからです。「コンテキストウィンドウの約10%」というしきい値は実在しますが、デフォルトのトリガーでは**ありません**。環境変数`ENABLE_TOOL_SEARCH`のオプトインのモードの1つです。

| `ENABLE_TOOL_SEARCH` | 挙動 |
| --- | --- |
| *（未設定）* — デフォルト | すべてのMCPツールを遅延させ、必要に応じてロード |
| `true` | 未設定と同じ |
| `auto` | しきい値モード。遅延可能なツールは、定義の合計がコンテキストウィンドウの10%未満の間は**最初に**ロードされ、10%以上になるとツール検索がオンになる |
| `auto:N` | 独自の割合を指定するしきい値モード（`N`は0〜100）。例：`auto:5` |
| `false` | すべてのMCPツールを最初にロード、遅延なし |

つまり、10%未満ならツールが最初にロードされると当てにしていたなら、デフォルトを逆に理解しています。`auto`を指定しない限り、最初にロードされるものは何もありません。しかも`auto`は**粘着的**です。合計がしきい値を超えてツール検索がオンになると、合計が再びしきい値を下回った後も、それらのツールは遅延されたままになることがあります。

<Callout type="warning" items={["ツール検索をオフにし、ENABLE_TOOL_SEARCHを完全に無視するものが3つある：CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS（Claude Code v2.1.227以降、組織は管理設定でオンのままにできる）、HIPAA構成が適用されたセッション（上書き手段は一切なし）、そしてAzureでホストされるMicrosoft Foundryのデプロイ（サーバー側で拒否される）。権限でToolSearchツールを拒否した場合も、すべてが最初にロードされる。", "モデルの下限がある：Claude Codeがツール検索を使うのはClaude Opus 4、Sonnet 4、Haiku 4.5以降。それより前のモデルではすべてが最初にロードされ、ENABLE_TOOL_SEARCH=trueでもこれは上書きされない。Google CloudのAgent Platformでは下限が高く、Opus 4.5、Sonnet 4.5、Haiku 4.5以降となる。"]} />

MCPサーバーを書く側にとっては、遅延は説明文の予算も変えます。しかも非対称です。**最初に**ロードされるツールは4,096文字で切り捨てられ（サーバーの指示と同じ上限）、**ツール検索経由**でロードされるものは16,384文字です。ただし検索自体は短いほうの上限に対してしかマッチしないため、Claudeが検索しそうな言葉はどちらの場合も先頭近くに置く必要があります。

<Steps items={[{title: "接続したものを棚卸しする", body: "アクティブなサーバーと、それぞれがおおよそ何個のツールを公開しているかを一覧にします。/contextを実行してください。ツール検索が適用されているツールには(deferred)または(loaded on-demand)と表示されるので、どのサーバーが実際にスキーマのトークンを使っていて、どれが名前だけを使っているかが分かります。"}, {title: "このタスクに不要なものは切断する", body: "最も安い対策はサーバーを減らすことです。カタログ全体ではなく、タスクが実際に使う2つか3つだけを接続します。遅延されていても、すべてのサーバーは毎ターン、ツール名とサーバーの指示を負担します。"}, {title: "残りは遅延させる", body: "Claude Codeではすでにそれがデフォルトです。それ以外では、defer_loading + Tool Searchに対応したクライアント/設定を選び、スキーマが検索されたときだけロードされるようにします。"}]} />

## 対策2 — コード実行で結果をコンテキストの外に保つ

より深い対策はコスト2を狙います。モデルがツールを1つずつ呼び出し、すべての結果がモデルを通過する代わりに、モデルがツールを呼び出す**コードを書き**、中間データは実行環境の中にとどまります。AnthropicはMCPサーバーを、エージェントがファイルシステムのように探索する**ツールのファイルツリー**として公開し、必要な定義だけをロードします — そして*「中間結果はデフォルトで実行環境にとどまり…エージェントは明示的にログまたは返却したものだけを見る」*のです。

その単一の設計変更こそが、Drive→Salesforceのワークフローを15万トークンから2千トークンに縮めるものです：レコードはコードを通って移動し、最終的なカウントだけがモデルに戻ります。開発者プラットフォームでは、同じ考え方が**Programmatic Tool Calling**として提供されます — Claudeが複数のツールをオーケストレーションし、出力がコンテキストに達する前にフィルタリングするPythonを書きます。

<Callout type="tip" items={["経験則：ツールが大きなもの（文字起こし、クエリのダンプ、ファイル）を返すなら、ブロブがコンテキスト外で処理されるようにコード実行が望ましい。ツールが小さなこと（イシューを作る、1行を送る）をするだけなら、直接呼び出しで十分。"]} />

## 対策3 — CLI呼び出しが勝つ場面を知る

時には、正解はより良いMCPセットアップではなく — MCPをまったく使わないことです。HN/Xの議論には本当の一理があります：`gh pr list`や`psql -c '…'`のようなシェルコマンドは往復で数百トークンで済む一方、同等のMCPパスはスキーマ＋構造化された結果に対して支払います。エージェントがすでにターミナルを持ち、CLIが存在するなら、それがしばしば最も軽いパスです。

<PromptCard title="ツールがすでにCLIなら、CLIを優先する">
{`# Instead of connecting a GitHub MCP server for read-only work,
# let the agent use the gh CLI it already has:
gh pr list --state open --json number,title,author

# ~200 tokens of command + compact output, no schema tax,
# no server to keep connected across the session.`}
</PromptCard>

MCPがそのオーバーヘッドに見合うのは、**型付きで、権限管理され、サーフェスをまたぐ**能力が必要なとき — 読み取り専用ロールを持つデータベース、駆動できるブラウザ、OAuth付きのSaaS API — か、同じツールが多くのターンで再利用され、キャッシュがスキーマコストを償却するときです。能力が一度きりで、すでにスクリプト化可能で、小さなものを返すなら、CLIに手を伸ばしましょう。どちらが「良い」ということではなく、コストカーブ上の異なる点です。
