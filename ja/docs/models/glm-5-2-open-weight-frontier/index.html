GLM-5.2:オープンウェイト・フロンティアのコーディングモデル

中級

2026年6月13日、Z.ai(旧 Zhipu AI)は GLM-5.2 をリリースした — 7530億パラメータの Mixture-of-Experts モデルで、100万トークンコンテキスト、地域制限のない平易な MIT ライセンスで Hugging Face に公開。続く 2 週間で、ローンチそのものより無視しにくい 3 つのことが起きた:長ホライズンのコーディングベンチマークで Claude Opus 4.8 の約 1 ポイント差に着地し、API がフロンティア価格を約 6 倍下回り、Semgrep のセキュリティチームが GLM-5.2 がほとんどスキャフォールディングなしで Claude Code を実世界の IDOR 脆弱性ベンチマークで上回ったと静かに報告した。

このページは GLM-5.2 について実際に非自明な点をカバーする — 1M トークン推論を扱いやすくする IndexShare アーキテクチャ変更、Claude と GPT-5.5 に対する誠実なベンチマーク像、今日セルフホストにかかるコスト、そしてクローズドフロンティアモデルに手を伸ばすより真に優れたツールとなる場面。

What you'll learn
  • IndexShare とは何か、なぜ長コンテキスト計算を ~2.9× 削減するかを理解する — マーケティング数値ではなくアーキテクチャ数値
  • 誠実なベンチマーク像を読む:GLM-5.2 が Claude Opus 4.8 に一致する場所、しない場所、ベンダースコアで信頼すべきもの
  • 実効コスト計算を知る:Claude Opus のフロンティア価格に対して入力/出力 M あたり ~$1.20–1.40 / $4.10–4.40
  • GLM-5.2 を 3 行で API 経由、または vLLM 0.23+ でセルフホスト(FP8 と 2ビットパスを明記)
  • GLM-5.2 vs Claude をいつ選ぶか — 明確に勝つ 2 つのタスク、明確に勝たない 2 つ

一文サマリー​

GLM-5.2 は オープンウェイト(MIT)、753B 総 / ~40B アクティブのスパース Mixture-of-Experts モデルで、Z.ai 製、1M トークンコンテキスト、131,072 トークン最大出力、長ホライズンのエージェンティックコーディング向けに構築 — クローズドフロンティア API の約 6 分の 1 の価格で、独立評価では自律エージェント作業に重要なコーディングベンチマークで Claude Opus 4.8 から 1 ポイント差にある。

見出しからは自明ではない GLM-5.2 の 3 点​

1. IndexShare が本当のアーキテクチャストーリー​

GLM-5.2 の見出しの変更は「より大きな MoE」ではなく IndexShare だ。スパースアテンションは、各クエリが過去のどのトークンにアテンドするかを決めるインデクサを必要とする。1M トークンコンテキストで層ごとにそのインデクサを実行するのは高価だ。Z.ai の IndexShare は 同じインデクサを 4 つのスパースアテンション層すべてで再利用し、1M ウィンドウ全体でトークンあたり FLOPs を ~2.9× 削減する。

実用的な結果:GLM-5.2 は、完全な二次アテンションモデルで同じ仕事をすると経済的に不合理な価格で、実世界の長コンテキストワークロードを提供できる。これはまた、FP8 チェックポイント(zai-org/GLM-5.2-FP8として公開)が 8× H200 で 131K トークンセッションの余地を持って動作する理由でもある;IndexShare なしなら、同じハードウェアはそこに至る前に KV キャッシュで詰まる。

GLM-5.2 は投機的デコード用の改善された Multi-Token Prediction (MTP) 層も出荷し、Z.ai は ~20% の受容長アップリフトを報告 — これは論文メトリックだけでなく、実際の推論での速いトークン/秒として現れる。

最終検証: 2026-07-29。

アーキテクチャ詳細(IndexShare、MTP 受容アップリフト、753B/40B 構成)は公式 Hugging Face モデルカードと Z.ai のローンチ資料から。計算節約主張(2.9×)はベンダー報告;1M コンテキストでの独立した推論コスト測定は 2026年7月末時点でまだ疎です。

次の情報源で確認してください: 公式情報源.

2. ベンチマークストーリーは「GPT-5.5 に勝つ」より強く「Opus に勝つ」より弱い​

ベンダー表とニュース報道はこれをサウンドバイトに圧縮する。誠実な読み:

ベンチマークGLM-5.2Claude Opus 4.8GPT-5.5注記
Terminal-Bench 2.181.0~85.0—長ホライズン shell/エージェント作業;4 ポイントギャップ
SWE-bench Pro62.1—58.6自律的なリポレベルの修正;GPT-5.5 の先、GLM-5.1 (58.4) の先
GPQA Diamond91.2——難しい科学 QA;強い
AIME 202699.2——ベンダー報告;極端な数値、慎重に扱う
Artificial Analysis Intelligence Index51——ローンチ時点で任意のオープンウェイトモデルの最高スコア
Code Arena (グローバル)#2——一つのクローズドモデルに次ぐ

内面化すべき 2 点:

  • エージェント作業に対応するコーディングベンチマーク(SWE-bench Pro、Terminal-Bench 2.1、Code Arena)では、GLM-5.2 は GPT-5.5 より Claude Opus 4.8 に近い。任意のオープンウェイトモデルにとって初めてのことだ。
  • 最も難しい推論タスクと開かれた知識では、クローズドフロンティアモデルが依然リードする。AIME 99.2 見出しはベンダー報告で独立評価と並べて読むべき — Z.ai の Artificial Analysis Index スコア 51 の方がよりキャリブレーションされた要約だ。
Pro tip

誰かが「GLM-5.2 が Claude Opus に勝つ」または「GLM-5.2 が GPT-5.5 に勝つ」とリンクしたら、どのベンチマークで誰の測定かを確認せよ。長ホライズンコーディングで:Opus から 1 ポイント差、GPT-5.5 より明確に先。一般推論で:依然クローズドフロンティアの後。両方とも真だ。

3. Huawei Ascend NPU で訓練され、Nvidia ではない​

GLM-5.2 は Nvidia H100/H200 ではなく、報告によれば Huawei Ascend アクセラレータで訓練された。それはベンチマーキングの詳細ではない — サプライチェーンの事実だ。Z.ai が米国 Entity List にあり、ホスト型 API が中国インフラを経由することと組み合わせると、3 つの実際の判断を形成する:

  • 規制環境は本番に配線する前に、ホスト型 API を輸出管理ポリシーに対して評価すべきだ。MIT ウェイトは制限がない;API はコンプライアンスレビューの代替にならない。
  • データ機密ワークロードは、Z.ai の API エンドポイントにプロンプトを送るのではなく、セルフホストパス(下記)を優先すべきだ。
  • アグリゲータ(OpenRouter、NVIDIA Build、OpenRelay)は非 Z.ai インフラを通じて GLM-5.2 を提供する — モデルは欲しいがオリジンルーティングは欲しくないなら、それがルートだ。

実効コスト計算​

Z.ai 自身の API 価格は、プロバイダ全体で入力トークン 100 万あたり約 $1.20–$1.40、出力トークン 100 万あたり $4.10–$4.40 付近に位置する。Claude Opus 4.8 テリトリー($15/M 入力、$75/M 出力のフロンティア価格)と比較すると、比率は入力で約 1:6、出力で 1:15+ だ。Semgrep の IDOR ベンチマークは脆弱性あたりコストを ~$0.17 for GLM-5.2 に置き、フロンティア相当は数ドル。

見逃しやすい罠:GLM-5.2 はモデルレベルで「high」または「max」思考努力で動くので、同じタスクに対して出力トークン数は非思考モデルより高い。タスクあたりコストは依然低いが、比率はトークンあたり価格が示唆するほど極端ではない — 各々より低い価格で、答えあたりより多くのトークンを支払っている。

API 経由で始める​

GLM-5.2 は OpenAI 互換 chat completions を話す。エンドポイント URL とモデル ID はプロバイダによって変動する — 一つを選べ:

プロバイダベース URLモデル IDEnv
Z.ai(直接)https://api.z.ai/api/paas/v4/glm-5.2ZAI_API_KEY
OpenRouterhttps://openrouter.ai/api/v1z-ai/glm-5.2OPENROUTER_API_KEY
NVIDIA Buildhttps://integrate.api.nvidia.com/v1z-ai/glm-5.2NVIDIA_API_KEY
OpenRelayhttps://inference.openrelay.inc/v1openrelay/glm-5.2OPENRELAY_API_KEY
Guided walkthrough1 of 3
  1. 直接アクセスの場合、z.ai でサインアップしキーを作成せよ。アグリゲータアクセス(米国 Entity List 側にいる場合推奨)には OpenRouter または NVIDIA Build を使う。
  2. 公式 openai SDK は変更なしで動作する — base_url とモデル名を変更。OpenAI の API 形状(LangChain、LlamaIndex、Vercel AI SDK)で構築された任意のフレームワークは同じように動作する。
  3. 関数呼び出し、JSON モード、1M トークンコンテキストは標準の chat.completions 形状で動作する。長コンテキストを「有効化」する特別なパラメータはない — 常に利用可能だ。

OpenAI SDK (Python) 経由の GLM-5.2、OpenRouter を通じて

import openai

client = openai.OpenAI(
  api_key="YOUR_OPENROUTER_KEY",
  base_url="https://openrouter.ai/api/v1",
)

response = client.chat.completions.create(
  model="z-ai/glm-5.2",
  messages=[
      {"role": "user", "content": "Refactor this 800-line auth module for testability. Preserve behavior; return a unified diff."},
  ],
)
print(response.choices[0].message.content)

Z.ai 直接エンドポイント経由の GLM-5.2 (Python)

import openai

client = openai.OpenAI(
  api_key="YOUR_ZAI_API_KEY",
  base_url="https://api.z.ai/api/paas/v4/",
)

response = client.chat.completions.create(
  model="glm-5.2",
  messages=[
      {"role": "system", "content": "You are a careful staff engineer."},
      {"role": "user", "content": "Review this repo and list the top 5 risks, with file:line references."},
  ],
)
print(response.choices[0].message.content)

セルフホスティング:3 つの現実的パス​

MIT ライセンスと公開された FP8 ウェイトは、多くのチームにとってセルフホスティングを全ポイントにする。3 つの実用的パス、最もハードウェアが必要なものから最も少ないものへ:

パス A — vLLM で 8× H200 上の FP8(本番グレード)​

リファレンスデプロイメント。公式 FP8 チェックポイントをダウンロードし、vLLM 0.23.0+(または SGLang 0.5.13.post1+)で提供する。これは Z.ai 自身の推論に最も近い config だ;完全な 131K トークン最大出力と安定したスループットを与える。

vLLM で 8× H200 上に GLM-5.2 FP8 をデプロイ

# 1) Download the FP8 weights (~750 GB)
huggingface-cli download zai-org/GLM-5.2-FP8 \
--local-dir /models/glm-5.2-fp8

# 2) Serve with vLLM 0.23.0+
python -m vllm.entrypoints.openai.api_server \
--model /models/glm-5.2-fp8 \
--served-model-name glm-5.2-fp8 \
--tensor-parallel-size 8 \
--quantization fp8 \
--enable-expert-parallel \
--max-model-len 131072 \
--kv-cache-dtype fp8_e5m2 \
--gpu-memory-utilization 0.92 \
--enable-chunked-prefill \
--max-num-seqs 32 \
--port 8000

パス B — Mac Studio または 24 GB GPU + 256 GB RAM 上の 2 ビット GGUF​

Unsloth の動的 2 ビット GGUF は GLM-5.2 を ~1.51 TB から ~239 GB へ圧縮する — 256 GB Mac Studio (Ultra) または 24 GB GPU に 256 GB システム RAM を持つワークステーションに収まる小ささ(MoE ルーティングは一度に少数のエキスパートだけをホットに保つので、DRAM オフロードが機能する)。これは「実際に店で買えるハードウェアで動かす」パスだ。H200 ラックより遅いトークン/秒を予期せよ、しかし単独エージェントワークロードには使える。

パス C — コミュニティからの AWQ/W4A16 量子化​

サードパーティ量子化(例:QuantTrio/GLM-5-AWQ、PhalaCloud/GLM-5.2-W4AFP8)は vLLM の AWQ カーネルと互換な 4 ビット重みパスを狙う。これは FP8 より小さいメモリフットプリントを望むが 2 ビット GGUF より余裕を望むときに有用。Z.ai は 2026年7月末時点で公式 AWQ 版を公開していない — 本番で使う前にコミュニティ版のキャリブレーションを検証せよ。

Watch out

任意のティアで GLM-5.2 をセルフホストする際、トークナイザとチャットテンプレートには依然注意が必要だ。Hugging Face モデルカードは両方を出荷する;プロンプトを手動で組み立てるのではなく add_generation_prompt=True で apply_chat_template を使え。テンプレートの不一致は「なぜ私のオープンウェイトモデルは API よりずっと悪いのか?」レポートの単一で最も一般的な原因だ。

GLM-5.2 vs Claude をいつ選ぶか​

真により良いツールとなる 2 つのタスク:

  • プライベートコードベース上の長ホライズン自律コーディング。 セルフホスト FP8 は、コードやコンテキストがインフラを離れずにフロンティア隣接の SWE-bench Pro スコアを与える。Claude Opus 4.8 は Terminal-Bench 2.1 で髪の毛ほど鋭いが、オンプレ推論のコンプライアンス勝ちがしばしば 4 パーセントポイントを上回る。
  • 敵対的ペイロードでのセキュリティ研究。 Semgrep の IDOR 実験(裸プロンプトハーネスで F1 39%、Claude Code の 37% を先行)は、GLM-5.2 が Claude の安全訓練が偽陽性をトリガーする防御的セキュリティタスクで意味のある拒否率の低さを示唆する。

Claude が依然より良いツールである 2 つのタスク:

  • 開かれた推論と事実知識の質問。 GLM-5.2 は一般知識と開かれた推論でクローズドフロンティアモデルに遅れる;Claude Opus/Sonnet 5 と Fable 5 がここで先行する。
  • 拒否モードのニュアンスが重要な任意のもの。 Claude の害回避はよりニュアンスに富む(正当な作業での過剰拒否が少なく、真の害でよりシャープに停止)。GLM-5.2 の安全層はエッジケースに対してより薄くキャリブレーションが低い。
Pro tip

クロスリンク:より広いオープンウェイトランドスケープには DeepSeek、Qwen とオープンウェイトの波 と Kimi K3:世界最大のオープンウェイトモデル を参照。「これは全くローカルで実行すべきか?」判断には Local vs Claude エージェント を参照。

Semgrep の IDOR 結果を一段落で​

Semgrep は脆弱性データセット(実際のオープンソース IDOR 欠陥)、F1 スコアリング、システムプロンプトを一定に保ち、モデル + 周辺ハーネスを変えた。GPT-5.5 とのカスタム Semgrep Multimodal リグは 61% F1;Opus 4.8 との同じリグは 53%。GLM-5.2 をプロンプトだけ(裸の Pydantic AI ハーネス、エンドポイント列挙なし、案内付きナビゲーションなし)でテストしたとき、39% F1 を記録 — 同じタスクで Claude Code (37% F1) を約 脆弱性あたり $0.17 で上回った、フロンティアコストの約 6 分の 1。彼ら自身の見出し:「私たちは家に Mythos がある。」 重要な但し書き:一つのタスク、一つのデータセット、一つの実行 — 発見は方向性があり、SSRF、XSS、または他のクラスへの一般化を約束するものではない。

Key takeaways
  • GLM-5.2(2026年6月13日)は長ホライズンコーディングで Claude Opus 4.8 の 1 ポイント差まで迫った最初の MIT ライセンスオープンウェイトモデル — オープンウェイト層の真のターニングポイント。
  • IndexShare がアーキテクチャストーリー:スパースアテンションインデクサを 4 層ごとに再利用、1M コンテキストで ~2.9× のトークンあたり計算削減 — 長コンテキスト提供を経済的にする。
  • 実効コストは入力トークンあたり Claude Opus の ~1/6、出力トークン数の高さ(既定で high/max 思考オン)で部分的に相殺。Semgrep は IDOR 脆弱性検出あたり ~$0.17 と測定。
  • 3 つのセルフホストパス:vLLM で 8× H200 上の FP8(本番)、Mac Studio / 24 GB + 256 GB ボックス上の 2 ビット動的 GGUF(アクセス可能)、またはコミュニティ AWQ/W4 量子化(中間)。
  • プライベート長ホライズンコーディングと防御的セキュリティ研究には GLM-5.2 に手を伸ばせ;開かれた推論、事実知識、ニュアンスに富む安全エッジには Claude を保て。
