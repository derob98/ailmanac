Pi 1.0: ミニマルなハーネスと、MCP のトークン肥大を解消する codemode の技

上級

Pi 1.0 は 2026年10月1日にリリースされ、翌朝には 1,500 ポイント超で Hacker News のトップに座っていた。売り文句はほとんど攻撃的なくらい地味だ。「自分のものに 作り変えられる、ミニマルで拡張可能なエージェントハーネス」。MIT ライセンス、 TypeScript、ターミナルコマンド1つ。

この売り文句は実態を過小に見せている。TUI の下で Pi が出荷しているのは、どのエー ジェントハーネスも3か月目にぶつかる問題に対して、これまで誰も公開したことがない ほど完全な答えだ。すなわち MCP サーバーはコンテキストウィンドウを破壊するのに、 誰もそれを認めたがらない という問題である。Pi は1年にわたり公然と MCP のサポート を拒み続け、そして出荷した——ツールをプロンプトに一切入れないという方法で。その仕組 みは文書化されており、計測可能で、あなたが Pi を動かすかどうかに関係なくコピーで きる。

このページはその仕組み、その背後にある数字、そして自分のハーネスについての考え方を 変えることになる Pi の3つの設計判断についての話だ。

What you'll learn
  • codemode を理解する: ネストしたツール呼び出しがモデルのコンテキストに一切入らない QuickJS/WASM サンドボックス——入るのはスクリプトの出力だけ
  • Pi の4つの MCP 露出モードと、デフォルト（codemode）がモデルに対して何ひとつ宣言しない理由を学ぶ
  • 正確な予算を見る: インライン化されるツール宣言に 3,000 トークン、MCP 結果が削られ始めるまで 20 KB、スクリプトには見えてモデルには見えない bash 出力が 1 MiB
  • プロンプトキャッシュの技をコピーする: ツール定義を書き換える代わりに、変化したシステムプロンプトのセクションをトランスクリプトに追記する
  • 意図的な欠落（サブエージェントなし、プランモードなし、呼び出しごとの承認なし）と、クローンしたリポジトリの AGENTS.md を確認なしで読み込む信頼のギャップを知る

1段落版​

Pi は Earendil（Radius と Lefos も作っている）によるモデル非依存のターミナル エージェントだ。リポジトリ github.com/earendil-works/pi は、個別に利用できる13 パッケージの TypeScript モノレポである。約30プロバイダにまたがる統一 LLM API、 エージェントループ、TUI ライブラリ、スタンドアロンの MCP クライアント、WASM サンド ボックス、そして実験的な永続ランタイム。Node.js 22.19+ が必要だ。意図的に サブエージェントなし、プランモードなし で出荷され、すべてのツール呼び出しの 前に承認を求めることもしない。代わりに出荷されているのはコンテキストエンジニア リングだ。codemode——モデルがスクリプトを書くための JavaScript サンドボックスで、 ツール呼び出しはトランスクリプトの外側で起き、戻ってくるのはスクリプトが蒸留した 出力だけである。

最終検証: 2026-10-02。

バージョン、ライセンス、依存関係、パッケージに関する事実は、2026年10月2日にリポジ トリと GitHub API から読み取ったもの: タグ v1.0.0 は 2026-10-01T19:20:55Z に公開、 MIT、リポジトリ作成は 2025-08-09、執筆時点で約 111.6k スター / 約 14.2k フォーク。 設定のデフォルト値と上限は、main に追従するリポジトリ内ドキュメント packages/coding-agent/docs/ から引用している——codemode.inlineBudget のような 数字は設定値であり、設定値は再調整される。特定の値に依存する前に、リポジトリの settings.md と mcp.md を読み直すこと。

次の情報源で確認してください: 公式情報源.

インストールしなくても重要な理由​

どのハーネスも始まり方は同じだ。便利そうだから MCP サーバーを3つ追加する。それぞれ が20個のツール定義をシステムプロンプトに流し込む。こうして、あらゆるセッションの あらゆるモデル呼び出しが、呼ばれることのない大半を含む60個のツールスキーマの代金を 払うことになり、サーバーが再接続してツール一覧がずれるたびにプロンプトキャッシュが 壊れる。

AILmanac は以前これを計測している—— MCP サーバーが実際にトークンでいくらかかるのか を参照。Pi の答えは「サーバーを減らせ」とは構造的に違う。

codemode: 実際の仕組み​

codemode ツールは入力として 生の JavaScript ソース を受け取る——JSON でも、 フェンス付きコードブロックでもない。Pi はそれを WebAssembly にコンパイルされた QuickJS VM の中で async 関数の本体として実行するので、トップレベルの await と return が使える。

このサンドボックスの唯一の能力は、注入されたツールを呼ぶことだ。タイマーも fetch も process も require もモジュールも、ネストした WebAssembly もない。 （eval と Function は動くが、同じ VM 内にコードをさらに生むだけだ。）リモートの 画像 URL は拒否され、base64 の data: URL と画像ブロックだけが通る。

その帰結こそが要点そのものである。

ネストしたツール呼び出しは LLM のコンテキストに入らない。入るのはスクリプトの出力 と戻り値だけだ。

だからスクリプトは10個のツール呼び出しを並列にファンアウトし、400 KB の結果を4行に 絞り込める。そしてモデルが見るのは4行だ。10回の呼び出し、その引数、生の結果は、 一度もトランスクリプトのエントリにならない。

Guided walkthrough1 of 5
  1. スクリプトの中では、呼び出せるすべてのツールが `tools` のメソッドになる。JavaScript の識別子として無効な文字はアンダースコアになるので、MCP ツール `mcp__dev-radius__search` は `tools.mcp__dev_radius__search` で到達できる。モデルがこれらを呼ぶのに、プロンプトでの宣言は必要ない。
  2. スクリプトには `ALL_TOOLS`（呼び出し可能な全ツールの名前と説明）、BM25 関連度でツールをランク付けしデフォルト上限8件の `searchTools(query)`、ツールの TypeScript 宣言を返す `describeTool(name)`、MCP サーバーの説明・指示・ツール名を返す `describeNamespace(name)` が渡される。ツール発見は、プロンプト時のダンプではなく実行時のクエリになる。
  3. スクリプトはオプション行から始めてもよい。`max_output_tokens` のデフォルトは 10,000 で、それより長い出力は先頭と末尾が保たれ、全文は一時ファイルに書き出されてそのパスが結果に含まれる——だからモデルは本当に必要ならツールで読みに行ける。`timeout_ms` はデフォルトで未設定で、スクリプト全体に対する厳格な期限になる。
  4. ドキュメントは明示している。失敗より前に行われた呼び出しは取り消されない。スクリプト終了時にまだ実行中の呼び出しはキャンセルされ、await されていない promise は破棄される。失敗したスクリプトは部分的な出力を保持し、その後 `Script error:` とエラーを報告する。10回のうち7回目でタイムアウトすれば6回は完了済みで残るのだから、再実行しても安全なスクリプトを書くこと。
  5. `store(key, value)` と `load(key)` は codemode 呼び出しをまたいで JSON を保持する。書き込みはスクリプトが成功したときだけ残され、値を保存した成功スクリプトはそれぞれセッションに `codemode-store` エントリを追記する——だから再開したセッションは値を保ち、フォークしたブランチは自分の経路で書かれたものだけを見る。

覚えておく価値のある bash の数字​

直接の bash 呼び出しがモデルに見せる結果は 2,000 行または 50 KB が上限だ。codemode スクリプトの内側から呼ばれると、同じツールは構造化された値に解決され、その output フィールドは 最大 1 MiB を保持する——それより長い場合は、省略マーカーを挟んで先頭 と末尾の 512 KiB を残し、truncated を立て、全出力を full_output_path で指し示す。

これはスクリプトに対してコマンド出力の窓が20倍広いということであり、そのスクリプト がモデルに何を見せていいかを決める。MCP も同様だ。20 KB を超えるテキスト結果は …N chars truncated… マーカーの周りで中央を除去されてモデルに届くが、codemode スクリプトは structuredContent と isError を含む完全な CallToolResult を受け取る。

4つの露出モード​

これは自分の設計ノートにコピーすべき表だ。Pi の各 MCP サーバーには exposure があり、 それがモデルからそのサーバーのツールへの到達方法を決める。各ツールは mcp__<server>__<tool> として登録される。

露出モデルに見えるもの使いどころ
codemode (デフォルト)何も見えない。宣言されず、codemode の説明にすら列挙されない。スクリプトが searchTools()、describeTool()、ALL_TOOLS で見つける。一般的なサーバー、とくにスクリプトが呼び出しを組み合わせたり絞り込むべき場合
deferred何も見えない。tool_search が次のモデル呼び出しのためにマッチをロードするまでは。ロード後は宣言され、そのブランチ上では宣言されたままになる。発見後に直接呼ぶべきツールを持つ大きなサーバー
direct組み込みツールのように宣言され、codemode からも呼べる。小さく、頻繁に使うツール群
hidden登録はされるが到達不能。利用不可のままにしておくべきサーバーやツール

toolExposure はサーバー単位の設定をツールごとに上書きする。キーは厳密なツール名か * パターンで、厳密な名前がパターンに勝ち、パターン同士では最初にマッチしたものが 勝つ。だから hidden なサーバーがちょうど1つのツールだけを公開することもできるし、 deferred なサーバーが破壊的なツールを到達不能に保つこともできる。

.pi/mcp.json でのツールごとの露出

{
"mcpServers": {
  "github": {
    "exposure": "deferred",
    "toolExposure": {
      "search_code": "direct",
      "get_*": "codemode",
      "delete_*": "hidden"
    }
  }
}
}

見落としやすい詳細が2つある。第一に、codemode と deferred のツールはどちらの 間接的な仕組みからも到達できる——スクリプトが呼べるし、tool_search がロードもできる ——そして codemode の呼び出しはアクティブなツールセットに依存しない ので、ブランチ 切り替えや再開、フォークのあとでも動く。第二に、codemode も tool_search もアク ティブでない場合、Pi は一度だけ警告する。その状態では direct 以外のツールは単に 呼べないからだ。

プロンプトキャッシュの技​

このページで最もコピーしやすい唯一のアイデアがここにある。

Pi はセッション開始時に、有効なすべての MCP サーバーをバックグラウンドで接続する。 codemode または deferred のツールを持つサーバーは、システムプロンプトの mcp_servers セクションに列挙される——1行ずつ、設定された description から、あるいは 接続後はサーバー自身の指示から。

そのセクションはサーバーが接続するにつれて変化する。素朴なハーネスならシステム プロンプトかツール宣言を書き換えるだろうが、それはその背後のキャッシュ済みプレ フィックスをすべて無効化する。Pi はそうではなく、

ツール宣言を変更する代わりに、新しいセクションを会話に追記するので、より前の メッセージはキャッシュされたままになる。

プレフィックスの変更はキャッシュ全体のコストを払わせる。サフィックスの変更はコスト ゼロだ。Pi はプロンプトの書き換えをトランスクリプトへの追記に変換している。だからこそ codemode ツールの説明文そのものも、サーバーが接続する間に変化しないよう設計されて いる——deferred 露出のツールは意図的にそこから除外されているのだ。

最初のプロンプトが待つのは最大 10秒 で、しかも direct ツールを持つサーバーに 限られる。それらはリクエストで宣言しなければならないからだ。それ以外はすべて遅延的に 待たれる。スクリプトは自分が名前を挙げたサーバーを待ち、searchTools() を呼ぶか ALL_TOOLS を読むときだけ全サーバーを待つ。

Anthropic の API の上に構築しているなら、同じ理屈が自分のプレフィックスにも当てはまる ——プロンプトキャッシング と 会話中のツール変更 を参照。これはまさに Pi 1.0 が「会話中のシステムメッセージ」と呼んでいる機能だ。

codemode.mode をデフォルトの "on" ではなく "only" に設定すると、組み込みツールと 拡張ツールはモデルから完全に隠され、代わりに codemode の説明に列挙される——モデルは すべてにスクリプト経由で到達する。これはこのアイデアの最も極端な形であり、設定キー 1つの距離にある。

サンドボックス内の非 LLM モデル​

codemode スクリプト内の models グローバルは、セッションの資格情報で 分類器 と 画像 モデルを実行できる。チャットモデルは列挙されるがスクリプトから実行はできない ——この境界は意図的なものだ。

分類器のインターフェースは state オブジェクトと質問のマップを取り、それらすべてに 1回の呼び出しで答える。質問には3つの形がある。choice（ラベルを1つ選ぶ、criteria が各ラベルの意味を対応づける）、score（最低値を先頭に記述した順序付きスケール）、 そして bool。答えは散文ではなく、確率と確信度として返ってくる。

これは AILmanac が System One の決定モデル: Jev、Kev とオープンなクローン と 自分の決定モデルを訓練する で扱っている System One / 決定モデルと同じカテゴリだ。Pi は TypeSafe を第一級の プロバイダとして出荷しており、ドキュメントはモデル ID がプロバイダごとに異なること ——typesafe/jev-latest 対 openrouter/typesafe/jev-1.13——を注記している。だから ハードコードせず models.getAvailableOfType("classifier") で解決する。

これが開く型はこうだ。フロンティアモデルが、MCP サーバーから150件のイシューを取得し、 それぞれを安価な校正済み分類器で4並列に分類し、重要な6件を返すスクリプトを書く。150件 のイシューは高価なモデルのコンテキストに一度も触れない。

Watch out
  • `classify()` と `generateImages()` はプロバイダのエラーで throw しない——`stopReason` と `errorMessage` を自分で確認しないと、失敗を結果として黙って扱ってしまう。
  • スクリプト内の分類器・画像の使用量は codemode のツール結果に加算され、セッションコストに計上される。1回あたりが安いことは、150回でも無料という意味ではない。
  • 画像生成は数分かかることがある。画像を生成するスクリプトに短い `timeout_ms` を付けると、途中で殺されてしまう。

キャッシュウォーミングと 0.05ドルの規則​

Pi には cacheWarming 設定があり、値は3つ——"off"、"streaming"（デフォルト、実行 中にウォーミング）、"idle"（実行の合間にも）。

面白いのはゲートのほうだ。キャッシュウォーミングが走るのは、モデルがキャッシュ寿命を 宣言し、かつ Pi が回避できるキャッシュミスのコストを少なくとも 0.05ドル と 見積もるときだけである。リフレッシュの使用量はセッション合計に計上されるが モデルのコンテキストには入らない。/session が次の判断を表示し、拡張は cache_warming_decision フックでそれを上書きできる。

オープンソースのハーネスの中にドル建ての閾値がハードコードされているのは、異例なほど 正直なエンジニアリングだ。キャッシュのウォーミング自体が課金対象のリクエストなので、 ある損益分岐点より下では最適化ではなく税金になる。自分でウォーミングループを作った のにその閾値を計算したことがないなら、おそらくその税金を払っている。経済学は プロンプトキャッシングの経済学 と同じものだ。

設定、そして何が置換され何が追加されるのか​

ユーザーレベルの設定は エージェントディレクトリ に置かれ、デフォルトは ~/.pi/agent（PI_CODING_AGENT_DIR で上書き）。プロジェクト設定は作業ディレクトリ 配下の .pi/ にあり、プロジェクトの信頼が付与されたあとにのみ読み込まれる。

パス役割
<agent-dir>/settings.json設定、デフォルト値、リソースパス、パッケージ宣言
<agent-dir>/mcp.json、models.json、auth.jsonグローバルな MCP サーバー、互換エンドポイントと上書き、保存された資格情報
<agent-dir>/SYSTEM.mdPi のデフォルトシステムプロンプトを 置換
<agent-dir>/APPEND_SYSTEM.mdPi のシステムプロンプトに 追加
<agent-dir>/AGENTS.md — または CLAUDE.md作業ディレクトリ横断で適用されるユーザー指示
<agent-dir>/extensions/、skills/、prompts/、themes/ユーザーリソース、prompts/ はスラッシュコマンドになる
.pi/SYSTEM.md、.pi/APPEND_SYSTEM.mdプロジェクト版。信頼されたプロジェクトのファイルがエージェントディレクトリのものに 優先する ——同名ファイルは結合されない

内面化しておく価値があることが2つ。Pi は CLAUDE.md をコンテキストファイルとして 読むので、既存の Claude Code のリポジトリはすでに Pi 用に設定済みということになる—— コーディングエージェント CLI 比較 からのポータビリティの論点は双方向に成り立つ。そして AGENTS.override.md が AGENTS.md や CLAUDE.md を置換するのは 同じディレクトリ内でのみ で、エージェント ディレクトリや祖先ディレクトリから継承されたコンテキストファイルを抑制はしない。

組み込みツールは read、bash、powershell、edit、write、grep、find、ls で、デフォルトで有効なのは read、bash、edit、write だけだ。組み込み拡張は builtin:mcp、builtin:llama.cpp、builtin:codemode、builtin:tool-search ——llama.cpp が第一級の組み込み であることに注目。ローカルの重みはここでは後付けでは ない。

セキュリティモデル、率直に述べる​

Pi 自身のセキュリティドキュメントは気持ちよく率直で、以下の3文は自分が書いていない リポジトリに向けて Pi を走らせる前に真剣に受け取るべきものだ。

Watch out
  • Pi はすべてのツール呼び出しの前に承認を求めない。拡張、パッケージインストーラ、言語サーバーは、Pi を起動したアカウントと同じ権限で子プロセスとして動く。拡張は Pi のプロセスにロードされる TypeScript モジュールであり——サンドボックス化されていない。codemode の VM が守るのはモデルの出力経路であって、あなたのマシンではない。
  • プロジェクトの信頼は起動時の境界ではない。Pi は信頼を解決する前にプロジェクトの `sessionDir` 設定を読むので、信頼を拒否してもその参照は取り消せない。`.pi` ディレクトリが空なら信頼のプロンプトはそもそも出ない。
  • コンテキストファイルの発見にプロジェクトの信頼は不要だ。クローンしたリポジトリの `AGENTS.md` や `CLAUDE.md` は、あなたに尋ねることなくシステムプロンプトに読み込まれる——これは設定上の便利さではなく、プロンプトインジェクションの攻撃面である。
  • ドキュメントは率直に言っている。トランスクリプトを見張ること、プロジェクトの信頼を使うこと、変更をレビューすることは、セキュリティ境界を作らない。境界はコンテナ、VM、または専用の OS ユーザーだ。

最後の点が初耳なら、次は 攻撃されるコーディングエージェント と ローカルおよびハイブリッドなエージェントを守る を読むこと。Pi が正しくやっている小さな緩和が1つある。npm のインストール経路が npm install -g --ignore-scripts @earendil-works/pi-coding-agent として文書化されて おり、通常のインストールで Pi は依存関係のライフサイクルスクリプトを必要としない。

欠落こそがプロダクトだ。機能が自らを証明するまで拒むハーネスは、コンテキスト予算が 読み取り可能なまま保たれるハーネスである——これは エージェントがトークンを燃やす理由 と同じ議論を、引き算によって述べたものだ。

Pi Durable、ひと息で​

@earendil-works/pi-durable は 実験的 とフラグが立てられており——API はリリース間 で予告なく変わる——リポジトリの中で最もアーキテクチャ的に興味深いパッケージだ。会話、 モデルのターン、ツール呼び出し、そしてあなた自身の状態は、何かが表示される前に ストレージへコミットされる。プロセスがターンの途中で死んでも、ストレージを開き直せば 止まったところから続く。

その語彙はインストールしなくても盗む価値がある。conversation は不変の entry （pi.user、pi.assistant、pi.tool-result、pi.system、pi.reset）のトランス クリプト。document はトランスクリプトの隣に保存される型付き JSON の状態 （モデル選択の pi.agent、実行中の生成の pi.live、キューに入った投入の pi.inbox、 支出の pi.usage）。task はすべてのステップでチェックポイントを打つ永続的な状態 機械で、だから pi.generation が自分のツール呼び出しの pi.tool タスクを所有し、 再起動したプロセスは最後のチェックポイントから続く。そしてモデルが見るのは 最新の reset 以降 のエントリだけだ——reset は削除ではなく、トランスクリプトの エントリである。

エージェントのメモリアーキテクチャ と 長時間稼働するエージェントハーネス と比べてみてほしい。

乗り換えるべきか​

正直な答え: おそらく全面的にはしなくていい。そしてそれでいい——成果物はアイデアのほう なのだから。

  • Pi を試すべきなのは 多数のプロバイダをまたぐ1つのハーネスが欲しい場合、ローカル の重みを動かしている場合（llama.cpp が組み込み）、あるいは MCP の表面積がコンテキスト ウィンドウを超えて育ってしまった場合。
  • 今の場所に留まるべきなのは サブエージェント、プランモード、呼び出しごとの承認 プロンプトに依存している場合。Pi にはそれらがなく、そのことを謝る気もない。
  • いずれにせよ盗むべきもの: 露出のはしご（codemode / deferred / direct / hidden）、プロンプトのセクション変更をサフィックス追記にする技、そしてキャッシュを ウォーミングする前に損益分岐点を計測すること。
