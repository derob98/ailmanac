Claude Opus 5.5:フィールドガイド

中級

2026 年 9 月 22 日、Anthropic は Claude Opus 5.5（claude-opus-5-5）をリリースし、ほとんどのワークロードで推奨される出発点に据えました。見出しになるのは価格です。入力 $4 / 出力 $20 per MTok で Opus 5 の $5/$25 より 20% 安く、キャッシュ読み取りは $0.20。さらに Anthropic 自身の見積もりでは、デフォルト設定の典型的なワークロードで合計コストが約 40% 低下します。トークン単価が下がったうえに、同じタスクをより少ないトークンで終えるからです。

面白いのは価格ではありません。リクエスト/レスポンスの契約について 5 つのことが変わったという点です。そのうち 4 つは 400 を返し、5 つ目は 200 を返しながら進捗 UI を静かに壊します。そして初日にいちばん高くつくミスは、直感とは正反対です。Opus 5 の effort 設定をそのまま持ち越すと、請求額が上がる可能性があるのです。

What you'll learn
  • 実際の数字を押さえる:$4/$20 per MTok、5% ティアの $0.20 キャッシュ読み取り、1M コンテキスト、128k の最大出力、2026 年 6 月のナレッジカットオフ
  • Opus 5 のコードベースを 400 エラーにする 4 つの破壊的変更を直す — そして 200 を返して進捗 UI を黙らせる 5 つ目も
  • なぜ effort:medium が新しいデフォルトなのか、そしてなぜ各レベルが Opus 5 のときより多く思考するのかを理解する — この 2 つの変更は逆方向を向いている
  • モデルと会話の両方に紐づけられるようになった thinking ブロックを扱う。2026 年 8 月 31 日以降に作成されたアカウントを直撃する 400 を含む
  • 発表時のベンチマークを正直に読む:81.8%/48.7% の OSWorld の乖離と、セーフガードのフォールバックによって押し下げられたスコア
  • ツール呼び出しではなく進捗報告でターンを終えるモデルに、無人のエージェントループを適応させる
最終検証: 2026-09-22。

モデル ID、価格、コンテキストと出力の上限、effort のデフォルト、4 つの破壊的変更、エラー文字列、ベータヘッダー、拒否カテゴリは、2026 年 9 月 22 日に Anthropic の発表記事、Claude Platform のモデル概要、Opus 5.5 の「What's new」ページ、Opus 5.5 の移行ガイド、Effort リファレンス、Opus 5.5 のプロンプティングガイドに照らして確認しました。発表時のベンチマーク数値は Anthropic の自己申告であり、執筆時点では独立した検証はされていません。Sonnet 5.5 と Haiku 5.5 は「今後数週間のうちに」提供されると告知されており、ここでは扱いません。価格と提供状況は動きます。モデルを固定する前に Current Models & Pricing の表を確認してください。

次の情報源で確認してください: 公式情報源.

1 段落で言うと​

Opus 5.5 は、より安く、より速く、よりおしゃべりでない Opus 5 に、より厳格な API 契約を付けたものです。1M トークンのコンテキストも、同期 Messages API での 128k の最大出力も、Fable 5.1 と同じ 2026 年 6 月という信頼できるナレッジカットオフも、そのままです。価格は $4/$20 per MTok に、キャッシュ読み取りは $0.20 に下がりました — これは基本入力価格の 0.05 倍で、プラットフォームの標準は 0.10 倍です。長いエージェントセッションではキャッシュ読み取りが請求額を支配するため、見出しの値下げよりこちらのほうが効いてきます。アダプティブ thinking は常時オンになり、どの effort レベルでもオフにできません。強制 tool_choice は廃止。レガシーの computer_20251124 ツールは Claude API と Google Cloud で拒否されます（Bedrock ではまだ動きます）。thinking ブロックは、モデルと会話のプレフィックスに暗号的に紐づけられます。デフォルトの effort は high から medium に下がり、Anthropic の報告では、コーディングとナレッジワークの評価で Opus 5.5 の medium が Opus 5 の high に匹敵するか上回ります。提供終了は2027 年 9 月 22 日より前には行わないとコミットされています。

じっと見るべき行はキャッシュ読み取り倍率です。Anthropic のプラットフォーム標準は基本入力の 10%、Fable 5.1 と Mythos 5.1 は 2.5%、そして Opus 5.5 は独自の 5% ティアに座っています。同じリポジトリのコンテキストが毎ステップ再生される長いエージェントセッションでは、キャッシュ読み取りが最大の費目になります。したがって Opus 5 に対する実効的な節約は、定価 20% 引きを大きく上回ります。キャッシュ可能な最小プロンプトは 512 トークンです。これらのレートを実際の請求額に変える計算は、プロンプトキャッシュの経済学のページにあります。

Fast mode はリサーチプレビューで、Claude API 限定です — Bedrock、Claude Platform on AWS、Google Cloud、Microsoft Foundry では使えません。fast-mode-2026-02-01 ベータヘッダーとともに speed: "fast" を設定すると、入力 $8 / 出力 $40 per MTok（標準の 2 倍）を支払う代わりに、実時間でおよそ 2.5 倍の速度が得られます。

まずここから:エラーにならない変更​

Anthropic は 4 つの破壊的変更を挙げており、いずれも 400 を返します。それらは 2 番目に直してください。最初に直すべきはこちらです。400 は CI の最初のリクエストで自ら名乗り出ますが、こちらは 200 を返し、ステータスコードを確認するテストをすべて通過し、ユーザーのもとへ届いてしまうからです。

Opus 5 では、モデルがツール呼び出しの合間に書く短いメモは text ブロックとして返ってきました。Opus 5.5 では — Fable 5.1 と同様に — そのナレーションは進捗更新（progress-update）の thinking ブロックとして返り、各ツール呼び出しの前に最大 1 つ入ります。thinking.display のデフォルトである "omitted" では、その thinking フィールドは空です。

何も失敗しません。しかし、そのテキストを進捗としてユーザーにストリーミングしていたアプリケーションは、長いエージェント的ターンの全区間にわたって沈黙します。ユーザーは「マイグレーションを確認しました。次はテストを更新します」の代わりに、スピナーを見ることになります。

Guided walkthrough1 of 5
  1. ナレーションが type 'text' で届くという前提をやめてください。content ブロックを走査し、'tool_use' ブロックの直前にある 'thinking' ブロックを進捗更新として扱いましょう。
  2. display: "updates"（ベータ、ヘッダー thinking-display-updates-2026-08-18）は、推論そのものは隠したまま、各進捗更新の短い要約を返します。display: "summarized" は両方を混ぜて返します。デフォルトの "omitted" では空文字列になります。
  3. そこが本来書かれた位置です。そのブロックは、モデルがこれからやろうとしていることを説明しています。
  4. 取り除いたり、並べ替えたり、書き換えたりしないでください。Opus 5.5 ではバインディングのメタデータを持っており（後述）、編集するとそのターンが無効になります。
  5. レスポンスが thinking ブロックで始まることもあれば、始まらないこともあります。response.content[0].text を読むコードは、thinking を無効化した Opus 5 では動いていましたが、いまや潜在的なバグです。

4 つの 400 エラー​

1. thinking は無効化できない — どの effort レベルでも​

Opus 5 は high 以下の effort で thinking: {"type": "disabled"} を受け付けていました。Opus 5.5 はどこでも受け付けません。無効化の形も手動バジェットの形も、どちらも 400 invalid_request_error を返します:

"thinking.type.disabled" is not supported for this model. Use "thinking.type.adaptive" and "output_config.effort" to control thinking behavior.
"thinking.type.enabled" is not supported for this model. Use "thinking.type.adaptive" and "output_config.effort" to control thinking behavior.

ベータヘッダーは関係なく、オプトアウトもありません。thinking フィールドをまるごと省略するか、thinking: {"type": "adaptive"} を送ってください — 両者は等価です。トークン節約のために thinking を無効化していた箇所では、代わりに effort レベルを下げてください。

thinking 無効化の削除 — Opus 5 から Opus 5.5 へ

# Before — accepted on Opus 5, 400 on Opus 5.5
client.messages.create(
  model="claude-opus-5",
  max_tokens=16000,
  thinking={"type": "disabled"},
  messages=[{"role": "user", "content": "..."}],
)

# After — thinking is always on; effort is the only control
client.messages.create(
  model="claude-opus-5-5",
  max_tokens=16000,
  output_config={"effort": "low"},
  messages=[{"role": "user", "content": "..."}],
)

Opus 5 の統合を thinking 無効で動かしていた場合、パラメータ変更に加えて 3 つの後続の編集が必要です。thinking の代わりに推論をレスポンスへ書き出すよう求めていた指示はすべて削除してください — その指示は、新しい reasoning_extraction 拒否カテゴリのもとでそのまま拒絶されうるようになりました。代わりに display: "summarized" の thinking ブロックから推論を読んでください。思考しないよう命じていたルールはすべて外してください。いまや無意味です。そして、Opus 5 で追加した thinking 無効時の緩和策を再テストしてください（ツール呼び出し前に発話する許可、適合するツールがないときの振る舞い、内部タグの禁止）。それらは thinking をオフにしたときだけ現れるアーティファクトへの対処でした。

2. 強制ツール使用は廃止​

tool_choice: {"type": "any"} と tool_choice: {"type": "tool", "name": "..."} はどちらも 400 を返します:

tool_choice: type "tool" and "any" are not supported for this model.

同じバリデーションはトークンカウントのエンドポイントにも適用され、これは見落としやすいポイントです。実際のリクエストペイロードをそのまま写した事前のトークンカウントも失敗し始めます。

auto（デフォルト）と none は引き続きサポートされます。スキーマに適合する JSON を保証したい場合は、tool_choice: {"type": "auto"} のままにして、ツールに strict: true を設定するか、スキーマを構造化出力に移してください。テキストで答えるのではなくツールに手を伸ばさせたい場合は、そのツールがどんなときに当てはまるのかをプロンプトで述べてください — かつてパラメータが担っていた仕事を、いまは指示が担います。

強制 tool_choice を strict なツール使用に置き換える

# Before — 400 on Opus 5.5
tool_choice={"type": "tool", "name": "get_weather"}

# After — strict schema validation plus an instruction that names when the tool applies
client.messages.create(
  model="claude-opus-5-5",
  max_tokens=1024,
  tools=[{**tool, "strict": True} for tool in tools],
  tool_choice={"type": "auto"},
  messages=[{
      "role": "user",
      "content": "What's the weather in Paris? Use the get_weather tool.",
  }],
)

3. thinking ブロックはモデルと会話に紐づけられる​

これは 4 つのうち最も微妙で、ルーターや圧縮ステップ、コンテキスト編集のループを壊す可能性が最も高いものです。

すべての thinking ブロックはどのモデルが生成したかを記録しており、モデルは自分自身のブロックと、一部の他モデルのブロックしか読みません。そのグラフは非対称です:

第二に、API は thinking ブロックより前にあるものが変更されていないかをブロック生成時点と比較して検査します。対象は system プロンプト、tools 配列、そしてそれ以前のあらゆるメッセージです。これは 2026 年 8 月 31 日 00:00 UTC 以降に作成されたアカウントではデフォルトで強制され、Claude API とクラウドプラットフォームの双方に適用されます。そうしたアカウントでは、このような編集の後にブロックを再送すると 400 が返ります。それより古いアカウントでは、この検査はオプトインです。

effort の罠:逆方向を向いた 2 つの変更​

朗報は、品質カーブが動いた方向です。Anthropic のテストでは、Opus 5.5 のデフォルト medium が、コーディングとナレッジワークの評価で Opus 5 の high に匹敵するか上回り、しかもより少ないステップと少ないトークンで達成しました。いくつかのコーディング評価では、low でもかなり近いところまで、はるかに低いコストで到達します。コンピュータ使用では、デフォルトの effort が、Opus 5 がずっと高い設定でようやく届いた成功率に並びました。密度の高いチャートでは、最も低い effort の Opus 5.5 が、最も高い effort の Opus 5 より正確に値を読み取り、出力トークンはごく一部でした。

コードに触れなくても気づく挙動の変化​

報告のために立ち止まります。 長い多段タスクでは、Opus 5.5 は作業しながらユーザーに状況を伝え続けます。そしてその更新の一部は、ツール呼び出しではなくテキストでターンを終えます（stop_reason: "end_turn"）。テキストだけのターン終了を「タスク完了」と見なす無人のエージェントループは、そこで、タスクの途中で止まります。これは、自律的なハーネスが Opus 5.5 で静かに成果不足に陥る、最も起こりやすい経路です。

Guided walkthrough1 of 5
  1. タスクの各パートを、モデルが更新するチェックリスト — ToDo ツールやファイル — に保持してください。未完了の項目が残ったままブロッカーの申告もなくターンが終わったら、それらを名指しして続行を指示する短いユーザーメッセージを送りましょう。
  2. モデルが起動したバックグラウンドコマンドやサブエージェントがまだ動いているなら、タスクを閉じるのではなく、その出力を次のユーザーメッセージとして返してください。
  3. 本当に行き詰まった実行は、無限にループさせるのではなく終了させてレビューすべきです。
  4. Anthropic は、避けるべき早期停止の 4 つの具体的な形を挙げた長い段落を公開しています。セッション途中でそれを追加するとシステムプロンプトを編集することになり、その会話の以前の thinking ブロックが無効になります。したがって、最初のターンから入れておく必要があります。
  5. この指示は、モデルが本来なら確認を取っていた場面で進ませてしまいます。human-in-the-loop のアプリケーションでは、まるごと入れないでください。

要点を先に出し、専門用語を減らします。 Opus 5.5 は専門用語を使いにくく、重要な情報をメッセージの冒頭に置きやすくなりました。Opus 5 の言い回しをパースしていた後処理や、冗長さと戦っていたプロンプトは、再テストすべきです。

チャットでは、決着したはずの答えを蒸し返します。 複数ターンのチャットでは、Opus 5.5 は新しいメッセージについて考える際に、以前の答えを見直すことがあります — 短いフォローアップでさえも — その分、後半のターンでレイテンシが増えます。Anthropic の対処は、システムプロンプトの末尾に「答え済みの質問は片付いたものとして扱え」と伝える 2 文を置くことです。長い分析やエージェント作業では、後のステップが以前の誤りを正当に明らかにすることがあるので入れないでください。また、モデルが自分の誤りを自発的に申告しにくくなる可能性にも注意してください。

チャット用システムプロンプトから「答える前によく考えて」を削除してください。 モデルは自分で深さを決めます。制御するのは effort です。Anthropic がチャット製品で行ったテストでは、その 1 行を削除すると返答の開始が早まり、品質の明確な低下はありませんでした。

ビジョン向けの足場を再テストしてください。 Opus 5.5 はツールなしでもチャート、図、スクリーンショットをかなり正確に読むため、以前のモデル向けに作ったクロップ／ズームの回避策は、いまや余分な重荷かもしれません。最も密度の高い入力 — とりわけ技術図面 — では依然として役立ちますし、モデルは effort を上げるほど画像ツールを効果的に使います。ツールなしの場合、effort を上げると技術図面は改善しますが、チャートにはほとんど効きません。

新しい拒否カテゴリと、フォールバックが再試行しない 1 つ​

Opus 5.5 は Opus 5 より多くの安全性分類器を走らせます。生物学（新規、Fable 5.1 と同等）と reasoning_extraction（新規）が、サイバーセキュリティに加わりました。拒否は HTTP 200 で届き、stop_reason: "refusal" とカテゴリを示す stop_details オブジェクトを伴います — つまりステータスコードの確認では捕まえられません。拒否と安全性とサーバーサイドフォールバックを参照してください。

罠はこれです。サーバーサイドのフォールバックは reasoning_extraction の拒否を再試行しません。 その拒否はそのままあなたに返されます。他のすべてのカテゴリは fallbacks: "default" で推奨フォールバックモデル上で再試行できますが、これだけは自分で処理しなければなりません。しかもこれは、多くの Opus 5 統合が頼ってきたまさにそのプロンプトパターン — 「回答の中で推論を段階を追って書き出してください」 — で発火します。thinking を無効にしてテキストで推論を求めていたなら、そのプロンプトはいまや不要であり、かつ拒否されうるものです。削除して、display: "summarized" の thinking ブロックを読んでください。

残り 2 つについて。ソースコードの脆弱性を見つけることは許可されますが、リスクの高いデュアルユースのサイバーセキュリティ作業は許可されません。日常的な健康や教育の質問は生物学分類器の影響を受けません。正当なライフサイエンス業務がブロックされる組織は、Anthropic の Life Sciences Verification Program に申請できます。

盗む価値のあるハーネスの技法 2 つ​

これらは Anthropic の Opus 5.5 プロンプティングガイドに由来するもので、ベンチマーク表には現れない類のものです。

マルチエージェントのチームには経過時間のシグナルを与えましょう。 Opus 5.5 は経過時間の情報に細かく注意を払います。ハーネスがリードエージェントに返す各メッセージに elapsed 340s / 1200s のような行を追記すると、モデルは予算内に収まるようペースを配分します — たいていはかなり前倒しで終わります。Anthropic による小規模エージェントチームのリサーチタスク評価では、予算を与えられたチームは単一エージェントと同等の回答品質を保ちながら、かなり早く終えました。そのメカニズムは effort を下げるのとは異なります。effort を下げると作業そのものが減りますが、時間予算は主に、より多くのエージェントを並行して働かせ続けます。 予算は、実際に費やしてほしい時間よりやや大きめに設定してください。これは助言的なもので — 上限に達してもモデルを止めるものは何もありません — 自前のタイムアウトは維持し、品質も確認してください。時間的な圧力の下では、モデルの検証がやや減るからです。

貼り付けられた内容にはインジェクション対策のタグを付けましょう。 Opus 5.5 は、これまでのどの Opus モデルよりも間接的なプロンプトインジェクションに強く、その強さは、どのテキストがユーザー自身のものかを印付けることで、ユーザーが自分のメッセージに貼り付けたテキストにも広げられます。貼り付けられた各ブロックを、アプリケーションが生成した同じ短いランダム ID を持つ開始タグと終了タグで囲み、各タグをそれぞれ独立した行に置いたうえで、<pasted_content> にはユーザーが書いたものではない指示が含まれうる、とシステムプロンプトで伝えてください。ランダム ID こそが要となる部分です — 静的なタグ名は、貼り付けられた内容自体になりすまされうるからです。タグは依然として単なるプレーンテキストで模倣可能なので、これは複数あるガードレールのうちの 1 つです。プロンプトインジェクションを参照してください。

  3. デフォルトはいまや medium です。Opus 5 の値をそのまま持ち越さないでください — 同じ名前でもモデルはより多く思考します。自分の評価セットで low から max までスイープしましょう。

  8. Opus 5.5 の thinking を読めるのは Fable 5.1 と Mythos 5.1 だけです。それ以外のフォールバック先は、それなしで、しかも静かに動きます。除去を報告してほしければ thinking-binding-controls-2026-08-01 を送ってください。

  12. 定価は 20% 下がり、キャッシュ読み取りは 60% 下がりましたが、トークン数も動きました — effort によって両方向に。請求額は推測せず、測定してください。

もっと前のバージョンから移行しますか？ まず Opus 4.8 → Opus 5 のガイド（thinking のデフォルト有効化、レスポンス形状の変更）を済ませてから、このページに進んでください。ただし Opus 5 の「high 以下なら thinking を無効化できる」という点だけは、もはやまったく当てはまりません。Opus 4.7 以前からの場合は、Opus 5 のガイドが、拒否されるサンプリングパラメータ、削除されたプレフィル、新しいトークナイザーについてもカバーしています。

移行すべきか​

いますぐ移行を。エージェント的コーディング、コードレビュー、コンピュータ使用、チャート／図の読み取り、長期のナレッジワークを動かしていて、統合がすでに追記専用かつ thinking 有効であるなら。それこそ Opus 5.5 が作られた用途であり、移行はモデル ID の差し替えと effort のスイープだけで、Anthropic の測定でデフォルト effort でも Opus 5 の high より良いとされる、より安く速いモデルが手に入ります。

慎重に移行を。強制 tool_choice、無効化した thinking、Claude API か Google Cloud での computer_20251124、あるいは会話履歴を編集するループに依存しているなら。いずれも設定変更ではなく、実作業です。

当面は Opus 5 に留まりましょう。インシデント対応の最中であるか、今週中に評価スイープを走らせられないか、ルーター内の下流モデルが Opus 5 の thinking ブロックを読む必要があってバインディンググラフをまだ整理できていないなら。Opus 5 はレガシーモデルですが引き続き利用でき、提供終了も公表された日付より前にはなりません — 提供終了情報を確認してください。

代わりに Fable 5.1 を検討するのは、Opus 5.5 を高めの effort で動かしても評価が届かないときだけです。入力も出力も 2.5 倍の価格で、発表時の表ではすべての行で負けている以上、それはいまや狭い窓です。
