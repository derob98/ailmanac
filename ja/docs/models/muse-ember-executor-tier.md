## 一段落でまとめると

Muse Emberは、**クローズドウェイトで推論対応の長コンテキスト・エグゼキュータモデル**です。コンテキストウィンドウは100万トークン、**出力上限は512K**、200,000トークンまでのプロンプトで100万トークンあたり**$0.10 / キャッシュ$0.004 / $0.50**、それを超えると**3つの料金すべてが3倍**になります。Metaはこれを3モデルの階段の最下段に置いています(*Muse Wonderが計画し、Muse Sparkがコードを書き、Muse Emberが量をこなす*)。Meta自身の評価では、**Artificial Analysis Intelligence IndexでClaude Haiku 5.5と同点(36対36)で、タスクあたりのコストは約3分の1($0.136対$0.411)**です。Metaの10のベンチマーク行のうち8つで勝ち、コードを出荷する人にとって重要な1行で負けています。

## 第1部 — 3帯域の料金表

ローンチ報道が見逃した点です。Haiku 5.5とMuse Emberは**見出し価格が同じ**で、**1Mコンテキストウィンドウも同じ**、そしてどちらもプロンプトが長くなると高い料金表に切り替わります。しかしHaikuの境界は**100,000トークン**で**5倍**、Emberの境界は**200,000トークン**で**3倍**です。

並べると、見出し価格は主題ではなくなります。

| プロンプト長 | Haiku 5.5 入力 / 出力 / キャッシュ読み取り | Muse Ember 入力 / 出力 / キャッシュ読み取り | Emberの優位 |
|---|---|---|---|
| **≤ 100Kトークン** | $0.10 / $0.50 / $0.01 | $0.10 / $0.50 / $0.004 | 入力/出力は同じ、キャッシュ読み取りは**2.5倍**安い |
| **100K – 200Kトークン** | $0.50 / $2.50 / $0.05 | $0.10 / $0.50 / $0.004 | 入力/出力が**5倍**安い、キャッシュ読み取りが**12.5倍**安い |
| **> 200Kトークン** | $0.50 / $2.50 / $0.05 | $0.30 / $1.50 / $0.012 | 入力/出力が**1.67倍**安い、キャッシュ読み取りが**4.17倍**安い |

数値はすべて100万トークンあたり。Haikuの帯域はAnthropicの料金表、EmberはMetaのローンチ記事の脚注2によるものです。

この表から3つのことが見えてきます。どちらのベンダーの発表からも見えないものです。

### 勝負は中間の帯域にある

プロンプトが100,000〜200,000トークンの間では、Haiku 5.5はすでに再価格化され、Muse Emberはまだです。この窓では、同じ価格を掲げる2つのモデルが、入力・出力で**ちょうど5倍**、キャッシュ読み取りで**12.5倍**違います。

珍しい窓ではありません。数個のファイル、テストログ、ビルド出力を読んだコーディングエージェントは、セッションの中盤にはここにいます。大量のサブエージェント作業をルーティングしていて、トランスクリプトが日常的に100K〜200Kトークンに収まるなら、この帯域は最大のコストレバーです。プロンプトの削減よりも、キャッシュ戦略よりも、エフォート調整よりも大きい。

### 200Kを超えると、差は想像よりずっと縮む

両モデルが高い料金表に乗ると、Emberの優位は入力・出力で5倍から**1.67倍**に縮みます。ワークロードがすべて200Kトークン超にあるなら、第2帯域の計算が示唆するよりずっと近い存在です。価格ではなく、後述のFrontierCodeの結果、出力の冗長さ、レイテンシ、すでに使っているクラウドといった要因で決めるべきです。

### キャッシュ読み取りは静かな勝ち筋

Emberのキャッシュ入力料金**$0.004/M**は、比較全体で最も攻めた数字です。Metaはこれを自社の入力料金に対する96%割引と説明しています。100K以下のHaikuの$0.01に対しては2.5倍、100K超のHaikuの$0.05に対しては**12.5倍**です。

エージェントループでは特に効きます。エージェントは毎ステップ、安定したプレフィックス(システムプロンプト、ツールスキーマ)を再送するからです。このプレフィックスはキャッシュされます。キャッシュ*されない*のは、成長していくトランスクリプトで、毎ステップ新規入力として課金されます。つまり長いエージェント実行は、安いキャッシュ読み取りと、高くて伸び続ける末尾の組み合わせであり、キャッシュ読み取り料金は全実行の全ステップにわたって掛け算されます。

## 第2部 — 予算は平均ではなくピークコンテキストで立てる

リクエストを再価格化する境界には、平均が完全に隠してしまう帰結があります。**重要な数字は、単一リクエストの最高水位だけです。**

20ステップのエージェントループを考えます。各ステップは、システムプロンプト、ツールスキーマ、蓄積されたトランスクリプトを再送します。プレフィックスは安定していて$0.004/Mでキャッシュされます。トランスクリプトは毎ステップ伸び、新規入力として課金されます。

## 第3部 — Metaのベンチマーク表を正直に読む

Metaは、最大の推論エフォートで、Claude Haiku 5.5とGPT-6 Lunaに対する10行の比較を公開しました。Emberは8行で勝ち、1行で引き分け、1行で負けています。

| Agents' Last Exam(Linuxサブセット) | **61.6%** | 57.0% | 57.1% | Meta internal |
| Personal Superintelligence Index | **46.8%** | 36.1% | 37.0% | Meta internalの複合指標 |

### AutomationBenchの差こそ本当の見出しで、「コードが上手い」とは別の主張

**37.8%対Haikuの13.9%**は2.7倍で、表の中で圧倒的に広い差です。AutomationBench-AAは、厳格なpass@1で業務ワークフローの完遂を採点します。この結果が裏づけるのは特定の主張です。Emberは*複数ステップの手続き的な仕事をやり遂げる*のが際立って得意だということで、エグゼキュータという位置づけの最強の証拠です。コード品質については何も語っていません。

### 真剣に受け止めるべきはFrontierCodeの行

**Ember 27.2%、Haiku 34.9%**。7.7ポイントの負けで、Emberが負ける唯一の行です。FrontierCode 2.0-AAは実際のエンジニアリングタスクを採点します。Metaがこの行を省かずに載せたのは評価できます。

Emberが46対37で勝つCoding Agent Index-AAと並べると、一貫した姿が浮かびます。**Emberはコーディングエージェントのループを回すのは得意で、レビューを通るコードを書くのは苦手**です。エグゼキュータの典型的なプロファイルであり、本番のdiffを書くモデルとしては最悪のプロファイルです。

### Terminal-Benchのほぼ同点は、3つのモデルではなく3つのハーネスの比較

Metaの脚注1は、このページで最も重要な一文です。Terminal-Bench 4.0の行は、**各モデルをそれぞれの最良の公開ハーネス**で実行しています。

- Muse Ember → **mini-swe-agent**
- Claude Haiku 5.5 → **Claude Code**
- GPT-6 Luna → **Codex**

3つの*異なる*エージェントの足場にまたがる40.9対39.2は、1.7ポイントのモデル差ではありません。ハーネスの選択だけでエージェント系スコアは数ポイント動きます。まさに[AIベンチマークに騙されずに読む方法](/docs/models/reading-ai-benchmarks)が扱う罠です。この行は勝ちではなく「おおむね同等」と扱ってください。

### 指数は引き分け、効率が勝ち

Metaの表は、EmberとHaiku 5.5の両方をIntelligence Indexで最高の**36**と示しています。裏の散布図は少し見栄えが落ちます。**Ember 35.8(タスクあたり$0.136)、Haiku 36.2(タスクあたり$0.411)**。全体の階段は次のとおりです。

| モデル | タスクあたりコスト → 指数 |
|---|---|
| Muse Ember | $0.116 → 33.9 · $0.136 → **35.8** |
| Claude Haiku 5.5 | $0.092 → 24.6 · $0.159 → 29.6 · $0.248 → 34.3 · $0.411 → **36.2** |
| GPT-6 Luna | $0.073 → 21.4 · $0.104 → 23.3 · $0.152 → **27.8** |

正しく読めば、Metaの主張は「Haikuに勝った」ではありません。「Haikuの最高スコアに、タスクあたり約3分の1のコストで届き、GPT-6 Lunaのどの設定にも完全に勝つ」です。どちらも裏づけがあります。また、このデータではHaikuのエフォート階段は4段、Emberは2段です。Emberは推論対応とされていますが、**Metaはエフォート設定の文書を公開していない**ため、Haikuの`effort`パラメータのように$0.116の段を意図的に選ぶことはできません。

## 第4部 — 割引の一部を食う冗長さ

独立した指数の実行にある1つの数字は、Metaの記事には出てきません。Intelligence Indexで、Emberは**中央値9,710万に対し約1億1,500万の出力トークン**を出しており、評価者は「やや冗長」と述べています。

中央値より約18%多い出力です。しかも出力トークンは入力トークンの5倍の価格のモデルです。冗長さは、安いエグゼキュータが優位を静かに返してしまう唯一の場所で、ステップ数と複利で効きます。冗長なモデルが長い中間推論をトランスクリプトに書くと、トランスクリプトも速く膨らみ、実行が200Kの境界により早く近づきます。

ただし反証も実在し、Metaではなくローンチパートナーから出ています。You.comは自社のコーディングテストで**p95レイテンシ2.2秒**と**出力トークン36〜48%減**を報告し、Cloudflareは比較したモデルより**末尾で最大30%高速**だったと報告しています。どちらもローンチ記事内のパートナーの引用です。方向性の参考にはなりますが、独立した測定ではありません。

## 第5部 — Metaが出さなかったもの

欠落はスペックと同じくらい情報を持っていて、すべて同じ方向を指しています。

- **ウェイトなし。** Emberはプロプライエタリで、Metaが提供します。Metaのオープンウェイトのラインには入りません。
- **パラメータ数なし、アーキテクチャの説明なし、モデルカードなし。** 「最小で最も効率的」が開示のすべてです。
- **推論エフォートの段階なし。** 推論対応とされるだけで設定が公開されておらず、コストと品質の段を自分で調整できません。
- **知識のカットオフなし、レート制限なし、キャッシュ書き込み価格なし、バッチ価格なし。**
- **独立したスループット数値なし。** 毎秒トークン数、最初のトークンまでの時間、タスクあたりの時間のいずれも第三者からは出ていません。
- **対応モダリティには争いがある。** Metaはテキスト、画像、音声、動画のネイティブ理解を主張していますが、独立した掲載情報では執筆時点でテキストと画像の入力・テキスト出力のみです。音声や動画の入力が不可欠なら、その上に作る前に最新のモデルページで確認してください。

安全面では、Metaは、EmberがSuperintelligence Scaling Frameworkのもとで化学・生物、サイバーセキュリティ、制御喪失のリスクについて評価され、フレームワークの高リスク閾値を下回ったこと、そして小さいにもかかわらず同じ中核の安全訓練を受けたことを述べています。その中にはWebページ、文書、ツール出力に隠された指示への耐性のテストも含まれます。最後の項目は、信頼できないツール出力を読み続けるエグゼキュータにとって重要な点です。なぜそれをテストするのが正しく、内部評価を通っても保証にならないのかは、[プロンプトインジェクション](/docs/security/prompt-injection)を参照してください。

## 第6部 — どこに収まるか

Metaの位置づけは明確です。**最難問にはMuse Wonder、コーディングとエージェントのワークフローにはMuse Spark、反復可能な大規模作業にはMuse Ember。** 参考までに、Muse Spark 1.3は料金表$1.25/$4.25で、タスクあたり**$2.39**のとき指数37です。つまりMeta自身のラインナップ内で、Emberは指数でSpark 1.3より1ポイント低く、タスクあたりコストは約**17分の1**です。

提供形態は、Muse CodeとMeta Model APIで、Responses APIに対応します。Ember、Spark、WonderはGoogle CloudとOracle Cloudでも提供されます。ローンチパートナーのClineは、コーディングや文書分析のようなサブエージェント作業のために作られたものだと説明しています。

正直な結論は、価格とベンチマークの形のどちらも指すものです。**Emberについてのすべてがエグゼキュータを示し、公開された何ものもプランナーを示していません。** 判断にはフロンティアモデルを置き、量にはEmberを置きましょう。この2層構成を作るなら、仕組みは[モデルルーティングのパターン](/docs/models/model-routing-patterns)で、量が実際にどこから来るのかは[エージェントがトークンを燃やす理由](/docs/models/why-agents-burn-tokens)で扱っています。
